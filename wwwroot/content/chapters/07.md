# 第 7 章 继承、多态与接口，写出能扩展的结构

> **本章你会做出什么**
> 一个"多格式日志解析器"的骨架。**封装**保护解析器内部的规则不被绕过，**继承**让几种解析器共用同一套流程，**多态**让循环只认识接口，**接口**让同一套报告流程适用于不同的实现。
>
> ```text
> 解析结果：
>   plain-text成功 2 / 4 行
>   logfmt    成功 1 / 4 行
>
> 用 logfmt 解析器解析：
>   [error] order 处理订单失败
>
> 报告（多态）：
>   [Markdown] 共 **3** 条日志，其中问题 **2** 条
>   [纯文本] 共 3 条日志，其中问题 2 条
> ```
>
> 泛型与泛型约束放在[第 8 章](/chapter/08)，委托与事件放在[第 9 章](/chapter/09)。

## 7.1 三大特性各管一件事，先看没有它们的程序

先不用任何特性，写一段最直接的代码。它要处理三种格式，分别是空格分隔的纯文本、`key=value` 形式的 logfmt，以及逗号分隔的 csv。每种格式都要判断一行是否可用，还要说明自己是什么格式。

```csharp
// ---------- 1. 没有继承：每个解析函数都要写一遍空行检查 ----------
Console.WriteLine($"plain 空行：{ParsePlain("")}，plain 正常行：{ParsePlain("INFO api 启动")}");
Console.WriteLine($"logfmt 空行：{ParseLogfmt("")}，logfmt 正常行：{ParseLogfmt("level=error")}");
Console.WriteLine($"csv 空行：{ParseCsv("")}，csv 正常行：{ParseCsv("a,b,c")}");

// ---------- 2. 没有封装：字段公开，谁都能改成不合法的值 ----------
var counter = new PublicCounter();
counter.Count = -5;
Console.WriteLine($"Count 被外面改成了 {counter.Count}");

// ---------- 3. 没有多态：按名字分支，每加一种格式都要改这里 ----------
Console.WriteLine($"logfmt 的说明：{Describe("logfmt")}");
Console.WriteLine($"csv 的说明：{Describe("csv")}");

// ---------- 4. 循环里直接写判断，换个条件就要改循环 ----------
var sample = new[] { "level=error module=order", "INFO api 启动", "level=warn module=db" };
var withEquals = sample.Where(line => line.Contains('=')).ToList();
Console.WriteLine($"含有 = 的行：{withEquals.Count} 行");

static bool ParsePlain(string line)
{
    if (string.IsNullOrWhiteSpace(line)) return false;
    var parts = line.Split(' ', 2, StringSplitOptions.RemoveEmptyEntries);
    return parts.Length == 2;
}

static bool ParseLogfmt(string line)
{
    if (string.IsNullOrWhiteSpace(line)) return false;
    return line.Contains('=');
}

static bool ParseCsv(string line)
{
    if (string.IsNullOrWhiteSpace(line)) return false;
    return line.Count(c => c == ',') >= 2;
}

static string Describe(string kind) => kind switch
{
    "plain" => "空格分隔",
    "logfmt" => "key=value 形式",
    "csv" => "逗号分隔",
    _ => throw new ArgumentException($"未知格式 {kind}"),
};

public sealed class PublicCounter
{
    public int Count { get; set; }
}
```

输出如下。

```text
plain 空行：False，plain 正常行：True
logfmt 空行：False，logfmt 正常行：True
csv 空行：False，csv 正常行：True
Count 被外面改成了 -5
logfmt 的说明：key=value 形式
csv 的说明：逗号分隔
含有 = 的行：2 行
```

程序能跑，结果也对。问题藏在写法里，它有三处毛病。

第一，空行判断写了三遍。以后要改空行的规则，就得记得改三个函数，漏改一个，行为就不一致。

第二，`PublicCounter` 的 `Count` 是公开的。外面一句 `counter.Count = -5` 就能把计数改成不合法的值，没有任何代码来拦。

第三，`Describe` 用 `switch` 按名字分支。每多一种格式，就要回到这个方法里加一行。方法会越来越长，改动的地方也越来越多。

三大特性各自解决其中一类问题。

| 特性 | 解决的问题 | 对应上面的哪一处 |
| --- | --- | --- |
| 封装 | 数据被随便改成错误的状态 | 第二处，`PublicCounter.Count` |
| 继承 | 相似的类重复写同样的代码 | 第一处，三个函数的空行检查 |
| 多态 | 按类型分支的代码越来越长 | 第三处，`Describe` 的 `switch` |

封装里有一个词要先认识，它叫**不变式**。不变式是对象在任何时候都必须满足的规则，比如"缓冲区最多保存两行"。封装的目标是让这条规则只能由对象自己来维护。

三大特性之外，还有一条思路贯穿全章，它叫**抽象**。抽象是只保留调用方需要知道的约定，把具体做法留给实现。接口和抽象类是 C# 里实现抽象的两种主要工具，分别放在 7.6 节和 7.3 节讲。

## 7.2 封装，让对象守住自己的规则

封装的第一步是把数据藏起来，只开放带规则的方法。下面用一个最多保存两行的缓冲区来说明。

```csharp
public sealed class LogBuffer
{
    private readonly List<string> _lines = new();
    private readonly int _capacity;

    public LogBuffer(int capacity)
    {
        if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity));
        _capacity = capacity;
    }

    public int Count => _lines.Count;

    public IReadOnlyList<string> Lines => _lines.AsReadOnly();

    public bool TryAdd(string line)
    {
        if (_lines.Count >= _capacity) return false;
        _lines.Add(line);
        return true;
    }
}
```

```csharp
var closed = new LogBuffer(2);
Console.WriteLine($"封装版：{closed.TryAdd("第一行")} {closed.TryAdd("第二行")} {closed.TryAdd("第三行")}，共 {closed.Count} 行");
Console.WriteLine($"只读视图：{string.Join(" | ", closed.Lines)}");
```

输出如下。

```text
封装版：True True False，共 2 行
只读视图：第一行 | 第二行
```

`_lines` 前面的 `private` 让外面看不到它，外面也就没有办法直接 `Add`。写入只能走 `TryAdd`，上限的判断只写在这一个地方。`Lines` 返回的是 `AsReadOnly()` 的结果，调用方可以遍历和读取，不能修改。这个只读视图背后仍然是同一个列表，缓冲区变化时，拿到的视图也会跟着变。

编译器也会帮忙守边界。在外面写 `closed.Lines.Add("x")`，编译器报 `CS1061`，因为 `IReadOnlyList<string>` 上没有 `Add`。直接写 `closed._lines`，编译器报 `CS0122`，因为这个字段不可访问。

### 数据只保存一份

封装的另一面，是同一件事只存一份。看下面这个例子。

```csharp
public class BadCollector
{
    public List<string> Errors { get; } = new();
    public int ErrorCount { get; set; }
}
```

```csharp
var bad = new BadCollector();
bad.Errors.Add("磁盘满了");
Console.WriteLine($"列表 {bad.Errors.Count} 条，ErrorCount 是 {bad.ErrorCount}");
```

输出如下。

```text
列表 1 条，ErrorCount 是 0
```

`ErrorCount` 是另外存的一个数字。列表加了一条，计数却没有跟着变，两者已经对不上了。修正的办法是不再单独存计数，让它从列表算出来，调用方不必记得去加。

```csharp
public sealed class ErrorCollector
{
    private readonly List<string> _errors = new();

    public int ErrorCount => _errors.Count;

    public IReadOnlyList<string> Errors => _errors;

    public void Add(string message)
    {
        if (string.IsNullOrWhiteSpace(message))
        {
            throw new ArgumentException("错误信息不能为空", nameof(message));
        }

        _errors.Add(message);
    }
}
```

```csharp
var good = new ErrorCollector();
good.Add("磁盘满了");
good.Add("连接超时");
Console.WriteLine($"列表 {good.Errors.Count} 条，ErrorCount 是 {good.ErrorCount}");

try
{
    good.Add("   ");
}
catch (ArgumentException ex)
{
    Console.WriteLine($"拒绝写入：{ex.Message}");
}
```

输出如下。

```text
列表 2 条，ErrorCount 是 2
拒绝写入：错误信息不能为空 (Parameter 'message')
```

现在计数永远等于列表的长度，因为根本没有第二份计数。空白的错误信息也会在 `Add` 里被挡下来。

### 只读接口不等于只读

`ErrorCollector.Errors` 的类型是 `IReadOnlyList<string>`，但它返回的其实就是内部的 `List<string>` 对象。调用方不能直接调用 `Add`，却可以先把它强制转换回 `List<string>`。

```csharp
var hole = new ErrorCollector();
hole.Add("A");
((List<string>)hole.Errors).Add("绕过了 Add");
Console.WriteLine($"绕过之后 ErrorCount 是 {hole.ErrorCount}，Add 里的检查没有执行");
```

输出如下。

```text
绕过之后 ErrorCount 是 2，Add 里的检查没有执行
```

只读的接口只是约定。要真正只读，返回的对象就不能被转换回去。`AsReadOnly()` 返回的包装对象正是这样，它不能被强制转换回 `List<string>`。`ToArray()` 返回的新数组则与内部完全独立，外面改它不会影响内部。

```csharp
public sealed class SafeCollector
{
    private readonly List<string> _errors = new();

    public int ErrorCount => _errors.Count;

    public IReadOnlyList<string> Errors => _errors.AsReadOnly();

    public void Add(string message)
    {
        if (string.IsNullOrWhiteSpace(message))
        {
            throw new ArgumentException("错误信息不能为空", nameof(message));
        }

        _errors.Add(message);
    }

    public string[] Snapshot() => _errors.ToArray();
}
```

```csharp
var safe = new SafeCollector();
safe.Add("A");
try
{
    ((List<string>)safe.Errors).Add("绕过");
}
catch (InvalidCastException)
{
    Console.WriteLine("SafeCollector 拒绝了强制转换");
}

var copy = new SafeCollector();
copy.Add("原始");
var snapshot = copy.Snapshot();
snapshot[0] = "外面改的";
Console.WriteLine($"内部仍是：{copy.Errors[0]}");
```

输出如下。

```text
SafeCollector 拒绝了强制转换
内部仍是：原始
```

`Snapshot()` 返回的是一份副本。外面怎么改，都不会影响缓冲区内部的数据。7.10 节的练习 1 会要求你给 `LogBuffer` 加上同样的方法。

### 封装不等于给字段套上 get 和 set

常见的误解是，字段改成 `private`，再加一个 `public` 属性，就算封装了。如果这个属性带 `set`，外面就能整个替换掉列表，前面所有的检查都失效。

封装的判断标准是，外面能不能让对象进入不合法的状态。字段是不是 `private` 只是形式，要看的是对外的每一个入口是否都经过规则。

### 封装的好处

规则只写一次，所有调用方都要经过它。内部实现也可以换。比如 `LogBuffer` 以后想改成环形缓冲区，只改类的内部，`TryAdd` 和 `Lines` 的签名不变，外面的代码一行都不用动。

### 项目里的封装

`src/LogLens.Core/Models/LogEvent.cs` 里，续行保存在私有字段 `_continuationLines` 中（第 10 行），对外只暴露 `IReadOnlyList<LogEntry> ContinuationLines`（第 19 行）。行数由 `1 + _continuationLines.Count` 算出来（第 34 行），没有另外存一份。行数和列表永远对得上，因为根本没有第二份计数。

检查点里的 `LogEntry`（`code/ch07-inheritance/Program.cs` 第 241 行起）用 `required` 和 `init` 声明属性。创建时必须给全所有字段，创建之后不能再改。`IsProblem` 是计算属性（第 268 行），由 `Level` 算出来，不单独存，级别变了判断也跟着变。

`LogParserBase` 的 `TryParse`（第 84 行）是公开的固定流程。它先判断空行，再交给子类的 `TryParseCore`。`TryParse` 没有 `virtual`，子类改不掉它，所以任何子类都不会漏掉空行检查。子类能做的只有 `protected abstract` 留出的那一个口子，也就是 `TryParseCore`（第 97 行）。

## 7.3 继承，复用代码，也表达"是一种"的关系

继承的第一个用途是复用。几个类都要做的事，放进父类里写一次，子类只写自己不同的部分。

下面用一个简单的任务系统来说明。父类 `TaskBase` 负责保存标题，并提供一个可以被覆盖的 `Describe` 方法。

```csharp
public class TaskBase
{
    public TaskBase(string title)
    {
        Console.WriteLine($"TaskBase 构造：{title}");
        Title = title;
    }

    public string Title { get; }

    public virtual string Describe() => $"任务：{Title}";
}

public sealed class ChildTask : TaskBase
{
    public string Tag { get; } = Trace("ChildTask 的属性初始化");

    public ChildTask(string title) : base(title)
    {
        Console.WriteLine("ChildTask 构造函数体");
    }

    private static string Trace(string message)
    {
        Console.WriteLine(message);
        return message;
    }
}

public sealed class LoudTask : TaskBase
{
    public LoudTask(string title) : base(title) { }

    public override string Describe() => base.Describe().ToUpperInvariant() + "!";
}
```

```csharp
Console.WriteLine("== 构造顺序 ==");
var child = new ChildTask("导入日志");
Console.WriteLine($"创建完成：{child.Title}，{child.Tag}");

Console.WriteLine();
Console.WriteLine("== base 调用 ==");
Console.WriteLine(new LoudTask("backup").Describe());
```

输出如下。

```text
== 构造顺序 ==
ChildTask 的属性初始化
TaskBase 构造：导入日志
ChildTask 构造函数体
创建完成：导入日志，ChildTask 的属性初始化

== base 调用 ==
TaskBase 构造：backup
任务：BACKUP!
```

`LoudTask` 覆盖了 `Describe`，但它的实现先调用 `base.Describe()`，拿到父类的文字，再在后面加上感叹号。`base` 的意思是"我的父类"，它让子类能复用父类的行为，而不用把整段文字再抄一遍。

上面的输出还能看出构造的顺序，初学者常常猜错这个顺序。创建 `ChildTask` 时，先执行子类字段的初始化器（"属性初始化"那一行），然后执行父类的构造函数（"TaskBase 构造"），最后才执行子类构造函数自己的函数体。

### 构造函数里调用虚方法

顺序带来一个陷阱。父类的构造函数如果调用了一个虚方法，子类的代码就会在子类还没准备好的时候运行。

```csharp
public class RiskyBase
{
    public RiskyBase() => Setup();

    protected virtual void Setup() { }
}

public sealed class RiskyChild : RiskyBase
{
    private string? _label;

    public string? Seen { get; private set; }

    public RiskyChild() => _label = "已初始化";

    protected override void Setup() => Seen = _label ?? "null（字段还没赋值）";
}
```

```csharp
var risky = new RiskyChild();
Console.WriteLine($"RiskyChild 看到的 _label：{risky.Seen}");
```

输出如下。

```text
RiskyChild 看到的 _label：null（字段还没赋值）
```

`Setup` 在父类构造函数里运行，此时子类构造函数的函数体还没有执行，`_label` 仍然是 `null`。以后看到父类构造函数里出现 `virtual` 方法的调用，就要想一想，子类的哪些成员此时还没有准备好。最稳妥的做法是构造函数里只做赋值，把需要子类状态的工作放到别的方法里，由调用方在构造之后再调用。

### 关键字

| 关键字 | 用在哪里 | 含义 |
| --- | --- | --- |
| `abstract` | 类 | 不能直接 `new`，只能被继承 |
| `abstract` | 成员 | 只有签名没有实现，子类必须实现 |
| `virtual` | 成员 | 有默认实现，子类可以覆盖 |
| `override` | 子类成员 | 覆盖父类的 `virtual` 或 `abstract` 成员 |
| `sealed` | 类，或覆盖后的成员 | 不允许再被继承，或不允许再被覆盖 |
| `protected` | 成员 | 本类和子类能访问，外部不能访问 |
| `base` | 子类 | 指父类，如 `base.Describe()`，或构造函数里的 `base(...)` |

### sealed，到此为止

把类标成 `sealed`，就表示它不允许再被继承。如果写一个 `sealed` 类的子类，编译器报 `CS0509`，提示无法从 sealed 类型派生。

项目里的四个报告写出器（`TextReportWriter`、`CsvReportWriter`、`MarkdownReportWriter`、`JsonReportWriter`）都是 `sealed`，它们是完整的实现，不打算再有子类。`sealed` 也是一种说明。读代码的人看到它，就知道作者没有为继承留口子，改动时可以放心。

### 构造函数里的 base(...)

父类的构造函数需要参数时，子类必须通过 `base(...)` 把参数交上去。上面 `ChildTask` 的 `: base(title)` 就是这样。

项目里的 `LogLensException` 用的是同一种方式，只不过多了一个抽象属性。它的定义在 `src/LogLens.Core/Infrastructure/LogLensException.cs` 中。

```csharp
public abstract class LogLensException : Exception
{
    protected LogLensException(string message) : base(message) { }

    public abstract int ExitCode { get; }

    public virtual string? Hint => null;
}
```

基类的构造函数是 `protected`，只允许子类调用，所以 `LogLensException` 本身不能被直接 `new`。退出码没有放进构造函数，而是声明为抽象属性 `ExitCode`，由每个子类用 `override` 给出自己的值。`QuerySyntaxException` 返回 3，`LogFormatException` 返回 4，`LogSourceException` 返回 2。这样，CLI 顶层只需要一个 `catch`，就能按 `ExitCode` 决定退出码。

### 是一种，还是只是有一个

判断要不要用继承，可以看能不能完整地说出"A 是一种 B"。`PlainTextParser` 是一种解析器，说得通。`JsonLogParser` 是一种解析器，也说得通。

继承最常见的误用，是为了偷用父类的方法。比如有人想要一个能去掉空行的列表，就写一个 `class SafeBuffer : List<string>`。这样写的人想复用的只是列表的功能，可是 `Add`、`Clear`、`RemoveAt` 等所有公开方法都一起带了过来，外面可以随意修改，`SafeBuffer` 想守住的规则也就守不住了。这种情况应该用组合，也就是把列表放进一个私有字段里，只暴露自己需要的方法，就像 7.2 节的 `LogBuffer` 那样。

### 所有类型都继承自 object

前面讲的都是类继承类。其实 C# 里每一个类型都直接或间接地继承自 `object`。这包括你没有写过父类的类，也包括数字、枚举和结构体。

先看类。一个类如果没有写冒号和父类，编译器就把 `object` 当作它的父类。下面的 `TaskBase` 和 `ChildTask` 只用来展示继承链，名字与前面的例子相同，但这一段可以单独运行。

```csharp
public class Empty
{
}

public class TaskBase
{
}

public sealed class ChildTask : TaskBase
{
}

Console.WriteLine($"Empty 的父类：{typeof(Empty).BaseType}");
Console.WriteLine($"TaskBase 的父类：{typeof(TaskBase).BaseType}");
Console.WriteLine($"ChildTask 的父类：{typeof(ChildTask).BaseType}");
Console.WriteLine($"object 自己的父类：{typeof(object).BaseType is null}");
```

输出依次是 `Empty 的父类：System.Object`、`TaskBase 的父类：System.Object`、`ChildTask 的父类：TaskBase`，以及 `object 自己的父类：True`。`object` 是继承链的顶端，它没有父类，所以 `BaseType` 是 `null`。

`record` 也是一样。`record LogLine(...)` 声明的是一个类，它的父类同样是 `object`。`string` 是一个类，父类也是 `object`。

值类型也不例外。`int`、结构体和枚举都有自己的父类，它们最终也都会走到 `object`。下面的代码用到一个枚举和一个结构体，先把它们定义出来。

```csharp
public enum Severity
{
    Info,
    Warn,
}

public readonly struct Point
{
    public Point(int x, int y)
    {
        X = x;
        Y = y;
    }

    public int X { get; }

    public int Y { get; }
}
```

```csharp
Console.WriteLine($"int 的父类：{typeof(int).BaseType}");
Console.WriteLine($"Severity 的父类：{typeof(Severity).BaseType}");
Console.WriteLine($"Point 的父类：{typeof(Point).BaseType}");
Console.WriteLine($"ValueType 的父类：{typeof(ValueType).BaseType}");
Console.WriteLine($"Enum 的父类：{typeof(Enum).BaseType}");
```

输出依次是 `int 的父类：System.ValueType`、`Severity 的父类：System.Enum`、`Point 的父类：System.ValueType`、`ValueType 的父类：System.Object`、`Enum 的父类：System.ValueType`。

把这些结果连起来，就得到几条继承链。

- `int` → `ValueType` → `object`。
- 结构体 `Point` → `ValueType` → `object`。
- 枚举 `Severity` → `Enum` → `ValueType` → `object`。
- 类 `Empty` → `object`。

`ValueType` 和 `Enum` 是 .NET 提供的基类，写代码时我们一般不直接继承它们。`struct` 和 `enum` 关键字已经替我们选好了父类。值类型的结构体不能再继承别的类，但它仍然是 `ValueType` 的子类。

这些关系有一个直接的用处，任何类型的值都能赋给 `object` 类型的变量。

```csharp
object a = new Empty();
object b = 42;
object c = "文本";
object d = new int[] { 1, 2 };
Console.WriteLine($"{a.GetType().Name} / {b.GetType().Name} / {c.GetType().Name} / {d.GetType().Name}");
```

输出 `Empty / Int32 / String / Int32[]`。`GetType()` 返回的是变量里实际存放的类型，和变量声明的类型无关。

把值类型赋给 `object`，会发生装箱（boxing）。装箱会在堆上新建一个对象，把值复制进去。反过来用强制转换取回值，叫拆箱（unboxing）。

```csharp
int n = 7;
object boxed = n;
int unboxed = (int)boxed;
Console.WriteLine($"装箱后的类型：{boxed.GetType().Name}，拆箱得到 {unboxed}");

try
{
    string wrong = (string)boxed;
    Console.WriteLine(wrong);
}
catch (InvalidCastException ex)
{
    Console.WriteLine($"强制转换失败：{ex.GetType().Name}");
}
```

输出 `装箱后的类型：Int32，拆箱得到 7`。把装箱后的 `int` 转成 `string` 会失败，抛出 `InvalidCastException`，输出 `强制转换失败：InvalidCastException`。装箱之后，对象里存的是 `int`，它只能转回 `int`。

所有类型都继承 `object`，所以都带着 `object` 的四个公共成员。

| 成员 | 默认行为 | 什么时候要重写 |
| --- | --- | --- |
| `ToString()` | 返回类型名。`new Empty().ToString()` 的结果是 `Empty`，`Point` 的结果是 `Point` | 想让输出更有意义时，见 [7.5 节](#s7-5) |
| `Equals(object)` | 类比较引用，两个 `new Empty()` 相比结果是 `False`。结构体比较字段，两个 `Point(1, 2)` 相比结果是 `True`。`record` 比较内容 | 类想按内容比较时，见 [7.5 节](#s7-5) |
| `GetHashCode()` | 与 `Equals` 配对使用，两者的规则要一致 | 重写 `Equals` 时一起重写，见 [7.5 节](#s7-5) |
| `GetType()` | 返回对象的运行时类型 | 不能重写 |

`Equals` 的默认行为要特别注意。类默认比较的是引用，也就是“是不是同一个对象”。结构体和 `record` 的默认行为不一样，它们比较的是内容。这一点决定了 `List.Contains`、`Dictionary` 的键等集合操作能不能找到你想要的元素，7.5 节会用例子说明。

### 继承的代价

父类一改，所有子类都跟着变。`TaskBase.Describe` 的文字改一个字，所有没有覆盖它的子类输出都会变。继承层次越深，改动的影响范围越难看清楚。这是继承的代价，也是本章建议"先想组合，再想继承"的原因。

## 7.4 多态，同一个调用，由实际类型决定

多态的意思是，同一行代码在不同对象上，执行的是各自类型的实现。

先回到 7.1 节的 `Describe`。那里是一个 `switch`，每种格式都要在同一个方法里列出来。换成多态，每种格式各自负责自己的说明，调用方只说一句话。

```csharp
public abstract class ParserInfo
{
    public abstract string Describe();
}

public sealed class JsonInfo : ParserInfo
{
    public override string Describe() => "json：结构化字段";
}

public sealed class PlainInfo : ParserInfo
{
    public override string Describe() => "plain：空格分隔";
}

public sealed class CsvInfo : ParserInfo
{
    public override string Describe() => "csv：逗号分隔";
}
```

```csharp
var infos = new List<ParserInfo> { new JsonInfo(), new PlainInfo(), new CsvInfo() };
foreach (var info in infos)
{
    Console.WriteLine(info.Describe());
}
```

输出如下。

```text
json：结构化字段
plain：空格分隔
csv：逗号分隔
```

`infos` 的元素类型是 `ParserInfo`，它的**静态类型**是 `ParserInfo`。每个元素的**实际类型**分别是 `JsonInfo`、`PlainInfo` 和 `CsvInfo`。调用 `Describe()` 时，运行期会看对象的实际类型，执行那个类型的版本。这就是运行期的多态。

好处很直接。循环代码不需要知道一共有几种格式，以后加一个 `TsvInfo`，只要继承 `ParserInfo`，循环一行都不用改。

项目里的解析器注册表也是这种写法。`LogParserFactory` 中的 `Registry` 数组元素类型是 `ILogParser`，每个元素是不同的具体类。

```csharp
private static readonly ILogParser[] Registry =
[
    new JsonLogParser(),
    new SyslogLogParser(),
    new PlainTextLogParser(),
];
```

### 重载看声明类型，覆盖看实际类型

多态常常和重载混在一起。它们的决定时机不同。

```csharp
public sealed class Printer
{
    public void Print(object item) => Console.WriteLine("Print(object)");

    public void Print(string text) => Console.WriteLine("Print(string)");
}
```

```csharp
var printer = new Printer();
object item = "hello";
printer.Print(item);
printer.Print("hello");
```

输出如下。

```text
Print(object)
Print(string)
```

第一次调用时，变量 `item` 声明的类型是 `object`，指向的对象实际上是字符串。编译器在编译时只看声明类型，于是选中了 `Print(object)`。重载是编译期决定的。第二次调用的参数是字符串字面量，编译器直接选中了 `Print(string)`。

覆盖（`override`）则是运行期决定的。这两种决定机制要分清，否则很容易看错结果。

### new 隐藏与 override 覆盖

子类也可以写一个和父类同名的方法，前面加 `new`。这叫隐藏。它和覆盖看起来相似，结果却不一样。

```csharp
public class BaseReport
{
    public string Title() => "基础";

    public virtual string Body() => "基础正文";
}

public sealed class ErrorReport : BaseReport
{
    public new string Title() => "错误报告";

    public override string Body() => "错误正文";
}
```

```csharp
BaseReport report = new ErrorReport();
Console.WriteLine($"{report.Title()} / {report.Body()}");
```

输出如下。

```text
基础 / 错误正文
```

`Title` 用的是 `new`，子类只是多了一个同名方法。通过 `BaseReport` 类型的变量调用时，编译器看的是 `BaseReport.Title`，所以输出"基础"。`Body` 用的是 `override`，参与运行期分派，所以输出"错误正文"。

如果 `Title` 不写 `new`，编译器会给出警告 `CS0108`，提示子类成员隐藏了继承的成员。这个警告的意思是，子类的这个成员没有参与多态。

选择的标准很简单。需要子类改变行为时，父类用 `virtual`，子类用 `override`。只有确实要隐藏父类成员，并且清楚后果时，才用 `new`。

### 子类要守住父类的约定

多态能成立，前提是子类可以在父类出现的地方替换父类，程序的行为不会出乎调用方的意料。这叫里氏替换原则。

经典的反例是"正方形是不是一种矩形"。下面的 `Square` 继承了 `Rectangle`，它把宽和高绑在一起，修改其中一个，另一个也跟着变。

```csharp
public class Rectangle
{
    public virtual int Width { get; set; }

    public virtual int Height { get; set; }

    public int Area => Width * Height;
}

public sealed class Square : Rectangle
{
    public override int Width
    {
        get => base.Width;
        set
        {
            base.Width = value;
            base.Height = value;
        }
    }

    public override int Height
    {
        get => base.Height;
        set
        {
            base.Width = value;
            base.Height = value;
        }
    }
}
```

```csharp
static void Stretch(Rectangle r)
{
    r.Width = 5;
    r.Height = 4;
    Console.WriteLine($"{r.GetType().Name} 面积 {r.Area}");
}

Stretch(new Rectangle());
Stretch(new Square());
```

输出如下。

```text
Rectangle 面积 20
Square 面积 16
```

`Stretch` 只认识 `Rectangle`，它先把宽设为 5，再把高设为 4，按理说面积应该是 20。换成 `Square` 之后，结果是 16，因为高的赋值把宽也改成了 4。编译器不会报错，调用方的代码也没有错，错的是 `Square` 违反了父类的约定。

判断子类是否守住约定，可以问自己一个问题。调用方拿到父类的变量，会不会因为它其实是子类而感到意外。如果会，就不应该用继承，或者应该换一种建模方式。

### 用 is 判断类型

有时确实需要知道对象的具体类型。C# 的类型模式可以在判断的同时取出变量。

```csharp
static string Kind(ParserInfo info) => info switch
{
    JsonInfo => "结构化格式",
    PlainInfo or CsvInfo => "文本格式",
    _ => "未知",
};
```

```csharp
foreach (var info in infos)
{
    Console.WriteLine($"{info.GetType().Name} 属于 {Kind(info)}");
}
```

输出如下。

```text
JsonInfo 属于 结构化格式
PlainInfo 属于 文本格式
CsvInfo 属于 文本格式
```

这种判断适合少量的特殊处理。如果代码里到处都是类型判断，多半说明这些差异应该放进多态的方法里，让每个类型自己处理。

## 7.5 重写 object 方法，让类型表现得像它自己

每个类都继承自 `object`（7.3 节讲过），所以每个类都有 `ToString`、`Equals` 和 `GetHashCode` 三个方法。系统默认的实现通常不够用，重写它们，可以让对象在输出、比较和集合里表现得更合理。

### ToString，决定对象怎么显示

直接把对象放进字符串插值，就会调用它的 `ToString`。默认的实现只输出类型名。

```csharp
public class PlainEntry
{
    public string Level { get; init; } = "";

    public string Message { get; init; } = "";
}

public sealed class FancyEntry
{
    public string Level { get; init; } = "";

    public string Module { get; init; } = "";

    public string Message { get; init; } = "";

    public override string ToString() => $"[{Level}] {Module} {Message}";
}

public sealed record LogLine(string Level, string Module, string Message);
```

```csharp
var plain = new PlainEntry { Level = "error", Message = "处理订单失败" };
var fancy = new FancyEntry { Level = "error", Module = "order", Message = "处理订单失败" };
Console.WriteLine($"默认 ToString：{plain}");
Console.WriteLine($"重写 ToString：{fancy}");

var line = new LogLine("error", "order", "处理订单失败");
Console.WriteLine($"record 的 ToString：{line}");
```

输出如下。

```text
默认 ToString：PlainEntry
重写 ToString：[error] order 处理订单失败
record 的 ToString：LogLine { Level = error, Module = order, Message = 处理订单失败 }
```

`record` 会自动生成 `ToString`，输出里列出了所有属性。这也是 `record` 适合放数据的原因之一，它把相等比较和显示都替你写好了。

### Equals 与 GetHashCode，决定两个对象算不算"同一个"

默认的 `Equals` 比较的是引用，也就是两个变量是不是指向同一个对象。对于数据对象，常见的需求是比较内容。

```csharp
public sealed class PlainKey
{
    public PlainKey(string module, int code)
    {
        Module = module;
        Code = code;
    }

    public string Module { get; }

    public int Code { get; }
}

public sealed class FancyKey
{
    public FancyKey(string module, int code)
    {
        Module = module;
        Code = code;
    }

    public string Module { get; }

    public int Code { get; }

    public override bool Equals(object? obj) =>
        obj is FancyKey other && Module == other.Module && Code == other.Code;

    public override int GetHashCode() => HashCode.Combine(Module, Code);
}
```

```csharp
var k1 = new PlainKey("order", 1);
var k2 = new PlainKey("order", 1);
Console.WriteLine($"普通类：k1.Equals(k2) = {k1.Equals(k2)}，k1 == k2 = {k1 == k2}");
var plainSet = new HashSet<PlainKey> { k1 };
Console.WriteLine($"普通类的 HashSet 包含 k2？{plainSet.Contains(k2)}");

var f1 = new FancyKey("order", 1);
var f2 = new FancyKey("order", 1);
Console.WriteLine($"重写后：f1.Equals(f2) = {f1.Equals(f2)}，f1 == f2 = {f1 == f2}");
var fancySet = new HashSet<FancyKey> { f1 };
Console.WriteLine($"重写后的 HashSet 包含 f2？{fancySet.Contains(f2)}");

Console.WriteLine($"record 相等？{line == new LogLine("error", "order", "处理订单失败")}");
```

输出如下。

```text
普通类：k1.Equals(k2) = False，k1 == k2 = False
普通类的 HashSet 包含 k2？False
重写后：f1.Equals(f2) = True，f1 == f2 = False
重写后的 HashSet 包含 f2？True
record 相等？True
```

下面逐条说明。

第一，`Equals` 被重写以后，`f1.Equals(f2)` 变成了 `True`。但 `f1 == f2` 仍然是 `False`，因为 `==` 没有被重写，它默认比较的还是引用。想让两者保持一致，要么同时重写 `==`，要么让对象只通过 `Equals` 比较。如果只写了 `==` 和 `!=` 而没有重写 `Equals`，编译器会给出 `CS0660` 和 `CS0661` 两个警告。

第二，`HashSet` 依赖 `GetHashCode` 决定两个对象放在哪个桶里。只重写 `Equals` 而不重写 `GetHashCode`，相等的对象可能落进不同的桶，`Contains` 就会返回 `False`。规则很简单，两个对象 `Equals` 为真，它们的 `GetHashCode` 必须相同。

第三，`record` 的相等比较是按属性逐个比较的，不需要自己写。它适合那种"内容相同就是同一个东西"的数据对象。

### 运算符重载，让自定义类型能用 + 和 >

假设有一个表示耗时的类型。它的值不能是负数，还要支持相加和比较。运算符重载就是为这些运算符规定自定义类型上的行为。

```csharp
public readonly struct Latency : IComparable<Latency>
{
    public Latency(int ms)
    {
        if (ms < 0)
        {
            throw new ArgumentOutOfRangeException(nameof(ms), "耗时不能为负");
        }

        Ms = ms;
    }

    public int Ms { get; }

    public static Latency operator +(Latency left, Latency right) => new(left.Ms + right.Ms);

    public static bool operator >(Latency left, Latency right) => left.Ms > right.Ms;

    public static bool operator <(Latency left, Latency right) => left.Ms < right.Ms;

    public static bool operator ==(Latency left, Latency right) => left.Ms == right.Ms;

    public static bool operator !=(Latency left, Latency right) => !(left == right);

    public static implicit operator Latency(int ms) => new(ms);

    public static explicit operator int(Latency latency) => latency.Ms;

    public int CompareTo(Latency other) => Ms.CompareTo(other.Ms);

    public override bool Equals(object? obj) => obj is Latency other && this == other;

    public override int GetHashCode() => Ms.GetHashCode();

    public override string ToString() => $"{Ms} ms";
}
```

```csharp
Latency a = 120;
var b = new Latency(80);
Console.WriteLine($"a + b = {a + b}");
Console.WriteLine($"a > b ? {a > b}");
Console.WriteLine($"a == 120 ? {a == 120}");
int raw = (int)(a + b);
Console.WriteLine($"显式转换得到 raw = {raw}");

try
{
    _ = new Latency(-1);
}
catch (ArgumentOutOfRangeException ex)
{
    Console.WriteLine($"拒绝负数：{ex.Message}");
}

var list = new List<Latency> { 300, 50, 120 };
list.Sort();
Console.WriteLine(string.Join(", ", list));
```

输出如下。

```text
a + b = 200 ms
a > b ? True
a == 120 ? True
显式转换得到 raw = 200
拒绝负数：耗时不能为负 (Parameter 'ms')
50 ms, 120 ms, 300 ms
```

这几处要记清楚。

`Latency a = 120;` 能通过，是因为定义了从 `int` 到 `Latency` 的隐式转换（`implicit`）。隐式转换只能用在不会丢失信息、也不会失败的场合。反过来，从 `Latency` 到 `int` 定义为显式转换（`explicit`），所以必须写 `(int)`，提醒读代码的人这里有一次转换。

构造函数里检查了负数，所以任何 `Latency` 对象都不可能是负数。转换运算符也会经过构造函数，因此 `Latency` 的规则在所有入口都成立。

`IComparable<Latency>` 让 `List<T>.Sort()` 知道怎么排序，这是它和集合之间的约定。[第 4 章](/chapter/04)的集合和[第 10 章](/chapter/10)的 LINQ 都会依赖这类约定。

`Latency` 是 `readonly struct`，它是值类型，赋值时复制的是整个值。值类型与引用类型的区别，[第 5 章](/chapter/05)已经讲过，这里不再展开。

## 7.6 接口，只约定"能做什么"

继承表达的是"是一种"。接口表达的是"能做到"。接口只说明一个类型必须提供哪些成员，不负责具体怎么做。

抽象类和接口都能表达"只约定，不实现"。两者的区别见下表。

| | 抽象类（`abstract class`） | 接口（`interface`） |
| --- | --- | --- |
| 表达的关系 | "A 是一种 B" | "A 能做 B 要求的事" |
| 能继承几个 | 只能有一个父类 | 一个类可以实现多个接口 |
| 能有字段和构造函数吗 | 可以 | 不可以 |
| 能有实现吗 | 可以，包括普通方法 | 可以有默认实现（C# 8 起） |
| 典型用途 | 多个子类共享部分实现 | 定义能力，让互不相关的类都能满足同一个约定 |

### 定义和实现接口

接口的命名习惯是 `I` 开头。下面的 `ILogSink` 只规定了一件事，就是能接收一行文字。

```csharp
public interface ILogSink
{
    void Write(string text);
}

public sealed class ConsoleSink : ILogSink
{
    void ILogSink.Write(string text) => Console.WriteLine($"[sink] {text}");
}
```

看 `ConsoleSink` 里的方法写法。它没有 `public`，而是写成 `ILogSink.Write`，这叫**显式实现**。显式实现的成员只能通过接口类型来调用。

```csharp
ILogSink sink = new ConsoleSink();
sink.Write("hi");
```

输出如下。

```text
[sink] hi
```

如果直接写 `new ConsoleSink().Write("hi")`，编译器报 `CS1061`，因为 `ConsoleSink` 的公开成员里没有 `Write`。

显式实现有两个用处。一是两个接口有同名方法时，可以分别实现，互不干扰。二是不想让某个方法出现在类的公开成员里，只让通过接口使用它的人看到。

一个类可以同时实现多个接口。下面的 `CountingSink` 实现了 `ILogSink`，同时它还有一个公开的 `Count` 属性，用来记录写入的次数。

```csharp
public sealed class CountingSink : ILogSink
{
    public int Count { get; private set; }

    public void Write(string text) => Count++;
}
```

这个类后面会在依赖倒置的例子里，作为测试替身使用。

### 接口的默认实现

接口成员可以带一个默认实现（C# 8 起）。实现类如果不写，就用接口给出的默认值。

默认实现和 `virtual` 方法不一样。它不属于类的继承体系，这带来了两个容易出错的地方。下面先看第一个。

```csharp
public interface IDef
{
    string Name => "x";
}

public sealed class BadParser : IDef
{
    public override string Name => "y";    // CS0115：no suitable method found to override
}
```

类直接实现接口时，不能用 `override` 去覆盖接口的默认实现。直接写一个同名的 `public` 属性即可，不加 `override`。

第二个更隐蔽。假设父类已经实现了接口，子类再写一个同名属性，接口的调用会拿到哪一个值？下面的例子给出了答案。

```csharp
public interface ILogParser
{
    string Name { get; }

    int Priority => 0;
}

public abstract class PlainBase : ILogParser
{
    public abstract string Name { get; }
}

public sealed class HiddenParser : PlainBase
{
    public override string Name => "hidden";

    public int Priority => 10;      // 同名，但不是 override
}

public abstract class VirtualBase : ILogParser
{
    public abstract string Name { get; }

    public virtual int Priority => 0;
}

public sealed class FixedParser : VirtualBase
{
    public override string Name => "fixed";

    public override int Priority => 10;
}

public sealed class DirectParser : ILogParser
{
    public string Name => "direct";

    public int Priority => 10;
}
```

```csharp
ILogParser direct = new DirectParser();
ILogParser hidden = new HiddenParser();
ILogParser fixedParser = new FixedParser();
Console.WriteLine($"直接实现：{direct.Priority}");
Console.WriteLine($"父类已实现接口，子类写同名属性：{hidden.Priority}");
Console.WriteLine($"父类 virtual + 子类 override：{fixedParser.Priority}");
```

输出如下。

```text
直接实现：10
父类已实现接口，子类写同名属性：0
父类 virtual + 子类 override：10
```

`DirectParser` 直接实现接口，它的 `Priority` 就是接口的实现，得到 10。`HiddenParser` 的父类 `PlainBase` 已经实现了接口，接口的 `Priority` 对应的是默认实现。子类写的 `public int Priority` 是另一个成员，它和接口的成员没有关系，通过接口调用时，拿到的仍然是默认值 0。编译器不会给出任何提示。

正确的做法是让父类把成员声明为 `virtual`，子类用 `override` 覆盖它。`FixedParser` 就是这样写的，通过接口读到的是 10。检查点里的 `LogParserBase` 和 `LogfmtParser` 也是这样写的，第 [7.12 节](#s7-12)会再看到。

这两个错误的共同点是，编译器都不报错，只有运行结果是错的。所以写完一个接口默认成员，就该让它在父类和子类上各跑一次，确认通过接口访问时结果正确。

### 真实项目里的接口默认实现

`src/LogLens.Core/Parsing/ILogParser.cs` 是项目里真正的解析器接口。它比检查点的版本多了一个 `Confidence` 属性（第 16 行），表示解析器对自己的判断有多大把握。它还有一个带默认实现的方法 `LooksLikeContinuation`（第 28 行）。默认实现判断一行是否像是上一条日志的续行，例如以空白开头的堆栈行。大部分解析器直接用这个默认值，只有需要特殊判断的解析器才会覆盖它。

### 接口和继承怎么选

先用接口定义能力。需要共享实现时，先考虑把对象放进字段里（组合）。实在需要共享代码，再考虑继承。

项目里的分析器就是这样用的。`src/LogLens.Studio/Services/ServiceRegistration.cs` 第 33 行注册的是 `services.AddSingleton<ILogAnalyzer, LogAnalyzer>();`。`WorkspaceService` 的构造参数（第 28 行）和 `ComparisonService` 的构造函数（第 23 行）接收的都是 `ILogAnalyzer`，换一个分析器实现，它们一行都不用改。

## 7.7 依赖倒置，让类依赖接口而不是具体类型

依赖倒置是一个很有用的原则。它的意思是，高层的代码不直接依赖低层的具体实现，两者都依赖一个接口。

先看不用接口的写法。`Analyzer` 自己创建了解析器，它和 `UpperParser` 绑死在一起，以后换一个解析器，就得回来改 `Analyzer`。

```csharp
public sealed class Analyzer
{
    private readonly UpperParser _parser = new();
}
```

改成依赖接口之后，解析器由外面传进来。这种做法叫**构造函数注入**。

```csharp
public interface ILineParser
{
    string? Parse(string line);
}

public sealed class UpperParser : ILineParser
{
    public string? Parse(string line) =>
        string.IsNullOrWhiteSpace(line) ? null : line.ToUpperInvariant();
}

public sealed class Analyzer
{
    private readonly ILineParser _parser;
    private readonly IEnumerable<ILogSink> _sinks;

    public Analyzer(ILineParser parser, IEnumerable<ILogSink> sinks)
    {
        _parser = parser;
        _sinks = sinks;
    }

    public void Run(string line)
    {
        var result = _parser.Parse(line) ?? "无法解析";
        foreach (var sink in _sinks)
        {
            sink.Write(result);
        }
    }
}
```

```csharp
var counting = new CountingSink();
var analyzer = new Analyzer(new UpperParser(), new ILogSink[] { new ConsoleSink(), counting });
analyzer.Run("warn disk full");
analyzer.Run("");
Console.WriteLine($"CountingSink 收到 {counting.Count} 条");
```

输出如下。

```text
[sink] WARN DISK FULL
[sink] 无法解析
CountingSink 收到 2 条
```

`Analyzer` 只知道"有一个能解析的东西"和"有几个能接收结果的东西"。它不知道具体是哪一种，也不关心。这带来三个好处。

第一，换实现不用改 `Analyzer`。比如以后写一个会去掉时间戳的解析器，只要实现 `ILineParser`，传进去就行。

第二，测试变得容易。`CountingSink` 没有输出，只统计次数，正适合当测试替身。测试的时候，可以检查 `Count` 是否等于预期，不需要去看控制台的输出。

第三，创建对象的责任移到了外面。外面可以统一决定用哪些实现，也可以统一替换。

这样的写法在大型程序里很常见，项目的依赖注入容器做的就是这件事。第 24 章会讲到，`AddSingleton<ILogAnalyzer, LogAnalyzer>()` 这样的注册语句，告诉容器遇到 `ILogAnalyzer` 时该创建哪个类。

## 7.8 动手，三大特性同台

下面是检查点的主流程。它用接口定义解析器，用两个实现分别解析两种格式，用注册表按名字挑选解析器，最后用抽象类做出两份报告。

```csharp
// 1) 用接口把"解析器"的能力定下来
var parsers = new List<ILogParser>
{
    new PlainTextParser(),
    new LogfmtParser(),
};

var lines = new[]
{
    "2026-11-01 12:00:00 INFO api GET /orders",
    "2026-11-01 12:00:05 WARN api 数据库查询较慢",
    "level=error module=order msg=\"处理订单失败\"",
    "这一行谁也解析不了",
};

// 2) 多态：同一份循环代码，跑出不同的结果
Console.WriteLine("解析结果：");
foreach (var parser in parsers)
{
    var ok = lines.Count(line => parser.TryParse(line, out _));
    Console.WriteLine($"  {parser.Name,-10}成功 {ok} / {lines.Length} 行");
}

// 3) 按名字选解析器（"注册表"模式，项目里叫 LogParserFactory）
var registry = parsers.ToDictionary(parser => parser.Name, parser => parser);
var chosen = registry["logfmt"];

Console.WriteLine();
Console.WriteLine($"用 {chosen.Name} 解析器解析：");
foreach (var line in lines)
{
    if (chosen.TryParse(line, out var entry) && entry is not null)
    {
        Console.WriteLine($"  [{entry.Level,-5}] {entry.Module,-6}{entry.Message}");
    }
}

// 4) 多态之二：抽象类 + 模板方法
Console.WriteLine();
Console.WriteLine("报告（多态）：");
var reports = new List<SummaryReport> { new MarkdownReport(), new PlainReport() };
foreach (var report in reports)
{
    Console.WriteLine($"  [{report.Title}] {report.Build(parsers, lines)}");
}
```

完整代码在 `code/ch07-inheritance/Program.cs`，共 249 行。上面只贴了主流程，实现部分要跳进文件里看。真实项目也是这样读的，先看主流程，再进入实现。

检查点里的 `ILogParser` 是缩小版。真实项目的接口多了 `Confidence` 和 `LooksLikeContinuation`，检查点只保留这一章要用的部分。`LogParserBase`、`PlainTextParser` 和 `LogfmtParser` 的写法与真实项目类似，只是更短。

### 三大特性在检查点里的位置

| 特性 | 位置 | 看什么 |
| --- | --- | --- |
| 封装 | 第 78 行，`LogParserBase.TryParse` | 固定流程，子类只能填 `TryParseCore` |
| 封装 | 第 241 行，`LogEntry` | `required` 与 `init` 限定创建方式，`IsProblem` 由 `Level` 算出 |
| 继承 | 第 71 行，`LogParserBase : ILogParser` | 公共逻辑只写一次 |
| 继承 | 第 104 行，`PlainTextParser : LogParserBase` | 子类只写 `Name` 和 `TryParseCore` |
| 多态 | 第 23 至 27 行，解析器循环 | 只认识 `ILogParser` |
| 多态 | 第 47 至 50 行，报告循环 | 只认识 `SummaryReport` |
| 多态 | 第 209 行起，`SummaryReport` | `Build` 定骨架，`Format` 由子类实现 |
| 接口 | 第 55 至 62 行，`ILogParser` | `Priority` 的默认实现在第 60 行 |
| 扩展方法 | 第 188 行，`SelectNotNull(this ...)` | 让 `parsers.SelectNotNull(lines)` 成立 |

### 两个容易出错的地方

第一个是接口默认成员的覆盖问题，7.6 节已经讲过。`LogParserBase` 把 `Priority` 声明为 `virtual`，`LogfmtParser` 用 `override` 覆盖它，通过 `ILogParser` 读取时才能得到 10。如果把 `virtual` 和 `override` 去掉，`LogfmtParser` 写的同名 `public` 属性就不会被接口调用到，结果会悄悄变成 0。

第二个是按空格切分。如果把时间当成一个词来切，比如写成 `line.Split(' ', 4)`，再取 `parts[1]` 当作级别，结果会是错的。

```csharp
var line = "2026-11-01 12:00:00 INFO api GET /orders";
var wrong = line.Split(' ', 4);
Console.WriteLine($"错误切分：[0]={wrong[0]} [1]={wrong[1]} [2]={wrong[2]}");
Console.WriteLine($"wrong[0] 能否解析：{DateTimeOffset.TryParse(wrong[0], out _)}");
```

输出如下。

```text
错误切分：[0]=2026-11-01 [1]=12:00:00 [2]=INFO
wrong[0] 能否解析：True
```

程序不会报错，因为 `DateTimeOffset.TryParse("2026-11-01")` 能成功。它只会悄悄地把 `12:00:00` 当成级别（规范化后变成 `info`），把 `INFO` 当成模块名。能运行和结果正确是两回事。

正确的写法是明确时间占两段，一次切成五段，再把前两段拼回时间。检查点第 112 行到第 124 行就是这样写的。

```csharp
// 注意：时间是"2026-11-01 12:00:00"两段，所以一次切 5 段
// [日期][时刻][级别][模块][消息]
var parts = line.Split(' ', 5, StringSplitOptions.RemoveEmptyEntries);
if (parts.Length < 5)
{
    return false;
}

// 日期和时刻要拼起来才能解析成一个时间点
if (!DateTimeOffset.TryParse($"{parts[0]} {parts[1]}", out var timestamp))
{
    return false;
}
```

项目里的 `PlainTextLogParser.cs` 和 `SyslogLogParser.cs` 用的是 `[GeneratedRegex]` 正则，没有用简单的 `Split`。时间的格式会有变化，字段的含义却必须稳定，用正则可以把两件事分开处理。

### 逐段解释

| 代码 | 说明 |
| --- | --- |
| `List<ILogParser> parsers` | 列表元素是接口类型，能装任何实现 |
| `parser.TryParse(...)` | 多态调用，执行的是对象实际类型的方法 |
| `parsers.ToDictionary(p => p.Name, p => p)` | 注册表，名字到解析器的映射 |
| `abstract class SummaryReport` | 模板方法，骨架在父类，细节在子类 |
| `line[..index]`、`token[(index + 1)..]` | 范围索引（C# 8），等价于 `Substring` |
| `fields.GetValueOrDefault("module", "unknown")` | 字典取不到值时给默认值 |

`SelectNotNull` 前面的 `this` 让它成为扩展方法，于是可以写成 `parsers.SelectNotNull(lines)`，就像 `parsers` 自己带着这个方法一样。扩展方法必须写在静态类里，并且是静态方法，第一个参数前加 `this`。

## 7.9 常见错误

下表中的错误码都是编译器报告的原始代码。

| 报错 | 原因 | 怎么改 |
| --- | --- | --- |
| `CS0535` 不实现接口成员 | 类声明了接口，却缺少成员 | 补上所有成员，或把类声明为 `abstract` |
| `CS0534` 没有实现继承来的抽象成员 | 非抽象类缺少某个 `abstract` 成员的实现 | 用 `override` 实现它，或把类声明为 `abstract` |
| `CS0506` 无法覆盖继承的成员 | 父类的成员没有标记为 `virtual`、`abstract` 或 `override` | 父类加 `virtual`；如果只是想隐藏，改用 `new` 并理解它的后果 |
| `CS0115` 没有找到合适的方法来重写 | `override` 的成员在父类（或接口默认实现）里找不到 | 检查名字和参数；类直接实现接口时，去掉 `override` |
| `CS0507` 无法更改访问修饰符 | 覆盖时改了可见性 | 覆盖的成员访问级别要与父类一致 |
| `CS0509` 无法从 sealed 类型派生 | 继承了 `sealed` 类 | 去掉父类的 `sealed`，或改用组合 |
| `CS0108` 隐藏了继承的成员（警告） | 子类同名成员没有写 `new` 或 `override` | 需要改变行为就用 `override`；确实要隐藏就写 `new` |
| `CS0144` 无法创建抽象类型的实例 | 直接 `new` 了抽象类 | 使用具体的子类 |
| `CS0266` 无法隐式转换，需要显式转换 | 把父类变量直接赋给子类变量 | 用 `(JsonParser)p` 强制转换，或用 `is` 判断 |
| `CS0122` 成员不可访问 | 访问了 `private` 成员 | 通过公开的方法访问 |
| `CS1061` 不包含此成员的定义 | 访问了不存在的成员，或直接调用了显式实现的接口成员 | 通过接口类型调用；扩展方法检查 `using` 与 `static class` |
| `CS0708` 不能在静态类中声明实例成员 | 静态类里写了非静态成员 | 加 `static`，或把类改为非静态 |
| `CS0660`、`CS0661` 只重载了 `==`（警告） | 定义了 `==` 或 `!=`，却没有重写 `Equals` 与 `GetHashCode` | 三者一起重写，保持一致 |
| `CS0019` 运算符不能用于这两个类型 | 结构体没有定义 `-` 运算符 | 为类型定义运算符，或不要使用它 |

编译器会按顺序报告错误，并且声明层面的错误会影响后面的检查。在同一次编译里，如果类或成员声明本身有错误，方法体里的错误可能根本不会被报告。所以遇到一大堆错误时，先修复类和成员声明的问题，例如 `CS0534`、`CS0115`、`CS0506`，再重新编译，看看方法体里还剩下什么。

**练习 1**

```csharp
public sealed class LogBuffer
{
    private readonly List<string> _lines = new();
    private readonly int _capacity;

    public LogBuffer(int capacity)
    {
        if (capacity <= 0) throw new ArgumentOutOfRangeException(nameof(capacity));
        _capacity = capacity;
    }

    public int Count => _lines.Count;

    public IReadOnlyList<string> Lines => _lines.AsReadOnly();

    public bool TryAdd(string line)
    {
        if (_lines.Count >= _capacity) return false;
        _lines.Add(line);
        return true;
    }

    public void Clear() => _lines.Clear();

    public string[] Snapshot() => _lines.ToArray();
}
```

`Snapshot()` 返回的是新数组，修改它不会影响 `_lines`。`Clear()` 之后，`TryAdd` 又能正常写入。这一段代码在探针中编译运行过。快照被外部改成 `changed` 后，缓冲区第一行仍是 `a`，计数为 2；`Clear()` 之后计数为 0，`TryAdd` 返回 `True`。

```csharp
public Result<ILogParser> Resolve(string? formatName)
{
    if (string.IsNullOrWhiteSpace(formatName))
    {
        // 没指定就用默认的纯文本解析器（它能覆盖绝大多数场景）
        return Result<ILogParser>.Ok(Registry[^1]);
    }

    var parser = Registry.FirstOrDefault(p =>
        string.Equals(p.Name, formatName, StringComparison.OrdinalIgnoreCase));

    return parser is null
        ? Result<ILogParser>.Fail($"不支持的日志格式 '{formatName}'，可选：{string.Join(", ", SupportedFormats)}")
        : Result<ILogParser>.Ok(parser);
}
```

`Registry` 是数组，元素类型是 `ILogParser`。`FirstOrDefault` 是泛型方法，接收的是一个 lambda。`Result<ILogParser>` 是泛型结构体，它把成功与失败都包装成一个值返回。`p => ...` 是 lambda 表达式。[第 4 章](/chapter/04)到第 7 章学过的东西，在这一个方法里都出现了。
