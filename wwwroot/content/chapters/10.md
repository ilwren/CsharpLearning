## 10.1 LINQ 是什么

LINQ 是 Language Integrated Query（语言集成查询）的缩写。它是一组扩展方法，定义在 `System.Linq` 命名空间的 `Enumerable` 类里。所有实现了 `IEnumerable<T>` 的集合，包括数组、`List<T>`、`Dictionary<TKey, TValue>` 和 `HashSet<T>`，都能直接调用这些方法。

`IEnumerable<T>` 的意思是“能按顺序一个一个遍历的东西”。它只规定了遍历的方式，不关心数据存在哪里、是否已经全部算好。这一点很重要，10.8 节讲延迟执行时会反复用到。

先看一个最直接的对比。下面两段代码做的事情相同，都是从日志里找出所有 `error`。

```csharp
var errors1 = new List<(string Level, string Module, int Ms)>();
foreach (var log in logs)
{
    if (log.Level == "error")
    {
        errors1.Add(log);
    }
}

var errors2 = logs.Where(log => log.Level == "error").ToList();
```

循环版要写四行，还要自己建一个列表、自己判断、自己添加。LINQ 版一行就完成了同样的事，读起来也更接近“从日志里挑出级别是 error 的”这句话。

`System.Linq` 在本教材的项目里已经由隐式 using 自动引入，所以代码里不需要再写 `using System.Linq;`。如果你的项目关闭了隐式 using，就要自己加上这一行。10.10 节的错误表里有这种情况的报错样子。

LINQ 为什么单独讲一章？因为它的每个方法，背后都用到了前面没有讲过的东西。

- 方法要接收条件和转换规则，这些是委托（[第 9 章](/chapter/09) 9.1 节讲过 `Func`）。
- 条件常常直接写成 lambda 表达式，lambda 的写法和它的几种兄弟形式需要单独讲清楚。
- 结果有时是匿名类型，比如 `new { Level, Module }`，它没有名字，需要专门解释。
- LINQ 方法本身，以及我们自己写的扩展方法，很多都是迭代器，用 `yield return` 逐个产出元素。

### 同一个任务，循环和 LINQ 各怎么写

前面的例子只有一两步，还看不出 LINQ 的好处。下面用一个稍微完整一点的任务来比较。任务是找出级别是 `warn` 或 `error` 的日志，统计每个模块有几条问题，按数量从多到少排列，最后只取前两个。

先看循环的写法。

```csharp
var countLoop = new Dictionary<string, int>();
foreach (var log in logs)
{
    if (log.Level == "warn" || log.Level == "error")
    {
        if (countLoop.ContainsKey(log.Module))
        {
            countLoop[log.Module]++;
        }
        else
        {
            countLoop[log.Module] = 1;
        }
    }
}

var sortedLoop = new List<KeyValuePair<string, int>>(countLoop);
sortedLoop.Sort((a, b) => b.Value.CompareTo(a.Value));
for (int i = 0; i < sortedLoop.Count && i < 2; i++)
{
    Console.WriteLine($"循环：{sortedLoop[i].Key} {sortedLoop[i].Value}");
}
```

再看 LINQ 的写法。

```csharp
var top2 = logs
    .Where(l => l.Level == "warn" || l.Level == "error")
    .GroupBy(l => l.Module)
    .Select(g => new { Module = g.Key, Count = g.Count() })
    .OrderByDescending(x => x.Count)
    .Take(2);

foreach (var item in top2)
{
    Console.WriteLine($"LINQ：{item.Module} {item.Count}");
}
```

两段代码的输出一样。

```text
循环：order 3
循环：api 1
LINQ：order 3
LINQ：api 1
```

循环版的统计部分有二十多行，LINQ 版的查询只有六行。行数少只是表面的差别，真正的不同在于写代码时要操心的事情。

循环版要自己决定用哪种字典、怎样判断键是否存在、怎样把字典转成可以排序的列表，还要记得排序的方向。它用了两个中间集合，`countLoop` 和 `sortedLoop`，每一个都是可能出错的地方。LINQ 版没有中间变量，每一步只做一件事，读完一行就知道它的作用。

### LINQ 比循环好在哪里

把上面的对比拆开看，LINQ 大致有下面几方面的优势。

**第一，写的是“要什么”，而不是“怎么做”。** `Where` 说明要筛选，`GroupBy` 说明要分组，`Take(2)` 说明只要两个。读的人可以按名字理解每一步，不必在脑子里模拟循环的每一圈。

**第二，中间状态少。** 循环里的累加器、临时列表、下标，都是需要自己初始化、自己更新、自己检查边界的状态。LINQ 把这些状态藏在方法内部，写代码的人只需要关心条件和转换规则。`Take(2)` 不会因为下标写错而多取或少取一个。

**第三，步骤可以拆开、保存、复用。** 一个条件可以先存进变量，在好几处使用。

```csharp
Func<string, bool> isProblemLevel = level => level == "warn" || level == "error";

var problemCount = logs.Count(l => isProblemLevel(l.Level));
var problemModules = logs.Where(l => isProblemLevel(l.Level)).Select(l => l.Module).Distinct();
```

循环里没有这种“把一段判断交出去”的办法，只能复制代码，或者把循环包成一个方法。

**第四，同一套写法适用于很多数据源。** 数组、列表、字典、字符串、XML，甚至数据库，都可以用同样的方法名来查询。下一节会列出这些数据源。

**第五，只做需要的那一部分。** LINQ 大多是延迟执行的（10.8 节讲过），遇到 `Take`、`First`、`Any` 这类方法，取到够了就停。循环要靠自己写 `break`，还容易漏掉。10.8 节有一个例子，只检查了 14 个数，就找到了前两个符合条件的结果。

### LINQ 也有代价

LINQ 不是任何时候都比循环好，学习时也要知道它的限制。

- 每一步都要调用一次委托，每一步处理结束后，有时还会产生新的中间对象。对于普通的业务代码，这些开销通常可以忽略。但在每秒要处理几百万条数据的热点代码里，应该先测量，再决定是否改回循环。不要凭感觉判断。
- 一长串链式调用，在调试时只能在某一行打断点，看不清中间的每一步。遇到难查的问题，可以把链条拆成几个 `var` 变量，逐个检查。
- 延迟执行带来的陷阱（10.8 节）只有读懂了才知道。多次遍历同一个查询、在遍历时修改数据源，都会让结果和预期不一样。
- 需要修改原集合、需要精确控制下标、或者逻辑本身有很多分支时，循环往往更清楚。LINQ 也不是为了替代所有循环而存在的。

判断标准其实很简单。描述“从一批数据里挑出、变换、汇总”时，LINQ 通常更好读；描述“一步一步改变某个状态”时，循环可能更合适。

### LINQ 能接入哪些数据源

LINQ 的方法定义在 `Enumerable` 和 `Queryable` 两个类里。`Enumerable` 处理的是内存里的序列，`Queryable` 处理的是可以被翻译成其他查询语言的序列。下表列出了常见的数据源。

| 数据源 | 典型类型 | 用到的 LINQ | 特点 |
| --- | --- | --- | --- |
| 内存集合 | 数组、`List<T>`、`Dictionary`、`HashSet`、`string` | `Enumerable` 的方法 | 本章的例子都属于这一类 |
| 生成的数字序列 | `Enumerable.Range`、`Enumerable.Repeat` | `Enumerable` 的方法 | 不需要先准备一个列表 |
| 文件的每一行 | `File.ReadLines` 的返回值 | `Enumerable` 的方法 | 边读边处理，不会把整个文件装进内存（10.8 节） |
| XML 文档 | `XDocument`（`System.Xml.Linq`） | `Enumerable` 的方法，加上 `Descendants`、`Attribute` 等 | 专门为 XML 设计的查询入口 |
| 数据库 | `IQueryable<T>`，由 Entity Framework Core 等 ORM 提供 | `Queryable` 的方法 | 查询被翻译成 SQL，在数据库里执行 |
| 并行处理 | 任意内存序列加 `AsParallel()` | PLINQ | 把工作分给多个 CPU 核心（10.8 节） |

下面的例子演示前几种数据源。它们都是 `Enumerable` 的方法，写法几乎一样。

```csharp
int[] numbers = { 5, 12, 8, 3, 20 };
Console.WriteLine(string.Join(",", numbers.Where(n => n > 6).Select(n => n * 10)));

Console.WriteLine("a1b2c3".Where(char.IsDigit).ToArray().Length);
Console.WriteLine(new string("a1b2c3".Where(char.IsLetter).ToArray()));

var stock = new Dictionary<string, int> { ["苹果"] = 3, ["香蕉"] = 0, ["橙子"] = 7 };
Console.WriteLine(string.Join(",", stock.Where(kv => kv.Value > 0).Select(kv => kv.Key)));

Console.WriteLine(string.Join(",", Enumerable.Range(1, 5).Select(i => i * i)));
```

依次输出 `120,80,200`、`3`、`abc`、`苹果,橙子` 和 `1,4,9,16,25`。字符串本身就是一串字符，所以可以直接对它调用 `Where`，结果是字符序列。字典的元素是 `KeyValuePair`，用 `kv.Key` 和 `kv.Value` 取出键和值。

XML 的例子稍微特别一些，它需要引入 `System.Xml.Linq`。

```csharp
using System.Xml.Linq;

var xml = XDocument.Parse("""
<logs>
  <log level="info">启动</log>
  <log level="error">订单失败</log>
  <log level="error">支付超时</log>
</logs>
""");

var errorTexts = xml.Descendants("log")
    .Where(e => (string?)e.Attribute("level") == "error")
    .Select(e => e.Value);
Console.WriteLine(string.Join(",", errorTexts));
```

输出 `订单失败,支付超时`。`Descendants("log")` 找出所有名为 `log` 的节点，`Attribute("level")` 取出属性，后面的 `Where` 和 `Select` 和处理普通集合时完全一样。

数据库是 LINQ 最有价值的数据源之一。这时的查询对象是 `IQueryable<T>`，它和 `List<T>` 不同，它把查询的条件交给数据库提供程序，由数据库执行。下面的小节会解释它为什么能做到这一点。

### 同一个 lambda，为什么能变成 SQL

前面说过，`Where` 接收的是 `Func<T, bool>`，是一段可以直接执行的代码。`IQueryable<T>` 对应的 `Where` 接收的是 `Expression<Func<T, bool>>`。这种类型描述的是一棵条件结构树，叫表达式树。

表达式树需要一个明确的类型，所以下面用一个 `record` 代替元组，并且要引入 `System.Linq.Expressions` 命名空间。

```csharp
public record LogRow(string Level, string Module, int Ms);
```

```csharp
Expression<Func<LogRow, bool>> expr = r => r.Ms > 100 && r.Level == "error";

Console.WriteLine(expr.Body);
Console.WriteLine(expr.Compile()(new LogRow("error", "order", 1520)));
Console.WriteLine(expr.Body.NodeType);
```

输出依次是 `((r.Ms > 100) AndAlso (r.Level == "error"))`、`True` 和 `AndAlso`。`expr.Body` 能被打印出来，说明 lambda 的内容已经变成了可以读取的结构。`Compile()` 才会把它变成能执行的委托。

数据库提供程序拿到的就是这样一棵树。它会逐个检查节点，比较运算是 `>`，字段名是 `Ms`，逻辑运算是 `AndAlso`，然后把它们拼成 SQL 的 `WHERE` 子句。同一个 `Where`，写在 `List` 上就在内存里执行，写在数据库查询上就变成 SQL 在数据库里执行，原因正在这里。

日常写代码时，你不需要手写表达式树。只需要记住一点，同一个 lambda 在不同的数据源上，可能被直接执行，也可能被翻译，这取决于它被传给了哪一种类型。

## 10.2 LINQ 怎么接收“条件”

`Where` 的参数是一个条件，它的类型是 `Func<T, bool>`。`Func` 的意思是“接收一个 `T`，返回一个 `bool`”。把它的签名简化一下，大致是这样。

```csharp
public static IEnumerable<T> Where<T>(this IEnumerable<T> source, Func<T, bool> predicate)
```

这一行有三个地方值得注意。

- `this IEnumerable<T> source` 说明这是一个扩展方法，所以我们可以写 `logs.Where(...)`，而不是 `Enumerable.Where(logs, ...)`。[第 7 章](/chapter/07)讲过扩展方法，写法是在第一个参数前面加 `this`，这样它就成了集合的“实例方法”。
- `Func<T, bool> predicate` 是“条件”。调用的时候传进来的 lambda 会被当作这个委托使用。
- 返回值是 `IEnumerable<T>`，也就是说 `Where` 本身不返回列表，而是返回一个“能遍历的东西”。这一点在 10.8 节讲延迟执行时会用到。

`Select` 的参数是 `Func<T, TResult>`，它接收一个元素，返回一个新的值。`TResult` 由 lambda 的返回值决定，所以 `Select` 可以把 `(string, string, int)` 变成 `string`，也可以变成匿名类型。

还有一些方法提供了“带下标”的重载，参数会多一个 `int`，表示当前元素在序列里的位置，从 0 开始。

```csharp
var evenRows = logs.Where((log, index) => index % 2 == 0);
```

这种重载在需要“第几条”的时候很方便，10.5 节会看到具体例子。

为了说明 `Where` 是怎么工作的，我们自己写一个简化版，叫 `MyWhere`。它的写法和 LINQ 的一样，只是多了一个 `yield return`，10.7 节会详细讲它。

```csharp
var slow = logs.MyWhere(log => log.Ms > 1000).ToList();
Console.WriteLine(slow.Count);

public static class MyLinq
{
    public static IEnumerable<T> MyWhere<T>(this IEnumerable<T> source, Func<T, bool> predicate)
    {
        foreach (var item in source)
        {
            if (predicate(item))
            {
                yield return item;
            }
        }
    }
}
```

输出 `2`，因为耗时超过 1000 ms 的只有 `1520` 和 `2815` 两条。`predicate(item)` 就是在调用传进来的条件，条件返回 `true` 时才产出这一条。

## 10.3 三种写法，具名方法、匿名方法与 lambda

同一个条件，可以用三种写法传给 `Where`。

| 写法 | 例子 | 说明 |
| --- | --- | --- |
| 具名方法 | `Where(IsError)` | 条件已经有名字，直接把方法名传进去 |
| 匿名方法 | `Where(delegate (...) { ... })` | C# 2.0 引入，没有名字的方法体 |
| lambda | `Where(log => log.Level == "error")` | C# 3.0 引入，最简短，现在最常用 |

```csharp
static bool IsError((string Level, string Module, int Ms) log) => log.Level == "error";

Console.WriteLine(logs.Where(IsError).Count());
Console.WriteLine(logs.Where(delegate ((string Level, string Module, int Ms) log) { return log.Level == "error"; }).Count());
Console.WriteLine(logs.Where(log => log.Level == "error").Count());
```

三行输出都是 `2`。

`IsError` 是一个静态的局部函数（[第 5 章](/chapter/05) 5.7 节讲过），它的名字只在这个方法里有效。第一种写法把它的名字交给 `Where`，编译器会把这个函数转换成委托。

匿名方法的写法是 `delegate (参数) { 方法体 }`。它必须写明参数类型，也必须用 `return` 返回值。C# 3.0 之后，lambda 基本可以代替它，所以现在多数代码都用 lambda。

lambda 的写法是 `参数 => 表达式`。参数类型通常由编译器根据上下文推断，不必写。多个参数要加括号，方法体比较长时可以用花括号。

```csharp
Func<int, int, int> add = (x, y) => x + y;
Func<int, int> square = x => { return x * x; };

Console.WriteLine(add(2, 3));
Console.WriteLine(square(4));
```

输出 `5` 和 `16`。`Func<int, int, int>` 的最后一个类型参数是返回值，前面的都是参数，所以 `add` 接收两个 `int`，返回一个 `int`。

lambda 还有一个重要特性，它可以使用外面定义的变量。这叫“捕获”，10.8 节讲延迟执行时会看到它带来的一个陷阱。

## 10.4 匿名类型，临时的数据形状

有时候我们需要一个只在这个方法里用的数据形状，没有必要为它单独写一个类，也没有必要起名字。这时可以用匿名类型。

```csharp
var item = new { Level = "error", Module = "order" };
Console.WriteLine(item.Level);
Console.WriteLine(item);

var other = new { Level = "error", Module = "order" };
Console.WriteLine(item.Equals(other));
Console.WriteLine(item.GetType() == other.GetType());
```

输出依次是 `error`、`{ Level = error, Module = order }`、`True` 和 `True`。

`new { Level = "error", Module = "order" }` 的意思是编译器会为它生成一个类，类里有两个只读属性 `Level` 和 `Module`。这个类没有名字，我们只能用 `var` 来接收它。

这里有三点需要注意。

- 两个匿名类型只要属性名、类型和顺序都相同，编译器就会把它们当成同一个类型。所以上面的 `item.GetType() == other.GetType()` 是 `True`。
- `Equals` 比较的是内容，不是引用。`item.Equals(other)` 为 `True`，就是因为两边的属性值相同。
- 匿名类型不能作为方法的返回类型，因为方法的返回类型必须写出名字。需要从方法里返回一组数据时，应该用元组或 `record`。

LINQ 里最常见的匿名类型用法有两种。第一种是分组的键。当分组依据有两个字段时，可以写成。

```csharp
var byLevelAndModule = logs.GroupBy(log => new { log.Level, log.Module });

foreach (var group in byLevelAndModule)
{
    Console.WriteLine($"{group.Key.Level}/{group.Key.Module} → {group.Count()}");
}
```

输出六行，依次是 `info/api → 2`、`warn/api → 1`、`error/order → 2`、`info/order → 1`、`info/cache → 1` 和 `warn/order → 1`。`group.Key` 本身就是一个匿名类型，所以可以直接用 `.Level` 和 `.Module` 取出它的字段。

第二种是 `Select` 里投影出的新形状。`select new { l.Module, l.Ms }` 会生成一个只含两个字段的匿名类型，属性名就是变量名，不需要再写一遍。10.6 节的查询语句里还会看到这种写法。

下面是三种“临时数据”的对比。

| 类型 | 有名字吗 | 能作为返回类型吗 | 典型用途 |
| --- | --- | --- | --- |
| 元组 `(string, int)` | 没有类型名，字段可以起名 | 可以 | 临时把几个值捆在一起（[第 4 章](/chapter/04) 4.6 节） |
| 匿名类型 `new { ... }` | 没有名字 | 不可以 | 方法内部的查询中间结果，比如分组的键 |
| `record` | 有名字 | 可以 | 要在多个地方传递的数据（[第 6 章](/chapter/06) 6.8 节） |

## 10.5 常用的查询方法

这一节按用途介绍常用的 LINQ 方法。每一小节的例子都用同一批日志，先把它定义在这里。之后各小节直接使用 `logs`，不再重复定义。

```csharp
var logs = new List<(string Level, string Module, int Ms)>
{
    ("info", "api", 45),
    ("info", "api", 62),
    ("warn", "api", 968),
    ("error", "order", 1520),
    ("info", "order", 23),
    ("error", "order", 2815),
    ("info", "cache", 12),
    ("warn", "order", 680),
};
```

### 筛选、转换与排序

`Where` 筛选，`Select` 转换。这两个方法最常用，也最能体现“先筛再转”的思路。

```csharp
Console.WriteLine(string.Join(",", logs.Where((log, i) => i % 3 == 0).Select(log => log.Module)));
Console.WriteLine(string.Join(",", logs.Select((log, i) => $"{i}:{log.Ms}").Take(3)));
```

第一行输出 `api,order,cache`，它是下标 0、3、6 的三条日志的模块名。第二行输出 `0:45,1:62,2:968`，`Select` 的 lambda 同时拿到了下标和元素。

如果更想要“下标和元素”这一对值，可以用 `Index()`（.NET 9 起可用）。它返回的每一项都是一个元组，`Index` 是下标，`Item` 是元素。

```csharp
foreach (var (index, item) in logs.Index().Take(2))
{
    Console.WriteLine($"Index() {index} {item.Module}");
}
```

输出 `Index() 0 api` 和 `Index() 1 api`。

`SelectMany` 用来把“集合的集合”压平成一个序列。下面的 `lists` 里有三个列表，`SelectMany` 把它们连成一条。

```csharp
var lists = new List<List<int>> { new() { 1, 2 }, new() { 3 }, new() { 4, 5, 6 } };
Console.WriteLine(string.Join(",", lists.SelectMany(l => l)));
Console.WriteLine(string.Join(",", lists.SelectMany(l => l, (l, x) => x * 10)));
```

第一行输出 `1,2,3,4,5,6`。第二行的重载多了一个结果选择器，在压平的同时把每个元素转换一次，输出 `10,20,30,40,50,60`。

排序用 `OrderBy` 和 `OrderByDescending`，同级排序用 `ThenBy` 和 `ThenByDescending`。LINQ 的排序是稳定的，也就是说两条记录的排序键相同时，它们在原来序列里的先后顺序会保留。

```csharp
Console.WriteLine(string.Join(",", logs.OrderBy(l => l.Level).ThenByDescending(l => l.Ms).Select(l => $"{l.Level}{l.Ms}")));
```

输出 `error2815,error1520,info62,info45,info23,info12,warn968,warn680`。先按级别的字母顺序排，同一级别里再按耗时从大到小排。

`Reverse` 把整个序列倒过来。`Take(n)` 取前 n 个，`Skip(n)` 跳过前 n 个。`TakeWhile` 从头开始取，遇到第一个不满足条件的元素就停下；`SkipWhile` 则是跳过开头满足条件的部分，剩下的全部保留。

```csharp
Console.WriteLine(string.Join(",", logs.Select(l => l.Level).Reverse()));
Console.WriteLine(string.Join(",", logs.Take(2).Select(l => l.Ms)) + " | " + string.Join(",", logs.Skip(6).Select(l => l.Ms)));
Console.WriteLine(string.Join(",", logs.TakeWhile(l => l.Level == "info").Select(l => l.Ms)));
Console.WriteLine(string.Join(",", logs.SkipWhile(l => l.Level == "info").Select(l => l.Ms)));
```

依次输出如下。

```text
warn,info,error,info,error,warn,info,info
45,62 | 12,680
45,62
968,1520,23,2815,12,680
```

`TakeWhile` 只取到第一个 `warn` 之前，所以是 `45,62`。`SkipWhile` 跳过开头两条 `info`，剩下的从 `968` 开始，后面的 `info` 也保留了。

`Distinct` 去掉重复的元素，`DistinctBy` 按指定的键去重，每个键只留第一条。`Chunk(n)` 把序列切成长度为 n 的块，和 10.7 节里的 `Chunked` 功能相同，但 `Chunk` 是 LINQ 自带的。

```csharp
Console.WriteLine(string.Join(",", logs.Select(l => l.Level).Distinct()));
Console.WriteLine(string.Join(",", logs.DistinctBy(l => l.Module).Select(l => l.Module)));
Console.WriteLine(string.Join(",", logs.Select(l => l.Module).Chunk(3).Select(c => c.Length)));
```

依次输出 `info,warn,error`、`api,order,cache` 和 `3,3,2`。`DistinctBy` 留下的是每个模块第一次出现的那条日志，本例里是 `api`、`order` 和 `cache`。

### 分组、连接与集合运算

`GroupBy` 按某个键把元素分组，结果是一个“组的序列”，每一组有一个 `Key` 和它里面的元素。

```csharp
var groups = logs.GroupBy(l => l.Level, l => l.Ms, (level, ms) => $"{level}:{ms.Count()}:{ms.Max()}");
Console.WriteLine(string.Join(" ", groups));
```

这里用了三参数的重载。第二个参数是元素选择器，只保留每条日志的 `Ms`；第三个参数是结果选择器，接收一个键和这一组的元素，返回你想要的结果。输出 `info:4:62 warn:2:968 error:2:2815`。

`ToLookup` 和 `GroupBy` 很像，但它立即执行，结果可以用键直接取出一组。取一个不存在的键时，返回空序列，不会报错。

```csharp
var lookup = logs.ToLookup(l => l.Module, l => l.Level);
Console.WriteLine($"lookup[order] = {string.Join("/", lookup["order"])}; lookup[none] 数量 = {lookup["none"].Count()}");
```

输出 `lookup[order] = error/info/error/warn; lookup[none] 数量 = 0`。

连接用 `Join`。它需要两个序列，一个键选择器作用在外层元素上，另一个作用在内层元素上，键相等的元素才会配对。下面的 `modules` 记录了每个模块属于哪个团队。

```csharp
var modules = new List<(string Name, string Team)> { ("api", "平台组"), ("order", "交易组"), ("auth", "安全组") };

var joined = logs.Join(modules, l => l.Module, m => m.Name, (l, m) => $"{m.Team}-{l.Ms}");
Console.WriteLine(string.Join(",", joined));

var grouped = modules.GroupJoin(logs, m => m.Name, l => l.Module, (m, ls) => $"{m.Name}={ls.Count()}");
Console.WriteLine(string.Join(",", grouped));
```

`Join` 是内连接，只保留两边都能配对上的结果。日志里的 `cache` 在 `modules` 里没有，所以它的记录没有输出，`auth` 在日志里没有记录，也没有输出。结果是 `平台组-45,平台组-62,平台组-968,交易组-1520,交易组-23,交易组-2815,交易组-680`。

`GroupJoin` 对外层的每个元素，给出一组配对上的内层元素，即使一条都没有配对，也会保留外层元素。第二行输出 `api=3,order=4,auth=0`，`auth` 的数量是 0，但它仍然在结果里。

如果想做左连接，也就是保留左边的每一条，即使右边没有对应的值，需要用 `GroupJoin` 加 `DefaultIfEmpty`，或者用 10.6 节的查询语句写法。那部分会有完整例子。

集合运算包括下面几种。它们会把两个序列组合成一个新序列。

```csharp
Console.WriteLine(string.Join(",", new[] { 1, 2, 3 }.Zip(new[] { "a", "b" }, (n, s) => $"{n}{s}")));
Console.WriteLine(string.Join(",", new[] { 1, 2, 2 }.Concat(new[] { 3 })));
Console.WriteLine(string.Join(",", new[] { 1, 2, 2 }.Union(new[] { 2, 3 })));
Console.WriteLine(string.Join(",", new[] { 1, 2, 3 }.Intersect(new[] { 2, 3, 4 })));
Console.WriteLine(string.Join(",", new[] { 1, 2, 3 }.Except(new[] { 2 })));
Console.WriteLine(string.Join(",", new[] { 2, 3 }.Prepend(1).Append(4)));
```

依次输出如下。

| 方法 | 作用 | 输出 |
| --- | --- | --- |
| `Zip` | 两个序列按位置配对，短的那个决定长度 | `1a,2b` |
| `Concat` | 直接首尾相接，保留重复 | `1,2,2,3` |
| `Union` | 合并后去重 | `1,2,3` |
| `Intersect` | 两边都有的元素 | `2,3` |
| `Except` | 左边有、右边没有的元素 | `1,3` |
| `Prepend` / `Append` | 在开头或末尾加一个元素 | `1,2,3,4` |

`UnionBy`、`IntersectBy` 和 `ExceptBy` 是对应的“按键”版本，比较的是你指定的键，而不是整个元素。下面的例子用模块名做键，合并两个来源的模块列表。

```csharp
Console.WriteLine(string.Join(",", logs.UnionBy(modules.Select(m => (Level: m.Name, Module: m.Name, Ms: 0)), l => l.Module).Select(l => l.Module)));
```

输出 `api,order,cache,auth`。`logs` 中已经有的 `api`、`order`、`cache` 都保留了第一次出现的版本，`modules` 中独有的 `auth` 被加到了末尾。

### 统计与聚合

统计类方法的结果都是一个数字或一个值。它们会遍历整个序列，所以调用一次就会执行一次完整的遍历。

```csharp
Console.WriteLine($"Count={logs.Count} CountWarn={logs.Count(l => l.Level == "warn")} LongCount={logs.LongCount()}");
Console.WriteLine($"Sum={logs.Sum(l => l.Ms)} Avg={logs.Average(l => l.Ms):F1} Min={logs.Min(l => l.Ms)} Max={logs.Max(l => l.Ms)}");
Console.WriteLine($"MaxBy={logs.MaxBy(l => l.Ms).Module} MinBy={logs.MinBy(l => l.Ms).Ms}");
```

依次输出 `Count=8 CountWarn=2 LongCount=8`、`Sum=6125 Avg=765.6 Min=12 Max=2815`，以及 `MaxBy=order MinBy=12`。

`Count` 的参数是可选的。写了条件，就只数满足条件的元素。`LongCount` 返回 `long`，适合元素数量可能超过 `int` 范围的情况，日常使用 `Count` 即可。

`Max` 和 `Min` 只返回最大或最小的值，要找出“最大值那条记录”，应该用 `MaxBy` 和 `MinBy`。它们返回的是原始元素，不是键。

`Aggregate` 是最通用的聚合方法。它把一个累加器从左到右传过每一个元素，累加器的值由你的 lambda 决定。

```csharp
Console.WriteLine($"Aggregate sum={logs.Aggregate(0, (acc, l) => acc + l.Ms)}");
Console.WriteLine($"Aggregate text={logs.Select(l => l.Module).Aggregate((acc, m) => acc + "|" + m)}");
Console.WriteLine($"Aggregate seed result={logs.Aggregate(0, (acc, l) => acc + 1, acc => $"共{acc}条")}");
```

第一行的 `0` 是种子，也就是累加器的初始值，结果是 `6125`。第二行没有种子，第一个元素就是初始的累加器，结果是 `api|api|api|order|order|order|cache|order`。第三行多了一个结果选择器，把最后的累加器变成你想要的形式，输出 `共8条`。

`CountBy` 和 `AggregateBy` 是 .NET 9 新增的方法。它们把“分组加统计”合成一步，结果是键和值的配对，适合只要统计结果、不需要组内元素的场景。

```csharp
foreach (var pair in logs.CountBy(l => l.Level))
{
    Console.WriteLine($"CountBy {pair.Key}={pair.Value}");
}
foreach (var pair in logs.AggregateBy(l => l.Module, 0, (sum, l) => sum + l.Ms))
{
    Console.WriteLine($"AggregateBy {pair.Key}={pair.Value}");
}
```

依次输出 `CountBy info=4`、`CountBy warn=2`、`CountBy error=2`，以及 `AggregateBy api=1075`、`AggregateBy order=5038`、`AggregateBy cache=12`。`api` 的 1075 是 45、62、968 相加，`order` 的 5038 是 1520、23、2815、680 相加。

空序列上的统计结果要特别注意，不同方法的行为不一样。

| 调用 | 空序列上的结果 |
| --- | --- |
| `Count()`、`Sum()` | 返回 `0` |
| `Average()`、`Max()`、`Min()` | 抛出 `InvalidOperationException`，消息是 `Sequence contains no elements` |
| `Aggregate(func)`（没有种子） | 同样抛出 `InvalidOperationException` |
| `Aggregate(seed, func)` | 返回种子 |

`Max` 在空序列上会抛异常，这常常让人意外。如果希望空序列时返回一个默认值，可以先用 `DefaultIfEmpty(1).Max()`。这一句会返回 `1`，因为空序列被换成了只含 `1` 的序列。

```csharp
Console.WriteLine($"DefaultIfEmpty Max={new List<int>().DefaultIfEmpty(1).Max()}");
```

### 取元素与判断

`First`、`Last` 和 `ElementAt` 取出一个元素，`Single` 要求序列里恰好只有一个符合条件的元素。带 `OrDefault` 后缀的版本在找不到时返回默认值，而不是抛异常。

```csharp
Console.WriteLine($"First={logs.First().Module} FirstOrDefault(none)={logs.FirstOrDefault(l => l.Ms > 99999).Module ?? "null"}");
Console.WriteLine($"Last={logs.Last().Module} ElementAt(2)={logs.ElementAt(2).Module}");
Console.WriteLine($"Single(warn)={logs.Where(l => l.Level == "warn" && l.Ms == 968).Single().Module}");
```

输出 `First=api FirstOrDefault(none)=null`、`Last=order ElementAt(2)=api`、`Single(warn)=api`。

`FirstOrDefault` 找不到时返回的是默认值。对引用类型是 `null`，对元组这种值类型是各字段的默认值。上面的代码访问 `.Module` 时，默认值的 `Module` 是 `null`，所以用 `?? "null"` 显示出来。

`Single` 要求恰好一条。如果有多条，会抛出异常。

```csharp
try
{
    _ = logs.Single(l => l.Level == "error");
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"Single 多条：{ex.Message}");
}
```

输出 `Single 多条：Sequence contains more than one matching element`。`error` 有两条，所以 `Single` 无法决定取哪一条。

判断类方法返回 `bool`。`Any` 只要有一个满足条件就返回 `true`，`All` 要求所有元素都满足，`Contains` 判断是否包含某个值。

```csharp
Console.WriteLine($"Any={logs.Any(l => l.Ms > 2000)} All={logs.All(l => l.Ms > 0)} Contains={new[] { 1, 2 }.Contains(3)}");
Console.WriteLine($"SingleOrDefault(none)={logs.SingleOrDefault(l => l.Ms == 1) == default}");
Console.WriteLine($"SequenceEqual={new[] { 1, 2 }.SequenceEqual(new[] { 1, 2 })}");
```

依次输出 `Any=True All=True Contains=False`、`SingleOrDefault(none)=True` 和 `SequenceEqual=True`。`SequenceEqual` 逐项比较两个序列，顺序和内容都要相同。

判断“有没有”的时候，优先用 `Any()`，不要用 `Count() > 0`。`Any()` 找到第一条就停下，`Count()` 要数完整个序列。

`OfType<T>` 只保留能转换成 `T` 的元素，`Cast<T>` 则要求每一个元素都能转换，否则抛出异常。

```csharp
object[] mixed = { 1, "二", 3 };
Console.WriteLine($"OfType<int>={string.Join(",", mixed.OfType<int>())}");
try
{
    Console.WriteLine(string.Join(",", mixed.Cast<int>()));
}
catch (InvalidCastException ex)
{
    Console.WriteLine($"Cast 失败：{ex.GetType().Name}");
}
```

输出 `OfType<int>=1,3`，`Cast` 遇到 `"二"` 时抛出 `InvalidCastException`，输出 `Cast 失败：InvalidCastException`。

### 转成集合

LINQ 的大多数方法返回的是延迟执行的序列。需要一个真正的集合时，要用 `ToList`、`ToArray`、`ToHashSet`、`ToDictionary` 或 `ToLookup` 把结果保存下来。

```csharp
var arr = logs.Select(l => l.Ms).ToArray();
var hash = logs.Select(l => l.Module).ToHashSet();
Console.WriteLine($"array={arr.Length} hash={hash.Count}");
```

输出 `array=8 hash=3`。`ToHashSet` 会自动去掉重复的模块名，所以只剩 3 个。

`ToDictionary` 需要为每个元素提供唯一的键。键重复时会抛异常。

```csharp
var dict = modules.ToDictionary(m => m.Name, m => m.Team);
Console.WriteLine($"ToDictionary count={dict.Count} order团队={dict["order"]}");

try
{
    logs.ToDictionary(l => l.Module);
    Console.WriteLine("没有重复");
}
catch (ArgumentException ex)
{
    Console.WriteLine($"ToDictionary 重复键：{ex.GetType().Name}");
}
```

第一行输出 `ToDictionary count=3 order团队=交易组`，因为 `modules` 的名字都不重复。第二段代码试图用 `logs` 的模块名做键，`api` 出现了三次，于是抛出 `ArgumentException`。如果键可能重复，要么先 `DistinctBy` 去重，要么改用 `ToLookup`，让一个键对应多个值。

## 10.6 查询语句，另一种写法

前面几节用的都是方法语法，也就是 `logs.Where(...).Select(...)` 这种一层接一层的写法。LINQ 还有第二种写法，叫查询语句（query expression）。它以 `from` 开头，以 `select` 或 `group ... by` 结束，读起来接近 SQL 的 `SELECT ... FROM ... WHERE`。

两种写法不是两套功能。编译器会把查询语句翻译成 10.5 节的方法调用，所以同一个查询用两种写法写出来，结果一定相同。选哪一种，主要看哪种更容易读。

### 基本结构

先看一个带筛选、排序和投影的例子。

```csharp
var q1 = from l in logs
         where l.Level == "error" || l.Level == "warn"
         orderby l.Ms descending
         select new { l.Module, l.Ms };

foreach (var x in q1)
{
    Console.WriteLine($"{x.Module}-{x.Ms}");
}
```

输出四行，`order-2815`、`order-1520`、`api-968`、`order-680`。

这段查询语句等价于下面的方法语法。

```csharp
var m1 = logs
    .Where(l => l.Level == "error" || l.Level == "warn")
    .OrderByDescending(l => l.Ms)
    .Select(l => new { l.Module, l.Ms });
```

对照两段代码，可以看到对应关系。

- `from l in logs` 声明了一个范围变量 `l`，它代表 `logs` 里的每一条日志。它相当于 `foreach` 的循环变量，只是放在了最前面。
- `where` 对应 `Where`，条件的写法和 `Where` 里的 lambda 一样。
- `orderby l.Ms descending` 对应 `OrderByDescending(l => l.Ms)`。不写 `descending` 时默认是升序（`ascending`）。
- `select` 对应 `Select`，它决定最终每个元素是什么形状。

查询语句的子句有固定的顺序，先是 `from`，然后可以出现任意多个 `from`、`where`、`join`、`orderby`、`let`，最后是 `select` 或 `group`。`select` 或 `group` 必须是查询的最后一部分，否则会出错，10.10 节的错误表里有这种例子。

### 和 SQL 的对照

如果你学过 SQL，查询语句的各个子句基本可以对上号。下表列出常见的对应关系。

| SQL | 查询语句 | 方法语法 |
| --- | --- | --- |
| `FROM logs` | `from l in logs` | 方法的调用对象 `logs` |
| `WHERE Level = 'error'` | `where l.Level == "error"` | `Where(l => ...)` |
| `ORDER BY Ms DESC` | `orderby l.Ms descending` | `OrderByDescending(l => l.Ms)` |
| `SELECT Module, Ms` | `select new { l.Module, l.Ms }` | `Select(l => new { ... })` |
| `GROUP BY Module` | `group l by l.Module` | `GroupBy(l => l.Module)` |
| 分组后的 `HAVING` | `group ... into g where g.Count() > 1` | `GroupBy(...).Where(g => g.Count() > 1)` |
| `INNER JOIN ... ON` | `join m in modules on l.Module equals m.Name` | `Join(...)` |
| `LEFT JOIN` | `join ... into ls` 加 `from l in ls.DefaultIfEmpty()` | `GroupJoin(...)` 加 `SelectMany(...)` 与 `DefaultIfEmpty()` |
| 没有直接对应，靠子查询或 `WITH` 保存中间结果 | `let slow = l.Ms > 500` | 在 lambda 里再算一次，或用匿名类型保存 |
| `DISTINCT` | 没有对应子句 | `Distinct()` |
| `TOP 3` | 没有对应子句 | `Take(3)` |

有两点和 SQL 不同。第一，查询语句里的 `where` 写的是 C# 表达式，所以 `==` 比较的是 C# 的值，不是 SQL 的 `=`。第二，`DISTINCT`、`TOP` 这类没有对应子句，要用方法语法加在查询后面。

### 排序与多个排序键

`orderby` 后面可以写多个排序键，用逗号隔开。每个键可以单独指定升序或降序，`descending` 只作用在它前面的那个键上。

```csharp
var q7 = from l in logs
         orderby l.Level, l.Ms descending
         select $"{l.Level}{l.Ms}";
Console.WriteLine("orderby: " + string.Join(",", q7));
```

输出 `orderby: error2815,error1520,info62,info45,info23,info12,warn968,warn680`。先按 `Level` 升序，同一级别里再按 `Ms` 降序。这和 10.5 节的 `OrderBy(...).ThenByDescending(...)` 是同一个结果。

### 分组与分组后的筛选

`group ... by ... into` 把分组的结果起一个名字，后面的子句可以继续处理这个名字。`into` 之后，前面的范围变量 `l` 就不能用了，只能用分组变量。

```csharp
var q2 = from l in logs
         group l by l.Module into g
         where g.Count() > 1
         orderby g.Key
         select $"{g.Key}:{g.Count()}";
Console.WriteLine("group: " + string.Join(",", q2));
```

输出 `group: api:3,order:4`。`cache` 只有一条，被 `where g.Count() > 1` 过滤掉了。

`into` 之后的 `where` 相当于 SQL 的 `HAVING`，它筛选的是分组，而不是原始的日志。上面的代码等价于。

```csharp
var m2 = logs
    .GroupBy(l => l.Module)
    .Where(g => g.Count() > 1)
    .OrderBy(g => g.Key)
    .Select(g => $"{g.Key}:{g.Count()}");
```

### 临时变量 `let`

`let` 可以在查询中声明一个中间变量，供后面的子句使用，避免同一个计算写两遍。

```csharp
var q3 = from l in logs
         let slow = l.Ms > 500
         where slow
         select l.Module;
Console.WriteLine("let: " + string.Join(",", q3));
```

输出 `let: api,order,order,order`，它是耗时超过 500 ms 的四条日志的模块名。`slow` 只算了一次，`where` 直接使用它。

### 内连接 `join`

`join` 把两个集合按键配对。`on` 后面写的是两边的键，左边是前面的范围变量，右边是 `join` 声明的变量，中间用 `equals` 连接，不能写 `==`。

```csharp
var modules = new List<(string Name, string Team)> { ("api", "平台组"), ("order", "交易组"), ("auth", "安全组") };

var q4 = from l in logs
         join m in modules on l.Module equals m.Name
         select $"{m.Team}:{l.Level}";
Console.WriteLine("join: " + string.Join(",", q4));
```

输出 `join: 平台组:info,平台组:info,平台组:warn,交易组:error,交易组:info,交易组:error,交易组:warn`。`cache` 的日志在 `modules` 里没有对应项，所以没有出现在结果里，这和 10.5 节的 `Join` 结果一致。

### 左连接 `join ... into` 加 `DefaultIfEmpty`

内连接只保留能配对上的结果。要保留左边的每一条，即使右边没有对应的值，需要用 `join ... into`，它会把右边的配对结果收集成一组，然后用 `DefaultIfEmpty()` 处理“一条都没有”的情况。

```csharp
var q6 = from m in modules
         join l in logs on m.Name equals l.Module into ls
         from l in ls.DefaultIfEmpty()
         select $"{m.Name}:{l.Module ?? "无"}:{(l == default ? 0 : l.Ms)}";
Console.WriteLine("left: " + string.Join(",", q6));
```

输出 `left: api:api:45,api:api:62,api:api:968,order:order:1520,order:order:23,order:order:2815,order:order:680,auth:无:0`。`auth` 在日志里没有记录，`ls` 是空序列，`DefaultIfEmpty()` 给它补上一个默认元素，所以 `auth` 仍然出现在结果里，它的日志字段是 `null` 和 0。

这里的 `l == default` 用来判断补上的是不是那个默认元素。元组是值类型，所以 `default` 就是每个字段都是默认值的元组。

### 多个 `from`

查询语句里可以写多个 `from`。第二个 `from` 相当于又一层循环，把两个集合里的元素两两组合，再用 `where` 筛选。

```csharp
var q5 = from m in modules
         from l in logs
         where l.Module == m.Name && l.Ms > 1000
         select $"{m.Name}/{l.Ms}";
Console.WriteLine("multi from: " + string.Join(",", q5));
```

输出 `multi from: order/1520,order/2815`。这种写法的效率取决于两个集合的大小，要确保内层集合不会太大。如果两个集合有明确的键，用 `join` 更清楚，也更高效。

### 混用两种写法

查询语句可以和方法语法混用。最常见的做法是用查询语句写主体，再用方法接一个收尾的操作。这时要给查询语句加上括号。

```csharp
var names = (from l in logs
             where l.Level == "warn" || l.Level == "error"
             select l.Module)
            .Distinct()
            .OrderBy(m => m);
Console.WriteLine(string.Join(",", names));
```

输出 `api,order`。查询语句的结果是一个序列，括号里的部分先算完，再把结果交给 `Distinct` 和 `OrderBy`。如果不加括号，编译器会把 `.Distinct()` 当成 `select` 后面的内容，结果不对。

同样的写法也可以只用方法语法，效果一样。这两段代码在这个例子里的差别只在可读性上。

### 什么时候用哪一种

下面是一个实用的判断标准。

- 查询只有一两步，比如一个 `Where` 加一个 `Select`，方法语法更短，也更直接。
- 有多个 `from`、`join`、`let`，或者要做左连接，查询语句的结构更清楚，读的人更容易跟上。
- 写分组加分组后筛选时，两种写法都可以，选你团队的习惯即可。
- 需要 `Distinct`、`Take`、`Skip` 这些没有查询子句的方法时，通常用方法语法收尾。

本教材的 LogLens 项目全部使用方法语法。10.12 节会列出项目里的具体位置。这不代表查询语句不好，而是团队选择了一种风格，读代码时两种都要认得。

查询语句在数据库访问库里也很常见。比如 Entity Framework Core 允许用同样的写法查询数据库，这时查询会被翻译成 SQL 在数据库里执行，而不是在内存里的 `List` 上执行。那时写法几乎不变，但执行的地点变了，这一点在学习数据库访问时再细讲。

## 10.7 迭代器，用 `yield` 边算边给

前面 10.2 节的 `MyWhere` 里有一个 `yield return`。它是 C# 的迭代器语法，让一个方法可以“一次给出一个元素，给完一个就暂停，等下一次被要求时再继续”。

迭代器方法的返回类型是 `IEnumerable<T>`，方法体里用 `yield return` 产出元素，用 `yield break` 结束。

```csharp
var lines = ErrorLines(logs);
Console.WriteLine("已创建，还没遍历");

foreach (var line in lines)
{
    Console.WriteLine(line);
}

static IEnumerable<string> ErrorLines(IEnumerable<(string Level, string Module, int Ms)> source)
{
    Console.WriteLine("进入迭代器");
    foreach (var log in source)
    {
        if (log.Level == "error")
        {
            yield return $"{log.Module} {log.Ms}ms";
        }
    }
}
```

输出依次是。

```text
已创建，还没遍历
进入迭代器
order 1520ms
order 2815ms
```

注意输出的顺序。调用 `ErrorLines(logs)` 的时候，方法体一行都没有执行，所以“进入迭代器”没有出现。直到 `foreach` 第一次要取元素，方法才开始运行，直到遇到第一个 `yield return` 为止。接着 `foreach` 处理完这一条，再次要求下一条，方法从上次停下的地方继续往下走。

这就是 LINQ 能够“边算边给”的原因。`Where`、`Select` 这些方法内部也是迭代器，它们每次只从上游取一个元素，处理完立刻交给下游，不需要先把整个集合复制一份。

迭代器有几条规则需要记住。

- 返回类型必须是 `IEnumerable<T>`、`IEnumerator<T>` 或它们的只读版本。
- 方法体里可以有多个 `yield return`，也可以用 `yield break` 提前结束。
- `yield return` 不能放在带 `catch` 的 `try` 块里（见 [10.10 节](#s10-10)的错误表）。
- 迭代器在被遍历时才执行，所以它的方法体里的异常，也要等到遍历时才会出现。

### 真实的例子是 LogLens 的 `Chunked`

LogLens 的工具类 `CollectionExtensions.cs` 里有一个迭代器，它把一个序列按固定大小切成若干块，比如把很多条日志分批处理。下面是它的代码，我们把它复制到一个示例里运行。

```csharp
var chunks = logs.Chunked(3);
foreach (var chunk in chunks)
{
    Console.WriteLine(chunk.Count);
}

public static class ChunkExtensions
{
    public static IEnumerable<IReadOnlyList<TItem>> Chunked<TItem>(this IEnumerable<TItem> source, int size)
    {
        ArgumentOutOfRangeException.ThrowIfLessThan(size, 1);

        var buffer = new List<TItem>(size);
        foreach (var item in source)
        {
            buffer.Add(item);
            if (buffer.Count == size)
            {
                yield return buffer;
                // 新建一个列表而不是 Clear，避免把已经交出去的列表改掉
                buffer = new List<TItem>(size);
            }
        }

        if (buffer.Count > 0)
        {
            yield return buffer;
        }
    }
}
```

输出依次是 `3`、`3`、`2`。8 条日志每 3 条一块，分成 3 块，最后一块只有 2 条。

这段代码有两个值得学的地方。一是 `yield return buffer` 之后要新建一个列表，而不是调用 `Clear()`。因为 `yield return` 交出去的是这个列表本身，如果原地清空，调用方手里的那一块也会跟着变空。二是 `if (buffer.Count > 0)` 处理最后不足一块的部分，这是迭代器里常见的收尾。

### 自定义扩展方法 `EveryNth`

下一个例子是练习里会用到的 `EveryNth`，它每隔 n 个取一个元素。

```csharp
foreach (var log in logs.EveryNth(3))
{
    Console.WriteLine(log.Module);
}

public static class EveryNthExtensions
{
    public static IEnumerable<T> EveryNth<T>(this IEnumerable<T> source, int n)
    {
        int index = 0;
        foreach (var item in source)
        {
            if (index % n == 0)
            {
                yield return item;
            }
            index++;
        }
    }
}
```

输出 `api`、`order` 和 `cache`，分别是下标 0、3、6 的日志。它和 LINQ 的方法一样，也是一个扩展方法，所以能直接接在 `logs` 后面。

## 10.8 延迟执行与常见陷阱

LINQ 最容易出错的地方，几乎都和一件事有关，查询什么时候真正执行。这一节先讲延迟执行的规则，再讲由它引出的几类陷阱。

### 延迟执行是怎么回事

下面的代码展示了一个重要的特性。

```csharp
var query = logs.Where(log => log.Ms > 1000);
Console.WriteLine("还没执行");

foreach (var item in query)
{
    Console.WriteLine(item.Ms);
}
```

输出 `还没执行`、`1520` 和 `2815`。`Where` 这一行执行完的时候，它只是记下了“要筛选什么”，并没有去筛选。直到 `foreach` 开始遍历，筛选才发生。这就是延迟执行。

LINQ 的大多数查询方法都是延迟执行的，包括 `Where`、`Select`、`OrderBy`、`GroupBy` 等。下面两类操作会立刻执行，它们会真正遍历一遍序列并给出结果。

- 转换成集合的方法，`ToList()`、`ToArray()`、`ToDictionary()`、`ToHashSet()`、`ToLookup()`。
- 返回单个结果的方法，`Count()`、`Sum()`、`Max()`、`First()`、`Any()` 等。

这两类方法在调用的那一行就会执行查询，之后每次使用它们的结果都不会再重新遍历。

### 后果一，每次遍历都会重新执行

延迟执行带来的第一个后果是，查询每被遍历一次，都要重新执行一遍。

```csharp
var errs = logs.Where(log => log.Level == "error");
Console.WriteLine(errs.Count());
Console.WriteLine(errs.Count());
```

输出两次 `2`。每次调用 `Count()`，都会把筛选重新执行一遍。数据量大、查询复杂时，这会白白浪费时间。要多次使用同一个结果，就应该用 `ToList()` 存下来。

同样的道理也适用于带副作用的查询。下面的例子在 `Select` 里计数，每次映射都会让计数加一。

```csharp
int evaluated = 0;
var counted = logs.Select(l => { evaluated++; return l.Ms; });
_ = counted.Count();
_ = counted.Count();
Console.WriteLine($"两次 Count 后执行 {evaluated} 次映射");
```

输出 `两次 Count 后执行 16 次映射`。`logs` 有 8 条，两次 `Count()` 各执行了一遍，所以是 16 次。如果只需要一次结果，就只调用一次，或者用 `ToList()` 存下来。

### 后果二，lambda 捕获的是变量，不是声明时的值

延迟执行带来的第二个后果，和 lambda 捕获变量的规则结合在一起，很容易让人困惑。

```csharp
var threshold = 500;
var slow = logs.Where(log => log.Ms > threshold);

threshold = 5000;
Console.WriteLine(slow.Count());
```

输出 `0`。查询在 `Count()` 的时候才执行，那时 `threshold` 已经变成了 5000。lambda 读的是变量本身，而不是声明时的那个数字。

如果希望固定住声明时的值，就在声明的时候立刻 `ToList()`。

```csharp
var threshold = 500;
var slow = logs.Where(log => log.Ms > threshold).ToList();

threshold = 5000;
Console.WriteLine(slow.Count);
```

输出 `4`。`ToList()` 在这一行就执行了筛选，之后 `threshold` 怎么改，结果都不会变。`4` 是耗时超过 500 ms 的四条日志，968、1520、2815 和 680。

> 要多次使用的查询结果，立刻 `ToList()` 存下来。查询里用到的外部变量，如果后面还会改，也要特别小心。

### 陷阱三，遍历时修改集合

`foreach` 遍历一个 `List<T>` 的时候，如果中途往这个列表里添加或删除元素，下一次取值时会抛出异常。

```csharp
var ints = new List<int> { 1, 2, 3 };
try
{
    foreach (var x in ints)
    {
        if (x == 2)
        {
            ints.Add(99);
        }
    }
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"遍历时修改：{ex.GetType().Name}");
}
```

输出 `遍历时修改：InvalidOperationException`。LINQ 的查询同样会检查这一点。如果查询还没执行完，就修改了它的数据源，也会遇到同样的异常。需要边遍历边删除时，应该先用 `ToList()` 复制一份，遍历副本，再修改原来的列表；或者用 `RemoveAll` 这样的方法一次完成。

### 陷阱四，`null` 数据源

调用 LINQ 方法时，如果数据源是 `null`，会立即抛出 `ArgumentNullException`，而不是等到遍历时才抛出。

```csharp
try
{
    List<int>? nul = null;
    _ = nul!.Where(x => x > 0);
    Console.WriteLine("未立即报错");
}
catch (ArgumentNullException ex)
{
    Console.WriteLine($"null 源：{ex.GetType().Name} 在调用时立即抛出");
}
```

输出 `null 源：ArgumentNullException 在调用时立即抛出`。这一点和迭代器不同。`Where` 的参数检查是在调用时完成的，只有真正的遍历被推迟到之后。

另一个常见的问题是空序列上的统计，10.5 节的表格里已经列出了结果。`Max()` 对空序列会抛异常，`Sum()` 则返回 `0`。写代码时要先想清楚，空数据时应该得到什么。

### 陷阱五，排序时的字符串比较

`Order()` 和 `OrderBy()` 对字符串排序时，默认使用当前文化的比较规则。不同文化下，大小写和重音字母的先后顺序可能不一样。需要固定顺序时，应该明确指定比较器。

```csharp
var words = new[] { "banana", "Apple", "cherry", "apple" };
Console.WriteLine("默认：" + string.Join(",", words.Order()));
Console.WriteLine("Ordinal：" + string.Join(",", words.Order(StringComparer.Ordinal)));
Console.WriteLine("OrdinalIgnoreCase：" + string.Join(",", words.Order(StringComparer.OrdinalIgnoreCase)));
```

在本教材的测试环境里，当前文化是不变文化（Invariant），三行输出依次是。

```text
默认：apple,Apple,banana,cherry
Ordinal：Apple,apple,banana,cherry
OrdinalIgnoreCase：Apple,apple,banana,cherry
```

默认比较把 `apple` 排在 `Apple` 前面，Ordinal 按字符编码比较，大写字母排在小写字母前面。`OrdinalIgnoreCase` 忽略大小写，`Apple` 和 `apple` 的先后取决于输入顺序。

LogLens 的 `MainWindowViewModel.cs` 在排序时就指定了 `StringComparer.Ordinal`（10.12 节会列出位置）。如果排序结果要在不同的机器上保持一致，比如导出报告或做测试，都应该显式指定比较器。

### 陷阱六，整数求和溢出

`Sum()` 对 `int` 求和时，结果超出 `int` 的范围会抛出 `OverflowException`。

```csharp
try
{
    Console.WriteLine(new List<int> { int.MaxValue, 1 }.Sum());
}
catch (OverflowException ex)
{
    Console.WriteLine($"Sum 溢出：{ex.GetType().Name}");
}
```

输出 `Sum 溢出：OverflowException`。遇到可能超出范围的总和，可以在选择器里先转成 `long`，`logs.Sum(l => (long)l.Ms)`。这样结果就是 `long` 类型，不会溢出。

### 提前停止，只处理需要的那一部分

延迟执行还有一个用处。查询按需取数据，一旦 `Take`、`First` 或 `Any` 已经得到答案，就不再往后走。

```csharp
int examined = 0;
var firstTwo = Enumerable.Range(1, 1_000_000)
    .Select(x => { examined++; return x; })
    .Where(x => x % 7 == 0)
    .Take(2)
    .ToList();
Console.WriteLine($"结果 {string.Join(",", firstTwo)}，只检查了 {examined} 个数");
```

输出 `结果 7,14，只检查了 14 个数`。虽然数据源里有一百万个数，但找到 7 和 14 之后，`Take(2)` 就结束了，后面的数字根本没有被计算。`examined` 计数器只是为了让这个过程看得见，正式代码里通常不需要这样做。

这一点对处理大文件特别有用。`File.ReadLines` 返回的序列是一行一行读的，文件的剩余部分不会一次全部装进内存。

```csharp
string path = Path.GetTempFileName();
File.WriteAllLines(path, new[]
{
    "INFO 启动",
    "INFO 连接数据库",
    "ERROR 订单 1001 失败",
    "INFO 重试",
    "ERROR 订单 1002 失败",
    "INFO 结束",
});

int linesRead = 0;
var firstTwoErrors = File.ReadLines(path)
    .Select(line => { linesRead++; return line; })
    .Where(line => line.StartsWith("ERROR", StringComparison.Ordinal))
    .Take(2)
    .ToList();
Console.WriteLine($"找到 {firstTwoErrors.Count} 条，一共读了 {linesRead} 行");
Console.WriteLine(firstTwoErrors[0]);

File.Delete(path);
```

输出依次是 `找到 2 条，一共读了 5 行` 和 `ERROR 订单 1001 失败`。第二条错误在第五行，程序读到它之后就停了，第六行 `INFO 结束` 没有被读取。日志文件可能有几个 GB，如果先用 `ReadAllLines` 把它全部读进内存，再去筛选，内存会被白白占用。`File.ReadLines` 加上 LINQ，就能做到“读到够了就停”。

注意 `Path.GetTempFileName()` 会在临时目录里创建一个真实的文件，所以示例最后要调用 `File.Delete` 删掉它。

### 并行查询，用 AsParallel 开启

如果数据量很大，而每一步的计算又相互独立，可以让 LINQ 把工作分给多个 CPU 核心。这叫 PLINQ（Parallel LINQ），只需要在数据源后面加上 `AsParallel()`。

```csharp
Console.WriteLine(Enumerable.Range(1, 1000).AsParallel().Sum());
Console.WriteLine(string.Join(",", Enumerable.Range(1, 20).AsParallel().AsOrdered().Select(x => x * x).Take(5)));
```

第一行输出 `500500`，是 1 到 1000 的和。第二行输出 `1,4,9,16,25`。

并行查询需要注意几件事。

- 并行处理的顺序默认不固定。需要保持原来的顺序，要加上 `AsOrdered()`，就像上面的第二行那样。
- 并行本身也有开销。数据量很小时，分配任务和合并结果的时间可能比计算本身还长，反而更慢。是否值得并行，应该在真实数据上测量。
- 在并行的 lambda 里修改共享的变量是不安全的。上面的计数器 `examined` 如果放在并行查询里，结果可能出错。并行的 lambda 应该只读取数据，然后返回结果。

并行写起来很简单，但它会让程序的行为变得难以预测，所以只在确有必要的时候使用。

## 10.9 动手，完整程序

下面的程序用 LINQ 重写了[第 4 章](/chapter/04)的统计，并在最后加了一个迭代器。前面五段的输出与[第 4 章](/chapter/04)的版本完全相同。

```csharp
// ============================================
// 第 10 章 · LINQ
// 运行方式：dotnet run
// ============================================

// 1) 准备一批日志（实际场景从文件读取，后面的章节会做）
var logs = new List<(string Level, string Module, int Ms)>
{
    ("info", "api", 45),
    ("info", "api", 62),
    ("warn", "api", 968),
    ("error", "order", 1520),
    ("info", "order", 23),
    ("error", "order", 2815),
    ("info", "cache", 12),
    ("warn", "order", 680),
};

Console.WriteLine($"共 {logs.Count} 条日志");
Console.WriteLine();

// 2) 级别分布：GroupBy 后按数量从多到少排序
Console.WriteLine("级别分布：");
var byLevel = logs
    .GroupBy(log => log.Level)
    .OrderByDescending(group => group.Count());

foreach (var group in byLevel)
{
    Console.WriteLine($"  {group.Key,-6}{group.Count()} 条");
}

Console.WriteLine();

// 3) 最慢的三条：OrderByDescending 配合 Take
Console.WriteLine("最慢的三条：");
var slowest = logs
    .OrderByDescending(log => log.Ms)
    .Take(3);

foreach (var (level, module, ms) in slowest)
{
    Console.WriteLine($"  {ms,5} ms  {module,-6}{level}");
}

Console.WriteLine();

// 4) 各模块的问题数：先 Where 筛出 warn 和 error，再 GroupBy
Console.WriteLine("各模块问题数：");
var problemsByModule = logs
    .Where(log => log.Level == "warn" || log.Level == "error")
    .GroupBy(log => log.Module)
    .OrderByDescending(group => group.Count());

foreach (var group in problemsByModule)
{
    Console.WriteLine($"  {group.Key,-6}{group.Count()} 个");
}

Console.WriteLine();

// 5) 用字典按级别查数量
var countByLevel = logs
    .GroupBy(log => log.Level)
    .ToDictionary(group => group.Key, group => group.Count());

if (countByLevel.TryGetValue("error", out var errorCount))
{
    Console.WriteLine($"error 共 {errorCount} 条，占总数的 {errorCount * 100.0 / logs.Count:F1}%");
}

Console.WriteLine();

// 6) 迭代器：逐条产出超过 500 ms 的日志
Console.WriteLine("超过 500 ms 的日志：");
foreach (var line in SlowLines(logs, 500))
{
    Console.WriteLine(line);
}

static IEnumerable<string> SlowLines(IEnumerable<(string Level, string Module, int Ms)> source, int limit)
{
    foreach (var log in source)
    {
        if (log.Ms > limit)
        {
            yield return $"  {log.Module,-6}{log.Ms} ms";
        }
    }
}
```

输出如下。

```text
共 8 条日志

级别分布：
  info  4 条
  warn  2 条
  error 2 条

最慢的三条：
   2815 ms  order error
   1520 ms  order error
    968 ms  api   warn

各模块问题数：
  order 3 个
  api   1 个

error 共 2 条，占总数的 25.0%

超过 500 ms 的日志：
  api   968 ms
  order 1520 ms
  order 2815 ms
  order 680 ms
```

### 逐段解释

| 代码 | 说明 |
| --- | --- |
| `GroupBy(log => log.Level)` | 按级别分组，`group.Key` 就是级别 |
| `.OrderByDescending(group => group.Count())` | 数量多的组排在前面，数量相同的保持原来的先后顺序 |
| `{group.Key,-6}` | 左对齐，占 6 个字符宽，[第 2 章](/chapter/02)讲过 |
| `.Take(3)` | 只取排好序的前 3 条，属于延迟执行，直到 `foreach` 才计算 |
| `foreach (var (level, module, ms) in slowest)` | 直接把元组拆成三个变量 |
| `log.Level == "warn" \|\| log.Level == "error"` | 先用 `Where` 筛出需要处理的日志，再分组 |
| `.ToDictionary(group => group.Key, group => group.Count())` | 把分组结果变成“级别到数量”的字典，每组的键都不同，所以不会重复 |
| `TryGetValue("error", out var errorCount)` | 安全取值，键不存在时不会崩溃 |
| `{errorCount * 100.0 / logs.Count:F1}%` | 数字和 `%` 手动拼在一起，`F1` 控制保留一位小数 |
| `SlowLines(logs, 500)` | 调用迭代器，每次遍历 `foreach` 时产出一条，不会先生成整个列表 |

## 10.10 常见错误

LINQ 的错误分两类。一类是编译时报出来的，写错了类型、少写了子句，编译器会直接指出来。另一类是运行时才抛出的异常，通常和数据有关，比如序列是空的，或者键重复了。

### 编译错误

下面的错误都来自本章的小段代码，错误码与编译器的报错含义一致。

| 错误码 | 现象 | 例子 | 怎么改 |
| --- | --- | --- | --- |
| CS0029 | 类型不能隐式转换 | `int first = logs.Select(l => l.Module).First();`，`string` 不能转成 `int` | 检查 `Select` 的结果类型，或改成正确的变量类型 |
| CS0029 | 条件不是 `bool` | `from l in logs where l.Ms select l`，`where` 后面是 `int` | 写成比较表达式，比如 `l.Ms > 0` |
| CS0029 与 CS1662 | lambda 返回值不符合委托 | `logs.Where(l => l.Ms)` 会同时报两个错误 | 改成 `l => l.Ms > 0`，返回 `bool` |
| CS1061 | 找不到成员 | 匿名类型只有 `Module`，却写了 `x.Ms` | 检查属性名，对照 `select new { ... }` 里写了哪些字段 |
| CS1061 | 找不到 LINQ 方法 | 关闭了隐式 using 后，`List<int>` 没有 `Where` | 在文件顶部加 `using System.Linq;` |
| CS0742 | 查询语句没有以 `select` 或 `group` 结束 | `from l in logs where l.Level == "error";` | 在末尾加上 `select l` |
| CS0826 | 隐式类型的数组找不到最佳类型 | `var mixed = new[] { 1, "二" };` | 显式写出元素类型，比如 `new object[] { 1, "二" }` |
| CS1626 | 迭代器的 `try` 块带 `catch` 时不能 `yield return` | 在 `try { yield return 1; } catch { ... }` 里产出元素 | 把 `catch` 的逻辑移出迭代器，或者在迭代器外层处理异常 |
| CS1631 | 在 `catch` 块里不能 `yield return` | `catch (Exception) { yield return 2; }` | 同上，把产出的动作放到 `try` 外面 |

有一个情况值得特别说明。下面的代码能通过编译，但读起来容易混乱。

```csharp
var logs = new List<int> { 1, 2, 3 };
var l = 5;
var big = logs.Where(l => l > 1).ToList();
Console.WriteLine(big.Count + l);
```

`Where` 的 lambda 参数 `l` 和外面的局部变量 `l` 同名。在本教材使用的 C# 版本里，这是允许的，lambda 里的 `l` 会遮住外面的 `l`。但读代码的人很难一眼看出哪个 `l` 指的是什么。建议给 lambda 参数起一个不会重复的名字，本章的示例大多数用 `log` 或 `l`，就是为了避免这种情况。

### 运行时异常

下面的异常都出现在前面的例子里，并且都在本章的程序中实际运行过。

| 异常类型 | 出现的情况 | 本章的例子 |
| --- | --- | --- |
| `InvalidOperationException`，消息 `Sequence contains no elements` | 对空序列调用 `First`、`Last`、`Max`、`Average`，或没有种子的 `Aggregate` | 10.5 节的统计表 |
| `InvalidOperationException`，消息 `Sequence contains more than one matching element` | `Single` 找到多条 | 10.5 节 |
| `InvalidOperationException` | 遍历时修改了数据源 | 10.8 节陷阱三 |
| `ArgumentException`，消息包含 `same key` | `ToDictionary` 的键重复 | 10.5 节转集合 |
| `OverflowException` | `int` 求和超出范围 | 10.8 节陷阱六 |
| `InvalidCastException` | `Cast<T>` 遇到类型不符的元素 | 10.5 节取元素与判断 |
| `ArgumentNullException` | 数据源为 `null`，在调用时立即抛出 | 10.8 节陷阱四 |

大多数运行时异常都可以提前避免。统计前先判断序列是否为空，用 `FirstOrDefault` 或 `Any()` 代替会报错的版本，用 `ToDictionary` 之前先确认键唯一。

## 10.11 小练习

下面五道练习覆盖本章的主要内容。每道题先自己写一遍，再对照参考答案。练习里的 `logs` 与本章开头的定义相同，`modules` 只包含 `api` 和 `order` 两个模块。

var modules = new List<(string Name, string Team)> { ("api", "平台组"), ("order", "交易组") };

**练习 1，查询语句与方法语法**

用查询语句找出所有级别是 `warn` 或 `error` 的日志的模块名，去重后按字母顺序排列。然后用方法语法再写一遍，两段代码的结果应该相同。

```csharp
var names1 = (from l in logs
              where l.Level == "warn" || l.Level == "error"
              select l.Module)
             .Distinct()
             .OrderBy(m => m);
Console.WriteLine(string.Join(",", names1));

var names2 = logs.Where(l => l.Level == "warn" || l.Level == "error")
    .Select(l => l.Module)
    .Distinct()
    .OrderBy(m => m);
Console.WriteLine(string.Join(",", names2));
```

输出两行 `api,order`。

**练习 2，内连接**

用查询语句的 `join`，把每条日志配上它所属的团队，每行输出形如 `平台组 info 45ms`。`modules` 里没有的模块，它的日志不输出。

参考答案如下。

```csharp
var rows = from l in logs
           join m in modules on l.Module equals m.Name
           select $"{m.Team} {l.Level} {l.Ms}ms";
foreach (var row in rows)
{
    Console.WriteLine(row);
}
```

输出七行，依次是 `平台组 info 45ms`、`平台组 info 62ms`、`平台组 warn 968ms`、`交易组 error 1520ms`、`交易组 info 23ms`、`交易组 error 2815ms` 和 `交易组 warn 680ms`。`cache` 模块没有出现在 `modules` 里，它的一条日志被跳过了。

**练习 3，分组与排序**

用查询语句按级别分组，计算每个级别的平均耗时，保留一位小数，并按平均耗时从大到小排列。

参考答案如下。

```csharp
var avgByLevel = from l in logs
                 group l.Ms by l.Level into g
                 let avg = g.Average()
                 orderby avg descending
                 select $"{g.Key} {avg:F1}";
foreach (var line in avgByLevel)
{
    Console.WriteLine(line);
}
```

输出三行，`error 2167.5`、`warn 824.0` 和 `info 35.5`。`let` 把平均值保存下来，`orderby` 和 `select` 都能用到它。

**练习 4，用 `Aggregate` 找最慢的一条**

不使用 `MaxBy`，用 `Aggregate` 找出耗时最长的那条日志，输出形如 `order 2815ms`。

参考答案如下。

```csharp
var slowest = logs.Aggregate((best, current) => current.Ms > best.Ms ? current : best);
Console.WriteLine($"{slowest.Module} {slowest.Ms}ms");
```

输出 `order 2815ms`。累加器 `best` 保存目前见过的最慢的那条，每遇到一条更慢的，就换成它。

**练习 5，写一个迭代器扩展方法**

写一个扩展方法 `Pairs`，它返回相邻两条元素组成的元组 `(Prev, Next)`。用它统计耗时比上一条多出 500 ms 以上的次数。

参考答案如下。

```csharp
int jumps = 0;
foreach (var (prev, next) in logs.Pairs())
{
    if (next.Ms - prev.Ms > 500)
    {
        jumps++;
    }
}
Console.WriteLine($"耗时比上一条多出 500 ms 以上的次数：{jumps}");

public static class PairExtensions
{
    public static IEnumerable<(T Prev, T Next)> Pairs<T>(this IEnumerable<T> source)
    {
        bool hasPrev = false;
        T prev = default!;
        foreach (var item in source)
        {
            if (hasPrev)
            {
                yield return (prev, item);
            }
            prev = item;
            hasPrev = true;
        }
    }
}
```

输出 `耗时比上一条多出 500 ms 以上的次数：4`。四次跳升分别是 62 到 968、968 到 1520、23 到 2815，以及 12 到 680。`Pairs` 在第一条时不产出，因为它还没有“上一条”。

## 10.13 数据源，以及 LINQ 相对循环的优势

前面几节的数据都放在 `List<T>` 里。LINQ 的一个重要特点是，它不关心数据从哪里来。只要是 `IEnumerable<T>`（或者 `IQueryable<T>`），就能接上同样的方法。本节先看几种常见的数据源，再讨论 LINQ 相对于循环和 `if` 的优势，以及它的代价。

### 能接入 LINQ 的数据源

| 数据源 | 类型 | 怎么接入 | 要注意的地方 |
| --- | --- | --- | --- |
| 内存集合 | `List<T>`、数组、`Dictionary<K, V>` | 直接调用 | 前面几节已经用过 |
| 字符串 | `string`，本身就是 `IEnumerable<char>` | 直接调用 | 结果是字符序列，要用 `new string(...)` 转回字符串 |
| XML | `XDocument`、`XElement` | `Descendants()`、`Elements()` 返回 `IEnumerable<XElement>` | 属性要先转换类型，属性不存在时强制转换会抛异常（这里没有演示） |
| 文件逐行 | `File.ReadLines` | 返回惰性的 `IEnumerable<string>` | 不要用 `File.ReadAllLines`，它会一次性把整个文件读进内存 |
| 数据库 | `IQueryable<T>`，EF Core 等 ORM 提供 | 查询会被翻译成 SQL 在数据库里执行 | 只能用能被翻译的方法，数据库内容在后面的章节再实际运行 |
| 并行 | `AsParallel()` | 同一组方法并行执行 | 顺序与共享变量的问题，见 [10.8 节](#s10-8) |

下面的检查点逐个演示其中四种。

**字符串。** 字符串可以直接用 `Where`，它的元素是 `char`。

```csharp
var digits = new string("ERROR 42 timeout 7".Where(char.IsDigit).ToArray());
Console.WriteLine($"  {digits}");
```

运行结果。

```text
  427
```

**XML。** `Descendants("log")` 找出所有名为 `log` 的元素，然后像处理普通集合一样筛选。

```csharp
var xml = XDocument.Parse(
    "<logs>" +
    "<log level=\"warn\" module=\"api\" ms=\"968\">慢请求</log>" +
    "<log level=\"info\" module=\"cache\" ms=\"12\">命中</log>" +
    "<log level=\"error\" module=\"order\" ms=\"1520\">下单超时</log>" +
    "</logs>");
var slowXml = xml.Descendants("log")
    .Where(e => (int)e.Attribute("ms")! > 500)
    .Select(e => $"  {(string?)e.Attribute("module")}: {e.Value}");
foreach (var line in slowXml)
{
    Console.WriteLine(line);
}
```

运行结果。

```text
  api: 慢请求
  order: 下单超时
```

这里的 `(int)e.Attribute("ms")!` 用了 `!`，告诉编译器这个属性一定存在。如果 XML 里真的缺少这个属性，程序会在这一行抛出异常，而不是悄悄地给出错误的结果。

**文件逐行。** `File.ReadLines` 不会一次把文件读完，它每次只取一行。因此，`Take` 能让它在找到足够的结果后立即停止。下面的例子生成一个 10 万行的文件，每 1000 行出现一次 `ERROR`，然后取前三条。

```csharp
var path = Path.Combine(Path.GetTempPath(), "loglens-ch10-linq.log");
File.WriteAllLines(path, Enumerable.Range(0, 100_000)
    .Select(i => i % 1000 == 999 ? $"ERROR 第 {i} 行" : $"INFO 第 {i} 行"));
var readCount = 0;
var firstThreeErrors = File.ReadLines(path)
    .Select(line => { readCount++; return line; })
    .Where(line => line.StartsWith("ERROR"))
    .Take(3)
    .ToList();
Console.WriteLine("文件中前三条 ERROR：");
foreach (var line in firstThreeErrors)
{
    Console.WriteLine($"  {line}");
}
Console.WriteLine($"  为了找到它们，一共读了 {readCount} 行（文件共 100000 行）");
File.Delete(path);
```

运行结果。

```text
文件中前三条 ERROR：
  ERROR 第 999 行
  ERROR 第 1999 行
  ERROR 第 2999 行
  为了找到它们，一共读了 3000 行（文件共 100000 行）
```

第三条 `ERROR` 在第 2999 行，所以一共只读了 3000 行，后面的 97000 行没有被读取。`readCount` 是在 `Select` 里计数的，它记录的正是真正被读取的行数。

**数据库。** 这里没有数据库，所以只演示 `Expression` 树本身。`Expression<Func<...>>` 保存的是判断的结构，而不是编译好的代码。数据库的 ORM 会读取这份结构，并把它翻译成 SQL。

```csharp
Expression<Func<LogRow, bool>> isSlowError = log => log.Level == "error" && log.Ms > 500;
Console.WriteLine($"表达式树的内容：{isSlowError.Body}");
var compiled = isSlowError.Compile();
Console.WriteLine($"编译成委托后直接调用：{compiled(new LogRow("error", "order", 1520))}");
```

运行结果。

```text
表达式树的内容：((log.Level == "error") AndAlso (log.Ms > 500))
编译成委托后直接调用：True
```

`Func<T, bool>` 与 `Expression<Func<T, bool>>` 的区别是，前者是一段可以直接调用的代码，后者是一份可以被检查和翻译的数据。`Compile()` 会把它变成前者。第 [10.8 节](#s10-8)讲过的延迟执行，在 `IQueryable<T>` 上也是同样的道理，查询在被遍历时才交给数据源执行。

### 相对循环和 `if` 的优势

**第一，判断可以当作数据传递和组合。** 循环里的 `if` 写死在代码里，运行时很难改。而 `Func<T, bool>` 是一个值，可以放进列表，在运行时决定要加哪些条件。

```csharp
string? wantLevel = "error";     // 假设来自命令行参数，null 表示不过滤级别
int? minMs = 500;                // 假设来自命令行参数，null 表示不过滤耗时
var conditions = new List<Func<LogRow, bool>>();
if (wantLevel is not null)
{
    conditions.Add(log => log.Level == wantLevel);
}
if (minMs.HasValue)
{
    var min = minMs.Value;
    conditions.Add(log => log.Ms > min);
}
var dynamicMatches = rows.Where(log => conditions.All(c => c(log))).ToList();
Console.WriteLine($"动态条件匹配 {dynamicMatches.Count} 条：{string.Join(", ", dynamicMatches.Select(l => l.Module))}");
```

运行结果。

```text
动态条件匹配 2 条：order, order
```

如果命令行没有传 `--level`，`wantLevel` 就是 `null`，对应的条件不会加入列表。循环版本也能做到，但每增加一个条件，就要在循环里多写一层 `if`，条件多了之后很难维护。项目里的 `QueryEngine.CompilePredicate` 也是这个思路。用户输入的查询文本会被编译成一个 `Func<LogEvent, bool>`（`src/LogLens.Core/Query/QueryEngine.cs` 第 92 行），之后每条日志都只需要调用它一次。

**第二，描述"要什么"，而不是"怎么做"。** 第 [10.9 节](#s10-9)的完整程序里，按级别分组、排序、取前几条，用几个方法链就写完了。循环版本要自己维护字典、计数和排序，代码量更多，读的人要先在脑子里把循环跑一遍才能看出意图。

**第三，惰性求值和提前停止可以自然地组合。** 上面的文件例子中，`Take(3)` 让整个查询在找到三条后停止。循环也能做到，只是要自己写 `break`，并且在和其他步骤组合时，结构会变得复杂。

**第四，同一段查询可以换数据源。** 只要数据源是 `IEnumerable<T>` 或 `IQueryable<T>`，查询的写法不变。循环只能在你手里的数据上运行。`IQueryable<T>` 还能把同一段查询交给数据库执行，这是循环做不到的。

### LINQ 的代价

LINQ 不是免费的，下面三点要一起考虑。

**性能。** 下面的检查点对 1000 万个整数做同样的求和。先用 `for` 循环，再用 `Where` 和 `Sum`。

```csharp
var big = Enumerable.Range(0, 10_000_000).ToArray();
var sw = Stopwatch.StartNew();
long loopSum = 0;
for (var i = 0; i < big.Length; i++)
{
    if (big[i] % 3 == 0)
    {
        loopSum += big[i];
    }
}
var loopMs = sw.ElapsedMilliseconds;

sw.Restart();
var linqSum = big.Where(x => x % 3 == 0).Sum(x => (long)x);
var linqMs = sw.ElapsedMilliseconds;
Console.WriteLine($"循环求和 = {loopSum}，耗时约 {loopMs} ms");
Console.WriteLine($"LINQ 求和 = {linqSum}，耗时约 {linqMs} ms（结果相同：{loopSum == linqSum}，耗时只作参考）");
```

运行结果（同一次运行）。

```text
循环求和 = 16666668333333，耗时约 25 ms
LINQ 求和 = 16666668333333，耗时约 29 ms（结果相同：True，耗时只作参考）
```

在这台机器上，检查点连续运行了四次。循环版本约 24 至 27 毫秒，LINQ 版本约 29 至 38 毫秒，LINQ 略慢。通常的原因是每个元素都要经过一次委托调用。对于大多数业务代码，这点差距不影响使用；但对于热点路径，即每秒要执行成千上万次、处理大量数据的代码，循环可能更合适。数字因机器而异，只作参考。

**调试。** 一条长长的方法链写在一行或几行里，断点只能停在整个语句上，要看中间的结果需要拆开或加临时变量。循环的每一步都在一个地方，调试器更容易看清楚。

**延迟执行。** 第 [10.8 节](#s10-8)讲过，查询在遍历时才执行，多次遍历会重复执行，遍历时修改数据源会出问题。这些陷阱是 LINQ 的代价，不能因为写法简洁就忽略它们。

### 什么时候改回循环

- 热点路径，对性能敏感，并且已经用测量确认 LINQ 是瓶颈。
- 逻辑需要同时修改多个变量，或者需要在中途根据状态跳出、回退。
- 需要 `Span<T>` 这类低分配的数据类型。`Span<T>` 不是 `IEnumerable<T>`，不能直接使用 LINQ。
- 链式表达式已经长到很难读懂，这时拆成几个有名字的方法，或者改成循环，往往更清楚。

选择的标准是哪种写法更容易让读的人看懂，并且满足性能要求，而不是哪种写法更新潮。
