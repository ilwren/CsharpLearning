# 第 11 章 出错不可怕，异常与 `Result`

> **本章你会做出什么**
> 一个"安全的解析流程"，用户输入合法就输出结果，不合法就给出**人话解释 + 退出码**；

> ```
>
> 上面是效果示意。真实运行时，`…` 会换成你所在目录的完整路径；11.7 节给出了逐行的真实输出。

## 11.1 三种失败，应该分别对待

新手常犯的错误是"所有失败都用 `try/catch` 一把抓"，可以分成三类。

| 类型 | 例子 | 该怎么处理 |
| --- | --- | --- |
| **① 程序 bug** | 数组越界、空引用、逻辑写错 | 让它崩（开发时就该暴露），修代码 |
| **② 可预期的失败** | 用户输入 `abc` 当数字、日志行格式不认识 | **用返回值表达**，给出提示，继续跑 |
| **③ 外部故障** | 文件不存在、没权限、磁盘满 | 用**异常**捕获，转成友好提示 + 退出码 |

**关键判断**，这个失败是"正常业务流程的一部分"吗？

- 是（用户可能输错）→ 用返回值（`bool TryParse` 或 `Result<T>`）
- 不是（环境坏了）→ 用异常

> 为什么"用户输错"不该用异常？异常表达的语义是"意外"，而用户输错是每天都会发生的正常事。
> 另一个原因是性能。在本书的验证环境（Debug 构建）里，抛出并捕获 20 万次异常花了约 450 毫秒，
> 而 `int.TryParse` 对 20 万个非法字符串返回失败只用了约 7 毫秒。数字会随机器和构建方式变化，但差距是数量级的。
> 用异常处理用户输入，既慢，又会让代码充满 `try/catch` 噪音。

### 异常到底是什么

异常是一个对象，类型继承自 `System.Exception`（[第 7 章](/chapter/07)的继承在这里又出现了）。
`throw` 把它抛出去之后，运行时沿着调用栈往上找能接住它的 `catch`。
如果一直找不到，程序就会被终止，并打印出 `Unhandled exception.` 和调用栈。

```csharp
Console.WriteLine("开始");
Work();
Console.WriteLine("这一行不会执行");

static void Work() => throw new InvalidOperationException("没人接的错误");
```

在验证环境里，标准错误输出是这样的（前几行）。

```text
Unhandled exception. System.InvalidOperationException: 没人接的错误
   at Program.<<Main>$>g__Work|0_0() in .../Program.cs:line 5
   at Program.<Main>$(String[] args) in .../Program.cs:line 2
```

"开始"会打印出来，第二行不会。进程的退出码也不是 0（Linux 上是 134，Windows 上会是另一个值，不同系统不一样）。
这就是"崩溃"的样子。11.6 节要讲的骨架，目的就是让用户永远看不到这种红色堆栈。

## 11.2 `try` / `catch` / `finally`

```csharp
try
{
    // 可能出事的代码
    var text = File.ReadAllText("app.log");
    Console.WriteLine($"读到 {text.Length} 个字符");
}
catch (FileNotFoundException ex)
{
    // 只处理"文件找不到"这一种
    Console.WriteLine($"文件不存在：{ex.FileName}");
}
catch (IOException ex)
{
    // 处理其它 IO 问题（磁盘、权限…）
    Console.WriteLine($"读取失败：{ex.Message}");
}
finally
{
    // 无论成功还是失败都会执行
    Console.WriteLine("（这一行一定会打印）");
}
```

三个块的职责。

| 块 | 作用 | 会执行吗 |
| --- | --- | --- |
| `try` | 放可能出错的代码 | 一定 |
| `catch` | 出错时接管 | 只有对应异常发生时 |
| `finally` | 收尾（关文件、还原状态） | **一定**（哪怕 `return` 了、哪怕异常还没被接住） |

### `catch` 的顺序很重要

**从具体到宽泛**。因为第一个匹配的 `catch` 会接管。

```csharp
catch (FileNotFoundException ex) { ... }   // 具体：先放
catch (IOException ex) { ... }             // 父类型：后放
catch (Exception ex) { ... }               // 兜底：最后
```

写反了，编译器会直接报错。下面这段代码里，`Exception` 排在了 `InvalidOperationException` 前面。

```csharp
try
{
    throw new InvalidOperationException();
}
catch (Exception ex)
{
    Console.WriteLine(ex);
}
catch (InvalidOperationException ex)   // ❌ 永远到不了这里
{
    Console.WriteLine(ex);
}
```

编译器报 `CS0160: A previous catch clause already catches all exceptions of this or of a super type ('Exception')`。

> `FileNotFoundException` 是 `IOException` 的子类，**[第 7 章](/chapter/07)的继承在这里派上用场**。
> `catch` 判断的就是"异常对象的运行时类型是不是这个类型（或它的子类）"。

### `finally` 里不能 `return`

`finally` 一定会执行，所以它适合做收尾，但**不能从它里面跳出去**。下面的代码无法编译。

```csharp
static int F()
{
    try
    {
        return 1;
    }
    finally
    {
        return 2;      // ❌ CS0157: Control cannot leave the body of a finally clause
    }
}
```

有人会想让 `finally` 里的 `return` 覆盖前面的返回值，但 C# 直接不允许。
正确做法是，`finally` 只收尾，返回值放在 `try` 之后或 `try` 里。

### 常见异常类型速查

下面这些是新手最常遇到的异常。左边是类型，中间是典型原因，右边是在验证环境里得到的 `Message`（节选）。
`Message` 的文字会随系统语言变化，你的机器上显示的可能是中文。

| 异常类型 | 典型原因 | 验证环境里的消息（节选） |
| --- | --- | --- |
| `IndexOutOfRangeException` | 数组下标超出范围 | `Index was outside the bounds of the array.` |
| `NullReferenceException` | 对 `null` 访问成员 | `Object reference not set to an instance of an object.` |
| `FormatException` | 字符串格式不对，如 `int.Parse("abc")` | `The input string 'abc' was not in a correct format.` |
| `KeyNotFoundException` | 字典里没有这个键 | `The given key 'x' was not present in the dictionary.` |
| `FileNotFoundException` | 文件不存在 | `Could not find file '…'.` |
| `DirectoryNotFoundException` | 目录不存在 | `Could not find a part of the path '…'.` |
| `UnauthorizedAccessException` | 没有读写权限 | 本环境没有复现，常见于没有权限的路径 |
| `ArgumentNullException` | 参数传了 `null` | `Value cannot be null. (Parameter 'p')` |
| `ArgumentOutOfRangeException` | 参数超出允许范围 | `ms ('-1') must be a non-negative value. (Parameter 'ms')` |
| `InvalidOperationException` | 对象当前状态不允许该操作，如对空序列调用 `First()` | `Sequence contains no elements` |
| `OverflowException` | 整数溢出（只在 `checked` 上下文里抛出） | `Arithmetic operation resulted in an overflow.` |
| `InvalidCastException` | 类型转换失败，如把字符串强转成 `int` | `Unable to cast object of type 'System.String' to type 'System.Int32'.` |
| `OperationCanceledException` | 操作被取消（如按了 Ctrl+C） | `The operation was canceled.` |

> 看到异常类型，先想两件事，它说的是**我的代码写错了**，还是**外部环境出了问题**？
> 前者（空引用、越界、溢出）通常要修代码；后者（文件、权限、取消）要在合适的层级处理。

### `using` 是 `try/finally` 的简写

```csharp
using var stream = File.OpenRead(path);
// ……用 stream……
// 离开这个作用域时，stream 会被自动 Dispose
```

编译器会把它展开成"`try` 里使用、`finally` 里调用 `Dispose`"的形式。
所以只要资源实现了 `IDisposable`，就优先用 `using`，不要自己手写 `finally` 去关闭它。
这也是为什么 11.3 节的示例里没有出现 `finally`。

## 11.3 `throw`，主动抛异常

```csharp
public static int RequirePositive(int value)
{
    if (value <= 0)
    {
        throw new ArgumentOutOfRangeException(nameof(value), "必须是正数");
    }

    return value;
}
```

抛出去之后，异常会一路往上"冒泡"，直到遇到能处理它的 `catch`；没人处理，程序就崩。

### 项目里的异常体系

真实项目的异常基类在 `Core/Infrastructure/LogLensException.cs`。节选如下。

```csharp
/// <summary>本项目所有"可预期异常"的基类。</summary>
public abstract class LogLensException : Exception
{
    // protected 构造函数：只允许子类调用，保证基类不会被直接 new
    protected LogLensException(string message) : base(message) { }

    protected LogLensException(string message, Exception inner) : base(message, inner) { }

    /// <summary>建议的退出码，CLI 用它区分失败类型。</summary>
    public abstract int ExitCode { get; }

    /// <summary>给用户的"下一步怎么做"提示，可为空。</summary>
    public virtual string? Hint => null;
}

/// <summary>输入的文件/目录有问题。</summary>
public sealed class LogSourceException : LogLensException
{
    public LogSourceException(string path, string reason) : base($"无法读取日志源 '{path}'：{reason}")
    {
        Path = path;
    }

    public string Path { get; }

    public override int ExitCode => 2;

    public override string Hint => "确认路径存在；Linux/macOS 上注意文件权限，Windows 上注意是否被占用。";
}
```

几处设计值得留意。

1. **基类是 `abstract`**，`LogLensException` 本身没有意义，只有具体的子类才有，所以不允许直接 `new`（[第 7 章](/chapter/07)学过的抽象类）。
2. **`ExitCode` 是 `abstract` 属性**，每个子类用 `override` 给出自己的退出码。不同失败对应不同的码，调用方不用猜。
3. **`Hint` 是 `virtual` 属性**，默认返回 `null`，子类需要时才重写，给用户一句"下一步怎么做"。
4. **构造函数里带上上下文**，`Path` 保存的是用户原始输入的路径，错误信息也带着它。

> 本章 11.7 的完整程序为了能放进一个文件，把异常类写得简单了一些（构造时直接传入退出码）。
> 理解了上面的抽象版本，就能看懂那个简化版本为什么这样写。

用法。

```csharp
try
{
    using var stream = File.OpenRead(path);
}
catch (FileNotFoundException)
{
    throw new LogSourceException(path, "文件不存在");
}
catch (UnauthorizedAccessException)
{
    throw new LogSourceException(path, "没有读取权限");
}
```

好处。
1. **调用方能用 `catch (LogSourceException)` 精确处理**，不用去猜 `IOException` 的细节；
2. **每种异常自带退出码和提示**，命令行工具直接 `return ex.ExitCode;` 就完事；
3. 错误信息统一带上"文件路径""第几个字符"这类上下文。

### 包装异常，保留 `InnerException`

有时候你想给出自己的错误信息，但又不想丢掉底层的原因。这时可以把原始异常作为"内部异常"（`InnerException`）传进去。

```csharp
try
{
    File.ReadAllText(path);
}
catch (FileNotFoundException ex)
{
    throw new LogSourceException(path, "文件不存在", ex);    // ex 作为内层异常保存下来
}
```

> 本例为了演示，给 `LogSourceException` 多加了一个 `inner` 参数的构造函数，并把它交给基类。
> `: base($"无法读取日志源 '{path}'：{reason}", inner)`。项目里 `LogFormatException` 已经有这样的构造函数。

调用方可以同时看到外层和内层。

```text
外层：LogSourceException | 无法读取日志源 'missing.log'：文件不存在
内层：FileNotFoundException | Could not find file '…/missing.log'.
```

**如果构造时不传 `inner`，原始异常就永久丢失了**。这会让排查变得困难，你只看到"文件不存在"，却不知道是哪一行、哪个调用引发的。

### 重新抛出，保留原始堆栈

```csharp
catch (Exception ex)
{
    _logger.Error("分析失败", ex);
    throw;                  // ✅ 保留原始堆栈
    // throw ex;            // ❌ 堆栈被改写，排查时看不到真正的出错位置
}
```

下面用一个小实验说明差别。`Inner` 里抛出异常，中间的 `Middle` 捕获后分别用两种方式重新抛出。

```csharp
static void Inner() => throw new InvalidOperationException("深层错误");

static void MiddleRethrow()
{
    try { Inner(); }
    catch (Exception) { throw; }
}

static void MiddleBad()
{
    try { Inner(); }
    catch (Exception ex) { throw ex; }
}
```

检查两次捕获到的异常的 `StackTrace` 里是否还包含 `Inner`。

```text
throw; 堆栈包含 Inner：True
throw ex; 堆栈包含 Inner：False
```

`throw ex;` 之后，堆栈从 `throw ex;` 这一行重新开始，原来的 `Inner` 消失了。
编译器的分析器也会对 `throw ex;` 给出 `CA2200` 警告（"Re-throwing caught exception changes stack information"）。
一个字母的差别，排查难度可能差很多。

## 11.4 异常过滤器 `when`，只处理该处理的

```csharp
catch (IOException ex) when (ex.Message.Contains("No space"))
{
    Console.WriteLine("磁盘满了，请清理后重试");
}
catch (IOException ex)
{
    Console.WriteLine($"IO 出错：{ex.Message}");
}
```

`when` 让"是否接管"由你决定，而不用在 `catch` 块里再写 `if`。项目里常见用法。

```csharp
catch (Exception ex) when (ex is IOException or UnauthorizedAccessException)
{
    // 只把"环境类"问题转成退出码 5，其它异常继续往上抛
    return 5;
}
```

> 优点，**不匹配就继续往上层抛**，不会误吞异常。这是"精准捕获"的现代写法。

### `when` 先于 `finally` 执行

`when` 的条件并不是在 `catch` 块执行时才检查的。运行时会先从内向外**找**到能接住异常的 `catch`（这时才评估 `when`），然后才逐层执行 `finally`。下面的实验能看出顺序。

```csharp
try
{
    Deep();
}
catch (IOException) when (Log("  when 过滤器执行"))
{
    Console.WriteLine("  catch 块执行");
}

static void Deep()
{
    try
    {
        throw new IOException("No space left on device");
    }
    finally
    {
        Console.WriteLine("  finally 执行");
    }
}

static bool Log(string text)
{
    Console.WriteLine(text);
    return true;
}
```

输出是。

```text
  when 过滤器执行
  finally 执行
  catch 块执行
```

所以，**`when` 里只写判断，不要写有副作用的代码**（比如改状态、写日志）。
一旦过滤器和 `finally` 的先后顺序影响了结果，排查起来会非常难受。

## 11.5 `Result<T>`，把"失败"变成返回值

异常适合"意外"，但如果某个失败**很常见**（比如日志行格式不认识），
每次都 `try/catch` 会让代码很难读。这时用 `Result<T>`。

```csharp
/// <summary>操作结果：要么成功带值，要么失败带原因。</summary>
public readonly struct Result<T>
{
    private Result(bool isSuccess, T? value, string? error)
    {
        IsSuccess = isSuccess;
        Value = value;
        Error = error;
    }

    public bool IsSuccess { get; }

    public T? Value { get; }

    public string? Error { get; }

    public static Result<T> Ok(T value) => new(true, value, null);

    public static Result<T> Fail(string error) => new(false, default, error);

    /// <summary>两个分支都写在调用处，不用先 if 再取。</summary>
    public void Switch(Action<T> onSuccess, Action<string> onFailure)
    {
        if (IsSuccess && Value is not null)
        {
            onSuccess(Value);
        }
        else
        {
            onFailure(Error ?? "未知错误");
        }
    }
}
```

用它写一个"解析耗时"的函数。

```csharp
static Result<int> ParseDuration(string text)
{
    if (string.IsNullOrWhiteSpace(text))
    {
        return Result<int>.Fail("输入是空的");
    }

    if (!int.TryParse(text, out var value))
    {
        return Result<int>.Fail($"无法把 \"{text}\" 解析成整数");
    }

    if (value < 0)
    {
        return Result<int>.Fail("耗时不能是负数");
    }

    return Result<int>.Ok(value);
}
```

调用方。

```csharp
ParseDuration("1520").Switch(
    ms => Console.WriteLine($"解析成功：{ms} ms"),
    error => Console.WriteLine($"失败：{error}"));
```

### 什么时候用 `Result`，什么时候用异常？

| | 用 `Result<T>` | 用异常 |
| --- | --- | --- |
| 失败的频率 | 常见（用户输入、格式不匹配） | 罕见（文件没了、磁盘坏） |
| 调用方要不要"继续跑" | 要，只是这次不行 | 通常要中断当前流程 |
| 是否需要携带详细信息 | 需要（错误消息带给用户看） | 需要堆栈（给开发者看） |

### 项目里的真实版本

真实项目的 `Result<T>` 在 `Core/Infrastructure/Result.cs`，思路与上面一致，但细节更完整。下面是它与教学版本的主要差别。

| 方面 | 教学版 | 项目里的版本 |
| --- | --- | --- |
| 成功与否 | 单独的 `IsSuccess` 字段 | `IsSuccess => Error is null`，只用 `Error` 一个字段表示 |
| 取值方式 | `Value` 可能是 `default` | 失败时读取 `Value` 会抛出 `InvalidOperationException` |
| 创建结果 | 只能用 `Ok` / `Fail` | 还支持**隐式转换**，`return 42;` 直接代表成功 |
| 解构 | 无 | `var (ok, value, error) = result;` |
| 扩展方法 | 无 | `UnwrapOr`、`Sequence`（一批结果中有一个失败就整体失败） |

其中有两处需要特别注意。

```csharp
public T Value => Error is null
    ? _value!
    : throw new InvalidOperationException($"结果为失败，不能取值：{Error}");

public static implicit operator Result<T>(T value) => new(value, null);
```

第一处说明，**失败时不能直接取值**。下面的代码在验证环境里得到的是 `InvalidOperationException`，消息是 `结果为失败，不能取值：坏了`。

```csharp
_ = Result<int>.Fail("坏了").Value;
```

所以正确的写法永远是先 `IsSuccess` 或 `Switch`，再取值。

第二处说明，隐式转换让"成功"的写法更短，但它也意味着**一个方法返回 `Result<T>`，却写成 `return 某个 T 值`，只有在类型有隐式转换时才能编译**。
11.8 节的 `CS0029` 就是没有这个转换时的报错。

### 边界处的转换，异常变成 `Result`

实际项目里，异常和 `Result` 经常一起用，底层用异常报告意外，到了"对外"的方法边界，再把异常转成 `Result`。`Core/Reporting/ReportExporter.cs` 的导出方法就是这样。

```csharp
public async Task<Result<string>> ExportAsync(/* 参数省略 */)
{
    try
    {
        // ……写文件……
        return Result<string>.Ok(path);
    }
    catch (Exception ex) when (ex is IOException or UnauthorizedAccessException or DirectoryNotFoundException)
    {
        // 用 when 过滤异常类型：只处理"预期内"的 IO 错误，其余继续往上抛
        return Result<string>.Fail($"写入报告失败：{ex.Message}");
    }
}
```

调用方看到的是 `Result<string>`，不需要知道底层是不是抛了 `IOException`。

## 11.6 一组完整的错误处理骨架

一个命令行工具最外层通常长这样。

```csharp
try
{
    return await RunAsync(args);
}
catch (LogLensException ex)
{
    Console.Error.WriteLine($"✖ {ex.Message}");
    return ex.ExitCode;                  // 业务异常自带退出码
}
catch (OperationCanceledException)
{
    Console.Error.WriteLine("已取消");
    return 130;                          // 约定：Ctrl+C 用 130
}
catch (Exception ex)
{
    Console.Error.WriteLine($"✖ 未预期的错误：{ex}");
    return 99;                           // 兜底：说明这是 bug
}
```

三层结构对应第一节的三类失败。

1. **业务异常** → 友好提示 + 专用退出码；
2. **取消** → 单独一条路（它不是错误）；
3. **其它一切** → 打印完整堆栈（方便用户反馈 bug）+ 固定退出码 99。

### 真实项目比骨架多了几层

真实的 LogLens 把这套思路分成了两层。

**最外层**（`src/LogLens.Cli/Program.cs`）负责兜住一切。

- 应用装配失败（`CreateAsync` 返回失败）→ 打印错误，退出码 **6**；
- `OperationCanceledException` → 退出码 **130**；
- 其它任何异常 → 打印一句人话，退出码 **99**。这里的 `PrintFatal` 用 `#if DEBUG` 包住堆栈的打印，**开发时看得到完整堆栈，发布给用户的版本只打印一句话**。这种写法在 11.8 节详细讲。

**命令层**（`src/LogLens.Cli/CliApplication.cs` 的 `RunAsync`）处理大多数"已知"的失败，每种给出的提示和退出码都不同。

| 捕获的类型 | 处理方式 | 退出码 |
| --- | --- | --- |
| `CliUsageException`（参数用法写错） | 打印正确用法 | 2 |
| `QuerySyntaxException`（查询语法错） | 打印一个 `^` 箭头，指向出错的字符 | 3 |
| `LogLensException` 及其子类 | 打印消息和 `Hint`，返回 `ExitCode` | 视子类而定 |
| `OperationCanceledException` | 打印"操作已取消" | 130 |
| `IOException` / `UnauthorizedAccessException` | 打印"请检查路径、权限与磁盘空间" | 5 |

把它们汇总起来，就是 LogLens 命令行的退出码表。

| 退出码 | 含义 | 从哪来 |
| --- | --- | --- |
| 0 | 成功（如 `--version`，或命令正常完成） | 正常返回 |
| 2 | 用法错误，或日志源有问题 | `CliUsageException`、`LogSourceException` |
| 3 | 查询语法错误 | `QuerySyntaxException` |
| 4 | 日志格式无法识别 | `LogFormatException` |
| 5 | 文件系统错误（IO、权限） | `CliApplication` 的 `when` 过滤 |
| 6 | 应用启动失败（装配服务出错） | `Program.cs` |
| 99 | 未预期的错误，很可能是 bug | `Program.cs` 兜底 |
| 130 | 用户取消（Ctrl+C） | 约定 |

> 退出码是给**脚本**看的，`loglens ... ; echo $?` 或者 CI 里的判断，都靠它。
> 所以每一种失败都要有自己的码，不能统统返回 1。

## 11.7 动手，完整程序

下面的程序把前面的内容串起来。它是本章的检查点，文件在 `code/ch11-errors/Program.cs`。为了能放进一个文件，它用的是简化版的异常类（构造时直接传入退出码），
思路与 11.3 节项目里的抽象版本一致。

```csharp
// ============================================
// 第 11 章 · 异常与 Result
// 运行方式：dotnet run
// ============================================

// 输入不合法的统一退出码（与项目约定一致）。
// 注意：常量/局部变量必须"先声明后使用"，所以放在最上面；
// 而局部函数不受这个限制（第 5 章讲过）。
const int InputErrorExitCode = 3;

// ---- 1) 可预期失败：用 Result，不抛异常 ----
foreach (var input in new[] { "1520", "abc", "-5", "" })
{
    Console.WriteLine($"=== 输入 {(input == "" ? "(空)" : input)} ===");

    ParseDuration(input).Switch(
        milliseconds => Console.WriteLine($"  ✔ 解析成功：{milliseconds} ms"),
        error => Console.WriteLine($"  ✖ {error}（退出码 {InputErrorExitCode}）"));
}

// ---- 2) 外部故障：用异常，统一转成友好提示 ----
Console.WriteLine("=== 读文件 nope.log ===");
try
{
    var content = File.ReadAllText("nope.log");
    Console.WriteLine($"  读到 {content.Length} 个字符");
}
catch (FileNotFoundException ex)
{
    Console.WriteLine($"  ✖ 日志文件不存在：{ex.FileName}（退出码 2）");
}
catch (IOException ex) when (ex.Message.Contains("denied", StringComparison.OrdinalIgnoreCase))
{
    Console.WriteLine("  ✖ 没有读取权限（退出码 5）");
}
catch (Exception ex)
{
    // 兜底：不该靠它过日子，但要保证程序不崩
    Console.WriteLine($"  ✖ 未预期错误：{ex.GetType().Name}（退出码 99）");
}

// ---- 3) 自定义异常：带上路径与退出码 ----
Console.WriteLine("=== 自定义异常 ===");
try
{
    Guard.RequireFile("nope.log");
}
catch (LogSourceException ex)
{
    Console.WriteLine($"  ✖ {ex.Message}");
    Console.WriteLine($"    退出码 = {ex.ExitCode}，路径 = {ex.Path}");
}

Console.WriteLine();
Console.WriteLine("全部处理完毕，程序没有崩溃。");

// ---------- 工具与类型 ----------

/// <summary>把文本解析成耗时（毫秒）。失败用返回值表达，不抛异常。</summary>
static Result<int> ParseDuration(string text)
{
    if (string.IsNullOrWhiteSpace(text))
    {
        return Result<int>.Fail("输入是空的");
    }

    if (!int.TryParse(text, out var value))
    {
        return Result<int>.Fail($"无法把 \"{text}\" 解析成整数");
    }

    if (value < 0)
    {
        return Result<int>.Fail("耗时不能是负数");
    }

    return Result<int>.Ok(value);
}

// ---------- 类型定义 ----------

/// <summary>操作结果：要么成功带值，要么失败带原因。</summary>
public readonly struct Result<T>
{
    private Result(bool isSuccess, T? value, string? error)
    {
        IsSuccess = isSuccess;
        Value = value;
        Error = error;
    }

    public bool IsSuccess { get; }

    public T? Value { get; }

    public string? Error { get; }

    public static Result<T> Ok(T value) => new(true, value, null);

    public static Result<T> Fail(string error) => new(false, default, error);

    /// <summary>两个分支都写在调用处，不用先 if 再取。</summary>
    public void Switch(Action<T> onSuccess, Action<string> onFailure)
    {
        if (IsSuccess && Value is not null)
        {
            onSuccess(Value);
        }
        else
        {
            onFailure(Error ?? "未知错误");
        }
    }

    /// <summary>成功时把值转换一下，失败时原样传递错误。</summary>
    public Result<TNext> Map<TNext>(Func<T, TNext> map)
    {
        if (!IsSuccess || Value is null)
        {
            return Result<TNext>.Fail(Error ?? "未知错误");
        }

        return Result<TNext>.Ok(map(Value));
    }
}

/// <summary>所有 LogLens 异常的基类：自带退出码（主构造函数 + 表达式体初始化）。</summary>
public class LogLensException(string message, int exitCode) : Exception(message)
{
    public int ExitCode { get; } = exitCode;
}

/// <summary>日志源有问题（文件不存在、读不了）。</summary>
public sealed class LogSourceException(string path, string message)
    : LogLensException($"无法读取日志源 '{path}'：{message}", 2)
{
    public string Path { get; } = path;
}

/// <summary>教学用的小工具：只演示"检查文件是否存在"。项目里的 Guard（Core/Infrastructure/Guard.cs）提供的是 NotNull、NotBlank 等。</summary>
public static class Guard
{
    public static void RequireFile(string path)
    {
        if (!File.Exists(path))
        {
            throw new LogSourceException(path, "文件不存在");
        }
    }
}
```

运行输出（完整路径因运行目录而异）。

```text
=== 输入 1520 ===
  ✔ 解析成功：1520 ms
=== 输入 abc ===
  ✖ 无法把 "abc" 解析成整数（退出码 3）
=== 输入 -5 ===
  ✖ 耗时不能是负数（退出码 3）
=== 输入 (空) ===
  ✖ 输入是空的（退出码 3）
=== 读文件 nope.log ===
  ✖ 日志文件不存在：/你的目录/nope.log（退出码 2）
=== 自定义异常 ===
  ✖ 无法读取日志源 'nope.log'：文件不存在
    退出码 = 2，路径 = nope.log

全部处理完毕，程序没有崩溃。
```

> 注意 `ex.FileName` 打印出来的是**绝对路径**（`File.ReadAllText` 会自动把相对路径补全）。
> 想看用户当初输入的名字，就用自己构造异常时保存的 `ex.Path`，
> 这也是"自定义异常带上原始上下文"的一个实际理由。

### 逐段解释

| 代码 | 说明 |
| --- | --- |
| `Result<int>.Fail(...)` | 失败也走返回值，调用方不必写 `try` |
| `.Switch(onOk, onFail)` | 两个分支各传一个 lambda（[第 9 章](/chapter/09)的 `Action<T>`） |
| `readonly struct Result<T>` | 结果本身是值类型，不会为每次返回额外分配一个对象 |
| `catch (IOException ex) when (...)` | 异常过滤器，条件不满足就继续往上抛 |
| `class LogLensException(string message, int exitCode)` | **主构造函数**（[第 6 章](/chapter/06)），基类表达式体初始化。这是简化版，真实项目里是抽象类（见 11.3） |
| `throw new LogSourceException(...)` | 抛出后由上层统一处理，这一层不管怎么显示 |
| `ex.FileName` | `FileNotFoundException` 自带的属性（比解析消息字符串可靠） |
| `const int InputErrorExitCode = 3;` 放在文件最上面 | **局部变量必须"先声明后使用"**，常量也一样；而局部函数没有这个限制（[第 5 章](/chapter/05)） |

> 注意 `Result<T>` 里那个 `T? Value`，为了让它能表示"没有值"，用了可空。
> 真实项目的 `Result<T>` 没有 `Exception?` 之类的额外字段，而是用 `Error` 字符串表示失败（见 11.5）。

## 11.8 定位异常与常见错误

### 先读懂堆栈

11.1 节里那个没人接的异常，打印出来是这样的。

```text
Unhandled exception. System.InvalidOperationException: 没人接的错误
   at Program.<<Main>$>g__Work|0_0() in .../Program.cs:line 5
   at Program.<Main>$(String[] args) in .../Program.cs:line 2
```

读堆栈的顺序。

- 第一行是异常的类型和消息，先看它说的是什么。
- 每一行 `at` 是一层调用。**最上面一行是异常抛出的地方**，往下依次是调用它的人，一直到程序入口。
- `in 文件:line 5` 指向源码行号。`g__Work` 是编译器给局部函数 `Work` 起的内部名字。
- 在一大片堆栈里找自己的代码，跳过 `System.` 开头的框架调用，找第一行属于你项目的记录。
- 如果出现以 `---> ` 开头的内层异常，那一层往往说明了根本原因，要先看它。

### 用 IDE 调试器定位异常

先在怀疑的代码行左侧点一下，设置断点，然后按 F5 启动调试。默认情况下，调试器只在异常**没有被处理**时才停下。要让它在异常一抛出就停，需要打开"抛出时中断"。

| IDE | 设置位置 | 说明 |
| --- | --- | --- |
| Visual Studio | 菜单 **Debug > Windows > Exception Settings**（Ctrl+Alt+E） | 展开 **Common Language Runtime Exceptions**，勾选要中断的异常（或整类）。勾选的是"抛出时中断"，即使之后被 `catch` 接住，也会停在 `throw` 那一行 |
| Rider | 菜单 **Run > Stop On Exception**，或 **Run > View Breakpoints and Exceptions** | 添加 CLR Exception Breakpoint。可以启用 Any exception，再用 **Suspend if** 选择只在用户代码或外部代码中中断 |
| VS Code（C# Dev Kit） | 左侧"运行和调试"视图的 **BREAKPOINTS** 区域 | 勾选 **All Exceptions**（所有异常，包括被捕获的），或 **User-Unhandled Exceptions**（只在没人处理时中断）。名称可能随扩展版本略有不同 |

> "抛出时中断"发生在异常刚被抛出、还没有进入任何 `catch` 之前。所以同一个异常，调试器会先停在 `throw` 那一行，继续运行后才进入 `catch`。

停下之后，主要看四个地方。

1. **调用栈（Call Stack）**，和命令行的 `at` 行是同一个东西，但可以点击每一层，跳到那一层的代码，并看到那一层的变量。
2. **局部变量（Locals / Autos）**，看 `text`、`ms` 这些变量现在是什么值。很多异常的根源，就是一个不符合预期的值。
3. **异常对象**，在变量窗口或 Watch 中展开异常，看 `Message` 和 `InnerException`。IDE 通常还会弹出异常提示框，点"查看详细信息"就能看到。
4. **单步执行**，F10 逐过程（不进入调用），F11 逐语句（进入调用）。想跳出当前函数，用 IDE 菜单里的 Step Out，快捷键各 IDE 不一样。

如果一个循环跑了一千次，只想停在第一次出错的地方，可以给断点加条件，例如 `ms < 0`。右键断点就能设置，三个 IDE 都支持。

### 没有 IDE 时

- 命令行里的 `dotnet run` 默认使用 Debug 配置，堆栈会带行号（就是前面那个例子）。
- `ex.ToString()` 会把堆栈和所有内层异常一起打印出来。写日志时传入异常对象，用的就是这个内容。项目里的日志接口在 `Core/Infrastructure/IAppLogger.cs`。
- 发布版要注意行号。我们在验证环境里做了两次 Release 构建，默认生成 pdb 文件时，堆栈仍有行号；加上 `-p:DebugType=none` 不生成 pdb 后，堆栈就只剩方法名。

```text
Unhandled exception. System.InvalidOperationException: 没人接的错误
   at Program.<<Main>$>g__Work|0_0()
   at Program.<Main>$(String[] args)
```

  所以，发布版如果要保留定位能力，就要把 pdb 文件和发布包一起妥善保存。

### 开发版与发布版，`#if` 与 `[Conditional]`

前面说过，开发时和发布时需要的东西不一样。开发时要看完整堆栈，发布时只给用户一句话。C# 有两种办法，让同一份代码在不同构建里表现不同。

**第一种，用 `#if` 在编译时决定保留哪段代码。**

```csharp
#if DEBUG
Console.WriteLine("1) 当前是 Debug 构建：DEBUG 符号已定义");
#else
Console.WriteLine("1) 当前是 Release 构建：DEBUG 符号未定义");
#endif
```

`#if`、`#elif`、`#else`、`#endif` 叫做预处理指令。它们和运行时的 `if` 不同。条件在编译时就算好了，不满足的那一段不会进入编译结果。`DEBUG` 符号在 Debug 配置下有定义，`RELEASE` 符号在 Release 配置下有定义。用 `dotnet run -c Release` 就能切换到 Release 配置。

被 `#if` 排除的代码，编译器不检查它的类型。我们做过一个探针，里面用 `#if FALSE` 包住了一行类型明显写错的代码，`dotnet build` 照样通过。所以，平时不会执行的分支，最好也在对应的构建里编译一次，别等到发布时才发现它写错了。

`#define` 可以在文件里定义自己的符号，但它必须放在代码之前。如果写在 `Console.WriteLine` 后面，编译器会报出下面的错误。

```text
error CS1032: Cannot define/undefine preprocessor symbols after first token in file
```

**第二种，用 `[Conditional("DEBUG")]` 让调用本身在发布版里消失。**

```csharp
public static class DebugLog
{
    [Conditional("DEBUG")]
    public static void Write(string message) => Console.WriteLine($"[DEBUG] {message}");
}
```

标了这个特性的方法，在没有 `DEBUG` 符号的构建里，编译器会把每一处调用整个去掉，包括传进去的参数。下面是配套检查点 `code/ch11-conditional/` 里的一段。

```csharp
DebugLog.Write($"这条只在 Debug 构建里输出，汇总：{Summary.Build()}");
Console.WriteLine($"2) Summary.Build 被调用了 {Summary.Calls} 次");
```

`Summary.Build()` 每被调用一次，计数器就加一。实际运行的结果有两组。第一组是 Debug 构建（`dotnet run`）的输出。

```text
1) 当前是 Debug 构建：DEBUG 符号已定义
[DEBUG] 这条只在 Debug 构建里输出，汇总：错误 3 条
2) Summary.Build 被调用了 1 次
3) 符号 RELEASE 未定义，DEBUG 已定义
```

第二组是 Release 构建（`dotnet run -c Release`）的输出。

```text
1) 当前是 Release 构建：DEBUG 符号未定义
2) Summary.Build 被调用了 0 次
3) 符号 RELEASE 已定义
```

Release 构建里，`Summary.Build()` 一次都没有执行。所以，**传给 `[Conditional]` 方法的参数，只应该放没有副作用的东西**。如果参数里有写文件、改计数、发请求这类操作，发布版就会悄悄少做这些事，而且很难查。

`[Conditional]` 有一个限制，方法必须返回 `void`。我们把一个返回 `int` 的同类方法（名为 `Make`）放进探针里，编译器报出的错误是这样的。

```text
error CS0578: The Conditional attribute is not valid on 'DebugLog.Make(string)' because its return type is not void
```

因为调用点会被整个去掉，调用方拿不到返回值，所以编译器不允许这种写法。

**怎么选**

- 整段代码都要随构建变化，比如只在 Debug 下打印完整堆栈，就用 `#if`。
- 只是一个调试输出或检查调用，并且参数没有副作用，就用 `[Conditional]`。
- 发布版也需要保留的信息（例如错误日志），两者都不适合，应该交给正式的日志接口。

本项目里有两个 `#if DEBUG` 的例子。`src/LogLens.Cli/Program.cs` 第 21 行把 `PrintFatal` 中打印堆栈的代码包起来，就是 11.7 节讲的那种兜底。`src/LogLens.Studio/Program.cs` 第 28 行只在 Debug 构建里加上开发者工具，按 F12 就能打开。

### 调试时可能遇到的问题

| 现象 | 常见原因 | 怎么办 |
| --- | --- | --- |
| 断点是灰色的或空心的，一直不停 | 没有用 Debug 配置编译；改了代码却没重新编译，源码和 pdb 对不上；启动的不是要调试的那个项目 | 切换到 Debug 配置，执行 Rebuild，确认启动项目 |
| 单步时行号跳来跳去，变量显示"已优化掉" | Release 配置打开了编译器优化 | 调试时用 Debug 配置 |
| 程序在 `try/catch` 里出错，断点却没停 | 只开了 User-Unhandled（未处理才停），而异常被 `catch` 接住了 | 改为"抛出时中断"，或勾选 All Exceptions |
| 一开"抛出时中断"，就不停地停在框架内部 | 框架内部会正常抛出并捕获不少异常（例如查找配置文件），全部中断会很吵 | 只勾选关心的类型，或在 Rider 的 Suspend if 中限定用户代码 |
| 开了 Just My Code 后，调用栈里看不到库的代码 | 默认只显示你自己的代码，库的那几层被隐藏了 | 需要时关闭 Just My Code，或在 Rider 中勾选 External code |
| 调用栈只有一小段，之后就断了 | 异步方法在 `await` 之后由另一段代码继续执行，调用栈因此不连续 | 先看异常对象的 `StackTrace`；异步的完整规律在异步章节讲解 |
| 堆栈里只有方法名，没有文件和行号 | 发布版没有 pdb，或设置了 `DebugType=none` | 保留 pdb，或在 Debug 配置下复现 |
| Debug 时能看到的输出，Release 下没有了 | 输出语句被 `#if DEBUG` 包住，或调用的方法标了 `[Conditional("DEBUG")]` | 先确认是哪种写法；发布版需要保留的信息，改用正式的日志接口 |
| 异常被打印了，但程序没有停，输出里却多出一大堆 `Exception thrown` | 调试器在打印 first-chance 异常信息，这些异常可能正常被处理掉了 | 看清是否被 `catch` 接住；不必一看到就慌，关注最终的未处理异常 |

### 排查异常的一般步骤

1. **看类型和消息**，这是程序 bug（空引用、越界），还是外部故障（文件、权限）？这正是 11.1 节的三类失败。
2. **看堆栈**，从最上面找第一行属于自己代码的记录。
3. **看内层异常**，原因常常在 `InnerException` 里。
4. **在出错行附近设断点**，或开启"抛出时中断"，看局部变量。
5. **修好以后，留下痕迹**，如果这是一种可以预期的失败，就改成 `Result<T>` 的失败分支；如果是 bug，就补一个能复现它的测试。测试以后会再讲。

### 常见错误速查

| 报错 / 现象 | 原因 | 怎么改 |
| --- | --- | --- |
| `CS0161: 并非所有的代码路径都返回值` | 有分支漏了 `return` | 补全，或用 `Result.Fail` 兜底 |
| `CS0029: 无法将 "int" 隐式转换为 "Result<int>"` | 方法返回 `Result<T>`，却直接 `return` 了裸值，而类型没有隐式转换 | 用 `Result<T>.Ok(x)` 包一层；或像项目那样为类型加 `implicit operator` |
| `CS0157: 控制不能离开 finally 子句的主体` | `finally` 里写了 `return`，或 `break`、`continue`、`goto` 跳出 | 把返回值放到 `try` 之后；`finally` 只做收尾 |
| `CS0160: 前面的 catch 子句已经捕获了这个类型的所有异常` | 宽泛的 `catch` 写在了具体的前面 | 从具体到宽泛排序 |
| `Unhandled exception` 程序直接退出 | 抛了异常但没人 `catch` | 在合适层级捕获，或让顶层兜底 |
| 堆栈里看不到真实出错位置 | 用了 `throw ex;` | 改成 `throw;` |
| 排查时看不到原始原因 | 包装异常时没传 `inner` | 构造时把原始异常作为第三个参数传入 |
| `.Wait()` 或 `.Result` 抛出的是 `AggregateException` | 在异步代码上用阻塞方式等待，异常被包装了一层 | 用 `await`，它会直接抛出原始异常；需要时从 `InnerException` 取出原因 |
| `finally` 里的收尾代码出错，覆盖了原来的异常 | 收尾代码本身抛了异常 | 收尾逻辑保持简单；必要时单独 `try` 包住 |
| 程序"假装成功"（明明失败了却返回 0） | 吞了异常 | 记日志 + 返回非 0 退出码 |
| 空 `catch { }` | 吞掉一切 | 至少要记日志，否则 bug 永远查不到 |

### 关于"吞异常"

```csharp
try { DoSomething(); }
catch { }                    // ❌ 最糟的写法：出事了没人知道
```

```csharp
try
{
    DoSomething();
}
catch (Exception ex) when (ex is not OperationCanceledException)
{
    _logger.Error("DoSomething 失败", ex);      // ✅ 至少留下痕迹
    throw;                                       // ✅ 或者往上抛
}
```

注意第二段里的 `when`，取消（`OperationCanceledException`）不是错误，不应该被当成 bug 记下来。

```csharp
static Result<int> ParseLevel(string text)
{
    var level = text.Trim().ToLowerInvariant();

    return level switch
    {
        "debug" => Result<int>.Ok(1),
        "info" => Result<int>.Ok(2),
        "warn" => Result<int>.Ok(3),
        "error" => Result<int>.Ok(4),
        _ => Result<int>.Fail($"不认识的级别：{text}"),
    };
}

static Result<string> Describe(string text) =>
    ParseLevel(text).Map(number => $"级别 {text.ToUpperInvariant()} 的序号是 {number}");

Describe("warn").Switch(Console.WriteLine, Console.WriteLine);
// 级别 WARN 的序号是 3
Describe("trace").Switch(Console.WriteLine, Console.WriteLine);
// 不认识的级别：trace
```
