## 12.1 同步与异步

用点餐来比喻。

- **同步**，你站在窗口前等，厨师做完饭，你才能走开。这段时间你什么都做不了。
- **异步**，你点完餐，拿到一个取餐号，就去找座位、接水、回消息。饭做好了，叫号，你再回去取。

两种方式下，饭都要做那么久，这一点没有变。变的是你在等的时候，能不能做别的事。

这里要分清两个词，**等待**和**占着人**。饭需要时间做，这段时间无法消除，这是等待。异步消除的是"占着人"，等待期间，你这个人是自由的。

程序里也一样。读一个 2GB 的日志文件要花时间，这段时间里磁盘在忙，CPU 大部分时间闲着。如果写成同步代码，程序在读完之前什么也做不了，界面会卡住，按钮点了没反应。异步写法让程序在等的时候继续响应别的操作。

## 12.2 阻塞与非阻塞

这两个词和同步、异步很接近，但侧重点不同。

- **阻塞**，调用方在等结果期间什么也做不了。`Thread.Sleep(1000)` 就是阻塞，调用它的那个线程就停在这一行。
- **非阻塞**，调用方调用之后立即拿到一个"回执"，可以继续做事，结果晚点再来取。

回执在 C# 里就是 `Task`。下一节专门讲它。

一个简单的判断方法，**看调用方的线程在等待期间是否被占住**。被占住就是阻塞；没被占住、能去做别的事，就是非阻塞。

<a id="s12-3" class="lt-anchor-target"></a>

## 12.3 `Task`，一张"将来完成的工作票"

`Task` 表示一件还没有完成的事。它像一张工作票，票上写着"这件事正在做，做完会通知你"。`Task<T>` 是带结果的工作票，做完之后，票上写着结果 `T`。

先看检查点里的一个方法。

```csharp
static async Task<int> WorkAsync()
{
    Console.WriteLine("  work: 开始");
    await Task.Delay(100);
    Console.WriteLine("  work: 结束");
    return 42;
}
```

调用它的代码。

```csharp
Console.WriteLine("A: 调用前");
var pending = WorkAsync();
Console.WriteLine($"B: 调用后，IsCompleted = {pending.IsCompleted}");
var value = await pending;
Console.WriteLine($"C: 拿到结果 {value}");
```

运行结果（来自检查点）。

```text
A: 调用前
  work: 开始
B: 调用后，IsCompleted = False
  work: 结束
C: 拿到结果 42
```

读这段输出时，注意几点。

1. `WorkAsync()` 的返回类型是 `Task<int>`，不是 `int`。`pending` 是那张工作票。
2. `  work: 开始` 出现在 `B` 之前。`async` 方法在遇到第一个 `await` 之前，是按顺序同步执行的。这一段代码其实还是在调用方的线程上跑。
3. `IsCompleted = False` 说明方法返回时，工作还没有完成。
4. `  work: 结束` 出现在 `B` 之后，`C` 之前。`await pending` 等的就是它。
5. `42` 通过 `await` 拿到，类型是 `int`。

**`Task` 不等于线程。** `Task.Delay(100)` 的 100 毫秒里，并没有哪个线程在傻等。它靠计时机制，到点后通知等待的代码。线程是"干活的人"，`Task` 是"一件事的状态和结果"。两者常常有关系，但不是同一个东西。[第 13 章](/chapter/13)会专门讲线程。

## 12.4 `await` 到底做了什么

`await` 有两种情况。

**情况一，等的任务已经完成。** 方法直接往下执行，不暂停。

**情况二，等的任务还没有完成。** 方法会先记下当前位置，把控制权交还给调用方。调用方继续做自己的事。等任务完成后，运行时再从刚才记下的位置继续。

可以把它想成看电影时按下的暂停键。`await` 按下暂停，播放器（这里指执行的线程）就可以去做别的事；等事件完成，再按播放，从暂停的画面继续。播放器不用一直站在屏幕前盯着。

回到检查点。`await pending` 这一行，`Main` 发现 `WorkAsync` 还在等 `Task.Delay`，于是交还控制权。100 毫秒后，代码从这一行继续，打印 `C`。

有一点容易忽略，`await` 之后的代码不一定还在原来的线程上执行。控制台程序里没有特殊的"同步上下文"，继续执行时可能换到线程池里的另一个线程。[第 13 章](/chapter/13)会解释线程池，第 [12.12 节](#s12-12)会讲什么时候需要回到原来的线程。

## 12.5 `Task.Delay` 与 `Thread.Sleep`

这两个都是"等一会儿"，但含义完全不同。

- `Thread.Sleep(50)`，让当前线程停住 50 毫秒。这段时间里，这个线程什么也做不了。
- `await Task.Delay(50)`，返回一张工作票，50 毫秒后完成。等待期间，方法暂停，线程可以去做别的事。

检查点用两段代码做对比。

```csharp
var sw = Stopwatch.StartNew();
for (var i = 0; i < 20; i++)
{
    Thread.Sleep(50);
}
Console.WriteLine($"Thread.Sleep(50) 顺序 20 次：约 {sw.ElapsedMilliseconds} ms（数字因机器而异）");

sw.Restart();
await Task.WhenAll(Enumerable.Range(0, 20).Select(_ => Task.Delay(50)));
Console.WriteLine($"Task.Delay(50) 同时等待 20 个：约 {sw.ElapsedMilliseconds} ms（数字因机器而异）");
```

运行结果。

```text
Thread.Sleep(50) 顺序 20 次：约 1005 ms（数字因机器而异）
Task.Delay(50) 同时等待 20 个：约 54 ms（数字因机器而异）
```

前一段必须一个接一个地睡，20 × 50 毫秒，约 1000 毫秒。后一段的 20 个计时同时开始，等的是最长的那一个，约 50 毫秒。这里用到了 `Task.WhenAll`，第 [12.8 节](#s12-8)会详细讲。

这个对比有一个前提需要说清楚，两段代码的写法不同，比较的是"写法带来的差异"，不是"两个函数谁更快"。`Thread.Sleep` 那段是顺序执行的，`Task.Delay` 那段是同时开始的。

在项目里，`QueryStudioViewModel.cs` 的防抖校验就用了 `Task.Delay`（第 271 行至第 278 行）。用户每输入一个字，都会取消上一次的等待，重新开始计时；只有停下来 200 毫秒，才真正做语法校验。等待期间界面照常响应，没有任何线程被占住。

> **原则**，在 `async` 方法里需要"等一会儿"，就写 `await Task.Delay(...)`。在异步代码里使用 `Thread.Sleep`，会让线程白白占着，这是第 [12.24 节](#s12-24)要讲的常见错误。

## 12.6 第一个 `async`/`await` 程序

写异步方法有三条规则。

1. 方法声明里加 `async` 关键字；
2. 返回类型是 `Task`（没有返回值）或 `Task<T>`（有返回值）；
3. 方法体里用 `await` 等待一个 `Task`。

`async` 本身不会让方法跑到后台去。它只是允许方法里使用 `await`。

项目的入口就是这样写的。`LogLens.Cli/Program.cs` 第 34 行。

```csharp
var created = await CliApplication.CreateAsync(args);
```

这是顶层语句，文件里没有 `Main` 方法，C# 允许顶层语句直接写 `await`。检查点的 `Program.cs` 也是顶层语句。另一种写法是 `static async Task Main`，效果相同，本章统一用顶层语句。

### 不写 `async` 也可以

`async` 和 `await` 是配套使用的。只有方法里要用 `await` 时，才需要 `async`。方法里没有 `await`，也可以不写。

最常见的情况是，方法只是把别人的 `Task` 原样交出去。

```csharp
static Task<string> FetchForwardAsync(string name, int ms) => FetchAsync(name, ms);
```

这个方法没有 `async`，也没有 `await`，直接返回 `FetchAsync` 产生的任务。调用方照常 `await`。

```csharp
var forwarded = FetchForwardAsync("转发", 50);
Console.WriteLine($"转发的结果：{await forwarded}");
```

运行结果。

```text
转发的结果：转发(50ms)
```

不写 `async` 时，两者的区别在异常上最明显。检查点里有两个方法，分别演示。

```csharp
static Task<int> ThrowWithoutAsync() => throw new InvalidOperationException("没有 async：同步抛出");

static async Task<int> ThrowWithAsync()
{
    await Task.Yield();
    throw new InvalidOperationException("有 async：异常放进 Task 里");
}
```

调用它们的代码。

```csharp
try
{
    _ = ThrowWithoutAsync();
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"没有 async：调用那一行就抛出了异常：{ex.Message}");
}

var thrown = ThrowWithAsync();
Console.WriteLine($"有 async：调用那一行没有抛出，IsFaulted = {thrown.IsFaulted}");
try
{
    await thrown;
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"有 async：await 时才接到异常：{ex.Message}");
}
```

运行结果。

```text
没有 async：调用那一行就抛出了异常：没有 async：同步抛出
有 async：调用那一行没有抛出，IsFaulted = False
有 async：await 时才接到异常：有 async：异常放进 Task 里
```

这两种写法的调用方要用不同的方式接异常。没有 `async` 时，异常在调用那一行就出现了，`try` 必须包住调用本身，而不是 `await`。有 `async` 时，异常被放进返回的 `Task`，调用方要 `await` 之后才会抛出。

所以，判断要不要写 `async`，可以参考这几条。

- 方法里要 `await` 别的任务，写 `async`。
- 只是转发别人的 `Task`，中间没有需要处理的东西，可以不写。
- 希望所有异常都在 `Task` 里出现，统一用 `await` 接住，写 `async`。

有一个反例需要避免，方法加了 `async`，却没有任何 `await`。它能正常编译，本章用的 .NET 10 SDK 对这种写法也没有任何警告。它会多出一层状态机，却没有任何收益，只会让读代码的人以为这里有需要等待的东西。加 `async` 之前，先问一句，这个方法里真的有要等的任务吗？

## 12.7 返回值，`Task<T>`

有返回值时，方法声明为 `Task<T>`。`return` 时直接写 `T`，调用方 `await` 之后拿到的就是 `T`。

```csharp
static async Task<string> FetchAsync(string name, int ms)
{
    await Task.Delay(ms);
    return $"{name}({ms}ms)";
}

var text = await FetchAsync("源A", 500);   // text 的类型是 string
```

方法体里 `return` 的是 `string`；调用方 `await` 之后拿到的也是 `string`。中间那层 `Task<string>` 由 `await` 自动处理，不需要手动拆。

项目里的例子是 `LogLens.Core/Reporting/ReportExporter.cs` 第 34 行的 `ExportAsync`，它的返回类型是 `Task<Result<string>>`。这里有两层。

- 外层 `Task`，表示"异步操作是否完成"，管的是"等不等"；
- 里层 `Result<string>`，表示成功（带文件路径）或失败（带错误信息），管的是"成不成功"。

两层各管一件事，互不替代。

## 12.8 同时等多个任务

两个常用的工具。

- `Task.WhenAll(...)`，等**全部**完成。如果任务都是 `Task<T>`，返回值是一个结果数组。
- `Task.WhenAny(...)`，等**最先**完成的那一个。返回的是那个任务本身，要再 `await` 一次才能拿到结果。

检查点中的写法。

```csharp
var parallel = await Task.WhenAll(
    FetchAsync("源A", 500),
    FetchAsync("源B", 500),
    FetchAsync("源C", 500));

var first = await Task.WhenAny(FetchAsync("慢", 800), FetchAsync("快", 100));
Console.WriteLine($"WhenAny 最先完成的是：{await first}");
```

注意 `WhenAny` 的返回值，它返回的是 `Task<string>`，所以打印时写的是 `await first`，而不是直接用 `first`。这一点容易忽略。

还有一个细节，`FetchAsync("源A", 500)` 在传入 `WhenAll` 的那一刻就已经开始执行了，并不是等到 `await` 才开始。这正是"同时"的来源，下一节会用时间对比来验证。

运行结果。

```text
WhenAny 最先完成的是：快(100ms)
```

## 12.9 顺序等待与同时等待

假设有三个慢源，每个要 500 毫秒。

**顺序写法**。

```csharp
var a1 = await FetchAsync("源A", 500);
var b1 = await FetchAsync("源B", 500);
var c1 = await FetchAsync("源C", 500);
```

**同时写法**。

```csharp
var parallel = await Task.WhenAll(
    FetchAsync("源A", 500),
    FetchAsync("源B", 500),
    FetchAsync("源C", 500));
```

运行结果。

```text
顺序 await 三次：约 1501 ms，源A(500ms) 源B(500ms) 源C(500ms)
WhenAll：约 500 ms，源A(500ms) 源B(500ms) 源C(500ms)
```

顺序写法的总时间约等于 500 + 500 + 500。同时写法三个计时同时开始，总时间约等于最慢的那一个。

这里有两点要说清楚。

1. **这是模拟的慢源。** 真实的磁盘和网络，结果会受缓存、带宽、对方服务状态的影响。一次实测不能代表一切，写文档时要说明测试条件。
2. **同时的前提是任务彼此独立。** 如果第二个请求要用第一个请求的结果，就只能顺序 `await`。把有依赖的任务硬塞进 `WhenAll`，结果只会是错的或者更慢。

## 12.10 取消

取消是"请求停止"，不是"强行杀死"。代码要配合，才能停得下来。

三个主要角色。

- **`CancellationTokenSource`（取消源）**，负责发出取消信号。可以调用 `Cancel()`，也可以调用 `CancelAfter(毫秒)`，或者在构造时传入一个 `TimeSpan`，到点自动取消。
- **`CancellationToken`（令牌）**，从取消源里拿出来，交给要执行的代码。
- **响应方式**，代码可以主动检查 `token.ThrowIfCancellationRequested()`；也可以把令牌传给 `Task.Delay(ms, token)` 这类方法，让它们自己响应取消。

检查点中的长任务。

```csharp
static async Task LongJobAsync(CancellationToken token)
{
    for (var i = 0; i < 100; i++)
    {
        token.ThrowIfCancellationRequested();
        await Task.Delay(50, token);
    }
}
```

这个任务要跑 5 秒（100 次，每次 50 毫秒）。检查点用三种方式让它提前停下。

**方式一，手动取消。**

```csharp
using (var cts = new CancellationTokenSource())
{
    var job = LongJobAsync(cts.Token);
    cts.CancelAfter(200);     // 200 毫秒后发出取消信号
    try
    {
        await job;
    }
    catch (OperationCanceledException)
    {
        Console.WriteLine("手动取消：任务被取消（这是一种结果，不是程序故障）");
    }
}
```

**方式二，超时取消。**

```csharp
try
{
    using var timeout = new CancellationTokenSource(TimeSpan.FromMilliseconds(200));
    await LongJobAsync(timeout.Token);
}
catch (OperationCanceledException)
{
    Console.WriteLine("超时取消：TimeSpan 构造的令牌到点自动取消");
}
```

**方式三，合并两个取消源。** 用户按了取消，或者超时了，任何一个发生，任务都要停。`CreateLinkedTokenSource` 做的就是这件事。

```csharp
using (var userCts = new CancellationTokenSource())
using (var linked = CancellationTokenSource.CreateLinkedTokenSource(
           userCts.Token,
           new CancellationTokenSource(TimeSpan.FromMilliseconds(150)).Token))
{
    try
    {
        await LongJobAsync(linked.Token);
    }
    catch (OperationCanceledException)
    {
        Console.WriteLine($"合并令牌：超时来源触发，IsCancellationRequested = {linked.IsCancellationRequested}");
    }
}
```

运行结果（三种方式的输出）。

```text
手动取消：任务被取消（这是一种结果，不是程序故障）
超时取消：TimeSpan 构造的令牌到点自动取消
合并令牌：超时来源触发，IsCancellationRequested = True
```

第三种情况里，用户的取消源没有被触发，是超时那一路先到。合并令牌只要任何一个来源取消，它就取消。

**项目里的取消。** 三处都能看到同样的思路。

- `LogLens.Cli/CliApplication.cs` 第 148 行注册了 `Console.CancelKeyPress`。第 290 行起的 `OnCancelKeyPress` 在第一次按 Ctrl+C 时把 `e.Cancel` 设为 `true`，阻止进程立即退出，让清理逻辑跑完；再按一次才强制退出。
- `LogLens.Studio/ViewModels/MainWindowViewModel.cs` 第 39 行声明了 `_loadCancellation`，第 560 行每次加载时新建一个，第 472 行的 `CancelLoad()` 调用它的 `Cancel()`。
- `LogLens.Studio/ViewModels/QueryStudioViewModel.cs` 第 271 行，每次输入都新建一个防抖取消源，并先取消上一次的。

> 说明，本章的检查点没有模拟 Ctrl+C，上面的 CLI 行为是从源码里读出来的，本章没有在终端里实际按下 Ctrl+C 验证。

## 12.11 进度报告

长任务要告诉界面"做到哪了"。.NET 的做法是 `IProgress<T>`，任务只管调用 `Report(值)`，显示进度的一方负责订阅。`Progress<T>` 是它最常用的实现，构造时传入一个回调。

```csharp
static async Task RunStepsAsync(IProgress<int> progress)
{
    for (var step = 1; step <= 5; step++)
    {
        await Task.Delay(50);
        progress.Report(step * 20);
    }
}

await RunStepsAsync(new Progress<int>(p => Console.WriteLine($"进度 {p}%")));
await Task.Delay(100);   // 见下方说明
```

运行结果。

```text
进度 20%
进度 40%
进度 60%
进度 80%
进度 100%
```

检查点末尾那一行 `await Task.Delay(100)` 不是多余的。`Progress<T>` 的回调不一定立刻在 `Report` 那一行执行，它会在创建 `Progress<T>` 的地方捕获的"同步上下文"上执行。界面程序里，同步上下文就是界面线程，所以回调会回到界面线程。控制台程序没有同步上下文，回调会被投递到线程池。程序如果在回调还没跑完时就结束，最后几行进度可能看不到。

**项目里的进度。**

- `LogLens.Studio/ViewModels/MainWindowViewModel.cs` 第 588 行的 `CreateProgress()` 返回 `new Progress<LoadProgress>(...)`。它在界面线程上创建，所以回调里更新界面是安全的。
- `LogLens.Core/Parsing/LogIngestor.cs` 第 48 行的 `StreamAsync` 参数是 `IProgress<IngestProgress>?`。Core 层只依赖接口，不知道界面存在。这就是分层的好处，同一个解析器，既能在控制台打印进度，也能在窗口里更新进度条。

## 12.12 回到哪个线程，`ConfigureAwait`

前面说过，`await` 之后的代码不一定在原来的线程上执行。这个"原来的地方"叫**同步上下文**（SynchronizationContext）。

- 界面程序的同步上下文是界面线程。界面控件只能在界面线程上修改，所以界面代码通常需要回到它。
- `ConfigureAwait(true)`（也是默认行为），`await` 之后尽量回到原来的上下文。
- `ConfigureAwait(false)`，`await` 之后不需要回去，可以在任意线程上继续。库代码（不碰界面的代码）经常这样写，少了一次回切的开销。

在项目里。

- `LogLens.Core/Reporting/ReportExporter.cs` 第 61 行有 `.ConfigureAwait(false)`。Core 不碰界面，它不需要回到任何地方。
- `LogLens.Core/Parsing/LogLineSource.cs` 第 46 行的 `await foreach(...).ConfigureAwait(false)` 同样如此。
- `LogLens.Studio` 里的界面代码，比如 `MainWindowViewModel.cs` 第 452 行，显式写 `ConfigureAwait(true)`，表示"回到界面线程"。

整个项目里 `ConfigureAwait` 一共出现了约 114 处。

> 说明，控制台程序没有同步上下文，`ConfigureAwait(true)` 和 `(false)` 的效果在这里看不出区别。本章检查点没有显式写 `ConfigureAwait`，也没有做对比实验，这一节是原理说明。要看到差别，需要在界面程序里观察线程。

一条实用的规则，**写界面代码，默认就好；写不碰界面的库代码，习惯性加 `ConfigureAwait(false)`。**

## 12.13 异步流 `IAsyncEnumerable`

[第 10 章](/chapter/10)讲过 `IEnumerable<T>`，一个一个地拿元素，`foreach` 是它的消费方式。它是同步的，每拿一个元素，下一个元素必须已经准备好。

如果每个元素都要等（比如读文件时，每一行都可能要等磁盘），同步版本就只能让整个线程停住。`IAsyncEnumerable<T>` 是它的异步版本，每拿一个元素，都可以 `await`；消费它要用 `await foreach`。

检查点中的例子。

```csharp
static async IAsyncEnumerable<string> ReadLinesAsync(int count)
{
    for (var i = 1; i <= count; i++)
    {
        await Task.Delay(100);        // 模拟读下一行要等 100 毫秒
        yield return $"第 {i} 行";
    }
}
```

消费的代码。

```csharp
var sw = Stopwatch.StartNew();
long firstLineMs = -1;
var count = 0;

await foreach (var line in ReadLinesAsync(5))
{
    if (firstLineMs < 0)
    {
        firstLineMs = sw.ElapsedMilliseconds;
    }
    count++;
}
Console.WriteLine($"第一行在约 {firstLineMs} ms 时出现，共 {count} 行，全部完成约 {sw.ElapsedMilliseconds} ms");
```

运行结果。

```text
第一行在约 102 ms 时出现，共 5 行，全部完成约 501 ms
```

第一行在约 100 毫秒时就到了，不必等 5 行全部准备好。如果是 2GB 的日志文件，这个差别很大，读一行，处理一行，内存里同时只需要放得下很少的数据，而不是把整个文件一次读进内存。

`ReadLinesAsync` 里的 `yield return` 和[第 10 章](/chapter/10)的迭代器写法一样。区别只是方法前面多了 `async`，每次 `yield` 之前可以 `await`。

**项目里的异步流。** `LogLens.Core/Parsing/LogLineSource.cs` 第 35 行的 `ReadAsync` 就是 `IAsyncEnumerable<RawLine>`。它的文档注释（第 20 行）写得很直接，"边读边处理，不会把 2GB 日志一次性读进内存。"第 22 行提到 `[EnumeratorCancellation]`，它让取消令牌与调用方的 `.WithCancellation(ct)` 配合，取消时能停在读到一半的地方。`LogIngestor.cs` 第 46 行的 `StreamAsync` 也是异步流，它在 `LogLineSource` 的上一层，把原始行变成日志事件，逐个交给调用方。

## 12.14 限制并发数，`SemaphoreSlim`

如果同时发起 1000 个请求，即使每个都是异步的，对磁盘或远程服务来说也可能是压垮它的负载。我们需要一个"门"，同时最多放进去几个。`SemaphoreSlim` 就是这样的门。

- 构造时给它一个数量，比如 `new SemaphoreSlim(3)`，表示最多 3 张许可。
- 任务开始前 `await gate.WaitAsync()` 拿一张许可；没有许可的任务在那里排队等。
- 任务结束后 `gate.Release()` 归还许可。

检查点中的完整写法。

```csharp
var gate = new SemaphoreSlim(3);
var peakLock = new object();
var running = 0;
var peak = 0;

async Task Job(int id)
{
    await gate.WaitAsync();
    try
    {
        var now = Interlocked.Increment(ref running);
        lock (peakLock)
        {
            if (now > peak)
            {
                peak = now;
            }
        }
        await Task.Delay(100);
        Interlocked.Decrement(ref running);
    }
    finally
    {
        gate.Release();
    }
}

await Task.WhenAll(Enumerable.Range(1, 10).Select(Job));
Console.WriteLine($"10 个任务，并发上限 3，实际峰值 {peak}");
```

运行结果。

```text
10 个任务，并发上限 3，实际峰值 3
```

这段代码里有两个地方值得注意。

1. **`Release()` 放在 `finally` 里。** 即使任务中途抛出异常，许可也会归还。如果忘了归还，后面的任务会永远排队。
2. **计数器的保护方式（`Interlocked` 和 `lock`）留到[第 13 章](/chapter/13)讲。** 现在只要知道，多个任务同时修改同一个变量，需要保护。

项目中目前还没有使用 `SemaphoreSlim`（已用 grep 核实）。以后如果要同时读取多个日志文件，这就是可以直接用上的工具。

## 12.15 异步不会让计算变快

异步解决的是**等待**的问题，不是**计算**的问题。

- 如果任务要等磁盘、等网络，异步让线程不必空等，程序的其他部分可以继续工作。
- 如果任务是纯 CPU 计算（一直在算，没有等待），`await` 不会让它变快。它只是把工作交给线程池，让界面线程不被占住。

项目里有一个很好的例子。`LogLens.Studio/ViewModels/QueryStudioViewModel.cs` 第 341 行。

```csharp
var result = await Task.Run(() => _queryEngine.Execute(
    _events,
    queryText,
    new QueryRunOptions { Limit = Math.Max(1, Limit) })).ConfigureAwait(true);
```

查询本身是纯计算。放进 `Task.Run` 之后，它在线程池上跑，界面线程不会卡住；但查询的总耗时并没有因此变短。要让计算真正变快，需要用多个核心同时算，这是[第 13 章](/chapter/13)的内容。

## 12.16 暂停、恢复与断点续传

前面讲的取消，是"停下来，之后就算了"。很多真实场景需要的是"停下来，之后还能接着做"。下载大文件是最典型的例子，网络断了，或者用户点了暂停，下次应该从已经下载的地方继续，而不是从头再来。这就是**断点续传**。

这一节用异步写一个模拟的下载过程。为了专注于异步本身，我们不用真实的 HTTP，而是用一个假的服务器类 `FakeServer`。

```csharp
static class FakeServer
{
    public const int ChunkSize = 100;

    public static readonly byte[] Data = Enumerable.Range(0, 3000).Select(i => (byte)(i % 251)).ToArray();

    public static async Task<byte[]> RangeAsync(long offset, int count, CancellationToken ct)
    {
        await Task.Delay(30, ct);   // 模拟网络延迟；取消信号会立即打断这里的等待
        return Data.AsSpan((int)offset, count).ToArray();
    }
}
```

`RangeAsync` 的作用类似 HTTP 的 `Range` 请求，客户端说"从第 `offset` 字节开始给我 `count` 个字节"，服务器就返回这一段。真实的 HTTP 下载会发送类似 `Range: bytes=1000-` 的请求头，这里的 `RangeAsync` 模拟的就是这一步。

下载的核心是 `DownloadAsync`。

```csharp
static async Task DownloadAsync(string partPath, CancellationToken ct, Action<long> onChunkWritten)
{
    await using var file = new FileStream(partPath, FileMode.OpenOrCreate, FileAccess.Write, FileShare.None);
    file.Seek(0, SeekOrigin.End);
    var offset = file.Length;

    while (offset < FakeServer.Data.Length)
    {
        ct.ThrowIfCancellationRequested();
        var count = (int)Math.Min(FakeServer.ChunkSize, FakeServer.Data.Length - offset);
        var chunk = await FakeServer.RangeAsync(offset, count, ct);
        await file.WriteAsync(chunk, ct);
        await file.FlushAsync(ct);
        offset += chunk.Length;
        onChunkWritten(offset);
    }
}
```

这段代码有三个设计，分别说明。

1. **状态存在文件里。** 文件已经有多长，就表示已经下载到哪里。程序没有在内存里保存"进度变量"，所以即使程序退出，只要文件还在，下次就能续传。`file.Seek(0, SeekOrigin.End)` 把写入位置放到文件末尾，`offset` 就是续传的起点。
2. **一块写完并刷新，才算完成。** `FlushAsync` 把数据真正写到磁盘之后，才调用 `onChunkWritten` 通知外面。这样记录的进度不会超过磁盘上的实际内容。
3. **每一块之前检查取消。** `ct.ThrowIfCancellationRequested()` 放在循环的开头，暂停只会发生在两块之间，不会留下写到一半的块。

主程序演示三件事。

```csharp
var partPath = Path.Combine(Path.GetTempPath(), $"loglens-ch12-{Guid.NewGuid():N}.part");
try
{
    // 第一次下载：写到第 1000 字节之后暂停
    using (var pauseCts = new CancellationTokenSource())
    {
        try
        {
            await DownloadAsync(partPath, pauseCts.Token, written =>
            {
                if (written >= 1000)
                {
                    pauseCts.Cancel();
                }
            });
        }
        catch (OperationCanceledException)
        {
            Console.WriteLine($"第一次：已暂停，文件里已有 {new FileInfo(partPath).Length} 字节");
        }
    }

    // 第二次下载：从文件末尾接着下载
    var resumeFrom = new FileInfo(partPath).Length;
    await DownloadAsync(partPath, CancellationToken.None, _ => { });
    var content = await File.ReadAllBytesAsync(partPath);
    Console.WriteLine($"第二次：从 {resumeFrom} 字节续传，最终 {content.Length} 字节，内容一致：{content.SequenceEqual(FakeServer.Data)}");

    // 途中停止：请求还没返回时取消，文件长度仍是块大小的整数倍
    File.Delete(partPath);
    using (var stopCts = new CancellationTokenSource(TimeSpan.FromMilliseconds(100)))
    {
        try
        {
            await DownloadAsync(partPath, stopCts.Token, _ => { });
        }
        catch (OperationCanceledException)
        {
            // 途中停止是预期的结果
        }
    }
    Console.WriteLine($"途中停止：文件长度是 {FakeServer.ChunkSize} 的整数倍：{new FileInfo(partPath).Length % FakeServer.ChunkSize == 0}");
}
finally
{
    File.Delete(partPath);
}
```

运行结果。

```text
第一次：已暂停，文件里已有 1000 字节
第二次：从 1000 字节续传，最终 3000 字节，内容一致：True
途中停止：文件长度是 100 的整数倍：True
```

逐条看这三行输出。

- **第一次**，写入到 1000 字节时，回调调用了 `Cancel()`。下一块开始前，`ThrowIfCancellationRequested()` 抛出 `OperationCanceledException`，文件里正好有 10 块，共 1000 字节。这一步每次运行的结果都一样。
- **第二次**，不传取消令牌，从 1000 字节接着写，直到 3000 字节。最后把文件读回来，和原始数据逐字节比较，结果一致。
- **途中停止**，100 毫秒后取消。此时大概率正处于某一块的网络等待中，`Task.Delay(30, ct)` 被打断，那一块还没有写入。文件长度可能是任意的整块数，所以只检查它是不是 100 的整数倍。

**这里 `async` 起了什么作用？** `RangeAsync` 等待 30 毫秒的时候，线程不会被占住，取消信号也会立即打断这段等待。如果把它写成同步的 `Thread.Sleep(30)`，取消只能等睡醒之后再检查，停止会慢一拍。另外，同步版本的 `DownloadAsync` 要么一直占着线程，要么就得自己做很多额外的工作才能响应取消。

几点补充。

- 这里的"暂停"和"停止"用的是同一种机制，取消。区别只在于之后是否还用同一个文件。文件本身就是断点。
- 真实的下载还要处理更多情况，服务器是否支持 `Range`，下载完成后的完整性校验（比如哈希比对），以及文件被外部修改或删除。这些内容超出本章范围，这里只演示"可停止、可恢复"的基本结构。
- LogLens 本身没有下载功能。这一节只为了理解异步的"可停止、可恢复"，不涉及项目代码。

## 12.17 `await` 抛出的是原始异常

异步方法里的异常，接住的方式和同步代码很像。但有一个关键区别，异常以什么形式抛出，取决于你怎么等它。

检查点中的方法。

```csharp
static async Task<int> FailAsync(string name)
{
    await Task.Delay(50);
    throw new InvalidOperationException($"{name} 出错");
}
```

用 `await` 等它。

```csharp
try
{
    await FailAsync("任务1");
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"await 抛出原始类型：{ex.GetType().Name}，消息：{ex.Message}");
}
```

用 `.Wait()` 等它。

```csharp
try
{
    FailAsync("同步等待").Wait();
}
catch (AggregateException ae)
{
    Console.WriteLine($".Wait() 抛出 AggregateException，内部异常 {ae.InnerExceptions.Count} 个，类型：{ae.InnerException!.GetType().Name}");
}
```

运行结果。

```text
await 抛出原始类型：InvalidOperationException，消息：任务1 出错
.Wait() 抛出 AggregateException，内部异常 1 个，类型：InvalidOperationException
```

`await` 会把异常原样抛出来，所以 `catch (InvalidOperationException)` 直接就能接住，和同步代码一样。`.Wait()` 则把异常包进 `AggregateException`，要从 `InnerException` 里取出原始异常。

`.Result` 也会以同样的方式包装异常。本章实跑的是 `.Wait()`，`.Result` 没有单独运行，但它的包装方式相同。

**结论，优先用 `await`。** 避免 `.Wait()` 和 `.Result`，原因在第 [12.24 节](#s12-24)讲。

<a id="s12-18" class="lt-anchor-target"></a>

## 12.18 `try`、`catch` 与 `finally` 在异步方法里

在异步方法里，`await` 之后的代码仍然处在同一个 `try` 块中，所以 `catch` 能接住 `await` 之后抛出的异常。`finally` 会在 `await` 完成之后执行，不论成功还是失败。

```csharp
static async Task TryCatchFinallyAsync()
{
    try
    {
        Console.WriteLine("  try: 开始");
        await Task.Delay(50);
        throw new InvalidOperationException("await 之后出错");
    }
    catch (InvalidOperationException ex)
    {
        Console.WriteLine($"  catch: {ex.Message}");
    }
    finally
    {
        Console.WriteLine("  finally: 执行");
    }
}
```

运行结果。

```text
  try: 开始
  catch: await 之后出错
  finally: 执行
```

注意，异常发生在 `await` 之后，`catch` 也是在那之后才执行的。而 `finally` 总是最后执行。这和同步代码的规则完全相同，只是中间多了一段等待。

**项目里的集中处理。** `LogLens.Studio/ViewModels/ViewModelBase.cs` 第 45 行的 `RunGuardedAsync` 把界面命令的执行都包在一个 `try` 中。

- 第 64 行先接住 `OperationCanceledException`，这是用户主动取消，界面显示"操作已取消"，不当作错误；
- 第 69 行接住 `LogLensException`，这是领域异常，消息本身就是给用户看的；
- 后面还有 `catch (Exception ex) when (ex is IOException or UnauthorizedAccessException)`，用 `when` 过滤出文件系统类的错误，单独给一句人话。

所有异步命令都经过这一个地方，异常的处理方式因此统一。

## 12.19 多个任务同时失败

检查点中，三个任务各自抛出异常，然后用 `WhenAll` 等它们。

```csharp
var t1 = FailAsync("A");
var t2 = FailAsync("B");
var t3 = FailAsync("C");
var all = Task.WhenAll(t1, t2, t3);
try
{
    await all;
}
catch (InvalidOperationException)
{
    Console.WriteLine("await WhenAll 只抛出其中一个异常");
}
Console.WriteLine($"all.Exception 里共有 {all.Exception!.InnerExceptions.Count} 个异常");
```

运行结果。

```text
await WhenAll 只抛出其中一个异常
all.Exception 里共有 3 个异常
```

`await all` 只会抛出其中一个异常，本章不依赖具体是哪一个。如果需要看到全部失败，要读取任务的 `Exception` 属性。它是一个 `AggregateException`，`InnerExceptions` 里是全部异常。

这一点在排查问题时很重要，只看到一个异常，不代表只有一个任务失败了。

<a id="s12-20" class="lt-anchor-target"></a>

## 12.20 没有 `await` 的任务

忘记写 `await`，程序仍然能编译，也能运行。但是调用的任务抛出的异常，去了哪里？

```csharp
static async Task ForgetAsync()
{
    await Task.Delay(30);
    throw new InvalidOperationException("忘记 await 的错误");
}
```

检查点的调用方式。

```csharp
TaskScheduler.UnobservedTaskException += (_, e) =>
    Console.WriteLine($"  UnobservedTaskException 触发：{e.Exception.InnerException?.Message}");
#pragma warning disable CS4014 // 故意不 await，用来演示 12.20 与 12.24
ForgetAsync();
#pragma warning restore CS4014
await Task.Delay(100);
GC.Collect();
GC.WaitForPendingFinalizers();
GC.Collect();
await Task.Delay(100);
Console.WriteLine("  主程序仍在运行");
```

运行结果。

```text
  UnobservedTaskException 触发：忘记 await 的错误
  主程序仍在运行
```

`#pragma` 那两行只是为了让检查点保持无警告。在真实代码里，遇到 `CS4014` 应当先判断，这个调用到底需要不需要等待。

这段输出说明了三件事。

1. **进程没有因为这个异常崩溃。** 主程序仍在运行，这是 .NET 的默认行为。
2. **异常没有人接住。** 它成为"未观察的异常"。
3. **运行时只在任务被垃圾回收时，才会发出 `UnobservedTaskException` 事件。** 检查点用 `GC.Collect()` 强制回收，所以事件才能在这里出现。

还有一次对照实验，同样的 `ForgetAsync()`，不强制 GC，程序正常退出，退出码为 0，任何地方都没有输出这个异常。也就是说，**异常可能完全消失。**

所以，不要依赖 `UnobservedTaskException` 来记录错误。它出现的时机不确定，只适合作为最后的兜底，不能当成正常的错误处理。正确的做法是，`await` 它，或者显式处理它的异常。

**项目里的做法。** `LogLens.Studio/ViewModels/QueryStudioViewModel.cs` 第 274 行有一个不 `await` 的后台任务。

```csharp
_ = Task.Run(async () =>
{
    try
    {
        await Task.Delay(200, token).ConfigureAwait(false);
        Avalonia.Threading.Dispatcher.UIThread.Post(Validate);
    }
    catch (OperationCanceledException)
    {
        // 正常
    }
}, CancellationToken.None);
```

它用 `_ =` 明确表示"故意丢弃这个任务"，并在内部处理了取消。这就是不 `await` 时的基本要求，**异常必须在任务内部接住**，因为外面没有人会接。

## 12.21 `async void` 为什么会崩溃

`async` 方法有三种返回类型，`void`、`Task` 和 `Task<T>`。前两种之外，`async void` 是最需要小心的。

`async void` 没有返回值，调用方拿不到任务，也就没法 `await` 它，没法观察它的异常。异常发生时，没有任何调用者能接住它。它会在线程池上变成未处理异常，进程随之终止。

检查点中的演示（以 `void` 参数运行）。

```csharp
static async void Fire()
{
    await Task.Delay(50);
    throw new InvalidOperationException("Fire 出错");
}
```

调用的代码。

```csharp
Console.WriteLine("== 12.21 async void ==");
Fire();
await Task.Delay(500);
Console.WriteLine("主线程仍在运行");
```

运行 `dotnet run -- void`，结果如下。

```text
== 12.21 async void ==
Unhandled exception. System.InvalidOperationException: Fire 出错
```

进程的退出码为 134（Linux）。输出里没有"主线程仍在运行"，异常在 50 毫秒时就让进程崩溃了，程序还没走到那一行。

`async void` 的存在主要是为了事件处理器（比如按钮点击），因为事件的签名要求返回 `void`。除此之外，应当返回 `Task`。如果确实要在事件处理器里写异步代码，就要保证方法内部的异常全部被 `try`/`catch` 接住。

**项目里的情况。** 对整个项目 `grep` 的结果是 `async void` 出现 0 次。命令的返回类型都是 `Task`，例如 `QueryStudioViewModel.cs` 第 138 行的 `RunQueryAsync` 就返回 `Task`。

## 12.22 取消不是错误

第 [12.10 节](#s12-10)讲过取消。这里讲的是取消在异常处理中的位置。

`OperationCanceledException` 表示"操作按请求停止了"。这是一种正常的结果，不是程序的缺陷。`TaskCanceledException` 是它的子类，任务被取消时常会抛出这个类型，用 `catch (OperationCanceledException)` 一样能接住。

项目里有两处把取消当作正常结束。

- `LogLens.Cli/CliApplication.cs` 第 254 行，`catch (OperationCanceledException)` 输出"操作已取消"，返回退出码 130（这是 Unix 命令行里 Ctrl+C 的惯例值）。
- `LogLens.Studio/ViewModels/ViewModelBase.cs` 第 64 行，界面里同样接住它，显示"操作已取消"，但不走错误分支，不会调用 `onError`。

检查点的 `cancel` 参数可以看到退出码 130。

```text
操作已取消
```

（这行输出在标准错误流上，退出码为 130。）

不要把取消写成普通的 `catch (Exception)`。那样会把"用户主动停止"和"程序出错"混在一起，界面上就会弹出一个红色的错误框，而实际上什么都没有出错。

## 12.23 入口的异常与退出码

入口也是异步的。`Cli/Program.cs` 第 34 行的 `await CliApplication.CreateAsync(args)` 本身就可能失败。项目的做法是，失败时打印信息，然后返回一个明确的退出码。`Cli/Program.cs` 第 39 行就是 `return 6;`。

检查点里用参数演示三种退出情况。

| 运行命令 | 含义 | 退出码 |
| --- | --- | --- |
| `dotnet run` | 正常结束，顶层 `return 0;` | 0 |
| `dotnet run -- cancel` | 操作被取消，`catch` 中 `return 130` | 130 |
| `dotnet run -- crash` | 未处理的异常，进程崩溃 | 134（Linux） |

检查点的结尾。

```csharp
var mode = args.FirstOrDefault() ?? "";
switch (mode)
{
    case "cancel":
    {
        try
        {
            using var cancelAfter = new CancellationTokenSource(50);
            await Task.Delay(1000, cancelAfter.Token);
        }
        catch (OperationCanceledException)
        {
            Console.Error.WriteLine("操作已取消");
            return 130;
        }
        break;
    }
    case "crash":
        await Task.Delay(10);
        throw new InvalidOperationException("入口异常，没有人接住");
}

return 0;
```

顶层语句最后的 `return` 值就是进程的退出码。`return 130` 写在 `catch` 里，是主动映射；`throw` 没有被接住，则由运行时决定退出码，在 Linux 上是 134。Windows 上未处理异常的退出码不同，这里只记录 Linux 上的实际结果。

在命令行工具里，退出码是给脚本看的。脚本根据 `$?` 判断成功还是失败，所以把异常映射成明确的退出码，比打印一堆堆栈更有用。

## 12.24 常见错误

下面这些错误，初学者最容易遇到，也最难一眼看出来。

1. **忘记 `await`。** 编译器会给出 `CS4014` 警告，`Because this call is not awaited, execution of the current method continues before the call is completed.`（这是本章探针中实际得到的编号。）调用的任务在后台运行，异常可能丢失（见 12.20）。遇到这个警告，先判断是否真的需要等待，不要直接压掉。检查点中用 `#pragma warning disable CS4014` 只是为了演示。
2. **加了 `async` 却没有 `await`。** 这种写法能编译，本章用的 .NET 10 SDK 也不会警告。它只会多出一层不必要的状态机，还会误导读代码的人（见 12.6）。
3. **`async void` 导致进程崩溃。** 见 12.21。除了事件处理器，不要使用。
4. **在界面线程上用 `.Result` 或 `.Wait()` 阻塞。** 这两个写法会把当前线程停住，等待任务完成。如果那个任务需要回到这个被停住的线程，两者就会互相等待，程序卡死。本章没有实跑这种死锁的情况，线程和死锁会在[第 13 章](/chapter/13)结合具体示例讲解。
5. **取消后仍在写文件。** 取消只是"请求停止"，代码必须自己检查令牌，并决定停在哪里。写文件写到一半被取消，就会留下一个不完整的文件。写入类操作要考虑这种情况，比如先写临时文件，成功后再替换，或者像 12.16 那样把文件长度当作断点。
6. **以为 `WhenAll` 只会有一个异常。** `await` 只抛出其中一个，要看全部，读取 `Exception`（见 12.19）。
7. **在异步方法里使用 `Thread.Sleep`。** 它会占住线程，应该改用 `await Task.Delay(...)`（见 12.5）。

## 12.25 小练习与检查点

**练习一。** 写一个程序，并发读取三个"慢源"，每个源的耗时不同（例如 300、800、1500 毫秒）。要求。

1. 同时开始三个任务，汇总全部结果并打印；
2. 每完成一个源，报告一次进度（已完成 1/3、2/3……），用 `IProgress<T>`；
3. 支持取消，超过 1 秒时自动取消，并打印"已取消，已完成的结果如下"；
4. 其中一个源随机抛出异常，最后把**全部**失败的异常打印出来。

提示，可以用 `Task.WhenAll` 与 `CancellationTokenSource(TimeSpan)`；异常要读取任务的 `Exception` 属性。

**练习二。** 把 12.16 的下载改造成支持"暂停后换一种方式续传"的版本。

1. 写入每一块之后，把已下载的字节数写到另一个小文件里（例如 `.progress`），而不是只依赖目标文件的长度；
2. 续传时先读取这个记录，再从对应位置接着下载；
3. 思考，如果目标文件写入成功、记录文件却没有更新，会出现什么情况？这时哪一个值更可靠？

**检查点。** 配套代码在 `code/ch12-async/`。
