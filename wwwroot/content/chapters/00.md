# 第 0 章 程序、C# 与 .NET 从哪来

这一章不教 C# 语法。它先回答四个问题，程序到底是什么，它为什么要先编译才能运行，.NET 和 C# 各管哪一部分，图形界面又是怎么回事。最后带你把开发环境装好，包括在线装和离线装。

读完这一章，你会得到两样东西。一是对“程序、编译、内存、运行时、框架、事件循环”这些词的初步印象，足够看懂后面几章的解释。二是一台能编译、能运行 .NET 程序的电脑，以及一个确认环境正常的办法。

需要的条件很少。一台电脑，能联网更省事（完全离线的做法见 [0.20 节](#s0-20)），有安装软件的权限，再加上一两个小时。

最容易卡住的地方有两处。一是装完 SDK，终端却提示找不到 `dotnet` 命令，这通常是 PATH 没生效，0.19 节专门处理。二是第一次构建要下载大量的包，屏幕可能停在某一行很久，这时程序没有死，只是在下载。

## 0.1 从一行命令说起

下面是一次运行的过程。`$` 后面是你敲的命令，下一行是程序输出。用户名和版本号因机器而异。

```text
$ dotnet run hello.cs
你好，user。这是 .NET 10.0.14 上的一个单文件程序。
```

`hello.cs` 的内容只有两行。

```csharp
var name = Environment.UserName;
Console.WriteLine($"你好，{name}。这是 .NET {Environment.Version} 上的一个单文件程序。");
```

敲完回车，屏幕上多出一句话，整个过程用了四秒多一点。

这四秒里发生了一连串事情。`dotnet` 这个命令读到 `hello.cs`，把它交给 C# 编译器。编译器产出一种中间形式的文件。运行时接过这个文件，把它翻译成你这台机器的 CPU 能执行的指令。CPU 执行，结果输出到终端。每一步背后都有几十年的历史，接下来的几节会一步一步展开。

<a id="s0-2" class="lt-anchor-target"></a>

## 0.2 程序是什么

程序是一份写给机器的步骤表。每一步只做一件很小的事，比如取出两个数，把它们相加，再把结果写到屏幕上。机器按顺序执行，不跳过，也不替你补充没写的步骤。

做菜可以作为类比。菜谱是程序，厨师是 CPU，食材是数据。菜谱写得含糊，厨师就会做错，机器也一样，它不会猜你的意思。

下面几个词会反复出现，先在这里认个脸。

指令是 CPU 能直接执行的最小动作，例如“取出一个数”“做加法”“跳到第 20 步”。

数据是指令操作的对象，例如一个整数、一段文字、一张表格。

执行是 CPU 一条一条取出指令，并把每条指令要求的动作做完的过程。

程序员很少直接写指令，因为指令是一串数字，人读起来非常费劲。于是人们发明了各种语言，让人用接近日常表达的写法描述步骤，再由工具把它们变成指令。C# 就是这样一门语言。

## 0.3 从打孔卡到存储程序

在有电子计算机之前，“程序”这个想法已经存在了。

1801 年，法国人约瑟夫·玛丽·雅卡尔做出一台织布机。它用一串打孔卡控制经线的抬起和落下。卡上有孔的位置对应一个动作，没有孔的位置对应另一个动作。换一种花纹，不需要改动机器，只需要换一叠卡。这是第一次有人把“做什么”从机器里拿出来，存成一叠可以替换的东西。

1822 年，英国人查尔斯·巴贝奇开始造差分机，用来自动算多项式表，因为当时的航海和工程表格里错误很多。十几年后他把计划改成分析机，里面有运算部件，有存放中间结果的仓库，也有依据条件决定下一步去哪里的机制。分析机没有造完，但它的设计图上已经有了今天计算机的基本形状。

</figure>

给分析机写程序的人，是阿达·洛芙莱斯。1843 年她翻译了一位意大利工程师关于分析机的文章，并在附注里写下一套完整的计算步骤，用分析机算出伯努利数。她还在注里指出，如果机器处理的对象既可以是数字，也可以是符号，它也许能处理音乐和文字。她去世时三十六岁，那台机器一台都没有造出来。

![阿达·洛芙莱斯的肖像](/content/images/ch00-ada-lovelace.jpg)

<figcaption class="lt-note"><span class="lt-note-tag">注</span>阿达·洛芙莱斯。图片来自 Wikimedia Commons，属公有领域。</figcaption>

一百年后，1936 年，英国人图灵发表论文，给“能算的东西”划了一条清楚的边界。他设想一台机器，有一条无限长的纸带，一个读写头，一张规则表。规则表说明，读到什么符号时，写回什么，往哪边移动，接下来去执行哪一条规则。凡是能被这样一台机器算出来的，就叫可计算。这个模型不关心硬件有多快，它只定义能与不能的边界。

同一年，美国人阿隆佐·邱奇用另一套数学方法得到了同样的边界。1937 年，香农证明电路可以实现布尔逻辑运算，电路和逻辑从此连在了一起。1941 年，德国人楚泽用继电器造出 Z3，它是最早能够编程控制的计算机之一。

1946 年 2 月，美国宾夕法尼亚大学的 ENIAC 对外公布。它有大一万七千多根电子管，编程的办法却很原始。工程师要在一排排插线板上重新接线，改一道题，改的是物理连线，常常要花好几天。当时负责编程的是六位女性，她们在图纸上把问题拆成运算顺序，再翻译成接线方案。

<figure class="lt-figure">

![两位女性操作 ENIAC](/content/images/ch00-eniac-women.jpg)

<figcaption class="lt-note"><span class="lt-note-tag">注</span>两位女性操作 ENIAC。图片来自美国陆军的官方照片，属公有领域。</figcaption>

</figure>

1945 年 6 月，冯·诺依曼写了一份关于 EDVAC 的草稿报告，提出把指令和数据一样放进存储器里。这样一来，改程序就变成了改内存里的数字，机器不需要再重新接线。这份报告在 1946 年公开，随后几年几乎影响了所有计算机的设计。

存储程序这个想法，把“软件”和“硬件”分开了。程序从此成为一种可以写、可以复制、可以修改、也可以出错的东西。今天的程序员每天面对的很多问题，追根溯源都能落到“指令和数据放在同一块存储器里”这件事上。

## 0.4 机器只认数字

CPU 不认识“加法”两个字。它只能分辨电信号的高和低，工程上把它们记作 1 和 0。

一个 0 或 1 叫一个位，英文是 bit。八个位组成一个字节，英文是 byte。一个字节一共有 256 种状态，从 0 到 255，足够表示一个英文字母、一个很小的整数，或者一条简单的指令。

打孔卡的一列，正好就是这种东西。孔在，记作 1；孔不在，记作 0。

<figure class="lt-figure">

![一张 80 列打孔卡](/content/images/ch00-punch-card.jpg)

<figcaption class="lt-note"><span class="lt-note-tag">注</span>80 列打孔卡。图片来自 Wikimedia Commons，采用 CC0 公共领域贡献协议。</figcaption>

</figure>

下面是一条示意的机器指令。它并非某台真实机器的指令，只用来说明形式。

```text
1011 1000 0000 0001
```

前几位是操作码，告诉电路要做哪件事。后面几位是数据，或者数据放在哪里。十几位二进制数字，人读起来和一串没有标点的数字没有区别。写错一位，机器不会提醒你，它会照做，然后给出一个错误的结果。

缓解的办法是给指令起名字。用一个短词代表那串 0 和 1，再用一个程序把这些短词翻译回数字。这个翻译程序叫汇编器，那套短词叫汇编语言。上面那条指令在汇编里可能写成 `MOV R0, 1`，人读得懂，机器仍然需要汇编器来翻译。

汇编解决了一个问题，又留下了一个问题。每种 CPU 的指令集都不同，为一台机器写的程序搬到另一台机器上就不能用了。1964 年 IBM 推出 System/360，特意让一整个系列共用一套指令集，就是为了减轻这种痛苦。整个 1970 年代，换一个型号就要重写程序，“可移植”于是成了一项硬性需求。

## 0.5 内存是一排编号的格子

前一节说的 0 和 1，要存放在某个地方。这个地方就是内存。

内存可以想象成一排格子，每个格子装一个字节，每个格子都有一个编号，叫地址。CPU 要读某个数，就告诉内存地址；要写一个数，同样先给地址，再给数据。内存断电之后里面的内容会丢失，这一点和硬盘不同。硬盘断电后数据还在，但它慢得多。

CPU 内部还有几个更快的小格子，叫寄存器，数量只有几十个。计算时数据要先搬到寄存器里才能运算，运算完再搬回内存。所以一个程序的速度，很大程度取决于数据在哪里、搬得多不多。

程序里的变量，说到底就是内存里的一块格子，外面贴了一个好记的名字。

```csharp
int count = 3;
```

这一行说的是，在内存里找一块能放下整数的地方，放进去 3，之后用名字 `count` 来指它。C# 里的 `int` 是 32 位整数，占 4 个字节。

程序运行时，内存大致被分成两块来用，叫栈和堆。

栈是按调用顺序放东西的地方。每次调用一个方法，就在栈顶压入一块区域，放这个方法的局部变量；方法执行完，这块区域就被整个弹出。栈的分配和回收都很快，但它的大小有限，而且只能按后进先出的顺序使用。

堆是放对象的地方。`new` 出来的东西，比如一个列表、一段很长的文字，都放在堆上。堆可以很大，但回收的工作比较复杂，C# 把这件事交给了垃圾回收器，0.8 节会讲它怎么工作。

栈上的变量和堆上的对象通过引用连起来。引用可以理解为一个地址，指向堆上的那个对象。下面这张图把这些关系画出来了。

<img class="lt-img-light" src="/content/images/ch00-fig03-stack-heap.svg" alt="栈与堆的关系" />
<img class="lt-img-dark" src="/content/images/ch00-fig03-stack-heap-dark.svg" alt="栈与堆的关系" />

图里 `Main` 方法的 `log` 变量并不直接装着列表，它只装着列表在堆上的地址。`Parse` 方法的 `line` 也是一样。两个方法都结束之后，它们的栈帧会被弹出，`log` 和 `line` 这两个名字就失效了。堆上的对象是否还能回收，要看还有没有引用指向它。这就是下一节 GC 的工作依据。

## 0.6 从源代码到机器码

编译，英文是 compile，意思是把一种形式的源代码翻译成另一种形式。负责翻译的程序叫编译器。

<img class="lt-img-light" src="/content/images/ch00-fig01-compile.svg" alt="从源代码到运行的两个阶段" />
<img class="lt-img-dark" src="/content/images/ch00-fig01-compile-dark.svg" alt="从源代码到运行的两个阶段" />

你写的 C# 源代码，是给人看的。编译器读它，检查有没有语法错误和类型错误，检查通过之后，输出另一种形式的东西。这个东西可以是 CPU 能直接执行的机器码，也可以是一种中间形式，等运行时再翻译成机器码。.NET 走的是第二条路，下一节会讲这种中间形式。

有些语言不先编译，而是边读边执行，逐句翻译、逐句运行。这叫解释执行。两种做法各有取舍。编译时多花一点时间，运行时就能快一些，还能在运行之前发现更多错误。解释执行的开发反馈更快，但错误往往要运行到那一行才会暴露。

编译器内部大致要经过五个阶段。

| 阶段 | 做的事 | 出错时的典型表现 |
| --- | --- | --- |
| 词法分析 | 把字符流切成一个个词，比如关键字、名字、数字、符号 | `CS1011` 空字符常量、引号没有配对 |
| 语法分析 | 按语法规则把词拼成结构，比如判断一句话是不是合法的语句 | `CS1002` 少了分号、`CS1513` 少了右大括号 |
| 语义分析 | 检查类型是否匹配、名字是否已经定义 | `CS0246` 找不到类型、`CS0029` 类型不匹配 |
| 优化 | 在结果不变的前提下，让生成的代码更快或更小 | 很少报错，只是你很难猜到生成的指令长什么样 |
| 生成 | 输出目标形式，对 .NET 来说是 IL 加元数据 | 通常到这一步才会暴露程序集之间的引用问题 |

报错信息前面的 `error CS0246` 里，CS 表示这是 C# 编译器 Roslyn 报出的错误，后面的数字对应上面某个阶段。附录 A 把常见错误码按阶段分好了类，遇到报错可以去那里查。

编译还有一个容易被忽略的步骤，叫链接。当一个程序由多个文件、多个库组成时，编译器先为每个文件产出一份中间结果，再由链接器把它们拼成一个完整的产物。在 .NET 里，这一步的痕迹藏在 `dll` 和引用关系里，你平时不太会直接看到它，但项目文件里写的每一个 `Reference` 和 `PackageReference`，最后都要在这一步落实。

编译的历史和语言的历史是绑在一起的。最早的程序员直接写机器码，后来用汇编，再后来有了能让人用接近英语或公式的方式写程序的高级语言。

1953 年，IBM 的约翰·巴克斯带队研究一种能让工程师直接写公式的语言，1957 年发布，叫 FORTRAN。它的写法大致如下。下面的代码是示意，不是一段要运行的程序。

```fortran
SUM = 0.0
DO 10 I = 1, N
    SUM = SUM + A(I)
10 CONTINUE
```

这段代码和汇编之间的差距，主要体现在谁能看懂、谁能维护上。写的人看得懂这段，编译器知道怎样把它变回机器指令。

FORTRAN 之后，语言按用途分头发展。1958 年，麦卡锡做出 LISP，用来处理符号和列表。1959 年，美国国防部牵头定出 COBOL，专门处理商业报表。格蕾丝·霍珀在它的设计里坚持用接近英语的写法描述数据，这一点影响了很多后来的语言。1960 年的 ALGOL 60 确立了块结构和递归，还留下了描述语言语法的记法，今天的很多语言规范都沿用了它的思路。1972 年，贝尔实验室的丹尼斯·里奇为了让 UNIX 能搬到不同的机器上，设计了 C 语言。

C 语言的位置很特殊。它比汇编好写得多，编译出来的机器码却几乎和手写汇编一样紧凑。UNIX 用 C 重写之后，操作系统本身有了可移植性。后来 Windows、Linux、macOS 的内核仍然以 C 为主，数据库、解释器、图形库也大量使用 C 或它的衍生语言。你每天用的程序，脚下几乎都踩着这一层。

## 0.7 中间语言这条折中路

C 语言有一个麻烦。同一份源代码，换一个平台就要重新编译，编出来的程序只能在那种 CPU 上运行。商业软件发布时，通常要为每个平台准备一份单独的安装包。

另一条路是让程序跑在一台虚拟机器上。这台机器不存在于硬件里，而是由一个软件模拟出来。程序先被编译成这台虚拟机器能理解的指令，再由虚拟机器去执行。虚拟机器的实现却可以因平台而异，所以同一份指令到处都能跑。

1995 年，Sun 公司的 Java 把这条路做成了大众可用的样子。Java 源代码编译成字节码，字节码在任何装了 Java 虚拟机的机器上运行。

2002 年，微软用类似的思路推出了 .NET。它的中间形式叫 IL，全称是 Intermediate Language，中文常叫中间语言。

IL 长什么样，可以直接从编译好的程序里读出来。我们写了一个小实验，把两个方法的 IL 字节取出来看。C# 源代码只有一行。

```csharp
public static int Add(int a, int b) => a + b;
```

输出如下。

```text
=== 方法体在 IL 里长什么样 ===
Calc.Add      4 字节  02 03 58 2A
Calc.Multiply 4 字节  02 03 5A 2A
```

四个字节就是四条指令，一条一个字节。

| 字节 | IL 指令 | 含义 |
| --- | --- | --- |
| `02` | `ldarg.0` | 把第 0 个参数压到计算栈顶 |
| `03` | `ldarg.1` | 把第 1 个参数压到计算栈顶 |
| `58` | `add` | 弹出栈顶两个值，相加，结果压回栈顶 |
| `2A` | `ret` | 把栈顶的值作为返回值交出去 |

同一个实验里的 `Multiply` 方法，前两个字节和 `Add` 一模一样，只有第三个字节从 `58` 变成了 `5A`。`5A` 对应的是乘法指令 `mul`。这说明 IL 的结构很规整，改一个运算符，只需要改一个字节。

IL 不是机器码，CPU 不认识它。把它变成 CPU 能执行的东西，要靠运行时里的 JIT 编译器。JIT 的意思是即时编译。程序启动时，运行时把 IL 一段一段翻译成本机的机器码，翻过的代码会缓存下来，下次直接执行。同一个 `dll` 文件，在 x64 的 Windows、ARM 的 Mac、x64 的 Linux 上都能运行，每台机器上的 JIT 各自负责翻译成本机能懂的指令。

这条路还有一个好处。IL 带着完整的类型信息，运行时知道每个变量是什么类型，因此能在运行前后做更多检查。下一节讲的很多能力，都建立在这一点上。

这条路也有代价。JIT 要在程序启动时工作，启动会慢一点。为了减轻这个代价，.NET 还支持提前编译，叫 AOT。发布时就把 IL 直接翻译成机器码，启动快，但失去了 JIT 根据运行情况做的一部分优化。这种取舍在第 25 章讲发布时还会再见到。

<a id="s0-8" class="lt-anchor-target"></a>

## 0.8 CLR 替你做的四件事

.NET 的运行时叫 CLR，全称 Common Language Runtime，即公共语言运行时。它在你的程序运行时盯着，替你做了四件 C 语言不替你做的事。

第一件是类型与边界检查。在 C 语言里，越界写入数组通常不会当场报错，程序继续跑，坏的数据悄悄留在别处，问题可能几小时后才冒出来。CLR 里同样的操作会当场抛出 `IndexOutOfRangeException`，并给出出错的位置。代价是每次访问都多一次检查，在现代 CPU 上这个开销很小。

第二件是垃圾回收，英文是 Garbage Collection，简称 GC。C 语言里用 `malloc` 申请内存，用 `free` 归还，忘了归还就泄漏，归还两次就崩溃。CLR 里你只管 `new`，什么时候回收由 GC 决定。它从根出发，沿着引用找出所有还能被访问到的对象，标记为活的，其余的清理掉。

第 0 章的配套项目 ch00-origins 里有一个小实验，可以验证 GC 确实在工作。程序先读一次托管堆的大小，然后分配二十万个一百个字符的字符串，再读一次，并记录发生了几次回收。

```text
=== GC 什么时候动手 ===
分配前托管堆 0.1 MB
分配后托管堆 16.0 MB
0 代回收次数 1
名义上申请了 38.1 MB，实际占着 15.9 MB
```

二十万个字符串，每个字符串一百个字符，按 C# 字符串每字符两个字节算，名义上要 38 MB 左右。实际只占 16 MB，中间发生了一次第 0 代回收。省下来的那二十多兆就是 GC 清理掉的字符串，程序里一行释放代码都没有写。

GC 不是没有代价。回收的时候要暂停一段时间，或者占用一些 CPU。这就是为什么做图形界面和高频处理的程序，要留意每一帧产生了多少临时对象。这些细节会在后面的章节中展开。

第三件是统一的异常模型。出错的时候，运行时抛出一个对象，里面带着类型、消息和调用栈，用 `catch` 接住就能处理。这套模型跨语言一致。C# 写的库被 F# 调用时，抛出的仍然是同一种异常对象。

第四件是元数据。每个 .NET 程序集里都保存着一张表，记录有哪些类型、哪些方法、参数叫什么名字、继承自哪个类。下面是在一个 6144 字节的 `dll` 文件里找到的一些痕迹。

```text
文件大小 6144 字节
开头两字节 b'MZ' （PE 可执行文件的标志）
BSJB 元数据签名出现在偏移 1100
签名后紧跟的版本字符串 b'BSJB\x01\x00\x01\x00\x00\x00\x00\x00\x0c\x00\x00\x00v4.0'
```

`MZ` 是 Windows 可执行文件的标准开头，`BSJB` 是 .NET 元数据的标记。有了这张表，工具可以在程序还没运行的时候列出所有类型。IDE 的跳转到定义、代码补全和重命名，都依赖它。

托管不等于慢，也不等于绝对安全。托管代码挡住了越界访问和悬空指针，却挡不住逻辑错误，也挡不住 SQL 注入这类攻击。

下面的表格把 C 语言和 C# 的差别放在一起看。

| | C 语言 | C# 与 .NET |
| --- | --- | --- |
| 申请内存 | `malloc` | `new` |
| 释放内存 | 手工 `free` | 由 GC 负责 |
| 越界访问 | 未定义行为，可能悄悄写坏内存 | 抛出 `IndexOutOfRangeException` |
| 编译产物 | 直接是机器码 | IL 加元数据 |
| 换平台 | 重新编译 | 同一个 `dll` 可用，由 JIT 翻译 |
| 启动速度 | 快 | JIT 有预热成本，可用 AOT 缓解 |

## 0.9 什么是 .NET

前面讲了编译、IL、运行时和 GC，它们都属于 .NET。现在可以给 .NET 下一个完整的定义了。

.NET 是一个开发和运行程序的平台。它包括下面几部分。

运行时，也就是 CLR，负责加载和执行程序，管理内存，处理异常。

基础类库，英文简称 BCL，是一大批现成的类，提供字符串、集合、文件、网络、时间等常用功能。`Console` 这个类就在其中，你每次输出文字都会用到它。

SDK，即软件开发工具包，包括编译器、构建工具和 `dotnet` 命令。写代码的电脑需要装 SDK。

语言，主要是 C#，另外还有 F# 和 Visual Basic。它们都编译成同一种 IL，所以可以互相调用。

工具和生态，包括包仓库 NuGet，IDE 集成，调试器，以及各种第三方库。

用一个比喻来说，.NET 像一个带工具箱的厨房。运行时是燃气和水电，类库是现成的调料和器具，SDK 是菜刀和砧板，C# 是你用来做菜的菜谱语言。

很多人会拿 .NET 和 Java 比较。Java 对应的大致是 JVM 加 JDK 加 Java 语言。.NET 的思路和它相似，但它的运行时、语言和库都是同一家团队设计的，类库的风格也比较统一。

下面先澄清几件容易混淆的事。

C# 是语言，.NET 是平台。C# 运行在 .NET 上，但 .NET 上也能跑 F# 和 Visual Basic。语言和平台是两回事，就像写文章用的中文，和承载它的印刷与发行体系不是一回事。

`.NET` 不等于 Windows 应用。今天的 .NET 是跨平台的，同一套代码可以在 Windows、macOS 和 Linux 上运行。它能做桌面程序，也能做网站、后台服务、命令行工具、移动应用和游戏。

.NET 是开源的。它的源代码托管在 GitHub 上，任何人都可以阅读和提交修改。这一点让它的历史跟许多商业闭源产品不同。

`dotnet` 这个命令是 SDK 的入口。你在终端里敲的 `dotnet new`、`dotnet build`、`dotnet run`，都是它在干活。它本身只是一个启动器，真正的编译和运行靠 SDK 里其他部分完成。

## 0.10 .NET 的三代

.NET 这个名字用过三代产品，很多人第一次接触时会被这三个东西搞混。

第一代是 .NET Framework。2002 年 2 月 13 日发布 1.0 版，和 C# 1.0 同时出现。它只能在 Windows 上运行，属于系统组件，一台机器通常只装一个版本。2005 年的 2.0 带来泛型，2007 年的 3.5 带来 LINQ，2010 年的 4.0 带来动态类型支持和并行库。2019 年发布的 4.8 基本停留在维护状态，之后只做安全修复。

用 .NET Framework 写的程序，今天在银行、医院和工厂里仍然大量运行着。你以后接手老项目，很可能会在项目文件里看到 `net48` 这样的写法。

与此同时，有一条线在绕开 Windows 的限制。2001 年，米格尔·德伊卡萨发起了 Mono 项目，目标是让 .NET 程序能跑在 Linux 上。它做了十几年，后来为游戏引擎 Unity 的脚本层提供了支持。2011 年，基于 Mono 的商业公司 Xamarin 成立，主攻移动开发。2016 年，微软收购了 Xamarin。

第二代是 .NET Core。2016 年 6 月 27 日发布 1.0 版。它是重新写的，开源，跨平台，而且多个版本可以在同一台机器上并排安装。2019 年 12 月发布的 3.1 是这条线上最后一个长期支持版本。

第三代从 .NET 5 开始。2020 年 11 月 10 日发布，微软去掉了 Core 这个后缀，把 .NET Framework、.NET Core 和 Xamarin 的能力合进同一个产品。从那以后，版本号不再是 4.x 这样的样子，而改用数字 5、6、7、8、9、10，一个数字一个年度版本。

## 0.11 C# 这门语言

C# 的主要设计者是安德斯·海尔斯伯格。1983 年，他参与开发了 Turbo Pascal，后来又在 Borland 做 Delphi，两者都以编译快、工具好用著称。1996 年他加入微软，2000 年在 PDC 大会上首次公开 C#，2002 年随 .NET Framework 1.0 一起发布 1.0 版。

他对 C# 的取向，从语言的几处选择中能看出来。

组件导向。C# 的类天生带有属性、事件、特性和元数据，这些东西在 Java 和 C++ 里通常要靠额外框架来补。目的是让“把一段代码交给别人使用”变得简单。

保留值类型。C# 里有 `struct`，占多少字节就是多少字节。Java 里的 `int` 之类基本类型和对象是分开的，需要包装类才能当对象用。在解析器、图形和游戏里，这种区别会直接影响性能。

不要求声明异常。Java 要求方法在签名里写明可能抛出的异常，调用方必须处理。C# 没有这条规定，[第 11 章](/chapter/11)会讲这个选择带来的好处和代价。

保留 `unsafe` 的出口。极少数场景确实需要直接操作指针，C# 允许你在显式标记的代码块里这样做。

| | C# | Java |
| --- | --- | --- |
| 属性 | 语言内置 `get` 与 `set` 语法 | 通常手写 getter 与 setter |
| 值类型 | 有 `struct`，可以自定义 | 只有内置基本类型 |
| 泛型的实现 | 运行时保留类型参数 | 编译期擦除 |
| 事件 | 内建 `event` 关键字 | 通常用观察者模式自己搭 |
| 受检异常 | 没有 | 有 |
| 运算符重载 | 支持 | 不支持 |
| 中间产物 | IL 加元数据 | 字节码 |

C# 的版本和 .NET 的版本是两件不同的事。语言版本决定你能写哪些语法。目标框架决定你能用哪些库，程序能跑在什么运行时上。项目文件里可以写 `<LangVersion>7.3</LangVersion>`，同时编译到 `net10.0`，也可以反过来，用新语言写老框架的代码。

下面是 C# 版本的一张窄表，够你在读别人的项目时不至于迷路。完整的版本演变会在[第 15 章](/chapter/15)展开。

| C# 版本 | 年份 | 主要新增 |
| --- | --- | --- |
| 1.0 | 2002 | 类、属性、事件、委托 |
| 2.0 | 2005 | 泛型、可空值类型、迭代器 |
| 3.0 | 2007 | LINQ、lambda、`var`、扩展方法 |
| 4.0 | 2010 | `dynamic`、命名参数、协变与逆变 |
| 5.0 | 2012 | `async` 与 `await` |
| 6.0 | 2015 | 插值字符串、`nameof`、`?.` |
| 7.0 | 2017 | 元组、模式匹配、局部函数 |
| 8.0 | 2019 | 可空引用类型、`switch` 表达式 |
| 9.0 | 2020 | `record`、顶级语句 |
| 10.0 | 2021 | `record struct`、文件范围命名空间 |
| 11.0 | 2022 | 原始字符串字面量、`required` |
| 12.0 | 2023 | 主构造函数、集合表达式 |
| 13.0 | 2024 | `params` 集合 |
| 14.0 | 2025 | `field` 关键字、扩展成员 |

读这张表有个实用的角度。看到项目里某段写法比较怪，可以先查一下它的版本。看到 `var` 和 `?.`，就知道它至少是 2007 年之后的写法。看到 `record`，就知道它至少是 2020 年之后的写法。

## 0.12 一个 .NET 程序由哪些零件组成

从源代码到屏幕上出现一行字，中间经过六个角色。下面的图只列出主要环节。

```text
你的代码 (.cs)
   │
   ├── 项目文件 (.csproj) 说明目标框架、依赖包、编译选项
   │
   ▼
MSBuild 读取项目文件，决定怎么编译
   │
   ▼
Roslyn 编译器把 C# 变成 IL 加元数据，输出 .dll
   │
   ▼
dotnet 宿主程序找到运行时，加载 .dll
   │
   ▼
CLR 启动，JIT 把 IL 翻译成本机指令
   │
   ▼
CPU 执行，输出到终端
```

`dotnet build` 之后，输出目录里会出现好几个文件。

```text
ilprobe
ilprobe.deps.json
ilprobe.dll
ilprobe.pdb
ilprobe.runtimeconfig.json
```

每个文件都有用途，缺少任何一个，程序都可能跑不起来。

| 文件 | 里面是什么 |
| --- | --- |
| `ilprobe.dll` | 你的代码，IL 加元数据 |
| `ilprobe.runtimeconfig.json` | 需要哪个版本的运行时 |
| `ilprobe.deps.json` | 依赖清单，记录用到的包和版本 |
| `ilprobe.pdb` | 调试符号，把 IL 的位置映射回源代码的行号 |
| `ilprobe` | 启动器，Windows 上是 `.exe` |

`runtimeconfig.json` 只有几行，可以看一眼。

```json
{
  "runtimeOptions": {
    "tfm": "net10.0",
    "framework": {
      "name": "Microsoft.NETCore.App",
      "version": "10.0.0"
    }
  }
}
```

其中 `tfm` 是 Target Framework Moniker 的缩写，意思是目标框架标识。`net10.0` 表示这个程序要运行在 .NET 10 上。你在项目文件里写 `<TargetFramework>net10.0</TargetFramework>`，编译器就会把它写进这个文件。

几个名词需要分清。

| 名词 | 是什么 | 你什么时候会碰到它 |
| --- | --- | --- |
| SDK | 编译工具链，包含编译器、MSBuild、项目模板 | 在写代码的电脑上安装 |
| 运行时 | 只负责运行程序，不含编译器 | 在用户的电脑上安装 |
| BCL | 基础类库，随运行时自带 | 天天用，`Console` 就在里面 |
| NuGet | 第三方包的仓库 | 第 22 章安装 Avalonia 时 |
| MSBuild | 读取项目文件、驱动编译的引擎 | 出错时查看它的日志 |
| 程序集 | 一个 `.dll` 文件，装着 IL 和元数据 | 引用别人的库时 |

SDK 和运行时的版本号看起来不一样，初学者几乎都会困惑。下面是 `dotnet --info` 的输出，节选了和版本有关的部分。

```text
.NET SDK:
 Version:           10.0.403

Host:
  Version:      10.0.14
  Architecture: x64

.NET SDKs installed:
  10.0.403 [/usr/share/dotnet/sdk]

.NET runtimes installed:
  Microsoft.AspNetCore.App 10.0.14 [/usr/share/dotnet/shared/Microsoft.AspNetCore.App]
  Microsoft.NETCore.App 10.0.14 [/usr/share/dotnet/shared/Microsoft.NETCore.App]
```

`10.0.403` 是 SDK 的版本号。第三位 403 是构建号，中间那个 4 表示它是 10.0 的第 4 次功能更新。`10.0.14` 是运行时的版本号，是 10.0 系列的第 14 个补丁。SDK 和运行时的版本号本来就是各自递增的，两个数字对不上很正常。

## 0.13 图形界面是怎么回事

前面讲的都是没有窗口的程序。从这一节开始，讲的是屏幕上有按钮、有文本框、能用鼠标拖动的程序。这类程序的原理和前面有很大不同，初学者最容易在这里迷路，所以放慢一点。

### 窗口和控件

图形界面程序里，你能看到的东西可以分成三类。

窗口是一块矩形区域，有标题栏和边框，是应用的顶层容器。一个程序可以有多个窗口，也可以只有一个。

控件是窗口里能交互的部件，例如按钮、文本框、下拉框、列表、滑块。每个控件负责两件事，一是画出自己，二是接收并处理输入。

容器是用来摆放其他控件的部件，例如网格、堆栈面板、停靠面板。容器自己通常不接收点击，它的作用是决定子控件的位置和大小。

历史上第一个带窗口、图标和鼠标的图形界面，出现在 1973 年施乐公司的 Alto 电脑上。1984 年苹果公司的 Macintosh 把它带进了大众市场。之后的 Windows、macOS、Linux 桌面，走的都是同一种思路。

### 屏幕、像素和 DPI

屏幕由一个个发光点组成，每个点叫一个像素。一块 1920 乘 1080 的屏幕，横向有 1920 个像素，纵向有 1080 个像素。

同样大的屏幕，像素可以多，也可以少。像素越多，每个点越小，画面越细腻，这叫分辨率。

DPI 是每英寸的点数，常被译为“每英寸像素数”。Windows 把 96 DPI 定为 100% 缩放的基准。用户把缩放调到 150% 时，系统会让界面的每个单位放大 1.5 倍。

为了让界面在不同屏幕上大小一致，图形框架通常使用逻辑像素，英文是 device-independent pixel 或 logical pixel。一个逻辑像素在 100% 缩放下等于一个物理像素，在 150% 缩放下等于 1.5 个物理像素。

这样一来，你在代码里写一个宽 300 的按钮，它在 100% 缩放下占 300 个物理像素，在 150% 缩放下占 450 个物理像素，在两块屏幕上看起来大小差不多。如果代码直接写物理像素，换一块屏幕，按钮就会忽大忽小。

### 事件与事件循环

用户的每一次操作，比如点击鼠标、按下键盘、拖动窗口，都会先被操作系统接收。操作系统把它包装成一条事件，按先后顺序放进一个队列。应用程序自己有一个循环，不停地从队列里取出事件，判断它属于哪个控件，交给那个控件处理。这个循环叫事件循环，英文是 event loop 或 message loop。

事件驱动的意思是，程序大部分时间在等事件，有事件来了才动一下。这和前面几章那种“从上到下一口气跑完”的程序完全不同。

下图画出了这个过程。

<img class="lt-img-light" src="/content/images/ch00-fig04-gui-loop.svg" alt="图形界面的事件循环" />
<img class="lt-img-dark" src="/content/images/ch00-fig04-gui-loop-dark.svg" alt="图形界面的事件循环" />

事件循环的每一圈大致是这样。取出一条事件，找到目标控件，控件修改自己的状态，比如把按钮的文字改成“已确定”，然后请求重绘。等界面需要更新时，框架重新布局，再把控件画到屏幕上。队列为空的时候，循环会阻塞等待，不占 CPU。

下面是一段演示，它用一个普通队列模拟事件循环。这个演示没有窗口，却能说明同样的道理。它是第 0 章检查点程序的一部分。

```text
=== 一个最小的事件循环 ===
取出事件  鼠标点击 确定按钮
          重绘第 1 次
取出事件  键盘输入 a
          重绘第 2 次
取出事件  定时器 500 毫秒到了
          重绘第 3 次
取出事件  窗口关闭
循环结束，还有 1 个事件没处理，共重绘 3 次
```

注意最后一行。窗口关闭之后，循环就停下来了，队列里剩下的鼠标移动事件没有被处理。真实的框架在关闭窗口时也会做类似的收尾。

这里有一个初学者常踩的坑。界面控件通常只能在事件循环所在的线程里修改，英文叫 UI 线程。如果在后台线程里直接修改按钮的文字，程序可能崩溃，或者表现得很奇怪。正确做法是把修改的动作交还给界面线程，在 Avalonia 里用 `Dispatcher.UIThread.Post`。LogLens 的源码里就有这样的写法。

```csharp
Avalonia.Threading.Dispatcher.UIThread.Post(ApplyFilter);
```

这一行说的是，请把 `ApplyFilter` 排进界面线程的队列，等轮到它的时候再执行。第 23 章和第 24 章会反复用到这个模式。

### 布局，先问需要多大，再决定放在哪

界面不是靠坐标一个一个摆出来的。大多数框架使用布局系统，让容器决定子控件的位置和大小。

以一个很常见的界面为例。窗口里有一个停靠面板，上面是菜单，下面是状态栏，中间是网格。网格里又放着文本框、按钮和列表。它们组成一棵树，叫控件树。

下图是这棵树的样子，以及布局时的两趟遍历。

<img class="lt-img-light" src="/content/images/ch00-fig05-widget-tree.svg" alt="控件树与两趟布局" />
<img class="lt-img-dark" src="/content/images/ch00-fig05-widget-tree-dark.svg" alt="控件树与两趟布局" />

布局分两趟完成。第一趟是测量，从叶子节点开始，每个控件告诉父容器自己需要多大空间。第二趟是排列，从根节点往下走，父容器根据自己的空间，决定每个子控件放在哪里、占多大。全部确定之后，框架按树的顺序把控件画出来。

数据变化之后，框架通常不会整个重画，而是只重新测量和排列受影响的那一小片。这就是为什么界面上的一个文本变化，不会让整个窗口闪一下。

这种“控件树加属性”的做法，叫保留模式。控件是长期存在的对象，状态保存在对象里，框架负责记住哪部分需要更新。WPF 和 Avalonia 都是保留模式。

还有一种做法叫即时模式。它每一帧都从头描述整个界面，例如“画一个按钮，如果被点了就执行某段代码”，不保留控件对象。游戏调试界面常用这种做法，写起来快，但界面复杂之后，每一帧的开销会变大。

两种模式没有高下之分。桌面业务程序通常需要丰富的控件、复杂的输入法支持和无障碍功能，保留模式更适合。

### 声明式界面与 XAML

界面的描述有两种写法。一种是命令式，用代码一步步创建控件，设置属性，把它们加到容器里。另一种是声明式，用一种标记语言把界面的结构直接写出来，由框架负责创建对象。

XAML 是微软为 WPF 设计的声明式标记语言，它是 XML 的一种用法。Avalonia 沿用了 XAML 的思路，文件后缀是 `.axaml`。

下面是 LogLens 里一个真实的界面片段。它描述了一个文本框、一个下拉框和一个按钮。

```xml
<TextBox Width="260" PlaceholderText="按模板或样例搜索…" Text="{Binding SearchText}" />
<ComboBox ItemsSource="{Binding SortModes}" SelectedItem="{Binding SelectedSortMode}" Width="150" />
<Button Classes="ghost" Content="清除" Command="{Binding ClearFilterCommand}" />
```

这段代码没有写“创建一个按钮，把文字设成清除，然后绑定点击事件”之类的步骤。它只说明按钮长什么样、连到哪里。`{Binding ...}` 这种写法把界面和程序的数据连接起来，下一节讲它的原理。

### 数据绑定与 MVVM

界面要显示数据，程序要响应界面的操作，两边总得连起来。如果每个按钮都手动去更新一个文本框，代码很快就会变成一团。

数据绑定是框架提供的一种机制，让界面的某个属性自动跟随数据对象的某个属性。数据变了，界面自动更新。界面的输入变了，数据也跟着变。

MVVM 是围绕数据绑定组织代码的一种常见结构。它把程序分成三层。

View（视图）是 XAML 写的界面，只负责怎么显示。

ViewModel（视图模型）是界面需要的状态和命令，它不认识具体的控件，只保存数据和响应操作。

Model（模型）是业务数据和业务逻辑，例如日志条目和分析引擎，它完全不知道界面的存在。

<img class="lt-img-light" src="/content/images/ch00-fig06-mvvm.svg" alt="MVVM 三层的关系" />
<img class="lt-img-dark" src="/content/images/ch00-fig06-mvvm-dark.svg" alt="MVVM 三层的关系" />

这种分层的好处是，ViewModel 和 Model 可以脱离窗口单独测试。换一套界面，只需要重写 View，业务逻辑不用动。

LogLens 的 `ClustersView.axaml` 里，`Button` 的 `Command` 绑定到了 ViewModel 上的一个命令。这个命令就是普通的 C# 对象，可以像其他代码一样被测试。

### 样式、主题与资源

界面的外观不应该全部写死在每个控件上。框架提供了样式、模板和资源字典，让外观可以统一管理。

样式是一组属性的集合，例如“所有按钮的背景色是什么，字号多大”。模板决定控件内部长什么样，例如按钮是圆角还是直角。资源字典是一组可以按名字引用的值，例如颜色和字体。

主题决定整体的视觉风格。Avalonia 的 `FluentTheme` 是一套受微软 Fluent 设计语言启发的主题。应用可以跟随系统使用亮色或暗色，也可以强制指定。

下面是 `App.axaml` 里的一段内容。`RequestedThemeVariant="Default"` 的意思是跟随系统配色。

```xml
<Application.Styles>
    <FluentTheme />
</Application.Styles>
```

### 输入、焦点与无障碍

一个好用的界面，还要处理几件细小的事情。

焦点是指当前接收键盘输入的控件。按 Tab 键时，焦点应该按合理的顺序移动，而不是乱跳。

输入法对中文用户很重要。输入中文时，候选词窗口要跟着光标走，框架需要支持 IME。

无障碍是指让屏幕阅读器、键盘操作者和视力不好的用户也能使用界面。按钮要有可读的名字，颜色对比要够，所有功能都应该能用键盘完成。

国际化是指界面文字可以替换成其他语言。字符串放在资源文件里，而不是写死在代码中。

空状态是指列表没有数据时界面该怎么显示。好的程序会提示“还没有数据，请先导入日志”，而不是留一块空白。

这些内容初学时不必全部掌握。知道它们存在，遇到相关问题时知道去哪里找答案，就够了。

## 0.14 Avalonia 为什么轮到它

这本书后半程要做一个能在三个平台上运行的桌面程序。桌面界面的选择比服务端复杂，因为每个方案都带着自己的一段历史。

WPF 是微软 2006 年推出的 Windows 桌面框架，它用 XAML 描述界面，支持数据绑定、样式和模板。到今天它仍然是 Windows 上设计最成熟的桌面框架之一。它的局限写在名字里，只能在 Windows 上运行。

WinForms 更老，它的界面是拖控件、写事件，风格停留在上一个时代。

2013 年以后，Electron 流行起来。它把 Chromium 浏览器内核打包进程序，用网页技术写界面。代价是体积和内存占用，一个空窗口起步就要一百多兆，一个记事本大小的工具可能占用几百兆内存。

Qt 是 C++ 的老牌选择，性能和跨平台能力都很强，麻烦在授权条款和 C++ 的学习曲线。

还有一条路，是给 .NET 做一套跨平台的界面框架。Avalonia 走的就是这条路。2013 年底，史蒂文·柯克开始写一个实验项目，目标是做一个开源的、风格接近 WPF、又不受 Windows 限制的框架。那时它叫 Perspex。2015 年，XAML 支持接了进来，同年尼基塔·楚卡诺夫等人加入。2016 年 5 月 11 日，一次提交把项目改名为 Avalonia，原因是 Perspex 这个名字有商标风险。改名后三个月，0.4.0 版发布。2023 年 7 月发布 11.0，2026 年 4 月 7 日发布 12.0。LogLens 的桌面版使用 Avalonia 12.1.4，本书以这个版本为准。

### Avalonia 怎么画出界面

Avalonia 的基本做法是自己画。它不把按钮交给操作系统去画，而是在一层平台适配之上，自己实现一整套控件、布局、样式和数据绑定，再把结果画到窗口里。同一个界面在 Windows、macOS 和 Linux 上外观一致，不会出现左边是 Windows 原生按钮、右边是 Linux 原生按钮的情况。

按职责看，它大致分成下面几层。

| 层 | 做的事 |
| --- | --- |
| 平台层 | 创建窗口，接收鼠标和键盘的输入，再交给上层 |
| 绘制层 | 把每个控件的外形画到窗口上，各个系统上的绘制逻辑基本相同 |
| 控件与布局层 | 按钮、文本框、网格这些控件组合成界面树，第 [0.13 节](#s0-13)讲过的布局在这里完成 |
| 描述与绑定层 | XAML 用标记描述界面树，数据绑定把界面和数据连起来，样式决定外观 |

这种做法的优点是外观统一。代价是每个细节都要框架自己负责，框架成熟到什么程度，直接决定使用体验。选择 Avalonia 时，这一点要放在心上。

### Avalonia 与 WPF 的关系

XAML 和绑定模型沿袭 WPF，所以熟悉 WPF 的人上手很快，很多概念可以直接搬过来。不同之处在于，Avalonia 不依赖 Windows，它的控件名字和属性大多相近，但并不完全一致，从 WPF 迁移时要逐个核对。

### 它适合什么，不适合什么

如果你只发布 Windows，WPF 更成熟，工具也更全。如果界面以网页内容为主，Electron 的生态更省事。Avalonia 的甜区是这样一类项目，同一套桌面程序要发布到三个平台，团队会 C#，界面复杂度达到中等以上。本书的项目正落在这里。

### 本书怎么用它

第 22 章才会创建第一个 Avalonia 窗口，那时再看项目文件、入口代码和界面描述文件。现在只需要记住三件事。Avalonia 自己绘制界面，界面用 XAML 描述，界面和数据通过绑定连接。

## 0.15 这本书要做的程序

学了这些东西，总得有个去处。这本书的主线项目叫 LogLens，一个本地日志分析工具。

服务器上积累了几百兆日志，几十万行，人眼看不过来。哪个时段出过事？错误有几种？哪些是同一个毛病在反复刷屏？这次发布比上次好还是差？这些问题用 `grep` 也能凑出答案，但费时间，还容易漏。

LogLens 把答案整理成一眼能看懂的几样东西，包括级别分布、流量趋势、尖峰时段、问题模板排行，以及一个 0 到 100 的健康分。最后还能导出成可以贴进周报的 Markdown。项目分成三块。

```text
LogLens.Core     解析与分析引擎，纯逻辑，不认识界面
LogLens.Cli      命令行外壳，在终端里使用
LogLens.Studio   桌面界面，Avalonia 加 MVVM，用鼠标操作
```

整个仓库有 151 个 C# 文件，15 个 XAML 文件，合计 19,604 行。

这个项目适合做教材，理由有四条。它是你以后真的会遇到的问题，比如线上排查、发布前对比、给同事看结论。三块代码层次分得开，文本处理、统计、界面各自都能单独跑起来。它的覆盖面够宽，从 `int` 到异步流，从 `if` 到自绘图表，都有落脚点。规模也合适，大到能体现工程结构，小到一周能摸清主干。

这本书不会一上来就讲它的架构。你会先写小段程序，遇到需要结构的地方再回头加结构。第 16 章会把这个过程完整走一遍，那也是从“会写语法”到“会写程序”的分界线。

## 0.16 装 SDK 之一，包管理器

<img class="lt-img-light" src="/content/images/ch00-fig07-install-flow.svg" alt="安装路线的决策流程" />
<img class="lt-img-dark" src="/content/images/ch00-fig07-install-flow-dark.svg" alt="安装路线的决策流程" />

安装 .NET SDK 有四条路。前两条属于包管理器和官网安装包，后两条是安装脚本和压缩包。这一节讲包管理器。

包管理器是操作系统自带或者社区维护的软件安装工具。它记录软件的来源和版本，安装、升级、卸载都用一条命令完成。如果你的电脑上有包管理器，这通常是最省事的方式。

<!--tab pkg Windows-->

先说 Windows。Windows 自带的包管理器叫 winget。打开命令提示符（cmd）或者 Windows 终端，输入下面这条命令。

```bat
winget install --id Microsoft.DotNet.SDK.10 --exact
```

`--id` 指定包的名字，`--exact` 要求名字完全匹配，防止装到名字相似的其他东西。winget 会弹出确认提示，按要求同意即可。

如果你想固定某个版本，可以加上 `--version 10.0.403` 这样的参数。以后升级用 `winget upgrade --id Microsoft.DotNet.SDK.10 --exact`。

如果你的 Windows 上提示找不到 `winget`，说明系统里没有装 App Installer。打开 Microsoft Store，搜索 App Installer 并安装或更新即可。

<!--tab pkg macOS-->

再说 macOS。macOS 上常用的包管理器是 Homebrew，安装方法写在它的官网 [brew.sh](https://brew.sh) 首页上。装好之后执行下面这条命令。

```bash
brew install --cask dotnet-sdk
```

`--cask` 的意思是安装图形化的应用程序或者带安装器的软件，而不是命令行工具。Homebrew 的公开页面显示，当前的 `dotnet-sdk` 版本是 10.0.403，支持 macOS 12 及以上版本。

<!--tab pkg Linux-->

然后是 Linux。不同发行版的做法不同。下面以 Debian 13 为例。微软的软件源需要先登记一次，然后才能用 apt 安装。

```bash
wget https://packages.microsoft.com/config/debian/13/packages-microsoft-prod.deb -O packages-microsoft-prod.deb
sudo dpkg -i packages-microsoft-prod.deb
rm packages-microsoft-prod.deb
sudo apt-get update
sudo apt-get install -y dotnet-sdk-10.0
```

第一行下载的是一个配置包，它把微软的软件源加到系统里。第二行安装它。第三行删除下载下来的临时文件。第四行刷新软件列表，第五行装上 SDK。

Ubuntu 的情况略有不同。Canonical 官方仓库在 Ubuntu 24.04 LTS 及之后的版本中已经包含 .NET 10，因此不需要额外登记软件源，直接安装即可。

```bash
sudo apt-get update
sudo apt-get install -y dotnet-sdk-10.0
```

有一点要提前说。有些 Linux 发行版只提供 snap 形式的安装包。它能用，但微软自己也提醒，`dotnet tool` 和 `dotnet watch` 这类功能在 snap 下经常出问题。如果你要长期做开发，优先选 apt、dnf 或者安装脚本。

其他发行版，例如 Fedora、Arch，各自有对应的包名和步骤，建议直接查阅微软的官方安装文档 [learn.microsoft.com/dotnet/core/install](https://learn.microsoft.com/dotnet/core/install)。文档会按发行版列出完整命令，比记别人的博客靠谱。

<!--tab-end pkg-->

包管理器装好之后，可以用 `dotnet --list-sdks` 确认版本。第 [0.19 节](#s0-19)会讲验证的完整流程。

## 0.17 装 SDK 之二，官网安装包、安装脚本与压缩包

包管理器不是每台机器都有，有时它的版本也落后于官网。这时可以走后面三条路。

### 官网安装包

打开 [dotnet.microsoft.com/download/dotnet/10.0](https://dotnet.microsoft.com/download/dotnet/10.0)，页面会列出 .NET 10 的各种下载项。注意要选 SDK，不要选 Runtime。SDK 包含编译器和运行时，只用来运行别人编译好的程序的人才只需要运行时。

<!--tab setup Windows-->

Windows 上下载 `.exe` 安装包，双击运行，按提示一路下一步即可。默认安装位置是 `C:\Program Files\dotnet`。页面的 Binaries 区域还提供压缩包形式，Windows 上是 `.zip`，后面的压缩包一节会讲它的用法。

<!--tab setup macOS-->

macOS 上下载 `.pkg` 安装包，双击运行，按照安装器的提示完成。

<!--tab setup Linux-->

Linux 上可以下载 `.tar.gz` 压缩包，手动解压，这在后面的离线部署里会用到。

<!--tab-end setup-->

安装完成后，打开一个新的终端窗口，再执行版本检查。新开窗口是因为旧窗口的环境变量不会自动刷新，这是第一次安装时最常见的困惑之一。

### 安装脚本

微软提供了一个安装脚本，在 Linux 和 macOS 上叫 `dotnet-install.sh`，在 Windows 上叫 `dotnet-install.ps1`。它的好处是可以指定版本、安装目录，也不依赖包管理器。

<!--tab script Windows-->

Windows 上在 cmd 里运行下面两条命令。第一行下载脚本，第二行调用它。Windows 的脚本扩展名是 `.ps1`，在 cmd 里用 `powershell` 命令就能直接调用，不需要另外打开别的窗口。`-DryRun` 表示预演，只打印将要下载的地址，不做安装，适合先看一眼。

```bat
curl.exe -sSL https://dot.net/v1/dotnet-install.ps1 -o dotnet-install.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File dotnet-install.ps1 -Channel 10.0 -DryRun
```

<!--tab script Linux,macOS-->

Linux 和 macOS 上使用 shell 脚本，命令如下。

```bash
curl -sSL https://dot.net/v1/dotnet-install.sh -o dotnet-install.sh
bash dotnet-install.sh --channel 10.0 --dry-run
```

以 Linux 为例，预演的输出大致如下。文件名和用户目录因机器而异。

```text
dotnet-install: Payload URLs:
dotnet-install: URL #0 - aka.ms: https://builds.dotnet.microsoft.com/dotnet/Sdk/10.0.403/dotnet-sdk-10.0.403-linux-x64.tar.gz
dotnet-install: Repeatable invocation: ./dotnet-install.sh --version "10.0.403" --install-dir "/home/user/.dotnet" --architecture "x64" --os "linux"
```

这里能看到三件事。脚本选中的是 `10.0.403` 版本的 Linux x64 压缩包，它的下载地址就在输出里。默认安装目录是用户主目录下的 `.dotnet`，Windows 上默认是 `%LocalAppData%\Microsoft\dotnet`。最后一行给出了可以重复执行的完整命令，方便以后复制。

<!--tab-end script-->

去掉预演参数再执行，就会下载并安装。常用的参数如下。

| 作用 | Linux 与 macOS（shell 脚本） | Windows（ps1 脚本，在 cmd 中调用） |
| --- | --- | --- |
| 安装 10.0 系列的最新版本 | `--channel 10.0` | `-Channel 10.0` |
| 安装指定的精确版本 | `--version 10.0.403` | `-Version 10.0.403` |
| 指定安装目录 | `--install-dir 路径` | `-InstallDir 路径` |
| 只安装运行时，不装 SDK | `--runtime dotnet` | `-Runtime dotnet` |
| 安装后不修改 PATH | `--no-path` | `-NoPath` |
| 只显示下载地址，不安装 | `--dry-run` | `-DryRun` |
| 把压缩包保存到指定位置 | `--zip-path 路径` | `-ZipPath 路径` |
| 安装完成后保留压缩包 | `--keep-zip` | `-KeepZip` |
| 指定 CPU 架构，例如 x64 或 arm64 | `--architecture x64` | `-Architecture x64` |
| 指定操作系统 | `--os linux` | 不需要 |

脚本安装完之后，它会提示你把安装目录加进 PATH。PATH 的设置方法在下面的压缩包一节讲过，第 [0.19 节](#s0-19)会讲如何验证。

### 压缩包

压缩包是最朴素的一种安装方式。它只是一包文件，解压到一个目录里，就算装好了。它也是离线部署最常用的形式，因为它不需要任何包管理器和网络。

<!--tab zip Linux-->

Linux 上先下载压缩包，再解压到固定目录，然后设置两个环境变量。

```bash
mkdir -p "$HOME/.dotnet"
tar -zxf dotnet-sdk-10.0.403-linux-x64.tar.gz -C "$HOME/.dotnet"
export DOTNET_ROOT="$HOME/.dotnet"
export PATH="$DOTNET_ROOT:$PATH"
```

<!--tab zip Windows-->

Windows 上在 cmd 里执行下面的命令。压缩包可以放在任意位置，下面以 `C:\dotnet` 为目标目录。

```bat
mkdir C:\dotnet
tar -xf dotnet-sdk-10.0.403-win-x64.zip -C C:\dotnet
set DOTNET_ROOT=C:\dotnet
set PATH=C:\dotnet;%PATH%
```

Windows 10 及之后的系统自带 `tar` 命令，它能解压 `.zip`。也可以在资源管理器里右键压缩包，选择解压，效果相同。

<!--tab-end zip-->

解压之后，目录里有 `dotnet` 可执行文件、`sdk`、`shared` 等子目录。压缩包本身不会修改系统设置，所以要告诉系统去哪里找它。`DOTNET_ROOT` 告诉 `dotnet` 它自己在哪里，`PATH` 告诉终端去哪里找 `dotnet` 命令。

上面的 `export` 和 `set` 只对当前终端窗口有效。要长期生效，Linux 和 macOS 需要把它们写进 `~/.bashrc` 或 `~/.zshrc`。Windows 则在开始菜单搜索“环境变量”，打开后在用户变量里新建 `DOTNET_ROOT`，并在 `Path` 里加入 `C:\dotnet`，然后重新打开终端。不建议用 `setx` 去改 `PATH`，它会截断过长的路径。

解压之后，SDK 不依赖系统里已经装好的 .NET。只要 `DOTNET_ROOT` 和 `PATH` 指向这个目录，运行 `dotnet --list-sdks` 时，列出的就是这个目录里的 SDK。同时运行 `dotnet --list-runtimes`，可以看到它自带的 ASP.NET Core 和 .NET 运行时。方括号里是各自所在的目录，路径因解压位置而异。

## 0.18 装编辑器与 IDE

前面装的 SDK 是编译和运行程序的工具，它不带编辑界面。写代码需要一个编辑器，有的编辑器功能很全，称为 IDE，即集成开发环境。它们通常能补全代码、跳转到定义、显示错误、调试程序。

本书的代码不依赖某个编辑器，三种都能用。下面分别说明怎么下载和安装，最后再给一个选择建议。

### Visual Studio Code

VS Code 是微软出品的轻量编辑器，免费，跨平台。它本身是编辑器，靠扩展才能支持 C#，所以严格说不算完整的 IDE。

打开 [code.visualstudio.com](https://code.visualstudio.com)，根据系统下载对应的安装包。Windows 下是一个 `.exe` 安装器，macOS 下是一个 `.zip` 压缩包，解压后把应用拖进“应用程序”文件夹即可。Linux 下可以选 `.deb`、`.rpm` 或 `.tar.gz`，`.deb` 适用于 Debian 和 Ubuntu。

装好之后，要给 VS Code 装两个扩展。第一个是 C# Dev Kit，由微软发布，提供 C# 的代码补全、调试和项目管理。第二个是 Avalonia 扩展，用来编辑 `.axaml` 文件。

装 C# Dev Kit 的步骤如下。打开 VS Code，按 Ctrl+Shift+X（macOS 上是 Cmd+Shift+X）打开扩展面板，搜索 `C# Dev Kit`，点击安装。它会同时带上 C# 语言支持。

装 Avalonia 扩展时，搜索 `Avalonia`，找到发布者为 Avalonia Team 的 `Avalonia for VSCode`，点击安装。需要注意的是，Avalonia 官方仓库说明，这个扩展已经并入 Avalonia Pro 产品。安装之前请到扩展市场页面看一下当前的授权条款和功能范围，再决定是否使用。

也可以用命令行安装扩展，适合在脚本里批量处理。Windows 的 cmd 和 Linux、macOS 的终端都可以直接使用下面这条命令。

```bash
code --install-extension ms-dotnettools.csdevkit
```

这条命令假设 `code` 命令已经在 PATH 里。VS Code 的命令面板里有一个“在 PATH 中安装 'code' 命令”的选项，可以帮你设置它。

### Visual Studio

Visual Studio 是微软的完整 IDE，只在 Windows 和 macOS 上提供，功能最全，调试器和性能分析工具最成熟。2025 年 11 月 11 日，Visual Studio 2026 与 .NET 10 同时正式发布。

打开 [visualstudio.com](https://visualstudio.com)，下载 Community 版本。社区版对个人学习、开源项目和小团队免费，具体条款以官网页面为准。下载的是一个引导程序，名为 `vs_community.exe`，双击运行后会打开 Visual Studio Installer。

在 Installer 里选择“.NET 桌面开发”工作负载，它包含了 WPF、WinForms 以及 .NET 桌面程序需要的工具。勾选之后点击安装，等待下载完成。

装好 Visual Studio 之后，可以在扩展市场里搜索 Avalonia，安装名为 Avalonia for Visual Studio 的扩展。Avalonia 官方文档说明，这个扩展会自动带上 Avalonia 的项目模板，所以不需要再手动执行 `dotnet new install`。

### JetBrains Rider

Rider 是 JetBrains 公司出品的跨平台 .NET IDE，支持 Windows、macOS 和 Linux。它的代码分析和重构能力很强，Avalonia 官方网站也把它列为推荐的开发环境之一。

Rider 的授权方式要先看清。JetBrains 官网说明，Rider 对非商业用途免费，包括学习、开源贡献和个人内容创作。如果用于商业项目，需要购买订阅。

下载地址是 [jetbrains.com/rider](https://jetbrains.com/rider)。页面会根据系统推荐对应的安装包。Windows 下载 `.exe`，macOS 下载对应芯片的 `.dmg`，Linux 下载 `.tar.gz`。也可以使用 JetBrains Toolbox，它是一个统一管理 JetBrains 产品的小工具，适合同时用多款 JetBrains 软件的人。

Linux 上下载的是 `.tar.gz` 压缩包，解压到一个目录里，进入其中的 `bin` 子目录，运行 `rider.sh` 即可启动。压缩包内的目录名会随版本变化，具体以解压出来的内容为准。

第一次启动时，Rider 会让你选择主题、登录或者以试用模式开始。选择非商业用途即可。

Avalonia 官方文档在 IDE 设置页里给出了 Rider 的配置说明，安装完成后照着做一遍即可。

### 怎么选

| 情况 | 建议 |
| --- | --- |
| 想要轻量、跨平台，习惯用一个编辑器写各种语言 | VS Code 加 C# Dev Kit |
| 在 Windows 上做 .NET 开发，希望功能最全、调试最方便 | Visual Studio |
| 跨平台开发，想要重构和分析能力强，能接受非商业免费的条款 | Rider |
| 在没有图形界面的服务器上开发 | 终端加任意编辑器，例如 `nano` 或 `vim` |

本书的所有章节都可以只用终端完成。编辑器只是让你写得更舒服。

上面三款 IDE 的安装步骤，是根据官方文档和当前的下载页面整理的。界面的按钮位置会随版本变化，遇到不一致的情况，以官网最新页面为准。

## 0.19 第一次运行与常见失败

装好之后，按顺序做三件事。先确认命令能用，再跑一个最小的程序，最后看一下常见失败的症状，以便出问题时能对号入座。

第一件事是版本检查。打开命令提示符（cmd）或者终端，输入下面两条命令。

```text
dotnet --version
dotnet --list-sdks
```

`dotnet --version` 应该输出 `10.0.403` 或者类似的 10.0.x 版本号。`dotnet --list-sdks` 列出所有已安装的 SDK，每一行的格式是版本号加方括号里的安装路径。

如果 `dotnet --list-sdks` 什么也不输出，说明装的是运行时，或者 SDK 没有装上。这时候回去检查安装步骤。

第二件事是单文件运行。.NET 10 支持直接运行一个 `.cs` 文件，不需要先建项目。新建一个文件夹，用记事本、VS Code 或者任何纯文本编辑器新建 `hello.cs`，内容如下。

```csharp
var name = Environment.UserName;
Console.WriteLine($"你好，{name}。这是 .NET {Environment.Version} 上的一个单文件程序。");
```

保存之后，在这个文件夹里运行下面的命令。Windows 的 cmd 和 Linux、macOS 的终端都是同样的写法。

```text
dotnet run hello.cs
```

在一台 Linux 机器上，输出大致如下。用户名和版本号因机器而异。

```text
你好，user。这是 .NET 10.0.14 上的一个单文件程序。
```

第一次运行大约需要几秒钟，因为要做一次编译。以后再运行同一个文件会快很多。

第三件事是看一下 `dotnet --info`。这条命令会列出 SDK、运行时、操作系统和 RID 的完整信息。遇到问题时，把它的输出贴出来，通常能很快定位原因。

上面提到的 RID 是运行时标识符。它的格式是操作系统加架构，例如 `linux-x64` 表示 Linux 系统加 x64 架构，`win-x64` 表示 Windows 加 x64，`osx-arm64` 表示苹果芯片的 Mac。后面做发布时，它还会出现在输出目录的名字里。

常见失败的症状和解决方法如下。

| 你看到的 | 原因 | 怎么修 |
| --- | --- | --- |
| `dotnet: command not found` 或者“不是内部或外部命令” | 装好了，但安装目录不在 PATH 里 | 关闭终端重新打开；仍然不行就手动把安装目录加入 PATH |
| `dotnet --list-sdks` 为空 | 只装了运行时，没有装 SDK | 重新安装 SDK，不要选 Runtime |
| `NETSDK1045` 之类的错误，提示需要更高版本 | 装的是旧版本 SDK | 安装 10.0，然后用 `dotnet --list-sdks` 确认 |
| 包下载一直失败，超时 | 网络或代理问题 | 检查代理设置；用 `dotnet nuget list source` 查看当前的包源 |
| 构建报磁盘空间不够（Linux 上是 `No space left on device`） | 磁盘空间不够，包括临时目录 | 清理磁盘，或者换一个有足够空间的临时目录 |
| 路径里有中文或空格，个别工具报错 | 部分工具对非 ASCII 路径处理不好 | 把项目放在纯英文且较短的路径下，例如 `~/code` 或 `C:\code` |

最后两行值得多说几句。临时目录的空间也可能不够。有些 Linux 系统把 `/tmp` 挂载成内存盘，空间只有几百 MB 到一 GB 左右。SDK 压缩包和构建产物都很大，构建到一半时会报磁盘空间的错误，看起来像程序出了问题，实际是磁盘满了。清理空间，或者把项目放到空间充足的目录，就能解决。Linux 上可以用 `df -h` 查看磁盘使用情况，Windows 上可以在资源管理器里查看各个盘的剩余空间。

## 0.20 离线部署

有些场景下，目标电脑不能联网。例如实验室的隔离网络、工厂的生产线控制机、客户的内网环境。这时候，所有的东西都要提前在能联网的机器上准备好，拷过去之后再安装。这就是离线部署。

离线部署需要备的东西分成四类。

第一类是 SDK。使用压缩包或者官网下载的安装包，它们都是独立文件，可以直接拷贝。

第二类是编辑器和 IDE。VS Code 的安装包和需要的 `.vsix` 扩展文件，Rider 的 `.tar.gz`，Visual Studio 的离线布局，它们都能提前下载。

第三类是 NuGet 包。这是 .NET 的第三方库，你的项目用到的所有包都要带上。这一类最容易漏，后面详细讲。

第四类是模板。Avalonia 项目模板也是 NuGet 包，需要一并准备。

备货完成之后，按照下面的顺序在离线机器上安装。

先把 SDK 解压到固定目录，再设置 `DOTNET_ROOT` 和 PATH，然后用 `dotnet --list-sdks` 确认。接着设置本地的 NuGet 源，让还原操作只读本地文件夹。最后执行 `dotnet build`，构建通过就说明整个链条是通的。

<img class="lt-img-light" src="/content/images/ch00-fig08-offline.svg" alt="离线部署的流程" />
<img class="lt-img-dark" src="/content/images/ch00-fig08-offline-dark.svg" alt="离线部署的流程" />

下面说几种离线备货的具体做法。

Visual Studio 没有提供完整的离线安装包，而是提供一种叫 layout 的离线布局。在能联网的机器上，用引导程序加 `--layout` 参数，把指定的工作负载下载到一个文件夹里。之后把这个文件夹拷到离线机器上，用同一个引导程序加 `--noWeb` 参数安装。下面是示意的命令，`vs_community.exe` 对应 Community 版，专业版则换成 `vs_professional.exe`。

```text
vs_community.exe --layout C:\VSLayout --add Microsoft.VisualStudio.Workload.ManagedDesktop --lang en-US
```

离线机器上的安装命令示意如下。

```text
C:\VSLayout\vs_community.exe --noWeb --add Microsoft.VisualStudio.Workload.ManagedDesktop
```

`--noWeb` 很重要。没有它，引导程序在找不到某个组件时，会悄悄去联网下载，违背了离线的初衷。备货时选的工作负载要和安装时一致。布局的体积相当大，需要预留足够的磁盘空间，具体大小视选择的组件和语言而定。

VS Code 的扩展可以先在联网机器上下载成 `.vsix` 文件，再拷到离线机器上安装。Windows 上路径写成 `D:\offline\csharp-dev-kit.vsix` 这样即可。

```bash
code --install-extension /path/to/csharp-dev-kit.vsix
```

Rider 的 `.tar.gz` 压缩包解压即可使用，和前面 SDK 的做法一样。

NuGet 包的离线方案要多花一点力气。NuGet 把下载下来的包保存在一个全局目录里，可以用下面的命令查看位置。

```text
dotnet nuget locals all --list
```

以 Linux 为例，输出的内容类似下面这样。Windows 上 `global-packages` 通常位于 `%USERPROFILE%\.nuget\packages`。

```text
http-cache: /home/user/.local/share/NuGet/http-cache
global-packages: /home/user/.nuget/packages/
temp: /tmp/NuGetScratchuser
plugins-cache: /home/user/.local/share/NuGet/plugin-cache
```

其中 `global-packages` 就是包的全局目录。每个包的目录里都有一个 `.nupkg` 文件，那就是包本体。离线方案的核心，就是把这些 `.nupkg` 收集到一个文件夹里，让 NuGet 把这个文件夹当作包源。

以一个只有 Avalonia 的小项目为例，全局目录里的 `.nupkg` 文件有 40 个左右，约 400 MB。第一步，把这些文件复制到一个新文件夹。第二步，写一个 NuGet 配置文件，只保留这个本地文件夹作为包源。Windows 上把路径换成 `D:\offline\feed` 这样的形式即可。

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="offline-feed" value="/path/to/offline-feed" />
  </packageSources>
</configuration>
```

`<clear />` 清空了默认的 [nuget.org](https://nuget.org) 源，这样还原时不会尝试联网。第三步，把 NuGet 的全局缓存目录指向一个空目录，确保它不会用到原来已经下载的包。第四步，在项目目录里执行还原。Linux 和 macOS 用环境变量的前缀写法。

<!--tab restore Linux,macOS-->

```bash
NUGET_PACKAGES=/path/to/empty-cache dotnet restore --configfile /path/to/NuGet.Config
```

<!--tab restore Windows-->

Windows 的 cmd 里分两行写。

```bat
set NUGET_PACKAGES=D:\offline\empty-cache
dotnet restore --configfile D:\offline\NuGet.Config
```

<!--tab-end restore-->

还原成功时，输出的关键一行形如下面这样。耗时取决于机器。

```text
Restored /path/to/AvaDemo.csproj (in 4.59 sec).
```

空缓存加本地文件夹，足以完成还原。最后执行 `dotnet build --no-restore`，它跳过网络还原，直接编译，输出的结果是 `0 Error(s)`，也就是没有错误。

需要说明的是，这个例子只有 Avalonia 一个依赖，依赖关系完整地来自它本身。实际项目的依赖可能更多，备货时要确保依赖的完整闭包都在文件夹里。最稳妥的做法，是在能联网的同一台机器上，清空缓存后完整还原一次，再把得到的文件夹整体拷过去。

离线的 Avalonia 模板还需要单独处理。模板包也是一个 `.nupkg`，安装的时候指向那个文件即可。这一步目前只给出思路，具体命令以 `dotnet new install --help` 的输出为准。

离线部署里最容易出错的是版本不一致。备货时用的 SDK 版本、NuGet 包版本、IDE 版本，最好都在同一天、同一台机器上确定，然后整套打包。混着用不同日期下载的东西，常常会在最后一步出现奇怪的版本冲突。

## 0.21 这本书的用法

每一章都配一个能独立运行的项目，放在 `tutorial/code/` 下面，目录名和章号对应。运行方法是进入目录，执行 `dotnet run`。界面章节要加上 `verify` 参数，以无界面的方式运行，不弹出窗口，也能验证代码是否正确。

<!--tab cd Linux,macOS-->

```bash
cd tutorial/code/ch00-origins
dotnet run
```

<!--tab cd Windows-->

Windows 的 cmd 中，路径改用反斜杠，例如 `cd tutorial\code\ch00-origins`，后面的 `dotnet run` 相同。

<!--tab-end cd-->

第 0 章的这个项目把本章的几个实验放在一起。运行一次，能同时看到运行时信息、两个方法的 IL 字节、GC 前后的堆大小，以及事件循环的演示。后面每一章都有这样一个目录，可以直接运行，也可以改了再运行。

正文里的输出都对应章节里的项目。你的机器上，用户名、路径和版本号可能不同，以你看到的为准。

遇到报错时，顺序是这样的。先把报错信息完整读一遍，编译器通常已经告诉你哪一行、哪个名字有问题。然后去附录 A 按错误码查。如果查不到，就把代码缩小，删到只剩触发错误的那几行。这一步能解决大部分问题，因为剩下的少数问题，往往藏在被删掉的那部分里。

最后一条建议。不要只是抄代码，要改成你自己的东西。每章的练习都是为此设计的。改动越小越好，哪怕只是把变量名换成你熟悉的词，理解也会比复制粘贴深一层。

## 0.22 自测与练习

先合上书，凭记忆回答。答不出来的，再翻回去看。

1. 存储程序这个想法解决了什么具体问题？为什么它比“程序写在纸带上”更重要？
2. 汇编语言解决了一个问题，又留下了一个问题。分别是哪两个？
3. IL 是什么？它和机器码相差哪一步？JIT 在这中间起什么作用？
4. `02 03 58 2A` 这四个字节执行完之后，计算栈上剩下什么？
5. 内存里的栈和堆各自放什么？为什么 `new` 出来的对象要放在堆上？
6. 垃圾回收器是怎么判断一个对象可以清理的？它的代价是什么？
7. .NET 的四个主要组成部分是什么？SDK 和运行时分别给谁用？
8. .NET Framework 和 .NET 最实际的区别是什么？看到项目文件里的 `net48`，为什么要小心？
9. 图形界面的事件循环每一圈做哪几件事？为什么界面控件通常只能在 UI 线程里修改？
10. 布局为什么要分测量和排列两趟？数据变化之后，框架为什么不整个重画？
11. MVVM 的三层分别是什么？为什么说 ViewModel 不认识控件，是一件好事？
12. 离线部署时，NuGet 包为什么不能只带项目源码，而要带 `.nupkg` 文件？

四个练习，动手做比读三遍有用。

练习一，去 `dotnet --info` 的输出里找到 RID，再查一下它对应的操作系统和架构。如果你用的是苹果芯片的 Mac，看看输出里的 `osx-arm64` 和你在 Windows 上见过的 `win-x64` 有什么不同。

练习二，把第 0 章 GC 实验里的循环次数改成两百万，再运行一次，记下托管堆的大小和回收次数。对比两次的数字，说说 GC 是怎样跟上你的分配速度的。

练习三，在 `Program.cs` 里再加一个方法 `Multiply` 的 IL 对比。你会发现前两个字节和 `Add` 一样，只有第三个字节从 `58` 变成了 `5A`。解释一下，为什么参数的读取指令没有变，而运算指令变了。

练习四，修改事件循环的演示。把“窗口关闭”事件放在队列的最后，然后运行。预测一下输出的最后一行会是什么，再运行验证。接着把“窗口关闭”放到第一个位置，再预测一次。对比两次的结果，说明事件的先后顺序对程序行为有什么影响。

最后留一句。这一章你一行 C# 语法都没有学，但按下回车之后那四秒钟里发生了什么，你现在可以一段一段讲清楚了。接下来[第 1 章](/chapter/01)开始写代码，前面那些模糊的地方，会在代码里慢慢变得具体。
