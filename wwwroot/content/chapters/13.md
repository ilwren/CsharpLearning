## 13.1 什么是线程

先区分两个场景。

- **一个人做多件事**，你一边煮饭，一边洗衣服。锅在烧的时候你不用盯着它，去洗衣服就行。这就是异步（[第 12 章](/chapter/12)），一个执行路径，在等待的时候让出去。
- **多个人同时做事**，你和朋友一起做饭，一个切菜，一个炒菜。两件事真的在同一时刻进行。这就是多线程。

**线程**是操作系统分配 CPU 时间的基本单位。一个程序可以有多个线程，它们共享同一块内存（同一个进程里的数据），各自有独立的执行位置。操作系统决定哪个线程在哪个 CPU 核心上运行，程序员无法精确控制它的先后顺序。

这一点很重要，**线程的先后顺序是不确定的。** 你写下的代码顺序，只是一种"可能的执行顺序"，并不保证实际运行时就是这个顺序。后面几节的很多问题，都来自这一点。

## 13.2 `Thread` 类

直接创建线程，用 `Thread` 类。

```csharp
Console.WriteLine($"  主线程 ID = {Environment.CurrentManagedThreadId}（数字因机器而异）");
var worker = new Thread(() => Console.WriteLine($"  子线程 ID = {Environment.CurrentManagedThreadId}"));
worker.Start();
worker.Join();
Console.WriteLine("  子线程已结束（Join 返回）");
```

运行结果（节选）。

```text
  主线程 ID = 1（数字因机器而异）
  子线程 ID = 4
  子线程已结束（Join 返回）
```

三个方法各管一件事。

- `new Thread(...)`，创建线程，传入要执行的代码。此时线程还没有开始。
- `Start()`，让线程开始执行。
- `Join()`，等待这个线程结束。调用 `Join()` 的线程会停在这里，直到目标线程完成。

`Join()` 是"汇合"，它保证"子线程已结束"这句话一定在子线程的工作完成之后输出。

**前台线程与后台线程。** `Thread` 有一个属性 `IsBackground`。默认是 `false`，也就是前台线程。前台线程没有结束时，进程不会退出。把它设为 `true`，就成了后台线程，主线程结束后，后台线程会被直接终止。

检查点用一个参数来演示这一点，运行 `dotnet run` 后面加参数 `background`。

```csharp
var background = new Thread(() =>
{
    Thread.Sleep(2000);
    Console.WriteLine("后台线程：结束（这一行不会出现）");
})
{
    IsBackground = true
};
background.Start();
Thread.Sleep(100);
Console.WriteLine("主线程：即将结束，后台线程还在运行");
```

运行结果。

```text
== 13.2 后台线程 ==
主线程：即将结束，后台线程还在运行
```

后台线程要睡 2 秒，但程序在 100 毫秒后就结束了，那一行"结束"从未输出。后台线程随进程一起被终止，没有机会收尾。所以，**不要把重要的写文件或清理工作放在后台线程里**，除非你接受它随时被中断。

## 13.3 线程的代价

创建线程不是免费的。它要向操作系统申请资源，要占用内存（每个线程都有自己的栈），切换执行时也要花时间。线程数量不是越多越好。

检查点做了一个粗略的对比，创建并结束 500 个线程，和投递 500 个 `Task.Run`。

```csharp
var sw = Stopwatch.StartNew();
var threads = Enumerable.Range(0, 500).Select(_ => new Thread(() => { })).ToList();
threads.ForEach(t => t.Start());
threads.ForEach(t => t.Join());
Console.WriteLine($"创建并结束 500 个线程：约 {sw.ElapsedMilliseconds} ms（只作参考）");

sw.Restart();
var tasks = Enumerable.Range(0, 500).Select(_ => Task.Run(() => { })).ToArray();
Task.WaitAll(tasks);
Console.WriteLine($"投递 500 个 Task.Run：约 {sw.ElapsedMilliseconds} ms（只作参考）");
```

运行结果（节选，同一次运行）。

```text
创建并结束 500 个线程：约 83 ms（只作参考）
投递 500 个 Task.Run：约 7 ms（只作参考）
```

这个对比只说明一个趋势，每次都新建线程，比复用已有线程要慢。数字取决于机器，只能作参考。这也解释了为什么 .NET 提供了线程池（下一节）。

## 13.4 线程池

**线程池**是系统预先准备好的一组工作线程。任务来了就分给空闲的线程；任务做完，线程不销毁，留着下次用。这样就省去了反复创建线程的成本。

`Task.Run` 默认使用线程池。你平时写的大多数并行代码，实际上都跑在线程池上。

检查点用 `ThreadPool` 类查看线程池的状态。

```csharp
ThreadPool.GetMinThreads(out var minWorker, out _);
ThreadPool.GetAvailableThreads(out var availWorker, out _);
Console.WriteLine($"ProcessorCount = {Environment.ProcessorCount}（数字因机器而异）");
Console.WriteLine($"线程池最小工作线程数 = {minWorker}，当前可用 = {availWorker}");
```

运行结果（本机）。

```text
ProcessorCount = 2（数字因机器而异）
线程池最小工作线程数 = 2，当前可用 = 32767
```

这里有两个数字需要解释。

- `GetMinThreads` 返回的是线程池一开始就准备好的最小工作线程数，本机与核心数相同，为 2。
- `GetAvailableThreads` 返回的是"最大线程数减去当前正在活动的线程数"，本机的最大值较大，所以显示为 32767。**这个数字不表示你可以同时跑这么多任务。** 线程池不会一下子开出这么多线程，它会根据需要逐步增加，下一节会看到这一点。

`ProcessorCount` 是逻辑核心数。它是讨论并行时最常用的参考值，第 [13.11 节](#s13-11)会用到。

## 13.5 线程饥饿

线程池线程是有限的。如果一个线程池线程什么也不做，只是在那里**阻塞**（`Thread.Sleep`、`.Result`、`.Wait()`），它就占着这个线程，别的任务只能排队等。线程池发现排队的任务多了，才会慢慢增加线程，这个过程不会很快。这种现象叫**线程饥饿**。

检查点用 40 个任务做了两组对比。两组做的都是"等待 100 毫秒"，区别只在于等待的方式。

阻塞写法。

```csharp
Enter();
Thread.Sleep(100);            // 在线程池线程上阻塞
Interlocked.Decrement(ref running);
```

异步写法。

```csharp
Enter();
await Task.Delay(100);        // 等待期间不占线程
Interlocked.Decrement(ref running);
```

（`Enter()` 是检查点里的辅助方法，用来记录"同时在跑的任务数"的最大值。）

运行结果（同一次运行）。

```text
阻塞写法：40 个任务，耗时约 1603 ms，同时在跑的最多 3 个（数字因机器而异）
异步写法：40 个任务，耗时约 103 ms，同时在跑的最多 40 个（数字因机器而异）
```

阻塞写法里，同时跑的最多只有 3 个，其余 37 个都在排队。如果每次只能同时跑 3 个，理想的总耗时约为 40 ÷ 3 × 100 毫秒，也就是约 1333 毫秒。实测约 1603 毫秒，比这个估算更长，因为线程池增加线程需要时间。异步写法里，40 个任务全部同时在等待，总耗时约等于一次 100 毫秒。

**线程饥饿在真实程序里的样子**，一个 Web 服务器的线程池全部被"等数据库"占住，新的请求只能排队，界面和接口都变慢，有时看起来像是程序卡死了。解决办法通常是把阻塞改为异步，而不是盲目增加线程。

## 13.6 线程资源释放

线程结束后，系统才回收它占用的资源。这一点你不用操心。需要操心的是**线程以外的资源**，文件句柄、网络连接、事件订阅、取消源、定时器。它们通常实现了 `IDisposable`（同步释放）或 `IAsyncDisposable`（异步释放），用完要释放。

在这一节里，检查点用一个自定义类型演示 `await using` 的执行顺序。

```csharp
sealed class DemoResource(string name) : IAsyncDisposable
{
    public async ValueTask DisposeAsync()
    {
        await Task.Yield();
        Console.WriteLine($"  释放资源 {name}（DisposeAsync）");
    }
}

await using (var resource = new DemoResource("A"))
{
    Console.WriteLine("  使用资源 A");
}
Console.WriteLine("  离开 await using 块之后");
```

运行结果。

```text
  使用资源 A
  释放资源 A（DisposeAsync）
  离开 await using 块之后
```

`await using` 在离开块的时候调用 `DisposeAsync()`，并且等它完成。它和 `using` 的关系，就像 `await` 和普通调用的关系，异步版本要等待，同步版本不需要。

**忘记释放的后果很难在控制台里直接观察。** 有时只是多占了一点内存，有时是事件一直被订阅，导致对象无法回收，或者后台任务继续在跑。所以这部分更多靠习惯和检查清单。下面是项目里的例子。

**项目里的释放。** `LogLens.Cli/CliApplication.cs` 第 148 行订阅了 `Console.CancelKeyPress`，第 182 行在 `finally` 中取消订阅。不论命令成功还是失败，退出前都会取消订阅。

`LogLens.Studio/ViewModels/TailViewModel.cs` 第 343 行的 `Dispose()` 做了两件事，取消订阅 `BatchReceived` 事件，并在跟随任务还在运行时停止它。注释写得很直接，"页面卸载时不让跟随任务变成'孤儿'，直接停掉。" 这里有一个细节，`_ = _tail.StopAsync();` 没有被 `await`，它是第 [12.20 节](/chapter/12#s12-20)讲过的"不 await 的任务"。`Dispose()` 本身是同步方法，无法等待它。

## 13.7 共享数据与竞争

线程之间共享数据，最容易出的问题是**竞争**（race）。

看一行很普通的代码。

```csharp
unsafeCount++;
```

它看起来是一步，实际上至少分成三步，读出 `unsafeCount` 的值，加 1，写回去。如果两个线程同时执行，可能出现这样的情况。

1. 线程 A 读到 `100`；
2. 线程 B 也读到 `100`；
3. 线程 A 写回 `101`；
4. 线程 B 也写回 `101`。

两个线程都加了 1，结果只增加了 1。这就是**丢失更新**。

检查点用两个线程，各加 1000 万次，期望结果是 2000 万。

```csharp
var unsafeCount = 0;
var incA = new Thread(() => { for (var i = 0; i < 10_000_000; i++) unsafeCount++; });
var incB = new Thread(() => { for (var i = 0; i < 10_000_000; i++) unsafeCount++; });
incA.Start();
incB.Start();
incA.Join();
incB.Join();
Console.WriteLine($"两个线程各加 10000000 次：期望 20000000，实际 {unsafeCount}，丢失 {20_000_000 - unsafeCount}（数字因机器而异）");
```

运行结果（三次运行的实际值）。

```text
实际 13516695，丢失 6483305
实际 15141817，丢失 4858183
实际 13467498，丢失 6532502
```

每次结果都不同，而且都明显少于期望值。这说明结果不可预测。

有一次我们在测试时，把循环次数改小（每个线程 100 万次），第一次运行得到了正确的 200 万。这并不说明代码是安全的，只说明竞争没有在那次运行中出现。**不能因为一次运行结果正确，就认为代码没有竞争。** 没有保护的共享数据，就是一颗不定时的炸弹。

## 13.8 保护共享数据

保护共享数据有三种常见方式。它们适用的场景不同。

**方式一，`lock`。** 同一时间只允许一个线程进入代码块。

```csharp
var lockGate = new Lock();
var lockCounts = new Dictionary<string, int>();

lock (lockGate)
{
    lockCounts[level] = lockCounts.GetValueOrDefault(level) + 1;
}
```

`Lock` 是 .NET 9 起专门用于 `lock` 语句的类型，项目里的 `UiAppLogger.cs` 也是这样写的（第 16 行）。如果项目的目标框架低于 .NET 9，可以用 `private readonly object _gate = new();`，效果相同。

**方式二，`Interlocked`。** 对一个数字做原子操作，比如加 1。它不需要锁，适合只改一个数字的场景。

```csharp
Interlocked.Increment(ref interlockedCounts[Array.IndexOf(levels, level)]);
```

**方式三，`ConcurrentDictionary`。** 线程安全的字典，适合多个线程同时读写"键值对"的场景。

```csharp
concurrentCounts.AddOrUpdate(level, 1, (_, old) => old + 1);
```

检查点用这三种方式统计同一批日志级别，400000 条日志，INFO、WARN、ERROR、DEBUG 各 100000 条，由四个线程同时统计。

运行结果（同一次运行）。

```text
lock：INFO=100000 WARN=100000 ERROR=100000 DEBUG=100000，耗时约 45 ms
Interlocked：INFO=100000 WARN=100000 ERROR=100000 DEBUG=100000，耗时约 43 ms
ConcurrentDictionary：INFO=100000 WARN=100000 ERROR=100000 DEBUG=100000，耗时约 107 ms
```

三种方式的结果都正确。耗时只能作参考，这个例子里，`lock` 和 `Interlocked` 差不多，`ConcurrentDictionary` 慢一些。它的优势不在速度，而在于**键是动态的**，你不需要事先知道有哪些级别，遇到新的键，它自己会添加。

怎么选。

- 只改一个数字，用 `Interlocked`。
- 要保护一段较复杂的逻辑（比如同时改两个字段，或者操作一个队列），用 `lock`。
- 键值对、键不固定、多个线程都要往里面写，用 `ConcurrentDictionary`。

**项目里的保护。** `LogLens.Studio/Services/UiAppLogger.cs` 第 16 行声明了 `private readonly Lock _gate = new();`。第 44 行的 `Write` 方法在锁里把日志放进队列，并把超出容量的旧记录出队。第 24 行的 `Recent` 属性在锁里取快照，注释写的是，"lock 保证多线程下取快照时不会读到'半更新'的队列。" 也就是说，写日志的线程和界面读日志的线程，都要经过同一把锁。

`LogLens.Core/Query/QueryEvaluator.cs` 第 19 行的正则缓存用的是 `ConcurrentDictionary`，第 249 行用 `GetOrAdd` 取得或创建编译好的正则。多个查询线程可以同时使用它，不需要额外的锁。

## 13.9 死锁

**死锁**是两个或更多线程互相等待，谁也无法继续。

最典型的情况是，线程 A 先拿锁 A，再等锁 B；线程 B 先拿锁 B，再等锁 A。两个线程都拿着一把锁，又在等对方的那一把，谁也不肯松手，程序就永远卡住。

检查点用一个确定的场景来演示。两个线程都先拿到自己的第一把锁，通过 `Barrier` 同步，确保两边都拿到了第一把锁，然后才去抢对方的锁。抢的时候设置超时，超时就放弃，程序不会真的卡死。

```csharp
var lockA = new object();
var lockB = new object();
var barrier = new Barrier(2);

var threadA = new Thread(() =>
{
    lock (lockA)
    {
        barrier.SignalAndWait();   // 两边都拿到第一把锁之后，再去抢第二把
        if (Monitor.TryEnter(lockB, 300))
        {
            Monitor.Exit(lockB);
            Console.WriteLine("  线程 A：拿到了两把锁");
        }
        else
        {
            Console.WriteLine("  线程 A：拿到 A，等 B 超过 300 ms，放弃");
        }
    }
});
```

线程 B 的代码与之对称，只是锁的顺序相反。

运行结果（三次运行的结果一致）。

```text
  线程 B：拿到 B，等 A 超过 300 ms，放弃
  线程 A：拿到 A，等 B 超过 300 ms，放弃
  两个线程都已退出，程序没有卡住
```

两行"放弃"的顺序每次可能不同，因为两个线程是同时执行的。

如果把 `Monitor.TryEnter(lockB, 300)` 换成 `lock (lockB)`，两个线程就会永远等下去。这正是真实程序中死锁的样子，没有报错，没有输出，程序只是停住了。

**预防死锁的常见做法，**

1. 所有线程按**相同的顺序**获取多把锁。如果都是先 A 后 B，就不会出现交叉等待。
2. 尽量缩短持锁的时间，在锁里只做必要的事，不要在锁里等待网络或磁盘。
3. 获取锁时使用超时（`Monitor.TryEnter` 带超时参数），超时后做出明确的处理，比如记录日志并重试或放弃。

## 13.10 异步与线程的关系

很多人把 `async` 和多线程混为一谈。它们不是一回事。

- `async` 不等于多线程。一个 `async` 方法可以完全在一个线程上运行，只是在等待时让出线程。
- `await` 之后不一定换线程。它取决于同步上下文（第 [12.12 节](/chapter/12#s12-12)）。控制台程序里，它通常会换到线程池的线程上。
- `Task.Run` 才是"把工作放到另一个线程上"的常用方法，它把 CPU 工作交给线程池。

检查点打印了每一步的线程 ID。

```csharp
Console.WriteLine($"  await 之前：线程 {Environment.CurrentManagedThreadId}");
await Task.Delay(50);
Console.WriteLine($"  await 之后：线程 {Environment.CurrentManagedThreadId}（可能相同，也可能不同）");
await Task.Run(() => Console.WriteLine($"  Task.Run 中：线程 {Environment.CurrentManagedThreadId}"));
```

运行结果（同一次运行）。

```text
  await 之前：线程 505
  await 之后：线程 505（可能相同，也可能不同）
  Task.Run 中：线程 508
```

这一次 `await` 前后的线程 ID 相同，`Task.Run` 的线程 ID 不同。换一台机器或另一次运行，前两者可能不同，这取决于线程池的调度。**不要依赖"await 之后一定在同一个线程上"这个假设**，也不要依赖"一定会换线程"。

这就是为什么界面程序需要 `ConfigureAwait(true)`（第 [12.12 节](/chapter/12#s12-12)），界面控件只能在界面线程上修改，编译器不会替你保证这一点。

## 13.11 CPU 并行

前面几节讲的都是"等待"和"共享"。这一节讲另一件事，让多个核心同时做计算。

`Parallel.For` 把循环分给多个线程执行。检查点用一个计算量较大的求和做对比。

```csharp
const int n = 50_000_000;
sw.Restart();
double seqSum = 0;
for (var i = 0; i < n; i++)
{
    seqSum += Math.Sqrt(i) * Math.Sin(i);
}
var seqMs = sw.ElapsedMilliseconds;

sw.Restart();
double parSum = 0;
var parGate = new object();
Parallel.For(0, n, () => 0.0,
    (i, _, local) => local + Math.Sqrt(i) * Math.Sin(i),
    local =>
    {
        lock (parGate)
        {
            parSum += local;
        }
    });
var parMs = sw.ElapsedMilliseconds;
```

这段代码里有三个值得注意的地方。

1. `Parallel.For` 的第三个参数是"线程局部变量的初始值"。每个线程先在自己的 `local` 里累加，最后才合并到 `parSum`。这样大部分时间不需要加锁。
2. 合并的那一步（`parSum += local`）仍然需要锁，因为多个线程可能同时合并。
3. 直接写 `parSum += ...` 而不加保护，就会出现第 [13.7 节](#s13-7)的丢失更新。

运行结果（同一次运行）。

```text
单线程：约 549 ms；Parallel.For：约 424 ms；核心数 2（只作参考）
两种求和结果相近：True
```

本机只有 2 个核心，所以加速比约为 1.3 倍。如果机器有 8 个核心，加速会更明显，但也不会等于 8 倍，线程的调度、合并的开销、内存带宽都会限制加速。

"两种求和结果相近"是用相对误差判断的。浮点数的加法顺序不同，最后几位可能不一样，所以不能用 `==` 比较浮点数。

[第 10 章](/chapter/10)讲的 PLINQ（`AsParallel()`）是同一类工具，本章不再重复。

## 13.12 线程局部数据

共享数据会带来竞争。有时候，每个线程需要的是一份自己的数据。比如每个线程用自己的 `Random`（`Random` 不是线程安全的），或者每个线程用自己的临时缓冲区。这时可以用 `ThreadLocal<T>`。

```csharp
var perThread = new ThreadLocal<int>(() => 0);
var threadTotals = new int[3];
var localThreads = Enumerable.Range(0, 3).Select(i => new Thread(() =>
{
    for (var k = 0; k < 1000; k++)
    {
        perThread.Value++;
    }
    threadTotals[i] = perThread.Value;
})).ToArray();
foreach (var th in localThreads)
{
    th.Start();
}
foreach (var th in localThreads)
{
    th.Join();
}
Console.WriteLine($"三个线程各自加 1000 次，各自看到：{string.Join(" ", threadTotals)}");
Console.WriteLine($"主线程看到的值：{perThread.Value}");
perThread.Dispose();
```

运行结果。

```text
三个线程各自加 1000 次，各自看到：1000 1000 1000
主线程看到的值：0
```

每个线程的 `Value` 都是自己的一份，互不影响。主线程看到的仍然是初始值 0。`ThreadLocal<T>` 用完要 `Dispose()`。

**线程局部数据遇到 `await` 会出问题。** 第 [13.10 节](#s13-10)讲过，`await` 之后可能换到另一个线程上继续。这时 `ThreadLocal<T>` 的值跟着线程走，而不是跟着异步方法走，结果就对不上了。异步代码里要保存的上下文，应该用 `AsyncLocal<T>`。

**`AsyncLocal<T>`** 的值跟着异步执行流走。它在 `await` 前后保持不变，即使中间换了线程。典型用途是请求编号、用户身份、日志关联编号这类"一次操作内都要用到"的信息。

```csharp
var requestId = new AsyncLocal<string>();
requestId.Value = "REQ-001";
await HandleRequestAsync("子任务");
Console.WriteLine($"  调用方：await 之后，请求编号 = {requestId.Value}");
await Task.Run(() => Console.WriteLine($"  Task.Run 中，请求编号 = {requestId.Value}"));

async Task HandleRequestAsync(string name)
{
    Console.WriteLine($"  {name}：开始，请求编号 = {requestId.Value}");
    await Task.Delay(20);
    Console.WriteLine($"  {name}：await 之后，请求编号 = {requestId.Value}");
    requestId.Value = "子任务改过的值";
}
```

运行结果。

```text
  子任务：开始，请求编号 = REQ-001
  子任务：await 之后，请求编号 = REQ-001
  调用方：await 之后，请求编号 = REQ-001
  Task.Run 中，请求编号 = REQ-001
```

`HandleRequestAsync` 里把值改成了"子任务改过的值"，但调用方看到的仍然是 `REQ-001`。异步方法里对 `AsyncLocal<T>` 的修改，不会传回调用它的代码。`Task.Run` 启动的任务则能拿到同一个请求编号。

**项目里的情况。** 本项目目前没有使用 `ThreadLocal<T>` 与 `AsyncLocal<T>`。如果将来要给每次分析附加一个关联编号，让它出现在每一条日志里，`AsyncLocal<T>` 是比较合适的选择。

## 13.13 生产者与消费者

一边读文件，一边分析，是很常见的需求。读文件的一方（生产者）和分析的一方（消费者）速度不一样，中间需要一个队列来缓冲。.NET 提供的是 `Channel<T>`，位于 `System.Threading.Channels` 命名空间。它有三个要点。

- **有界队列。** `Channel.CreateBounded<T>` 创建的队列有容量上限。队列满了，`WriteAsync` 会等待，直到消费者取走一些数据。这叫**背压**，它防止生产者太快，把内存撑爆。
- **结束信号。** 生产者写完后调用 `Writer.Complete()`，告诉消费者没有更多数据了。
- **读取。** 消费者用 `await foreach` 配合 `ReadAllAsync()`，队列结束后循环自动退出。

旧代码里常见 `BlockingCollection<T>`，它也能做有界队列。新代码通常用 `Channel<T>`，它和 `async`/`await` 配合得更自然。

检查点用一个生产者写入 10000 条，两个消费者同时读取。

```csharp
var channel = Channel.CreateBounded<string>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait
});
var produced = 0;
var consumed = new int[2];

var producer = Task.Run(async () =>
{
    for (var i = 0; i < 10_000; i++)
    {
        await channel.Writer.WriteAsync($"line {i}");
        produced++;
    }
    channel.Writer.Complete();
});

var consumers = Enumerable.Range(0, 2).Select(c => Task.Run(async () =>
{
    await foreach (var _ in channel.Reader.ReadAllAsync())
    {
        consumed[c]++;
    }
})).ToArray();

await producer;
await Task.WhenAll(consumers);
Console.WriteLine($"生产 {produced} 条，两个消费者分别处理 {consumed[0]} 和 {consumed[1]} 条，合计 {consumed.Sum()}");
Console.WriteLine($"全部处理完：{consumed.Sum() == produced}");
```

运行结果（同一次运行）。

```text
生产 10000 条，两个消费者分别处理 3965 和 6035 条，合计 10000
全部处理完：True
```

两个消费者分到的数量不固定。三次运行分别是 3965 与 6035、5000 与 5000、6044 与 3956，但合计每次都是 10000。数据没有丢，也没有被重复处理。

有三件事要记住。

1. **忘记 `Complete()`。** 消费者的 `ReadAllAsync()` 会一直等下去，程序卡住，没有任何报错。这是 `Channel<T>` 最常见的错误。
2. **容量要有限。** 无界队列看起来方便，但生产者比消费者快时，队列会一直增长，直到内存耗尽。
3. **计数要等任务结束后再读。** 检查点在两个任务都 `await` 完成之后才输出计数，读到的一定是最终值。

**项目里的情况。** 本项目目前没有使用 `Channel<T>`。日志尾随功能（`TailService`）用事件把批次交给界面，第 51 行声明了 `BatchReceived` 事件。两种做法解决的是相近的问题，一个是推送，一个是排队，可以对照着理解。

## 13.14 取消与超时

线程不能被"强行杀死"。.NET Core 之后 `Thread.Abort` 已经不再支持。在验证环境里，调用 `t.Abort()` 会让编译器给出 SYSLIB0006 警告，运行时抛出 `PlatformNotSupportedException`，消息是 `Thread abort is not supported on this platform.`。所以 .NET 采用**协作式取消**。由 `CancellationTokenSource` 发出取消请求，线程自己检查，自己退出。

### 为什么不能随意取消

强行停下一个线程，等于在它执行到任意一行的时候把它拿掉。它可能正持有一把锁，可能写到文件一半，可能刚改了一个字段，另一个字段还没改。这些东西没有人收拾，其它线程之后看到的，就是一个状态说不清的程序。这类问题很难复现，也很难排查。

协作式取消的代价是，**取消什么时候生效，留下什么状态，全部由你写的代码决定**。取消做得好不好，取决于检查点放在哪里。下面的六个后果，每一个都用可以运行的例子说明。

还有一种常见做法是超时，即不再等待，但工作本身不会停下。它和取消不是一回事，后面的例子会专门说明。

### 取消的基本用法

取消有三个要点。

1. 线程要定期检查 `token`，用 `ThrowIfCancellationRequested()` 或 `IsCancellationRequested`。不检查，取消就没有效果。
2. 普通的 `Thread.Sleep` 不会响应取消。要等待，并且能被取消唤醒，应该用 `token.WaitHandle.WaitOne(...)`。
3. `CancelAfter(毫秒)` 设置超时，到时间自动取消。

检查点的前三个实验演示基本用法。第一个实验，用 `Thread.Sleep` 睡 2 秒，同时在 100 毫秒时请求取消。

```csharp
using (var cts1 = new CancellationTokenSource())
{
    var sw1 = Stopwatch.StartNew();
    cts1.CancelAfter(100);
    Thread.Sleep(2000);           // 普通睡眠，不会因为取消而提前醒来
    Console.WriteLine($"Thread.Sleep(2000)：用了 {sw1.ElapsedMilliseconds} ms，期间已请求取消：{cts1.IsCancellationRequested}");
}
```

第二个实验，用同样的时间，但等待方式换成 `WaitHandle.WaitOne`。

```csharp
using (var cts2 = new CancellationTokenSource())
{
    var sw2 = Stopwatch.StartNew();
    cts2.CancelAfter(100);
    var cancelled = cts2.Token.WaitHandle.WaitOne(2000);   // 可以被取消唤醒
    Console.WriteLine($"WaitHandle.WaitOne(2000)：用了约 {sw2.ElapsedMilliseconds} ms，返回 {cancelled}（true 表示被取消唤醒）");
}
```

第三个实验，一个循环任务每次睡 5 毫秒，并在每次循环开始时检查取消。200 毫秒后取消。

```csharp
using (var cts3 = new CancellationTokenSource())
{
    var processed = 0;
    var cancelWorker = Task.Run(() =>
    {
        try
        {
            while (true)
            {
                cts3.Token.ThrowIfCancellationRequested();
                Thread.Sleep(5);
                Interlocked.Increment(ref processed);
            }
        }
        catch (OperationCanceledException)
        {
            return "已取消";
        }
    });
    cts3.CancelAfter(200);
    var status = await cancelWorker;
    Console.WriteLine($"循环任务：{status}，期间处理了约 {processed} 条（数字因机器而异）");
}
```

运行结果（同一次运行）。

```text
Thread.Sleep(2000)：用了 2000 ms，期间已请求取消：True
WaitHandle.WaitOne(2000)：用了约 100 ms，返回 True（true 表示被取消唤醒）
循环任务：已取消，期间处理了约 39 条（数字因机器而异）
```

第一个实验里，取消请求在 100 毫秒时已经发出，但 `Thread.Sleep` 还是睡满了 2000 毫秒，它不知道有取消这回事。第二个实验里，同样的 100 毫秒后，等待就结束了，返回 `True`。第三个实验里，循环在取消后抛出 `OperationCanceledException`，被 `catch` 接住，任务正常结束。处理的条数 39 与 200 毫秒除以每次约 5 毫秒的结果相近。

### 后果一，取消落在哪一行决定留下什么状态

下面的转账分两步，先从 A 扣款，再给 B 入账。两步之间如果有取消检查，取消就会落在中间。两个版本的区别只在检查点的位置。

```csharp
// 不安全：扣款之后、入账之前检查取消，取消会让钱凭空消失
static void TransferUnsafe(Dictionary<string, int> acc, int amount, CancellationToken token)
{
    acc["A"] -= amount;                                // 第一步：扣款
    token.ThrowIfCancellationRequested();              // 检查点落在两步之间
    acc["B"] += amount;                                // 第二步：入账
}

// 安全：所有检查都放在动手之前，要么全做，要么一点都不做
static void TransferSafe(Dictionary<string, int> acc, int amount, CancellationToken token)
{
    token.ThrowIfCancellationRequested();
    acc["A"] -= amount;
    acc["B"] += amount;
}
```

两个版本都在取消请求已经发出之后调用，运行结果如下。

```text
(a) 检查放在两步之间：A=0 B=0，合计 0（应为 100）
(a) 检查放在动手之前：A=100 B=0，合计 100
```

`TransferUnsafe` 已经扣了款，检查时抛出异常，入账这一步没有执行。100 块钱凭空消失了，合计变成 0。`TransferSafe` 把检查放在动手之前，取消时什么都没做，合计仍然是 100。

由此可以得出几条规则。

- 一组必须一起完成的修改（扣款与入账，更新两个字段），中间不要放取消检查。
- 检查放在一个完整操作的开始，或者放在一批修改全部完成之后。
- 如果操作很长，没法做成一个整体，就要在取消时补回已经做掉的部分（也就是回滚）。这需要专门设计，本章不展开。

### 后果二，超时不等于停止

下面模拟一次上传，每次发送要 50 毫秒，一共 10 次。主线程只等 120 毫秒。

```csharp
var sent = 0;
var upload = Task.Run(async () =>
{
    for (var i = 0; i < 10; i++)
    {
        await Task.Delay(50);                        // 模拟一次发送
        Interlocked.Increment(ref sent);
    }
});
var first = await Task.WhenAny(upload, Task.Delay(120));
Console.WriteLine($"(b) 等了 120 ms：{(first == upload ? "已完成" : "超时，不再等")}，此刻已发送 {sent} 条（数字因机器而异）");
await upload;
Console.WriteLine($"(b) 上传任务真正结束后：共发送 {sent} 条，超时之后它一直在跑");
```

```text
(b) 等了 120 ms：超时，不再等，此刻已发送 2 条（数字因机器而异）
(b) 上传任务真正结束后：共发送 10 条，超时之后它一直在跑
```

`Task.WhenAny` 等的是"任务结束"或"计时结束"，哪个先到就返回。计时先到的时候，`upload` 仍在运行。超时之后它还会继续发送，继续占用连接，继续修改共享的数据。调用方以为已经放弃了，实际上它还在做。

如果超时就意味着要停下，应该把同一个 `CancellationToken` 传给工作本身，超时时取消它（例如用 `CancelAfter`，就像上面的第三个实验），而不只是停止等待。如果做不到取消，就要在界面或日志里明确写"结果未知"，不要假装它已经失败。

### 后果三，取消可能留下半成品文件

写文件时取消，最容易留下半成品。下面先写一份"旧报告"，然后在写到第 30 行时取消。第一种写法直接覆盖目标文件；第二种先写临时文件，全部写完再替换。

```csharp
// 直接写：目标文件在写的过程中就已经被覆盖了
using var writer = new StreamWriter(report);
for (var i = 0; i < 100; i++)
{
    if (i == 30) cts.Cancel();                  // 写到第 30 行时用户取消
    cts.Token.ThrowIfCancellationRequested();
    writer.WriteLine($"第 {i} 行");
}
```

```csharp
// 临时文件：全部写完才替换目标文件
using (var writer = new StreamWriter(tmp))
{
    for (var i = 0; i < 100; i++)
    {
        if (i == 30) cts.Cancel();
        cts.Token.ThrowIfCancellationRequested();
        writer.WriteLine($"第 {i} 行");
    }
}
File.Move(tmp, report, overwrite: true);
```

```text
(c) 直接写：取消后目标文件只剩 30 行，旧报告已经丢了
(c) 临时文件：取消后目标仍是「旧报告」，临时文件已删除
```

直接写的方式，取消时旧报告已经被覆盖，目标文件只剩 30 行，既不是旧报告，也不是完整的新报告。临时文件的方式，取消时只需要删掉临时文件，目标文件保持原样。替换放在全部写完之后，临时文件最好和目标文件放在同一个目录里，这样替换只是在同一个磁盘上改名。

项目里的导出也要留意这一点。`src/LogLens.Core/Reporting/ReportExporter.cs` 第 59 至 60 行先在内存里生成完整内容，再用 `File.WriteAllTextAsync` 写入目标文件，并把 `cancellationToken` 传了进去。写入阶段没有用临时文件，如果在写入途中被取消或出错，目标文件就可能只写了一部分。这一点我们没有在项目里专门验证。第 65 行的 `when` 只过滤 IO 类异常，取消产生的 `OperationCanceledException` 不在其中，会继续往上抛。

### 后果四，异常穿过 `lock` 与 `using` 时资源会被收拾

取消是通过异常传出的。异常穿过 `lock` 时，锁会被释放；穿过 `using` 时，资源会被释放。下面的任务持有锁时被取消，主线程随后去拿同一把锁。

```csharp
var gate = new object();
var holder = Task.Run(() =>
{
    try
    {
        lock (gate)
        {
            Thread.Sleep(100);
            throw new OperationCanceledException("取消发生在持锁期间");
        }
    }
    catch (OperationCanceledException)
    {
        return "持锁的任务已取消";
    }
});
Console.WriteLine($"(d) {await holder}");
var got = Monitor.TryEnter(gate, 1000);
Console.WriteLine($"(d) 之后另一个线程能否拿到锁：{got}");
```

```text
(d) 持锁的任务已取消
(d) 之后另一个线程能否拿到锁：True
```

这正是协作式取消的好处，取消发生在检查点，检查点之外的代码仍然完整，`finally`、`using` 与 `lock` 会照常执行。前提是收尾代码写在这些结构里。如果收尾代码写在 `try` 的最后一行，取消发生时它就不会执行。

### 后果五，回调在 `Cancel()` 的线程上同步执行

`Register` 登记的回调，会在调用 `Cancel()` 的那个线程上同步执行，`Cancel()` 要等回调全部跑完才会返回。

```csharp
using var cts = new CancellationTokenSource();
cts.Token.Register(() => Thread.Sleep(300));         // 模拟一个慢的清理回调
var cancelTimer = Stopwatch.StartNew();
cts.Cancel();
Console.WriteLine($"(e) Cancel() 返回时，回调已经跑完：{cancelTimer.ElapsedMilliseconds >= 300}");
```

```text
(e) Cancel() 返回时，回调已经跑完：True
```

如果调用 `Cancel()` 的是界面线程，慢的回调就会让界面卡住。所以回调里只做轻量的事情，例如设置一个标志，或者启动另一个任务去做后续工作。

### 后果六，释放之后再使用会抛出异常

`CancellationTokenSource` 用完要释放（见 13.6）。释放之后，调用 `Cancel()` 会抛出 `ObjectDisposedException`，读取 `Token` 也会抛出同样的异常。这一点是探针验证过的。

```csharp
var released = new CancellationTokenSource();
released.Dispose();
try
{
    released.Cancel();
}
catch (ObjectDisposedException)
{
    Console.WriteLine("(f) Dispose 之后调用 Cancel() 抛出 ObjectDisposedException");
}
```

```text
(f) Dispose 之后调用 Cancel() 抛出 ObjectDisposedException
```

所以，把 `Token` 交给别的对象时，要保证源还没有被释放。通常的做法是由创建 `CancellationTokenSource` 的那一层负责释放，别的地方只使用 `Token`。

### 正确用法小结

- 取消检查放在状态一致的位置。一组要一起完成的修改之间不设检查点。
- 超时要同时取消工作本身，不能只停止等待。
- 写文件先写临时文件，全部写完再替换目标文件。
- 收尾代码放在 `finally`、`using` 或 `lock` 里。
- 回调只做轻量的事情。
- `CancellationTokenSource` 由创建它的一方释放，释放之后不要再使用。
- 取消不是错误。`OperationCanceledException` 要单独处理，不要当作 bug 记录（见[第 12 章](/chapter/12)关于取消的小节）。

**项目里的取消。** 本项目多处用到了取消，下面几处可以对照阅读。

- `LogLens.Cli/CliApplication.cs` 第 31 行的 `_cancellation`，与 `Console.CancelKeyPress` 配合。第一次按下 Ctrl+C 时取消正在进行的操作，再按一次才直接退出（第 148 行订阅，第 290 行处理）。
- `LogLens.Core/Parsing/LogLineSource.cs` 第 100 行调用 `ThrowIfCancellationRequested()`，读取大文件时可以中途停下。
- `LogLens.Studio/Services/TailService.cs` 第 68 行用 `CreateLinkedTokenSource` 把外部传入的取消和自己的取消合并。第 127 行的循环每次都检查 `IsCancellationRequested`。

## 13.15 UI 线程与后台工作

界面程序有一条硬规则。**界面控件只能由创建它的线程（界面线程）修改。** 在后台线程上直接写进度条的值或标签的文字，结果是不确定的，严重时会抛出异常。WinForms 在调试时会直接报错，Avalonia 同样有这个限制，项目里 `MainWindowViewModel.cs` 第 607至608 行的注释写的就是 `"The calling thread cannot access this object"`。

正确的做法是**后台算，界面线程改**。

- 耗时的计算放在 `Task.Run` 里，在线程池线程上执行。
- 需要更新界面时，用 `IProgress<T>`。`Progress<T>` 在创建时记住当前的界面线程，之后每次 `Report` 都会把回调排到界面线程上执行。
- `await` 之后的代码，默认会回到开始 `await` 的线程。在界面程序里，这个线程就是界面线程，因为界面框架提供了对应的 `SynchronizationContext`。

本节的代码在 `code/ch13-ui-winforms/`。它是一个 WinForms 窗口程序，只为说明同一个原理，窗口的样式不是本章的重点。下面是窗口的主要代码。

```csharp
public sealed class MainForm : Form
{
    private readonly Label _status = new() { AutoSize = true, Text = "等待开始" };
    private readonly ProgressBar _progress = new() { Width = 400, Maximum = 100 };
    private readonly Button _start = new() { Text = "开始统计（后台线程 + Progress）", AutoSize = true };
    private readonly Button _cancel = new() { Text = "取消", AutoSize = true, Enabled = false };
    private readonly Button _bad = new() { Text = "错误写法：后台线程直接改界面", AutoSize = true };
    private CancellationTokenSource? _cts;

    public MainForm()
    {
        // 省略窗口布局代码，三个按钮的 Click 事件如下
        _start.Click += async (_, _) => await StartCountingAsync();
        _cancel.Click += (_, _) => _cts?.Cancel();
        _bad.Click += (_, _) => StartBadWrite();
    }

    // 正确的写法：耗时工作放到后台线程，进度通过 Progress<T> 回到界面线程。
    private async Task StartCountingAsync()
    {
        _start.Enabled = false;
        _cancel.Enabled = true;
        var cts = new CancellationTokenSource();
        _cts = cts;

        // Progress<T> 在创建时记住当前的 SynchronizationContext（这里是界面线程），
        // 之后每次 Report 都会把回调排到界面线程上执行。
        var progress = new Progress<int>(percent =>
        {
            _progress.Value = percent;
            _status.Text = $"进度 {percent}%";
        });

        try
        {
            // Task.Run 把 CountSlowly 放到线程池线程上执行。
            var total = await Task.Run(() => CountSlowly(progress, cts.Token));

            // await 之后自动回到界面线程，这里可以安全地修改控件。
            _status.Text = $"完成，共处理 {total} 项";
        }
        catch (OperationCanceledException)
        {
            _status.Text = "已取消";
        }
        finally
        {
            _start.Enabled = true;
            _cancel.Enabled = false;
            _cts = null;
            cts.Dispose();
        }
    }

    private static int CountSlowly(IProgress<int> progress, CancellationToken token)
    {
        var total = 0;
        for (var percent = 1; percent <= 100; percent++)
        {
            token.ThrowIfCancellationRequested();
            Thread.Sleep(30);            // 模拟耗时工作，在后台线程上进行
            total += 1000;
            progress.Report(percent);    // 不直接碰控件
        }
        return total;
    }

    // 错误的写法：后台线程直接修改界面控件。
    // 调试运行时，WinForms 会抛出 InvalidOperationException（跨线程操作无效）。
    private void StartBadWrite()
    {
        var worker = new Thread(() =>
        {
            for (var percent = 1; percent <= 100; percent++)
            {
                Thread.Sleep(30);
                _progress.Value = percent;              // 错误：不在界面线程上
                _status.Text = $"进度 {percent}%";    // 错误：不在界面线程上
            }
        })
        {
            IsBackground = true
        };
        worker.Start();
    }
}
```

（上面的代码省略了窗口布局部分，完整代码见配套目录的 `MainForm.cs`。）

## 13.16 常见错误

下面是线程相关代码里最常见的错误。

1. **共享变量没有保护。** 见 13.7。只要两个线程都可能写同一个变量，就必须加保护，或者避免共享。
2. **线程池里阻塞。** 在 `Task.Run` 里写 `Thread.Sleep`、`.Result` 或 `.Wait()`，会占住线程池线程，导致线程饥饿（见 13.5）。
3. **忘记释放。** 取消源、定时器、事件订阅用完没有释放（见 13.6）。
4. **死锁。** 多把锁的获取顺序不一致（见 13.9）。
5. **在界面线程上 `.Result` 或 `.Wait()`。** 界面线程会停住，如果那个任务需要回到界面线程继续，两者就互相等待，界面卡死。第 [12.24 节](/chapter/12#s12-24)提到过这个问题。
6. **`Channel<T>` 忘记 `Complete()`。** 消费者一直等待，程序卡住，没有报错（见 13.13）。
7. **取消没有效果。** 循环里没有检查 `token`，或者用 `Thread.Sleep` 等待，取消请求发出后线程照样运行（见 13.14）。
8. **把 `ThreadLocal<T>` 用在跨 `await` 的代码里。** `await` 之后可能换线程，值对不上。异步上下文要用 `AsyncLocal<T>`（见 13.12）。
9. **后台线程直接修改界面控件。** 结果不确定，调试时会报跨线程错误（见 13.15）。
10. **超时后工作还在跑。** `Task.WhenAny` 或 `Task.Wait(超时)` 只是不再等待，工作本身不会停（见 13.14 的"后果二"）。
11. **取消落在两步之间。** 一组要一起完成的修改中间有取消检查，取消后数据只改了一半（见 13.14 的"后果一"）。

第 1、4 和 9 条很难靠测试发现，因为它们的表现不稳定，有时运行结果正确，有时又不对。第 6、7 条则是卡住或无效，表现明显，但需要知道要找哪一行。写代码时，应当先考虑"这个变量会不会被多个线程访问"，而不是等出了问题再去找。

## 13.17 小练习与检查点

**练习。** 假设你有一份日志文件，每行形如 `2026-11-01 12:00:00 INFO api ...`。请写一个程序，用多个线程统计这份文件里每个日志级别的数量。

1. 按行读取文件（可以用 `File.ReadLines`），把每一行交给线程处理；
2. 分别用 `lock`、`Interlocked`、`ConcurrentDictionary` 三种方式统计；
3. 三种结果应当完全一致，并比较它们的耗时；
4. 再写一个不加保护的版本，多运行几次，观察结果是否每次都正确。

提示，可以参考 [13.8 节](#s13-8)的三种写法，把"日志级别"换成从每一行解析出来的级别。

**参考解。** 为了让代码可以直接运行，参考解先生成一份 20 万行的示例日志，再统计它（临时文件用完即删）。

```csharp
using System.Collections.Concurrent;
using System.Diagnostics;

// 13.13 练习参考解。先生成一份示例日志，再用三种方式统计每个级别的数量。
string path = Path.Combine(Path.GetTempPath(), "loglens-ch13-exercise.log");
string[] levels = ["INFO", "WARN", "ERROR", "DEBUG"];
const int lineCount = 200_000;

File.WriteAllLines(path, Enumerable.Range(0, lineCount)
    .Select(i => $"2026-11-01 12:00:00 {levels[i % levels.Length]} api 第 {i} 条消息"));

Console.WriteLine($"日志行数：{File.ReadLines(path).Count()}");
Console.WriteLine();

// 方式一：lock 保护一个普通的 Dictionary。
var lockCounts = levels.ToDictionary(l => l, _ => 0);
var gate = new object();
long t1 = Measure(() => Parallel.ForEach(File.ReadLines(path), line =>
{
    string level = ParseLevel(line);
    lock (gate) lockCounts[level]++;
}));

// 方式二：Interlocked 原子加一，要求级别是事先已知的固定集合。
var interlockedCounts = new int[levels.Length];
long t2 = Measure(() => Parallel.ForEach(File.ReadLines(path), line =>
{
    Interlocked.Increment(ref interlockedCounts[Array.IndexOf(levels, ParseLevel(line))]);
}));

// 方式三：ConcurrentDictionary，AddOrUpdate 内部已经处理了并发。
var concurrentCounts = new ConcurrentDictionary<string, int>();
long t3 = Measure(() => Parallel.ForEach(File.ReadLines(path), line =>
{
    concurrentCounts.AddOrUpdate(ParseLevel(line), 1, (_, old) => old + 1);
}));

// 三种结果应当一致。
var lockResult = levels.Select(l => lockCounts[l]).ToArray();
var interlockedResult = interlockedCounts;
var concurrentResult = levels.Select(l => concurrentCounts[l]).ToArray();

Console.WriteLine("lock：        " + string.Join(" ", levels.Zip(lockResult).Select(p => $"{p.First}={p.Second}")) + $"  耗时 {t1} ms");
Console.WriteLine("Interlocked： " + string.Join(" ", levels.Zip(interlockedResult).Select(p => $"{p.First}={p.Second}")) + $"  耗时 {t2} ms");
Console.WriteLine("Concurrent：  " + string.Join(" ", levels.Zip(concurrentResult).Select(p => $"{p.First}={p.Second}")) + $"  耗时 {t3} ms");
Console.WriteLine($"三种结果一致：{lockResult.SequenceEqual(interlockedResult) && interlockedResult.SequenceEqual(concurrentResult)}");
Console.WriteLine();

// 不加保护的版本：多运行几次，观察总数是否每次都等于行数。
for (int run = 1; run <= 3; run++)
{
    var unsafeCounts = new int[levels.Length];
    Parallel.ForEach(File.ReadLines(path), line =>
    {
        unsafeCounts[Array.IndexOf(levels, ParseLevel(line))]++;
    });
    int total = unsafeCounts.Sum();
    Console.WriteLine($"不加保护第 {run} 次：总数 {total}，期望 {lineCount}，{(total == lineCount ? "正确" : "丢失了 " + (lineCount - total) + " 次计数")}");
}

File.Delete(path);

static string ParseLevel(string line) => line.Split(' ')[2];

static long Measure(Action action)
{
    var sw = Stopwatch.StartNew();
    action();
    return sw.ElapsedMilliseconds;
}
```

一次运行的输出如下（耗时与丢失的次数每次都会不同）。

```text
日志行数：200000

lock：        INFO=50000 WARN=50000 ERROR=50000 DEBUG=50000  耗时 118 ms
Interlocked： INFO=50000 WARN=50000 ERROR=50000 DEBUG=50000  耗时 51 ms
Concurrent：  INFO=50000 WARN=50000 ERROR=50000 DEBUG=50000  耗时 49 ms
三种结果一致：True

不加保护第 1 次：总数 199704，期望 200000，丢失了 296 次计数
不加保护第 2 次：总数 199432，期望 200000，丢失了 568 次计数
不加保护第 3 次：总数 199658，期望 200000，丢失了 342 次计数
```

三种加保护的方式结果都与期望一致。不加保护的版本每次都丢了计数，而且丢失的数量不固定，这正是第 [13.7 节](#s13-7)说的竞争条件。
