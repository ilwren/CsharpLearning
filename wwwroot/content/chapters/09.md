## 9.1 委托，把方法当成值来传递

[第 10 章](/chapter/10)会大量用到 `logs.Where(log => log.Ms > 500)` 这样的写法。`=>` 右边的东西是什么？它是一个方法，而 `Where` 能接收它，靠的就是委托。

**委托**是一种类型，它规定了方法的形状，也就是参数和返回值的类型。能符合这个形状的方法，都可以赋给这个委托类型的变量，然后通过变量调用。

下面先看一个自己声明的委托。`Transform` 规定了"接收一个 int，返回一个 int"的方法。

```csharp
public delegate int Transform(int x);

static int Square(int x) => x * x;

static int[] Apply(int[] values, Transform transform)
{
    var result = new int[values.Length];
    for (var i = 0; i < values.Length; i++)
    {
        result[i] = transform(values[i]);
    }

    return result;
}
```

```csharp
Transform square = Square;
Console.WriteLine($"square(4) = {square(4)}");
Console.WriteLine(string.Join(", ", Apply(new[] { 1, 2, 3 }, x => x * 10)));
```

输出如下。

```text
square(4) = 16
10, 20, 30
```

`Transform square = Square;` 把方法 `Square` 本身放进了变量里。`Apply` 接收的是"一个能把 int 变成 int 的东西"。调用方传进去的 `x => x * 10` 是一个 lambda，它也是一个方法，只不过没有名字。

委托也能指向实例的方法。

```csharp
public sealed class LevelFormatter
{
    private readonly string _left;
    private readonly string _right;

    public LevelFormatter(string left, string right)
    {
        _left = left;
        _right = right;
    }

    public string Wrap(string text) => $"{_left}{text}{_right}";
}
```

```csharp
var formatter = new LevelFormatter("[", "]");
Func<string, string> wrap = formatter.Wrap;
Console.WriteLine(wrap("error"));
```

输出如下。

```text
[error]
```

`formatter.Wrap` 没有加括号，它是一个方法组，表示"这个对象上的 Wrap 方法"。赋值之后，`wrap` 记住了是哪一个对象，调用它的时候，`_left` 和 `_right` 就是创建 `formatter` 时传入的值。

### 内置的 Func 与 Action

每次都声明一个新的委托类型很麻烦。.NET 提供了两组通用的委托。

| 类型 | 形状 | 例子 |
| --- | --- | --- |
| `Func<输入..., 输出>` | 有返回值 | `Func<int, bool>`，接收 int，返回 bool |
| `Action<输入...>` | 没有返回值 | `Action<string>`，接收 string，不返回 |

[第 10 章](/chapter/10)的 `Where`、`Select`、`OrderBy` 接收的都是 `Func`。`Where` 接收的是 `Func<T, bool>`，调用方决定哪些元素留下。`Select` 接收的是 `Func<T, TResult>`，调用方决定把每个元素变成什么。

项目里也是这样用的。`src/LogLens.Core/Query/QueryEngine.cs` 第 92 行的 `CompilePredicate` 返回一个 `Func<LogEvent, bool>`，也就是"给一条日志，返回是否命中"的判断函数。`src/LogLens.Core/Infrastructure/Result.cs` 中的 `Map`（第 42 行）接收一个 `Func<T, TOut>`，把成功的结果转换成另一种类型。

### 多播，一个委托可以指向多个方法

委托变量可以用 `+=` 加入更多的方法，调用时它们会按顺序全部执行。`-=` 则是移除其中一个。

```csharp
static void PrintA(string s) => Console.WriteLine($"A: {s}");

static void PrintB(string s) => Console.WriteLine($"B: {s}");

static void PrintC(string s) => Console.WriteLine($"C: {s}");
```

```csharp
Action<string>? chain = PrintA;
chain += PrintB;
chain += PrintC;
Console.WriteLine("-- 三个都调用 --");
chain?.Invoke("hello");
chain -= PrintB;
Console.WriteLine("-- 取消 B 之后 --");
chain?.Invoke("again");
```

输出如下。

```text
-- 三个都调用 --
A: hello
B: hello
C: hello
-- 取消 B 之后 --
A: again
C: again
```

`chain` 声明成了可空的 `Action<string>?`。这是因为 `-=` 之后，编译器无法保证委托不为空，所以调用时用 `?.Invoke`。如果写成 `chain("again")`，编译器会给出可空引用的警告。

多播的返回值有一个容易忽略的规则。带返回值的多播委托，调用后只能拿到最后一个方法的结果。

```csharp
Func<int, int> addOne = x => x + 1;
Func<int, int> timesTen = x => x * 10;
Func<int, int> both = addOne;
both += timesTen;
Console.WriteLine($"多播的返回值（取最后一个）：{both(3)}");
```

输出如下。

```text
多播的返回值（取最后一个）：30
```

`addOne` 的结果 4 被丢掉了，只剩下 `timesTen(3)` 的 30。如果你希望拿到每个方法的结果，就不能直接调用多播委托，要用 `GetInvocationList()` 逐个调用。

### 闭包捕获的是变量，不是当时的值

lambda 可以使用它外面的变量，这叫**闭包**。它捕获的是变量本身，所以变量后来改了，lambda 看到的也是新值。

```csharp
int factor = 2;
Func<int, int> times = x => x * factor;
Console.WriteLine($"factor=2 时 times(5) = {times(5)}");
factor = 10;
Console.WriteLine($"factor=10 时 times(5) = {times(5)}");
```

输出如下。

```text
factor=2 时 times(5) = 10
factor=10 时 times(5) = 50
```

闭包在 `for` 循环里还有一个更容易出错的地方，下面“委托的风险”的风险一会详细讲。

### 委托的风险，哪些在本项目里真实存在

委托很灵活，正因为灵活，它也容易被用过头。这一节先说明 LogLens 源码里的情况，再列出通用的风险。

我们在项目源码里搜索了所有 `+=`、`-=`、`event` 和 `EventHandler`，并逐处读了它们的上下文。结论是，项目里没有把委托作为公开字段直接订阅的写法，长期保存并订阅的地方都用 `event` 声明。另外，项目里的委托大多是方法参数或 LINQ 的条件，用完就丢。长期保存委托的例外是命令面板，它的每条命令都保存着一个 `Func<Task>`，下面的风险一会用到它。

下面的风险分成两类。第一类是项目里有证据的，第二类是通用风险，项目里没有找到对应的写法，但写代码时仍然可能遇到。

**风险一，循环里保存的 lambda 会共享同一个循环变量（通用风险）**

上一节说过，闭包捕获的是变量本身。在 `for` 循环里，这会带来一个具体的问题。先回顾一下闭包的基本行为。

```csharp
int factor = 2;
Func<int, int> times = x => x * factor;
Console.WriteLine($"factor=2 时 times(5) = {times(5)}");
factor = 10;
Console.WriteLine($"factor=10 时 times(5) = {times(5)}");
```

输出依次是 `factor=2 时 times(5) = 10` 和 `factor=10 时 times(5) = 50`。

这类错误最常出现在 `for` 循环里。`for` 只有一个循环变量 `i`，所有 lambda 共享它。下面两段代码看起来相似，结果却不同。

```csharp
var bad = new List<Action>();
for (int i = 0; i < 3; i++)
{
    bad.Add(() => Console.WriteLine($"for 捕获：{i}"));
}
foreach (var action in bad)
{
    action();
}

var good = new List<Action>();
for (int i = 0; i < 3; i++)
{
    int copy = i;
    good.Add(() => Console.WriteLine($"副本捕获：{copy}"));
}
foreach (var action in good)
{
    action();
}
```

输出依次是三行 `for 捕获：3`，以及三行 `副本捕获：0`、`副本捕获：1`、`副本捕获：2`。`bad` 的三个 lambda 共享同一个 `i`，循环结束后它已经是 3。`good` 每次循环都声明了新的 `copy`，每个 lambda 捕获的是各自的那一个。

`foreach` 不会有这个问题。每次迭代的循环变量都是新的，所以把 `foreach` 的变量交给 lambda 保存，结果是各自的值。

LogLens 里有一处这样的写法，就是命令面板。`MainWindowViewModel.cs` 第 333 行开始的 `foreach` 为每个导航项生成一条命令，第 342 行的 `Run` 捕获了循环变量 `item`，执行时把 `SelectedNavigation` 设为那一项。每条命令保存的都是自己对应的导航项。项目里没有找到 `for` 循环中保存 lambda 的写法，所以这里的 `foreach` 是安全的。

规避的方法有两个。一是在保存 lambda 之前复制一份变量，就像上面的 `copy`。二是在声明查询的时候立刻用 `ToList()` 固定结果，[第 10 章](/chapter/10)讲过这一点。

**风险二，多播的返回值只剩最后一个（通用风险）**

一个委托可以同时指向多个方法，调用它时，所有方法都会按顺序执行。但是调用的结果只有最后一个方法的返回值。

```csharp
Func<int> multi = () => 1;
multi += () => 2;
Console.WriteLine($"直接调用：{multi()}");
```

输出 `直接调用：2`。第一个方法返回的 `1` 没有任何地方保存，直接丢掉了。这种写法在有返回值的委托上很容易被忽略，尤其是当多播是在别处悄悄加上的。

规避的方法是不让多播去收集返回值。如果确实需要每个方法的结果，就用 `GetInvocationList()` 把它们拆开，逐个调用。

```csharp
foreach (Func<int> single in multi.GetInvocationList())
{
    Console.WriteLine($"逐个调用：{single()}");
}
```

输出 `逐个调用：1` 和 `逐个调用：2`。

**风险三，委托字段可以被外部整体覆盖（通用风险）**

如果把委托作为公开字段，外面可以用 `=` 整体替换掉前面所有的订阅者。

```csharp
var field = new FieldSource();
field.Changed += () => Console.WriteLine("订阅者 A");
field.Changed += () => Console.WriteLine("订阅者 B");
field.Changed = () => Console.WriteLine("外部覆盖了全部订阅者");
field.Fire();
```

输出 `外部覆盖了全部订阅者`。订阅者 A 和 B 都没有被调用。规避的方法是用 `event` 声明，9.2 节会讲它为什么能防止这种覆盖。

**风险四，一组委托总是一起出现，应该写成接口（设计上的风险）**

如果一个方法的参数里有好几个 `Func` 或 `Action`，调用方要自己记住每个参数代表什么，签名也会越来越长。这时可以把它们命名为一个接口，让每个成员都有名字。当一组委托总是一起出现，它们多半应该是一个接口。

**风险五，委托和事件混用，调用关系变得难以追踪（设计上的风险）**

如果只是想让一个对象调用另一个对象的某个行为，直接传入一个接口，比用委托更清楚。委托适合“这一次调用传入一段逻辑”的场合，比如 `Where` 的判断条件。把委托存起来、在别处再调用，这种用法在项目里出现时要多一分小心，因为读代码的人很难看出谁在什么时候调用了它。

## 9.2 事件，让对象发出通知

事件建立在委托之上。它让一个对象在某件事发生时通知其他对象，同时不允许外面随意改动通知的名单。

### 委托字段的问题

先看把委托直接作为公开字段的写法。

```csharp
public sealed class FieldSource
{
    public Action? Changed;

    public void Fire() => Changed?.Invoke();
}
```

```csharp
var field = new FieldSource();
field.Changed += () => Console.WriteLine("订阅者 A");
field.Changed += () => Console.WriteLine("订阅者 B");
field.Changed = () => Console.WriteLine("外部覆盖了全部订阅者");
field.Fire();
```

输出如下。

```text
外部覆盖了全部订阅者
```

`Changed` 是公开字段，外面可以用 `=` 直接替换掉前面两个订阅者，整个名单都被覆盖了。发布者失去了对自己订阅者名单的控制。

### event 关键字

把字段换成 `event`，外面就只能用 `+=` 和 `-=` 增加或移除订阅者，不能整体赋值，也不能直接调用。

```csharp
public sealed class EventSource
{
    public event Action? Changed;

    public void Fire() => Changed?.Invoke();
}
```

```csharp
var evented = new EventSource();
evented.Changed += () => Console.WriteLine("订阅者 A");
evented.Changed += () => Console.WriteLine("订阅者 B");
evented.Fire();
```

输出如下。

```text
订阅者 A
订阅者 B
```

如果在外面写 `evented.Changed = null`，编译器会报 `CS0070`，提示事件只能出现在 `+=` 或 `-=` 的左边，除非是在声明它的类型内部使用。事件把"谁来订阅"的权力交给了订阅者，把"什么时候通知"的权力留给了发布者。

### 观察者，一个对象发出，多个对象接收

用事件来实现观察者模式很常见。下面的 `LogWatcher` 每追加一行日志，就发出一个事件，订阅它的对象各自决定怎么处理。

```csharp
public sealed class LogAppendedEventArgs : EventArgs
{
    public LogAppendedEventArgs(string line) => Line = line;

    public string Line { get; }
}

public sealed class LogWatcher
{
    public event EventHandler<LogAppendedEventArgs>? LogAppended;

    public void Append(string line) => OnLogAppended(new LogAppendedEventArgs(line));

    private void OnLogAppended(LogAppendedEventArgs e) => LogAppended?.Invoke(this, e);
}

public sealed class ErrorCounter
{
    public int Errors { get; private set; }

    public void Handle(object? sender, LogAppendedEventArgs e)
    {
        if (e.Line.StartsWith("ERROR", StringComparison.Ordinal))
        {
            Errors++;
        }
    }
}
```

```csharp
var watcher = new LogWatcher();
var counter = new ErrorCounter();
watcher.LogAppended += counter.Handle;
watcher.LogAppended += (sender, e) => Console.WriteLine($"显示：{e.Line}");
watcher.Append("INFO 启动");
watcher.Append("ERROR 处理订单失败");
Console.WriteLine($"错误数：{counter.Errors}");
```

输出如下。

```text
显示：INFO 启动
显示：ERROR 处理订单失败
错误数：1
```

`LogWatcher` 不知道有几个订阅者，也不关心它们做什么。`ErrorCounter` 只统计错误，另一个 lambda 只负责显示。以后再加一个写文件的订阅者，`LogWatcher` 一行都不用改。

按照 .NET 的约定，事件处理器的签名是 `(object? sender, TEventArgs e)`。`sender` 是发出事件的对象，`e` 携带事件的数据。这就是为什么 `ErrorCounter.Handle` 能直接作为订阅者使用。

项目里的 `src/LogLens.Studio/Services/TailService.cs` 第 51 行声明了 `public event EventHandler<TailBatch>? BatchReceived;`。第 166 行在每批新内容处理完之后发出事件，哪怕这一批是空的，也要通知界面刷新"已读行数"。第 188 行在收尾时把最后剩下的事件也发出去。界面订阅这个事件，`TailService` 本身不需要知道界面的存在。

### 本项目里的事件，正确的写法和有代价的写法

这一节的每一条都能在 LogLens 源码里找到对应的位置，行号按当前版本记录。

先看几处写得比较稳妥的做法。

**后台线程发出，界面线程接收。** `TailService.cs` 第 51 行声明了 `public event EventHandler<TailBatch>? BatchReceived;`。第 166 行和第 188 行在后台读取文件的过程中发出这个事件。`TailViewModel.cs` 第 70 行订阅它，第 234 行起的 `OnBatchReceived` 先用 `Dispatcher.UIThread.CheckAccess()` 判断当前是不是界面线程，不是的话就用 `Dispatcher.UIThread.Post` 把工作交回界面线程（第 236 至 238 行）。订阅者自己负责切换线程，发布者不需要知道界面的存在。

**不再需要时退订。** `TailViewModel.Dispose`（第 343 行起）在第 351 行执行 `_tail.BatchReceived -= OnBatchReceived;`。注释写的是“避免服务继续往一个已经扔掉的页面里推数据”。`TailService` 会一直存在，如果页面不退订，页面就会一直被它引用。

**换人时先退订旧对象。** `Views/MainWindow.axaml.cs` 第 32 行订阅 `DataContextChanged`。第 36 行起的方法在 `DataContext` 换人时，先在第 40 行 `-=` 旧对象的 `PropertyChanged`，再在第 47 行 `+=` 新对象。注释写的是“避免内存泄漏”。

**无论成功还是异常都退订。** `CliApplication.cs` 第 148 行订阅 `Console.CancelKeyPress`，第 180 至 182 行的 `finally` 中退订。中间即使抛出异常，退订也会执行。

**换源时成对地退订和订阅。** `Controls/ListBoxBehaviors.cs` 第 84 行订阅集合的 `CollectionChanged`，第 92 行在 `Detach` 中退订。换源时先退订旧集合，再订阅新集合。

有代价的写法也有两处。

**匿名 lambda 订阅，无法退订。** `MainWindowViewModel.cs` 第 150 行写的是 `_themeService.ModeChanged += (_, _) => OnPropertyChanged(nameof(IsDarkTheme));`。这个 lambda 没有保存引用，以后无法 `-=` 掉它。好在 `ThemeService` 是单例（`ServiceRegistration.cs` 第 41 行注册），`MainWindowViewModel` 也是单例（`StudioBootstrapper.cs` 第 36 行注册），两者的生命周期与应用相同，所以影响有限。但如果以后对一个会被销毁的对象这样订阅，就会留下隐患。

**异步 lambda 作为事件处理器。** `App.axaml.cs` 第 75 行写的是 `desktop.ShutdownRequested += async (_, _) => { ... await settingsService.SaveAsync() ... };`。`async` 处理器里抛出的异常不会回到触发事件的那一行代码，发布者用 `try/catch` 也抓不到。这里保存的是窗口大小和设置，保存失败时需要有别的途径让人知道。

最后要说明一点，我们搜索了源码，没有找到把委托作为公开字段直接订阅的写法，也没有找到在循环里保存会捕获循环变量的 lambda。

### 通用风险，本项目中不常见但要知道

下面四种风险在本项目里没有引起问题，但它们是事件的通用特性，换一个项目很可能遇到。

**风险一，订阅者抛出的异常会打断后面的订阅者。** 事件按顺序依次调用订阅者，中途的异常会直接跳出整个调用过程。

```csharp
var noisy = new LogWatcher();
noisy.LogAppended += (sender, e) => throw new InvalidOperationException("第一个订阅者出错");
noisy.LogAppended += (sender, e) => Console.WriteLine("第二个订阅者");
try
{
    noisy.Append("x");
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"捕获：{ex.Message}");
}
```

输出只有 `捕获：第一个订阅者出错`，第二个订阅者没有被调用。规避的方法见后面的“逐个调用订阅者”。

**风险二，`-=` 只认委托的引用。** 两个 lambda 即使代码完全一样，也是两个不同的对象。下面的 `leaky` 没有取消成功，`clean` 把处理器保存在变量里，取消成功了。

```csharp
var leaky = new LogWatcher();
leaky.LogAppended += (sender, e) => Console.WriteLine("匿名处理");
leaky.LogAppended -= (sender, e) => Console.WriteLine("匿名处理");
leaky.Append("y");

var clean = new LogWatcher();
EventHandler<LogAppendedEventArgs> handler = (sender, e) => Console.WriteLine("可以取消的处理");
clean.LogAppended += handler;
clean.Append("z");
clean.LogAppended -= handler;
clean.Append("没人收到这一条");
```

输出依次是 `匿名处理`、`可以取消的处理`。`leaky` 的订阅没有被取消，所以 `匿名处理` 仍然输出。`clean` 的 `-=` 用的是同一个对象，取消成功，所以 `没人收到这一条` 没有输出。

**风险三，忘记退订会让订阅者无法回收。** 发布者持有订阅者的引用，只要订阅没有被移除，订阅者就不会被回收，即使它已经不再使用。长时间运行的程序里，这会让对象一直占着内存。

**风险四，事件默认在触发它的线程上同步执行。** 订阅者如果很慢，发布者就会被拖慢。跨线程发出的事件，订阅者要自己切回界面线程，就像 `OnBatchReceived` 那样。

### 规避方法

**逐个调用订阅者，收集异常。** 用 `GetInvocationList()` 拆开多播委托，每个订阅者单独调用并捕获异常，最后统一报告。

```csharp
EventHandler<string>? handlers = null;
handlers += (_, msg) => throw new InvalidOperationException($"处理器 1 失败：{msg}");
handlers += (_, msg) => Console.WriteLine($"处理器 2 收到：{msg}");
handlers += (_, msg) => throw new InvalidOperationException($"处理器 3 失败：{msg}");

var errors = new List<Exception>();
if (handlers is not null)
{
    foreach (EventHandler<string> handler in handlers.GetInvocationList())
    {
        try
        {
            handler(null, "启动");
        }
        catch (Exception ex)
        {
            errors.Add(ex);
        }
    }
}
Console.WriteLine($"共收集到 {errors.Count} 个异常");
```

输出依次是 `处理器 2 收到：启动` 和 `共收集到 2 个异常`。两个失败的处理器都被调用了，第二个处理器也完整地执行了。

**让订阅方法返回一个可释放的令牌。** 调用方用 `using` 包住订阅，离开作用域时自动退订。这种做法避免了“忘记 `-=`”和“匿名 lambda 取不回来”两个问题。

```csharp
public sealed class LogWatcher
{
    private EventHandler<LogAppendedEventArgs>? _logAppended;

    public event EventHandler<LogAppendedEventArgs>? LogAppended
    {
        add => _logAppended += value;
        remove => _logAppended -= value;
    }

    public int Count => _logAppended?.GetInvocationList().Length ?? 0;

    public void Append(string line) => _logAppended?.Invoke(this, new LogAppendedEventArgs(line));

    public IDisposable Subscribe(EventHandler<LogAppendedEventArgs> handler)
    {
        LogAppended += handler;
        return new Subscription(this, handler);
    }

    private sealed class Subscription : IDisposable
    {
        private readonly LogWatcher _owner;
        private readonly EventHandler<LogAppendedEventArgs> _handler;
        private bool _disposed;

        public Subscription(LogWatcher owner, EventHandler<LogAppendedEventArgs> handler)
        {
            _owner = owner;
            _handler = handler;
        }

        public void Dispose()
        {
            if (_disposed)
            {
                return;
            }

            _disposed = true;
            _owner.LogAppended -= _handler;
        }
    }
}
```

```csharp
var safe = new LogWatcher();
using (safe.Subscribe((sender, e) => Console.WriteLine("令牌订阅仍在")))
{
    safe.Append("第一次");
}
safe.Append("离开 using 之后");
Console.WriteLine($"令牌退订后剩余订阅者：{safe.Count}");
```

输出依次是 `令牌订阅仍在` 和 `令牌退订后剩余订阅者：0`。`using` 结束时，订阅已经被移除，所以 `离开 using 之后` 没有任何输出。

这里的 `LogWatcher` 用了显式的 `add` 和 `remove`，是因为要在其中维护 `_logAppended` 字段，并且统计订阅者数量。第一次看这段代码时，不必深究 `Subscription` 的细节，记住它的用途就够了，`Subscribe` 返回的对象负责在 `Dispose` 时退订。

**保存引用，再替换处理器。** 如果需要换一个处理器，先保存旧的引用并 `-=`，再 `+=` 新的。

```csharp
var rebind = new LogWatcher();
EventHandler<LogAppendedEventArgs> current = (sender, e) => Console.WriteLine("旧处理器");
rebind.LogAppended += current;
rebind.LogAppended -= current;
current = (sender, e) => Console.WriteLine("新处理器");
rebind.LogAppended += current;
rebind.Append("换源");
```

输出 `新处理器`。`-=` 用的是同一个引用，旧处理器被完整地移除了。

### 规避方法汇总

| 风险 | 规避方法 | 本项目中的做法 |
| --- | --- | --- |
| 订阅者异常打断后续订阅者 | 订阅者内部 `try/catch`，或逐个调用并收集异常 | 本项目里没有统一使用这两种方法，需要时采用 |
| 匿名 lambda 无法退订 | 保存到变量里再 `-=`，或返回可释放的令牌 | `TailViewModel.cs` 第 70 行使用方法名订阅，第 351 行退订 |
| 忘记退订导致对象无法回收 | 在 `Dispose`、`finally` 或换源时成对地退订 | `TailViewModel.cs` 第 351 行，`CliApplication.cs` 第 182 行，`Views/MainWindow.axaml.cs` 第 40 行 |
| 跨线程触发 | 先用 `CheckAccess` 判断线程，不对时用 `Post` 切回 | `TailViewModel.cs` 第 236 至 238 行 |
| 异步处理器的异常无人观察 | 处理器内部 `try/catch`，并记录或显示错误 | `App.axaml.cs` 第 75 行没有 `try/catch`，设置保存失败需要留意 |

### 事件被滥用的地方

事件最大的风险，是让调用关系变得看不见。`watcher.Append("...")` 这一行看上去只是写入一行文字，实际上可能触发了一串处理，而这些处理分散在不同的文件里。读代码的人必须找遍所有的 `+=`，才能知道一行调用会做什么。

所以，事件适合“一个发出，多个不相干的对象各自响应”的场合。如果只有一个接收方，或者接收方需要的是一个明确的动作，直接调用方法，或者传入接口，通常更容易理解、测试和维护。不要为了让代码“解耦”而把所有调用都换成事件。

## 9.3 Lambda 与 LINQ，委托最常见的用法

lambda 是写委托最简短的方式。它的语法是 `参数 => 表达式`，或者 `参数 => { 语句 }`。

```csharp
var sample = new[] { "level=error module=order", "INFO api 启动", "level=warn module=db" };
var withEquals = sample.Where(line => line.Contains('=')).ToList();
Console.WriteLine($"含有 = 的行：{withEquals.Count} 行");
```

输出如下。

```text
含有 = 的行：2 行
```

`Where` 接收的参数类型是 `Func<string, bool>`，所以 `line => line.Contains('=')` 的 `line` 就是 `string`，返回值是 `bool`。lambda 本身没有类型，它的类型由接收它的委托决定。这一点和 7.9 节的 `Apply(new[] { 1, 2, 3 }, x => x * 10)` 是一样的。

lambda 的参数个数和委托一致。事件的订阅者要两个参数，所以写 `(sender, e) => ...`。参数只有一个时，可以省略括号。

lambda 也能写成多行，只要用花括号包起来。

```csharp
Action<string> report = line =>
{
    var trimmed = line.Trim();
    Console.WriteLine($"[{trimmed.Length}] {trimmed}");
};
report("  warn disk full  ");
```

输出如下。

```text
[14] warn disk full
```

这段代码里，`report` 不接收外部的变量，所以它很简单。如果 lambda 使用了外面的变量，就会形成闭包，行为的细节在 9.1 节已经讲过。

LINQ 是建立在委托之上的一套查询方法。`Where`、`Select`、`OrderBy` 这些方法都接收 lambda，所以读懂了委托，就能读懂大部分 LINQ 的写法。[第 8 章](/chapter/08)会专门讲 LINQ，这里先记住一件事。LINQ 的每一步都是一个委托在做判断或转换，方法本身负责遍历。

项目里的 `Result<T>` 也用同样的方式。`Map` 接收一个 `Func<T, TOut>`，`Switch` 接收两个 `Action`，分别处理成功和失败的情况。调用方用 lambda 写出处理逻辑，`Result<T>` 决定什么时候执行它。

## 9.4 常见错误

下表中的错误码与现象都是在检查点或探针中实际出现的。

| 报错或现象 | 原因 | 怎么改 |
| --- | --- | --- |
| `CS0070` 事件只能出现在 `+=` 或 `-=` 的左边 | 在声明事件的类之外写了 `evented.Changed = null`，或直接调用事件 | 只做订阅与退订；触发事件只放在声明它的类里，像 `Fire` 那样 |
| `CS8602` 解引用可能为 null 的引用（警告） | 对 `Action<string>?` 直接写 `chain("again")`，没有检查它是否为 `null` | 用 `chain?.Invoke("again")` 调用 |
| 同一个 `for` 循环里的 lambda 输出都是 `3` | 所有 lambda 共享同一个循环变量 `i` | 在循环体内复制一份，写成 `int copy = i;` |
| 多播委托只得到一个返回值 | 调用多播委托时，只有最后一个方法的返回值被保留 | 用 `GetInvocationList()` 逐个调用 |
| 一个订阅者抛出异常，后面的订阅者没有运行 | 事件按顺序调用订阅者，异常直接跳出调用过程 | 逐个调用并收集异常，见 [9.2 节](#s9-2) |
| 退订失败，`-=` 之后还能收到通知 | 退订的是另一个 lambda 对象，而不是订阅时的那一个 | 把处理器保存在变量里，或使用返回可释放令牌的订阅方法 |

`CS8602` 是警告，程序仍然能编译，所以很容易被忽视。把警告当作错误看待，能更早发现这类问题。

## 9.5 小练习

**练习 1（事件的退订）**，用 `-=` 取消 `ErrorCounter` 对 `LogWatcher` 的订阅。取消之后，再 `Append` 的 `ERROR` 行不会再被计数。

<details>
<summary>参考答案</summary>

```csharp
var watcher = new LogWatcher();
var counter = new ErrorCounter();
watcher.LogAppended += counter.Handle;
watcher.Append("ERROR 一");
watcher.LogAppended -= counter.Handle;
watcher.Append("ERROR 二");
Console.WriteLine($"取消订阅之后错误数 = {counter.Errors}");
```

输出为 `取消订阅之后错误数 = 1`。`-=` 能成功，是因为委托比较的是目标对象和方法。同一个对象的同一个方法，即使是分开写的方法组，也会被当作同一个订阅来移除。

</details>

**练习 2（思考）**，`CountBy` 的 lambda 写成 `line => line.Split(' ')[1]`，运行时如果某一行只有一个词，会发生什么？这和委托有什么关系？

<details>
<summary>参考答案</summary>

`Split(' ')[1]` 会抛出 `IndexOutOfRangeException`。委托本身不会检查这件事。lambda 是被 `CountBy` 调用的，异常从调用处一路传出来。因此，在委托里访问数组和字典时，要把"可能失败"的情况放进 lambda 里处理，或者在调用前过滤掉。

</details>
