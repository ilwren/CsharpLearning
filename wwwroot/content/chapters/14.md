## 14.1 三种"工具"从哪来

写程序时用到的工具，大致有三个来源。

- **标准库**，.NET 自带的，像厨房里的锅碗瓢盆。`File`、`Path`、`Regex`、`JsonSerializer` 都在这里。你装好 .NET 就有，不用额外安装。
- **第三方库**，别人写好的半成品，比如 Newtonsoft.Json、CsvHelper。它们解决的是标准库没覆盖、或者覆盖得不够顺手的问题。
- **NuGet**，半成品的超市。第三方库都放在 [nuget.org](https://nuget.org) 上，你在项目里声明一下，NuGet 会帮你下载、放好、记录版本。

项目里能看到这三种工具的分布。`LogLens.Core` 只依赖标准库，它的 `.csproj` 里没有任何 `PackageReference`。`LogLens.Cli` 只引用了 `Core`。`LogLens.Studio` 是图形界面，它引用了 Avalonia 等 7 个包。这种"核心越干净，外围越丰富"的结构，是一个很值得学的习惯，14.28 节会回头看它。

## 14.3 文件与路径

读写文件是最常见的操作之一。.NET 给了三个好帮手。

- `File`，读写整个文件，比如 `File.ReadAllText`、`File.WriteAllText`、`File.Exists`。
- `Directory`，处理目录，比如 `Directory.CreateDirectory`、`Directory.Delete`。
- `Path`，处理路径字符串，比如 `Path.Combine`、`Path.GetFileName`、`Path.GetExtension`。

路径为什么要用 `Path.Combine`，而不是字符串拼接？因为不同系统的分隔符不一样。Windows 用反斜杠 `\`，Linux 和 macOS 用斜杠 `/`。你手写 `dir + "\\" + name`，换到另一台电脑上可能就出错了。`Path.Combine` 会替你处理这些细节。

```csharp
var workDir = Path.Combine(Directory.GetCurrentDirectory(), "demo-output");
Directory.CreateDirectory(workDir);

var logPath = Path.Combine(workDir, "app.log");
File.WriteAllText(logPath, "服务启动", Encoding.UTF8);

Console.WriteLine($"文件名：{Path.GetFileName(logPath)}，扩展名：{Path.GetExtension(logPath)}");
Console.WriteLine($"文件存在：{File.Exists(logPath)}");
```

项目里 `ReportExporter.cs` 的写法值得一读。它先用 `Path.GetFullPath` 把路径变成完整路径，再用 `Path.GetDirectoryName` 取出目录，确认目录存在后才写文件。这一串步骤的顺序很合理，先弄清楚"写到哪里"，再动手写。

## 14.4 文本与编码

### 拼字符串，`StringBuilder`

字符串是不可修改的。每次用 `+=` 拼接，都会生成一个新字符串。拼的次数少没问题；如果要在循环里拼很多次，用 `StringBuilder` 更合适。

```csharp
var sb = new StringBuilder();
foreach (var hit in hits)
{
    sb.AppendLine($"{hit.Level} {hit.Note}");
}
var text = sb.ToString();
```

### 编码，中文到底占几个字节？

字符和字节不是一回事。下面这段代码会告诉你答案。

```csharp
var chinese = "中文";
Console.WriteLine($"字符数 {chinese.Length}，UTF-8 字节数 {Encoding.UTF8.GetByteCount(chinese)}");
// 字符数 2，UTF-8 字节数 6
```

两个汉字，在 UTF-8 里一共是 6 个字节，每个汉字 3 个字节。文件大小、网络传输，都是按字节算的。

还有一个小细节。`Encoding.UTF8` 默认会在文件开头写一个叫 BOM 的标记。有些工具会把它当成多出来的字符。项目里 `ReportExporter.cs` L60 用的是。

```csharp
await File.WriteAllTextAsync(path, content, new UTF8Encoding(encoderShouldEmitUTF8Identifier: false), cancellationToken)
```

`encoderShouldEmitUTF8Identifier: false` 的意思就是"不要写 BOM"。这是为了让导出的报告能被更多工具正确读取。

控制台也有编码问题。`Cli/Program.cs` L13 设置了。

```csharp
Console.OutputEncoding = System.Text.Encoding.UTF8;
```

如果你在 Windows 终端里看到中文变成乱码，多半是这里的编码没设对。这个问题非常常见，值得养成习惯，输出中文之前，先确认编码。

## 14.5 计时，`Stopwatch` 比 `DateTime.Now` 更适合

想知道一段代码跑了多久，很多人会写。

```csharp
var start = DateTime.Now;
// ... 要计时的代码 ...
var cost = DateTime.Now - start;
```

这样写大多数时候没问题，但有一个隐患，`DateTime.Now` 取的是系统时钟，而系统时钟可能会因为时间同步、夏令时之类的原因被调整。计时中途如果时钟往回跳，结果就不准了。

`Stopwatch` 用的是专门为计时设计的单调时钟，它只往前走，更适合测量耗时。

```csharp
var sw = Stopwatch.StartNew();

// ... 要计时的代码 ...

sw.Stop();
Console.WriteLine($"耗时 {sw.ElapsedMilliseconds} ms");
```

项目的 `LogAnalyzer.cs` L26 和 `QueryEngine.cs` L51 都用它来统计分析和查询花了多久，这些数字最终会显示在报告里。

## 14.6 配置文件是什么

假设你的程序每次运行都要用到"最多显示多少行""默认看哪些级别"这类设置。最直接的做法是把它们写死在代码里。

```csharp
var maxRows = 5000;
```

但改一个数字就要重新编译一次。配置文件的思路是，把可以改的值放进一个单独的文件，程序启动时读取它。以后要改，直接改文件，不用碰代码。

这个文件就像程序的"说明书"。它通常是纯文本，格式有好几种，最常见的是 JSON。

LogLens 项目里就有两个这样的文件。

- `Cli/AppSettings.cs` 的文档注释写着，它持久化到 `settings.json`。这是命令行版本的用户偏好设置。
- `Studio/Services/AppSettingsService.cs` 把图形界面的设置存成 `studio-settings.json`，文件位置由 `DataDirectory` 决定。

两个文件用的都是 JSON。下一节先讲格式，再讲怎么读写。

## 14.7 常见格式一览

配置文件有很多种格式，各有各的脾气。下面这张表只是让你认识它们的样子，不做完整比较。

| 格式 | 长什么样 | 特点 | 常见于 |
| --- | --- | --- | --- |
| JSON | `{ "maxRows": 5000 }` | 结构清楚，几乎所有语言都支持；标准里不允许注释 | Web 接口、.NET 项目设置 |
| XML | `<maxRows>5000</maxRows>` | 很啰嗦，但格式严格，有成熟的校验机制 | 老的 .NET Framework 项目、企业系统 |
| YAML | `maxRows: 5000` | 靠缩进表示层级，写起来短，缩进错了很难发现 | 容器与 CI 配置 |
| TOML | `maxRows = 5000` | 类似 INI 但有类型与分组，语法小巧 | Rust 项目、部分 Python 工具 |
| INI | `maxRows=5000` | 最古老的一种，只有"节 + 键值"两层 | 老的 Windows 程序 |
| `.properties` | `maxRows=5000` | 键值对，Java 生态里最常见 | Java 项目 |
| 环境变量 | `MAXROWS=5000` | 不是文件，由系统或容器传入，适合部署时改 | 容器、服务器部署 |
| 命令行参数 | `--max-rows 5000` | 运行时直接给，适合临时覆盖 | 所有命令行程序 |

这张表里的示例只是格式的样子，我们没有用每种格式的解析器逐个运行。本章其余部分只实际用到 JSON。

在 .NET 里，配置文件还有一个常见的组合方式，先读一个默认文件，再让环境变量或命令行参数覆盖其中的个别值。这已经超出本章的范围，等讲到项目的服务和依赖注入（第 24 章）时再说。

## 14.8 JSON 入门

JSON 只有六种值。

| 类型 | 例子 |
| --- | --- |
| 对象 | `{ "name": "LogLens" }` |
| 数组 | `["error", "warn"]` |
| 字符串 | `"LogLens"`，必须用双引号 |
| 数字 | `5000`，不加引号 |
| 布尔 | `true`、`false` |
| 空 | `null` |

一个完整的例子。

```json
{
  "name": "LogLens",
  "maxRows": 5000,
  "levels": ["error", "warn"]
}
```

JSON 有两条很严格的规则，新手最容易踩。

1. **不能写注释**。标准 JSON 里没有 `//` 和 `/* */`。
2. **最后一项后面不能有逗号**。`"levels": ["error", "warn",]` 是不合法的。

我们故意写错，看看 `System.Text.Json` 会给出什么提示。

```csharp
var text = "{\"name\": \"x\",}";
System.Text.Json.JsonSerializer.Deserialize<Dictionary<string, string>>(text);
// 抛出 JsonException：The JSON object contains a trailing comma at the end which is not supported in this mode.
```

错误信息里会告诉你位置（`Path: $.name`、`BytePositionInLine: 13`）。读错误信息，是排查配置问题最快的方法。这和[第 11 章](/chapter/11)讲的"先读懂堆栈"是同一个习惯。

## 14.9 在 C# 里读写 JSON

.NET 里最常用的两个 JSON 库是 `System.Text.Json`（标准库自带）和 Newtonsoft.Json（第三方库）。本节先讲标准库的做法，14.17 节再讲 Newtonsoft。

### 读写一个配置类

先定义一个类，属性名对应 JSON 里的键。

```csharp
public sealed class AppSettings
{
    public string Name { get; set; } = "";
    public int MaxRows { get; set; } = 20000;
    public List<string> Levels { get; set; } = [];
}
```

然后读写。

```csharp
var json = File.ReadAllText("settings.json");
var settings = System.Text.Json.JsonSerializer.Deserialize<AppSettings>(json)!;

var output = System.Text.Json.JsonSerializer.Serialize(settings);
```

`Deserialize` 把文本变成对象，`Serialize` 反过来。

### 复用 `JsonSerializerOptions`

`JsonSerializerOptions` 是一组设置，比如要不要缩进、属性名用什么大小写。它的创建成本不低，应该做成静态只读的字段，反复使用。项目的 `JsonDefaults.cs` 正是这样做的。

```csharp
public static JsonSerializerOptions Pretty { get; } = new(JsonSerializerDefaults.Web)
{
    WriteIndented = true,
    Encoder = JavaScriptEncoder.UnsafeRelaxedJsonEscaping,
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull,
    Converters = { new JsonStringEnumConverter(JsonNamingPolicy.CamelCase) },
};
```

`JsonReportWriter.cs` L91 和 `AppSettingsService.cs` 都在用它。

### 大小写的坑

JSON 的键通常是小驼峰（`maxRows`），C# 的属性通常是大驼峰（`MaxRows`）。两者默认不会自动对上。这里有两个默认值需要分清。

- `System.Text.Json` 的默认设置里，`PropertyNameCaseInsensitive` 是 `false`，键名必须大小写完全一致。
- `JsonSerializerDefaults.Web` 是一组给 Web 场景用的预设，它把 `PropertyNameCaseInsensitive` 设为 `true`，并使用小驼峰命名。项目的 `JsonDefaults` 就是基于它。

所以，如果你在自己的代码里改用默认设置，突然发现字段读不进来，先看一下大小写。

### 注释和尾随逗号

这两件事在 `System.Text.Json` 里默认都不被允许。下面是默认设置下读取带注释的文件的结果。

```csharp
var text = """
    {
      // 注释
      "name": "LogLens"
    }
    """;
System.Text.Json.JsonSerializer.Deserialize<AppSettings>(text);
// 报错：'/' is invalid after a value. Expected either ',', '}', or ']'.
```

如果确实要允许，就要显式打开。

```csharp
var tolerant = new JsonSerializerOptions
{
    PropertyNameCaseInsensitive = true,
    ReadCommentHandling = JsonCommentHandling.Skip,   // 跳过注释
    AllowTrailingCommas = true,                       // 允许最后一项后面的逗号
};
```

检查点里就用这套设置，读到了带注释的 `settings.json`，结果正确。

## 14.10 配置文件的常见坑

把配置文件交给别人改，最容易出现下面这些问题。

1. **多一个逗号，或者少一个引号**。这是 JSON 最常见的错误，编辑器里看不出来，程序启动时才报错。推荐用支持 JSON 校验的编辑器。
2. **注释不被支持**。标准 JSON 不允许注释，写了注释的文件在默认设置下读不了。删掉注释是最简单的办法；像 14.9 那样打开选项也行；如果必须保留注释，可以换一种支持注释的格式，比如 YAML 或 TOML。
3. **大小写不一致**。`maxrows` 和 `maxRows` 在默认设置下不是同一个键。
4. **文件编码不统一**。配置文件最好统一用 UTF-8 保存。如果用记事本或其它编辑器保存成了别的编码，中文会变乱码，而读取方可能直接报错。
5. **路径写死**。`C:\\logs\\app.log` 在 Windows 上没问题，换到 Linux 就找不到了。路径尽量用相对路径，再用 `Path.Combine` 拼接。

## 14.11 正则表达式是什么

正则表达式（Regular Expression，简称 regex）是一门描述"文字长什么样"的小语言。你不用一条一条去比对字符，而是写一个模式，告诉程序，"找出所有像这样的文字"。

可以把它想象成给文字画一张**通缉令**。通缉令上写着，身高一米七左右，穿红衣服，左脸有痣。符合这些描述的人都会被抓出来。正则就是这样一张通缉令，符合它描述的文字都会被匹配到。

这个小语言在项目里也有用。`QueryParser.cs` 里的 `ValidateRegex` 方法（L360 起）就负责检查用户输入的正则是否合法。

```csharp
private static void ValidateRegex(string pattern)
{
    try
    {
        _ = System.Text.RegularExpressions.Regex.Match(string.Empty, pattern);
    }
    catch (ArgumentException ex)
    {
        throw new QuerySyntaxException($"正则表达式无效：{ex.Message}", 0, pattern);
    }
}
```

这里的做法很实用，拿一个空字符串去试跑一下正则，如果模式本身有语法错误，`Regex` 会抛出 `ArgumentException`。项目把它转换成查询语法错误，用户在查询框里写了一个坏掉的正则，程序会在解析阶段就给出提示，而不是等到匹配时才出问题。

## 14.12 常用语法速查

下面这张表列出日常最常用的语法。其中大部分在 14.14 节的实战里都用到了，剩下的可以在练习里自己试一试。

| 语法 | 含义 | 例子 | 能匹配 |
| --- | --- | --- | --- |
| `.` | 任意一个字符（换行除外） | `a.c` | `abc`、`a-c` |
| `\d` `\w` `\s` | 数字、单词字符（字母数字下划线）、空白 | `\d+` | `123` |
| `[abc]` | 括号里的任一个字符 | `[aeiou]` | `a`、`e` |
| `[^...]` | 不在括号里的字符 | `[^,]+` | 直到逗号前的一段 |
| `*` `+` `?` | 零个或多个、一个或多个、零个或一个 | `\d+` | `1`、`2024` |
| `{m,n}` | 出现 m 到 n 次 | `\d{4}` | 四位数字 |
| `^` `$` | 行首、行尾 | `^ERROR` | 以 ERROR 开头的行 |
| `\b` | 单词边界 | `\berror\b` | 独立的 error |
| `( )` | 分组 | `(ab)+` | `ab`、`abab` |
| `(?<名字>…)` | 命名分组 | `(?<level>\w+)` | 之后可以按名字取出 |
| `\|` | 或 | `error\|warn` | `error` 或 `warn` |
| `\` | 转义，让特殊字符变成普通字符 | `\.`、`\[`、`\(` | 字面的 `.`、`[`、`(` |
| `*?` `+?` | 惰性匹配（尽量少） | `<.*?>` | 单个标签 |

注意两点。第一，`[abc]` 是字符类，表示任选其中一个字符，不是"文字括号"。如果要匹配真正的方括号，要写成 `\[` 和 `\]`。第二，在 C# 里，正则字符串最好用逐字字符串 `@"..."`，这样反斜杠不用写两遍。

## 14.13 在 C# 里使用 `Regex`

`Regex` 类在 `System.Text.RegularExpressions` 命名空间里，它的常用方法如下。

```csharp
using System.Text.RegularExpressions;

var line = "2026-11-02 09:00:09 [ERROR] order: 数据库超时 (2815ms)";
var pattern = new Regex(@"\[(?<level>[A-Z]+)\] (?<module>[a-z]+): (?<msg>.*?)(?: \((?<ms>\d+)ms\))?$");

// IsMatch：只判断是不是匹配，返回 bool
Console.WriteLine(pattern.IsMatch(line));                  // True

// Match：拿到第一个匹配，再用 Groups["名字"] 取出分组的值
var m = pattern.Match(line);
Console.WriteLine(m.Groups["level"].Value);                // ERROR
Console.WriteLine(m.Groups["module"].Value);               // order

// Matches：拿到所有匹配
var all = Regex.Matches("a1 b22 c333", @"\d+");
foreach (Match x in all)
{
    Console.WriteLine(x.Value);                            // 1、22、333
}

// Replace：替换
Console.WriteLine(Regex.Replace("密码 abc123", @"\d", "*"));  // 密码 abc***
```

这里有两个小建议。

- 如果你要的是"有没有"，用 `IsMatch`，不要用 `Match` 再判断 `Success`，代码更直接。
- 分组一定要用名字（`(?<level>...)`），而不是数字下标。以后改了模式，名字还在，代码不会悄悄取错值。

## 14.14 实战，解析日志行

现在把前面的内容串起来。检查点里的日志样例是这样的。

```text
2026-11-02 09:00:01 [INFO] api: 服务启动
2026-11-02 09:00:05 [WARN] order: 库存接近下限, 请补货 (680ms)
2026-11-02 09:00:09 [ERROR] order: 数据库超时 (2815ms)
2026-11-02 09:00:12 [ERROR] payment: 第三方接口返回 503 (1520ms)
2026-11-02 09:00:20 [INFO] api: 请求完成 (968ms)
这一行没有格式，解析时应该被跳过
```

我们要从每行里拆出模块、级别、消息和耗时。模式是这样的。

```csharp
var logLine = new Regex(
    @"^(?<date>\d{4}-\d{2}-\d{2}) (?<time>\d{2}:\d{2}:\d{2}) \[(?<level>[A-Z]+)\] (?<module>[a-z]+): (?<msg>.*?)(?: \((?<ms>\d+)ms\))?$",
    RegexOptions.CultureInvariant);
```

逐段看一下。

- `^` 和 `$` 保证整行都要符合格式，前后不能有多余的东西。
- `\d{4}-\d{2}-\d{2}` 匹配日期。
- `\[(?<level>[A-Z]+)\]` 匹配方括号里的级别，`\[` 和 `\]` 是转义后的方括号。
- `(?<msg>.*?)` 是消息，用惰性匹配，尽量少吃，留给后面的耗时部分。
- `(?: \((?<ms>\d+)ms\))?` 是可选的耗时部分。问号表示"有就取，没有就算了"。

循环处理每一行。

```csharp
foreach (var line in File.ReadLines(logPath, Encoding.UTF8))
{
    var m = logLine.Match(line);
    if (!m.Success)
    {
        skipped++;
        continue;
    }

    var ms = m.Groups["ms"].Success
        ? int.Parse(m.Groups["ms"].Value, CultureInfo.InvariantCulture)
        : 0;

    hits.Add(new LogHit(
        Module: m.Groups["module"].Value,
        Level: m.Groups["level"].Value,
        Ms: ms,
        Note: m.Groups["msg"].Value));
}
```

这里有两个值得注意的地方。

第一，`m.Groups["ms"].Success` 要先判断。没有耗时的行，这一组是不匹配的，直接取 `.Value` 得到的是空字符串，`int.Parse` 会抛异常。

第二，`int.Parse` 传入了 `CultureInfo.InvariantCulture`。数字在不同文化下的写法可能不同（比如小数点是逗号的地区），不指定文化时，同一段文字在不同电脑上可能解析成不同的结果。

运行后，那行没有格式的文字被跳过，前 5 行都被解析出来。

## 14.15 正则的坑

正则非常强大，也非常容易写出性能很差的模式。下面四个坑都值得记住。

### 坑一，贪婪导致误匹配

`*` 和 `+` 默认是贪婪的，会尽量多吃。我们来看一下。

```csharp
var html = "<a><b>";
Console.WriteLine(Regex.Match(html, "<.*>").Value);    // <a><b>
Console.WriteLine(Regex.Match(html, "<.*?>").Value);   // <a>
```

`<.*>` 把从第一个 `<` 到最后一个 `>` 全部吃掉了。想只要第一个标签，就在 `*` 后面加一个问号，变成惰性匹配 `<.*?>`。

### 坑二，回溯灾难

有些模式在遇到特定输入时，匹配会呈指数级变慢。经典的例子是 `^(a+)+$`，它遇到一长串 `a` 后面跟一个不匹配的字符时，引擎会尝试大量组合。

```csharp
var evil = new string('a', 30) + "b";
var regex = new Regex("^(a+)+$", RegexOptions.None, TimeSpan.FromSeconds(1));
regex.IsMatch(evil);   // 1 秒后抛出 RegexMatchTimeoutException
```

注意构造函数的第三个参数，它是**超时时间**。没有超时参数的话，这段代码可能会卡住很久。

项目里的做法正是这样。`QueryEvaluator.cs` L257 创建正则时传入了 `TimeSpan.FromSeconds(1)`。用户输入的正则是不可信的，必须设置超时，否则一条恶意的查询就能让界面卡死。

### 坑三，不要在循环里反复构造

创建一个 `Regex` 对象要花时间。下面是一个小实验，同样的匹配做 20000 次。

```text
每次新建 Regex：91 ms；复用：2 ms（数字因机器而异）
```

差距有四十多倍。正确的做法是把 `Regex` 存成字段，或者像项目里 `QueryEvaluator.cs` L19 那样用字典缓存起来。那里的缓存是 `ConcurrentDictionary`，多个线程同时用也是安全的。

### 坑四，正则不是万能的

判断一个字符串是不是合法的邮箱、身份证号，正则可以做到大部分情况。但要完整实现 HTML 或 JSON 的解析，正则就力不从心了。那种情况下，应该用真正的解析器（比如 `System.Text.Json`）。

## 14.16 第三方库怎么选

标准库和第三方库之间，怎么选？下面是一份经验清单。注意，这是经验，不是规则。

1. **标准库能不能做？** 能做，就先用标准库。少一个依赖，就少一份维护成本。
2. **还在维护吗？** 看最近一次发布时间、提交记录和 issue 的回应速度。一个三年没更新的库，遇到新版 .NET 可能就有问题。
3. **有没有文档和示例？** 没有文档的库，即使功能很强，也会让你花很多时间猜。
4. **许可证是什么？** 商业项目要特别注意许可证是否允许你这样用。
5. **依赖多不多？** 一个库背后带了几十个依赖，引入它就等于引入了一整套东西。
6. **社区用得多吗？** 用的人多，遇到问题更容易搜到答案。

这份清单里没有绝对的标准。一个库可能在一个项目里是好选择，在另一个项目里却不合适。

## 14.17 Newtonsoft.Json

Newtonsoft.Json（通常直接叫它 Json.NET）是 .NET 生态里用了很多年的老牌 JSON 库。它的功能很全，很多老项目和教程都在用它。

### 安装

```bash
dotnet add package Newtonsoft.Json
```

检查点用的是 13.0.4 版本。版本号可以用 `--version` 指定，本章 14.21 节会讲。

### 读写

```csharp
using Newtonsoft.Json;
using Newtonsoft.Json.Linq;

// 读取：默认就能读注释
var settings = JsonConvert.DeserializeObject<AppSettings>(File.ReadAllText(configPath))!;
Console.WriteLine($"名称={settings.Name}，行数上限={settings.MaxRows}");

// 写出：带缩进
var text = JsonConvert.SerializeObject(settings, Formatting.Indented);

// 不写类，直接按路径取值
var root = JObject.Parse(configText);
Console.WriteLine(root["levels"]![0]);   // error
```

`JObject` 很适合"不想为一个配置专门定义类"的场景，它像一个字典，可以按键一层一层取。

### 和 System.Text.Json 对比

| 方面 | System.Text.Json | Newtonsoft.Json |
| --- | --- | --- |
| 来源 | .NET 标准库自带 | 第三方库，需要安装 |
| 性能 | 通常更快、更省内存 | 功能更多，性能一般 |
| 注释 | 默认不允许，要显式设置 | 默认能读 |
| 灵活性 | 较严格，写法需要按它的规则来 | 更宽松，遇到老代码或奇怪的 JSON 时更好用 |
| 适合 | 新项目、Web 场景、追求性能 | 老项目迁移、需要宽松解析、已经在用的项目 |

我们的检查点用同一份带注释的 `settings.json` 做了对比，Newtonsoft 直接读出结果，`System.Text.Json` 在默认设置下报错，显式设置后才能读。这个对比本身就说明了差别。

## 14.18 CsvHelper

CSV 是最朴素的表格格式，一行一条记录，字段用逗号分隔。它看起来简单，但有几个坑。

- 字段里本身有逗号怎么办？
- 字段里有换行怎么办？
- 字段里有双引号怎么办？

CSV 的规则是，含有逗号、引号或换行的字段，要用双引号括起来，字段里的双引号要写成两个双引号。自己写这套规则很容易出错，这正是 CsvHelper 帮你解决的问题。

### 安装

```bash
dotnet add package CsvHelper
```

### 写入与读取

检查点用 CsvHelper 34.0.0 写入 CSV。

```csharp
using (var writer = new StreamWriter(csvPath, false, Encoding.UTF8))
using (var csvOut = CsvWriter.Create(writer, new CsvWriterOptions { FormatProvider = CultureInfo.InvariantCulture }, leaveOpen: true))
{
    csvOut.WriteRecords(hits);
}
```

读回来。

```csharp
using (var reader = new StreamReader(csvPath, Encoding.UTF8))
using (var csvIn = CsvReader.Create(reader, new CsvReaderOptions { FormatProvider = CultureInfo.InvariantCulture }, leaveOpen: true))
{
    loaded = csvIn.GetRecords<LogHit>().ToList();
}
```

写出的第三行是这样的。

```text
order,WARN,680,"库存接近下限, 请补货"
```

备注里本来有逗号，CsvHelper 自动给它加了双引号。如果你自己用字符串拼接，这一行就会被拆成四个字段。

### 版本差异提醒

这里我们要说一件真实发生过的事。我们最初按照以前常见的写法（`new CsvWriter(writer, new CsvConfiguration(...))`）去写 CsvHelper，结果编译失败。原因是 CsvHelper 34 对 API 做了较大的调整。

- 不再用 `new CsvWriter(writer, new CsvConfiguration(...))`，而是 `CsvWriter.Create(writer, new CsvWriterOptions { ... })`。
- 类型要用 `[CsvRecord]` 标记，并且声明为 `partial`，因为 34 版本用源生成器来生成映射代码。

```csharp
[CsvRecord]
public sealed partial record LogHit(string Module, string Level, int Ms, string Note);
```

如果漏掉 `[CsvRecord]`，`dotnet build` 仍然会通过，但程序运行到 `WriteRecords` 时会抛出 `InvalidOperationException`，提示 `LogHit has no CSV record writer`。编译器不会替你检查这一点，只能靠运行来发现。

这件事说明两点。第一，**第三方库的 API 会随版本变化，教程里的代码可能已经过时**。第二，遇到编译错误时，先看一下你装的版本号，再去看那个版本的文档。

## 14.20 Serilog（简介）

前面我们一直用 `Console.WriteLine` 输出信息，它足够简单，但很难管理。日志库解决的是这些问题。

- 日志要分级别，比如 Debug、Information、Warning、Error。
- 日志要能同时输出到控制台和文件。
- 日志要带上结构化的数据，方便以后搜索和统计。

Serilog 是 .NET 里最流行的日志库之一。它最大的特点是**结构化日志**。

```csharp
var count = 5;
var skipped = 1;
Log.Information("解析完成：{Count} 行，跳过 {Skipped} 行", count, skipped);
```

（这是一个简化的例子。检查点中的写法与它相同，只是变量来自前面的解析结果。）

注意花括号里的 `Count` 和 `Skipped`，它们是属性名，不是字符串插值。Serilog 会把这些值作为独立的属性保存下来。使用支持结构化输出的目标（sink）时，每个属性都能被单独搜索和统计。如果写成 `$"解析完成：{count} 行"`，它就只是一段普通文字，没有结构。

### 安装与配置

Serilog 本身只负责"接收日志"，真正把日志写到哪里，要靠"输出目标"，也就是 sink。控制台的 sink 是单独的包。

```bash
dotnet add package Serilog
dotnet add package Serilog.Sinks.Console
```

配置。

```csharp
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Debug()
    .WriteTo.Console(outputTemplate: "[{Level:u3}] {Message:lj}{NewLine}")
    .CreateLogger();

Log.Information("解析完成：{Count} 行，跳过 {Skipped} 行", hits.Count, skipped);
Log.Warning("慢请求超过 {Threshold} ms 的共 {Slow} 条", 500, loaded.Count(h => h.Ms > 500));
Log.CloseAndFlush();
```

输出是。

```text
[INF] 解析完成：5 行，跳过 1 行
[WRN] 慢请求超过 500 ms 的共 4 条
```

`outputTemplate` 决定日志长什么样。我们为了让输出稳定，去掉了时间戳。在真正的项目里，通常会保留时间和来源。

最后那行 `Log.CloseAndFlush()` 很重要。日志库为了性能，可能会先缓存一部分日志，程序结束前不调用它，最后几条日志可能丢失。

项目里目前还没有用 Serilog。不过 `Core/Parsing/JsonLogParser.cs` 能解析"一行一个 JSON 对象"的结构化日志，它的注释里就把 Serilog 列为这类日志的常见来源之一。也就是说，LogLens 和 Serilog 处理的是同一类日志。

## 14.21 三种安装方式（在线）

dotnet add package CsvHelper

## 14.22 离线安装，本地文件夹作为源

有些机器不能上网，比如公司内网、保密环境。这时怎么装包？

思路很简单，在能上网的机器上把 `.nupkg` 文件下载或打包好，复制到离线机器上，然后告诉 NuGet "包在这个文件夹里"。

我们做了一个完整的验证。先在一个类库项目里打包。

```bash
dotnet pack -c Release -o feed
```

这会在 `feed` 文件夹里生成 `MyLib.1.0.0.nupkg`。然后，在使用它的应用项目里，清空本机缓存，只指定这个文件夹作为来源。

```bash
dotnet nuget locals all --clear
dotnet restore --source ../mylib/feed
dotnet run --no-restore
```

结果是应用成功还原并运行，输出 `你好，离线`。清空缓存之后还原依然成功，说明包确实是从本地文件夹读取的。

注意 `--source` 会**替换**掉默认的 [nuget.org](https://nuget.org) 来源。也就是说，这次还原只会看这个文件夹。如果你的包依赖了别的包，那些依赖也必须放在这个文件夹里，否则还原会失败。14.26 节会讲这种情况。

## 14.23 离线安装，配置本地源与缓存

每次都写 `--source` 很麻烦。可以把本地文件夹注册为一个长期的包来源。

```bash
dotnet nuget add source /path/to/feed --name offline-feed
```

`--name` 给这个来源起个名字，方便以后管理。查看和删除。

```bash
dotnet nuget list source
dotnet nuget remove source offline-feed
```

这些命令默认修改的是用户级的 NuGet 配置文件。为了不影响自己的电脑，我们在练习里用 `--configfile` 指定了一个临时配置文件去测试。

```bash
dotnet nuget add source /path/to/feed --name offline-feed --configfile test.config
```

测试结果是，配置文件里多出一条 `<add key="offline-feed" value="..." />`，`list source` 能看到它，`remove source` 能删掉它。

另外还有一个小知识，NuGet 会把已经下载过的包缓存到 `~/.nuget/packages` 文件夹里。如果一台离线机器的缓存已经有了需要的包，就可以不用额外的源直接还原。把这个文件夹整体复制过去，也是一种离线方式。不过它不如本地源清楚，建议只在没有别的选择时使用。

<a id="s14-24" class="lt-anchor-target"></a>

## 14.24 手动引用 DLL

还有一种最原始的方式，拿到第三方库的 `.dll` 文件，手动放进项目，然后在 `.csproj` 里引用它。

```xml
<ItemGroup>
  <Reference Include="SomeLibrary">
    <HintPath>libs/SomeLibrary.dll</HintPath>
  </Reference>
</ItemGroup>
```

这种方式在特别古老的项目里还能见到，但我们**不推荐**。原因很实际。

- 这个库依赖的其它库，你要一个一个自己找、自己放。
- 库升级时，要手动替换文件，很容易漏掉。
- 团队里的每个人都要有一份一模一样的 DLL。

这种方式我们没有在检查点里运行过，只作为一种存在的做法介绍。能用 NuGet 就用 NuGet。

## 14.25 内网包服务器与镜像（简介）

大公司和机构通常会搭建自己的包服务器，比如 Azure Artifacts、Nexus、ProGet 之类。它们的作用有两个，一是加速下载，二是控制员工能用哪些包。

对接它们，要在 `NuGet.Config` 里配置一个新的来源。

```xml
<packageSources>
  <add key="company" value="<包服务器的地址>" />
</packageSources>
```

具体地址由所在机构提供，本章不给出示例地址。如果你的公司用了这类服务，请直接问负责的同事要配置文件。

## 14.26 常见问题

下面列出装包和用包时最常遇到的问题。

| 现象 | 可能的原因 | 怎么办 |
| --- | --- | --- |
| 还原失败，提示找不到包 | 包名写错，或网络连不上 [nuget.org](https://nuget.org) | 检查包名拼写；确认能访问 [nuget.org](https://nuget.org)；离线就用本地源 |
| 编译报 `CS0246`，找不到类型 | 缺少 `using`，或者包没装 | 检查 `using`；用 `dotnet list package` 确认包在不在 |
| 编译报 `CS1729`，构造函数对不上 | 包的版本变了，API 也变了 | 看装的版本号，去那个版本的文档里找正确写法 |
| 编译报 `CS9035` | 类型标记了 `required` 但没有设置 | 在对象初始化器里补上这个属性 |
| 离线时还原失败，但在线能成功 | 依赖的依赖没有放进本地源 | 在联网机器上把整棵依赖树都打包进同一个文件夹 |
| 版本冲突，行为奇怪 | 两个包依赖同一个库的不同版本 | 用 `dotnet list package --include-transitive` 查看依赖树，统一版本 |
| 还原结果不对，怀疑缓存坏了 | 本地缓存损坏 | `dotnet nuget locals all --clear` 清空缓存后重新还原（已验证可用） |

### 关于 `CS1729` 的一个例子

14.18 节里我们遇到的 `'CsvWriter' does not contain a constructor that takes 2 arguments`，就属于这一类。它的意思是"这个类型没有你写的这种构造函数"。看到这类错误，第一反应应该是检查版本，而不是怀疑自己的语法。

## 14.28 回到项目

学完本章，再回头看 LogLens 的项目结构，它的依赖关系就很清楚了。

- `LogLens.Core`，纯逻辑类库，没有任何 `PackageReference`，只用标准库。它可以被任何界面复用，也不会因为某个第三方库的升级而受影响。
- `LogLens.Cli`，命令行程序，只有一个 `ProjectReference` 指向 `Core`。它几乎只用标准库。
- `LogLens.Studio`，图形界面，除了 `ProjectReference` 指向 `Core`，还有 7 个 `PackageReference`，包括 Avalonia、CommunityToolkit.Mvvm、Microsoft.Extensions.DependencyInjection 等。

依赖图大致是这样的。

```text
LogLens.Studio ──► LogLens.Core ◄── LogLens.Cli
   │ (Avalonia 等 7 个包)            （只依赖标准库）
```

这张图告诉你一个设计原则，**把依赖关在外面，让核心保持干净**。核心越干净，换界面、换平台、升级库时就越省心。

本章没有讲的内容，留给后面的章节，MVVM（CommunityToolkit.Mvvm）、Avalonia 界面、依赖注入（Microsoft.Extensions.DependencyInjection）。它们会在第 22 章起逐步出现。
